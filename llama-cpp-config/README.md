# llama-cpp-config

GUI + CLI configurator for [llama.cpp-framework](..).

```text
llama-cpp-config                  → launch the GUI
llama-cpp-config gui              → same, explicit
llama-cpp-config control start    → start llama-server
llama-cpp-config control stop     → stop llama-server
llama-cpp-config control restart  → restart llama-server
llama-cpp-config control stop-and-close → stop llama-server and close the GUI
llama-cpp-config server show      → print server.ini
llama-cpp-config server set ...   → update server.ini fields
llama-cpp-config preset list      → list models with their presets
llama-cpp-config preset show ...  → print one preset
llama-cpp-config preset delete .. → remove one preset
llama-cpp-config preset delete <id> --delete-files all|model,mmproj,draft [--even-if-shared]
                                  → also delete the model files it links (refused for a file another preset uses)
llama-cpp-config preset disable . → switch one preset off (enable: back on)
llama-cpp-config preset download "<words>" [--search] [--limit N]
                                  → search Hugging Face's GGUF repos: org/repo, downloads, MoE/dense and size, quantizations per row
llama-cpp-config preset download <org/repo[:QUANT]|URL> [--list] [--quant Q] [--no-mmproj] [--draft mtp|dflash|dspark] [--id ID]
                                  → list a Hugging Face repo's GGUFs, download one, create its preset
                                    (--list adds each quant's placement on this machine and a recommended one)
```

## GUI

Built with [Slint](https://slint.dev). The nav rail switches between five tabs (Server, Models, Benchmark, Integrations, Settings) and carries the server run controls (Start/Stop over Open chat UI over HW Monitor over View logs over Refresh) at its bottom, reachable from any tab. A status footer shows the llama-server state (running / not running) and version.

The non-obvious run controls:

- **Open chat UI** launches the URL the RUNNING server was started with (`AppState.launched_url`, snapshotted at launch: a save while running changes the file, not the listening process; the footer says "restart llama-server to apply"). When the GUI didn't start the server it falls back to the SAVED Base URL (`AppState.chat_url`, from `ServerConfig::opencode_base_url_or_default()`: uses the custom Base URL if set, otherwise auto-derives from host+port; a `0.0.0.0` bind maps to `localhost`, since a listen address isn't a connectable one). It is disabled, labelled **Web UI off**, while the running server has no web UI (`AppState.can_open_chat` over `chat_ui_enabled`: the `Webui` the GUI launched with, `launched_ui`, else the saved one, `chat_ui_saved`; the same two sources as the URL), since `/` then answers 404; the tray's item follows it (`gui::push_tray_status`, with each run-state change and the 5 s status tick).
- **Window sizes are remembered.** The configurator, the View-logs window, the Downloads window and the HW Monitor window each record their size in `settings.ini` (`MainWindowSize`, `LogWindowSize`, `DownloadsWindowSize`, `HwMonitorWindowSize`, as `<width>x<height>` in logical pixels) when they close and at Quit, and open at that size on the next launch; a maximized window is not recorded, and an empty key means the default size. The size reaches the window through its `initial_width`/`initial_height` properties, which the .slint binds its preferred size to (`gui.rs` `RememberedSize`), because the winit backend re-applies the preferred width on every show and would undo a plain `set_size`.
- **HW Monitor** (Linux and Windows; the button is absent elsewhere) opens an independent, non-modal window (`HwWindow`) with one card per device and one horizontal bar per metric, refreshed once a second while it is open: every GPU (GPU, VRAM, and what spills out of VRAM: GTT on amdgpu, Shared memory on Windows; Memory activity where the driver reports it; PCIe RX/TX on NVIDIA), the CPU, memory (RAM, page cache, swap on Linux; RAM, Cached, Committed on Windows) and the disk holding `ModelsDir` (read, write, busy). No helper process is involved. On Linux amdgpu, CPU, memory and disk are files under `/sys` and `/proc`. On Windows the adapters come from D3DKMT and their usage from the GPU performance counters Task Manager shows (any vendor, no vendor library), the CPU from `GetSystemTimes`, memory from `GetPerformanceInfo`, the disk from `IOCTL_DISK_PERFORMANCE`; none of it needs elevation. NVIDIA is on both the driver's NVML (`libnvidia-ml.so.1`, `nvml.dll`), loaded at runtime (absent driver, absent card); on Windows an NVIDIA card NVML does not answer for still gets the counters' bars. Each device is headed by a checkbox (ticked by default): unticked, the device's card is hidden and nothing is read for it until it is ticked again; the choice is kept in `settings.ini` (`HwMonitorHidden`). A rate has no natural 100%, so the PCIe and disk rate bars are drawn against the peak seen since the window opened, which the readout names. The source of every bar is tabled in `src\hwmon.rs`'s header.
- **View logs** opens `logs\llama-server.log` in an independent, non-modal window (`LogWindow`) that follows the file live like `tail -f`, leaving the main window fully interactive while it is open. Auto-scroll (checkbox, on by default) keeps the view on the last line; untick it to read scrolled-back text while the server keeps writing: the view then stays exactly where it is (new lines only extend the scrollbar), and ticking it again jumps back to the end. The log is a list of rows, one per line, not a text box: a line (or part of one) is selectable and Ctrl+C copies it, and **Copy all** puts every line the window holds on the clipboard. A header readout ("17.3 MB · updated 5 s ago") ages every tick, so a live-but-quiet tail (llama-server goes silent between requests) reads differently from a stuck one. Always enabled: the log outlives the process, so it's exactly what you want after a crash or failed start. The same window opens from the tray menu's **Open log** (`gui\tray.rs` invokes the same `view_logs` callback, so it is one viewer, not two), without surfacing the configurator. The tray menu lists **Open chat UI** (enabled while the server runs with its web UI on; `AppState.open_chat`, the rail button's own path), **Open HW Monitor** (where the button exists) and **Open log** in the rail's order, under **Open configurator**. The tail mechanics (a worker thread that polls every 500 ms and lives only while the window is open, so no file IO runs on the UI thread; a bounded number of retained rows; truncation/rotation handling) live in `gui\log_window.rs` and `ui\log_window.slint`. The rows are a virtualized `ListView` on purpose: a `TextEdit` lays its whole text out again on every append and every frame, which froze the window for most of each poll once the tail reached a few tens of KB. Rotation is real, not just tolerated: when llama-server stops and the log is larger than the Settings tab's threshold (`LogRotateKb`, 1024 KB by default; `LogRotate` off keeps one growing file), `runstate::stop` files it away as `llama-server-<yyyymmdd-hhmmss>.log` (closing instant, UTC) and leaves a blank one, so the window reads as empty after a stop and the next run starts clean; a run that died without a stop is filed at the next start under its last-write time, and the newest 10 closed logs are kept (`runstate.rs` module header).
- **Refresh** (the button, or F5) re-reads `server.ini` / `presets.ini`, re-scans the models directory, reloads integration state, and re-probes the run status, llama-server version, and GPU devices (the exe can change under us, e.g. a `xtask build` rerun). Use it after adding a model file or hand-editing a config file outside the GUI, without restarting.

Each tab body is its own Slint component (`ui\server_page.slint`, `ui\models_page.slint`, `ui\bench_page.slint`, `ui\integrations_page.slint`, `ui\settings_page.slint`). All shared state (every property and callback the pages and Rust both touch) lives in a single `export global AppState` (`ui\state.slint`); the pages read/write `AppState.<name>` directly and Rust drives it via `app.global::<AppState>()`. `ui\app.slint` is just the window chrome (nav rail, run controls, modals, footer) plus the tray.

Modal dialogs (New/Clone picker, the Hugging Face download, Rename, the Delete confirmation, the discard-confirm guard, and the chat-template preview) overlay the whole window: Esc or a backdrop click dismisses them (the Hugging Face dialog included: its download runs in the background, see the [Models tab](#models-tab-presetsini)), and the app-wide shortcuts (Ctrl+S, Ctrl+N (which jumps to the Models tab first), Ctrl+1–5, F5) are inert while any one is open (`AppState.modal_open`). The New/Clone picker is keyboard-completable: when the filter narrows the list to exactly one model, Enter picks and confirms it.

Any navigation that would replace a dirty form (switching presets, Refresh/F5, opening New…/Clone…/Rename…) first asks to discard the unsaved edits (`gui::confirm_discard_then` parks the action Rust-side until the verdict). A preset's on/off switch is deliberately not one of them: it moves the preset between two files without changing a word of it, so it keeps the form as it is (see the [Models tab](#models-tab-presetsini)).

### Server tab: `server.ini`

- Fields: port, bind addresses (one checkbox per address: localhost, 0.0.0.0 and each detected IPv4 interface; several may be checked and ride `--host` comma-separated, except 0.0.0.0, which is exclusive), load mode, threads, cache reuse, threads-batch, models-max, models-memory-margin (MiB kept free per device, the router unloading its least recently used models until a new one fits; llama.cpp v0.8.0), models-dir (with a Browse button). **threads** and **threads-batch** are sliders capped at the machine's logical-processor count, each with a "default" checkbox that omits the flag (let llama.cpp pick). The scalar fields (port, cache reuse, models-max, models-memory-margin) are `DefaultLineEdit`s: a "default" checkbox omits the flag, or an explicit integer (see [Numeric fields are text](#numeric-fields-are-text-never-a-spinbox) for why they are not SpinBoxes).
- **Advanced** card: **Web UI** (`Webui`, on by default, llama.cpp's own default), **Web UI MCP proxy** (`--webui-mcp-proxy`, on by default: the bundled chat UI needs it to call MCP tools) and **Log level** (`-lv`). They round-trip through `server.ini` and default to the framework values above when untouched.
  - **Web UI** off launches the router with `--no-ui`; on (and unset) passes nothing. It is a checkbox, not a tri-state: "default" and "on" would launch the same line. The flag belongs on the ROUTER's line because the router serves the page itself (`server_http_context::init` in `server-http.cpp` registers `/` and the embedded assets only under `params.ui`, run on the router's own params); it also reaches the children through `base_preset` (`LLAMA_ARG_UI` is not a reserved arg), which is harmless. Off, `/` answers 404 and upstream serves a `sw.js` that unregisters a browser's cached UI. The API routes are registered regardless, so the Integrations tab, the benchmark and the conversation snapshots are unaffected, and no probe of the configurator reads `/`. Knock-on effects: **Web UI MCP proxy** is greyed out (its value kept) and not passed while the UI is off, since `/cors-proxy` is registered whatever `--no-ui` says and nothing but the UI calls it; **Open chat UI** is disabled (see the run controls above). CLI: `server set --webui false`.
  - **Log level** is a **dropdown, not a number**: `-lv` has exactly six levels (`OUTPUT:0`, `ERROR:1`, `WARN:2`, `INFO:3`, `TRACE:4`, `DEBUG:5`; `common/arg.cpp`), a message prints when its own level is ≤ the threshold, and a free-number field could only ever offer levels that do not exist. The framework default is `TRACE:4`; `DEBUG:5` is what also logs the per-tensor `buffer type overridden` lines that `tools\report-memory.ps1` reads. The form carries the *label*, and `server_form::LOG_LEVELS` is asserted equal to `Options.log_levels` in the e2e so the two lists cannot drift.
- **SDK Tuning** card, the one card that holds no llama.cpp flags: environment variables of the GPU vendor's own libraries, exported onto llama-server at launch (`runstate::env_vars`, so the Command Line card renders them too) and inherited by the router's per-model children. It is split per SDK because a knob here is read *below* llama.cpp and is inert on every other backend; llama-server never sees it, so nothing validates it either. **CUDA** carries nothing today. **ROCm** carries **hipBLASLt** (`ROCBLAS_USE_HIPBLASLT`), a tri-state: `default` never exports the variable and leaves rocBLAS its own routing, `on` forces hipBLASLt (`=1`), `off` forces Tensile (`=0`). Beside it, **FlashAttention band** (`HipFaBand` → `GGML_HIP_FA_BAND_WMMA`, a dropdown `default`/`off`/`2`/`4`; `default` leaves the key unset, a commented line in `server.ini`, and exports the tool's default `4`; `off` exports nothing): an opt-in path of the framework's patched `libggml-hip` that runs the 1-8 query FlashAttention of head-256 / GQA 6 models (Qwen3.8-27B) on the WMMA kernel with the KV cache split round-robin over the CUs, inert everywhere else; and **Profiler attach** (`RocprofAttach` → `ROCP_TOOL_ATTACH=1`, a checkbox, off by default), which rocprofiler-sdk requires of a process before `rocprofv3 --attach <pid>` may trace it.
  - `off` is the one that pays, and only on **gfx1201** (Radeon AI PRO R9700) under ROCm/TheRock 7.14: rocBLAS routes 16-bit GEMMs through hipBLASLt there, and the **second** 16-bit GEMM in a process fails at kernel launch; f32 is immune, and the identical call sequence passes on Tensile (standalone repro: default and `=1` fail, `=0` passes across batched/strided/plain × bf16/f16; a single visible GPU changes nothing). llama-server aborts on the first prefill batch of any BF16/F16 model. Forcing Tensile is a cure, not a trade: pp512 587 t/s / tg128 35 t/s measured on Ornith BF16, where the older `GGML_CUDA_CUBLAS_COMPUTE_TYPE=f32` workaround managed ~19 t/s prefill. Upstream: llama.cpp #25836, ROCm #6461, TheRock #7271.
  - What actually fails is a MIX, and the second cure follows from it: Windows resolves a static import from the exe's own directory and then System32, both before PATH, and the AMD driver keeps its own `amdhip64_7.dll` in System32, so llama-server runs the dist's `rocblas.dll` + `libhipblaslt.dll` against the DRIVER's HIP runtime rather than the dist's. Put the dist's runtime next to the exe and the same GEMMs pass on ROCm 7.14.0, 10.0.0 and the 10.1 nightlies alike, `on` included, so hipBLASLt itself is healthy and no ROCm bump was ever going to fix this. `xtask package` does exactly that (it bundles the dist's whole runtime into `bin\`), which is why an installed tree can leave this knob at `default`; a build from source still runs the driver's runtime.
  - The card also carries the **ROCm availability warning**, which is not a setting but the only place a missing HIP backend is ever mentioned. ggml loads backends dynamically and drops one whose imports don't resolve **without a word**, so a machine whose ROCm dist is absent, half-extracted, or simply not on the child's PATH does not fail: the same AMD card keeps working through Vulkan, slower, with nothing saying why. The verdict comes from the device probe, never from a file list (`devices::rocm_warning`): an AMD GPU present with no `ROCm*` device beside it *is* the diagnosis, and it holds whatever ROCm version is installed. Only the *hint* inspects the runtime (llama-server's own directory when the installer bundled it there, else the dist `HIP_PATH` names), and it checks two landmarks that survive a version bump, `bin\hipblas.dll` and `bin\rocblas\library` (a fuller file list would be wrong: `origami.dll` ships in TheRock 10.0.0 and not in 7.14.0, so requiring it would report a healthy 7.14 install as broken). The three hints name three different remedies: nothing installed, installed but incomplete, or complete and therefore a launch that isn't reaching it (most often a missing or outdated Adrenalin driver, or on a build from source a console whose PATH still names a dist directory that has since been renamed). The second one is worth its own row because it fails LATE: with `rocblas\library` missing the backend loads and the device enumerates, then the first matrix multiply dies with `Could not initialize Tensile host`.
  - It is a tri-state and not a checkbox for the usual reason (`--flash-attn`'s shape, and the same `form::tri_state` / `tri_bool` pair): "don't export the variable" is a third instruction, and it is the framework default; the bug is per-arch, and hipBLASLt is the faster path everywhere it works. The CLI reaches all three as words (`server set --rocblas-use-hipblaslt default|on|off`), which is also the only way to clear it back.
  - **Tensor-split AllReduce** (`CudaAllreduce`, env `GGML_CUDA_ALLREDUCE`, `server set --cuda-allreduce default|nccl|internal|none`) is the card's multi-GPU knob: which AllReduce `--split-mode tensor` reduces through. ggml-cuda and ggml-hip are one source and read the SAME variable, so it is one value for both backends, server-wide (the env reaches every router child) and inert in the other split modes. Unset (`default`) leaves the backend its own choice: on Linux the collective library the build links (RCCL in ggml-hip, NCCL in ggml-cuda), then the internal AllReduce; on Windows the internal one. It is a closed list (`server_cfg::ALLREDUCE_MODES`, normalized on read and again in `env_vars`) because the backend does not refuse an unknown word: it warns and runs it as `none`. `none` is also the ONE value under which a tensor split mixing a CUDA and a ROCm device loads: the two backends declare the same guid, each takes the other's device for its own, and the direct AllReduce aborts on the first reduction (`server_cfg.rs` `cuda_allreduce` has the measurement). The Models tab says so on such a preset (`gpu_split::mixes_cuda_and_rocm` -> `preset_mixes_cuda_rocm` -> the last clause of `preset_split_mode_warning`). Both knobs of the card are dropdowns (`EnumComboBox` over `Options.tri_states` / `Options.allreduce_modes`).
- **Conversation snapshots** card: `SaveStateOnShutdown` + `StateDir`. Dumps each loaded model's KV cache to disk when the server stops and pushes the newest one back on the next start, which buys back the one cost no amount of VRAM tuning touches: reading a prompt is **quadratic** in its length and the cache is *process memory*, so a restart re-reads the whole conversation from zero. Measured on a 234k-token prompt (Qwen3.8-27B, hybrid `qwen35`, 17 of 65 blocks carrying attention): the marginal cost per token fits `0.95 ms + 0.0287 ms per 1k of context`, i.e. 984 t/s at position 4k against 142 t/s at 218k, which integrates to roughly **17 minutes** of prefill, against ~8.3 GiB of sequential IO to reload the same state. Off by default: the disk cost is real, stopping waits for the write, and the next start loads the model eagerly to push the state back in, so a machine running short prompts pays all of that for nothing.
  - **How the flag reaches the child**, which is the part that nearly made this impossible. The `/slots` endpoints only exist on a server started with `--slot-save-path`, and the framework always launches the **router** (`--models-preset`), whose per-model children are separate processes with their own command lines. `--slot-save-path` had **no env name** upstream until v0.7.0 (`LLAMA_ARG_SLOT_SAVE_PATH`, #30272), and none is needed: it propagates because `get_map_key_opt` (`common/preset.cpp`) maps every option by its **flag name with the dashes stripped** as well as by its env name: the router parses its own argv into `base_preset` (`load_from_args` then `common_params_to_map`, which keys off `opt.args`), `preset.merge(base_preset)` copies it onto every model, and `unset_reserved_args` does not prune it. One flag on the router's line therefore reaches every child.
  - **Why the restore is worth anything.** `SERVER_TASK_TYPE_SLOT_RESTORE` does not merely refill the KV buffer: it deserializes the token list saved alongside it into `slot->prompt.tokens`, which is exactly what the next request's `get_common_prefix` compares against. A restored slot is therefore indistinguishable from one the server prefilled itself, and the prompt is skipped. Without that half the dump would be a file nobody reads.
  - **The directory must exist before the launch.** llama.cpp validates `--slot-save-path` while *parsing* it (`fs_is_directory`, or it throws "not a directory"), so a missing folder does not degrade to "no snapshots this run", it stops the server from starting. `runstate::start` creates it, and the flag is emitted only when the toggle is on for the same reason.
  - Saving covers every model the router reports as `loaded` (never `loading`, which has no slot yet, nor `sleeping`, which has released its KV cache); dumps of models that are no longer loaded are pruned after a successful save, which is what keeps "the newest file" meaning "the model you were working on". Restoring deliberately takes **only** that newest dump: a dump is one conversation, restoring is an 8 GiB read plus a full model load, and the LRU would evict whatever a second restore pushed out anyway.
  - The path is overridable because the default sits under `%LOCALAPPDATA%`, on the system drive, and these files are large. Size follows the tokens the slot actually **holds**, not `ctx-size`: the dump is the conversation's KV cache, not the allocated context. Measured 4,703,061,864 bytes (4.38 GiB) for a 127,579-token conversation on Qwen3.8-27B, which is exactly the arch's 36 KiB per token; a full 262k context would be ~8.3 GiB. Plan disk against that ceiling, but a short conversation costs proportionally little. Those are v0.6.0 figures: since v0.7.0 the file also carries the slot's context checkpoints (#26004) and the draft context's state (#30574), so a restored hybrid model keeps its rollback points and a restored drafter does not start empty, at the cost of a larger file (up to `ctx-checkpoints` copies of the recurrent state plus the draft's KV; not re-measured yet).
- A read-only, multi-line **Command Line** card shows the exact `llama-server` invocation **Start** would run, one `--flag value` per line joined with the shell's line-continuation character (`` ` `` on Windows, `\` on Linux) so you can paste it straight into a terminal. It auto-sizes to its content (no inner scrollbar).
- **Network** card: **Base URL** and **API Key** fields for integration endpoints (opencode.json + Claude Code). **Base URL** has a **Default** checkbox: checked = auto-derived from host+port, nothing written to server.ini; unchecked = editable override (useful behind a reverse proxy or LLM gateway). The stored value is the base without `/v1`; the suffix is appended automatically only for opencode.json's `baseURL`. **API Key** has a **No key** checkbox: checked = no key used, field disabled; unchecked = editable. These fields also affect the Open chat UI button URL.

### Models tab: `presets.ini`

Scans `.gguf` files under the SAVED `ModelsDir`'s fixed subfolders: `models\` (main models), `mmprojs\`, `mtps\`, `dflashs\` (`model_scan::Category::subdir`); a file sitting at the `ModelsDir` root is not scanned, and an unsaved Server-tab `ModelsDir` edit doesn't move the scans until saved (like every client-facing projection, they follow the file). Shows the presets table, and edits per-model settings.

Every row of the preset list carries an **on/off switch**. On means the preset's section is in `presets.ini`, the file `llama-server --models-preset` reads; off **moves** it, verbatim (comments and hand-edits included), to `presets.ini.disabled` beside it, which nothing but this app reads. So a preset switched off is still listed (dimmed, after the enabled ones) and still editable, but llama-server stops offering it at its next start (the router reads `presets.ini` once, at launch), OpenCode drops it at once (see the [Integrations tab](#integrations-tab)), and the Benchmark tab no longer lists it, since a preset the server does not serve cannot be run. The design choices, all in `presets.rs`'s module header:

- **A second file, not commented-out lines.** Commenting a section out in place was the other option, and it loses on the way back: the file would then hold two kinds of `;` line, the user's own notes and parked keys, that no reader can tell apart.
- **The switch is not a navigation.** It rebuilds the list (`gui::refresh_preset_list`) and leaves the form alone, so an unsaved edit survives it and its Save lands in whichever file now holds the preset (`presets::save` resolves the file per id). Saving a switched-off preset therefore keeps it off.
- **Ids are unique across both files**: New… and Clone… de-conflict against the parked ids too, and Rename refuses one, because switching a preset back on onto a namesake would overwrite one of the two.
- **Destination first, then the source.** A switch interrupted between its two writes leaves the preset in both files, never in neither, and it then reads as enabled (the copy llama-server serves) until the next switch replaces the stale twin.

**New…** has two sources: a model file already under `ModelsDir`, or **From Hugging Face…**, a button in the same dialog that hands over to a second modal (`gui\hf_dialog.rs`; the GUI face of `preset download`, the backend is `hf.rs`). The modal holds the job up to the choice; **Download** closes it and hands the job to the background (`gui\downloads.rs`), so the main window is usable at once and the form is never replaced behind the user's back. In order:

- **Search.** One field takes either words or a repository (`hf::classify_input`): anything `hf::parse_spec` accepts (`org/repo`, `org/repo:QUANT`, the model page's URL) is a repository, words are a search (`qwen3 8b`, `gemma 3`), and the button reads **Search** or **List** accordingly on every keystroke. Slash-carrying text without a space that is not a repository (`a/b/c`, `org/repo:`) is a mistyped spec: the parse error shows under the field and keeps the button disabled. A search (`hf::search`, off the event loop) asks the HF model search for GGUF repositories, most downloaded first, 30 at most, and shows one two-line row per repository: `org/repo`, its downloads over the last 30 days, `gated`/`private` when it needs a token, the model's kind and size when the search's `gguf` summary (`expand[]=gguf`) tells them (`MoE 30.5B`, `dense 8.2B`: the architecture decides, then an `A3B`/`8x7B` name; an architecture neither list knows shows only the size, marked `dense/MoE unknown`, never a guess), then the quantizations its file names show (llama.cpp's own tag rules, ordered by bits) and its sidecars. The file lists come in the search answer itself (`expand[]=siblings`), so there is no request per row; sizes wait for the listing. The verified API parameters are in `hf.rs`'s module header.
- **List.** Clicking a result row puts its `org/repo` in the field and lists it; a typed repository lists directly, with no search round trip. The listing runs off the event loop and fills one row per GGUF quantization: quant, size, shard count, the sidecars llama.cpp would pair with it (mmproj, MTP, DFlash, DSpark), and a `default` mark on the one `llama-server -hf` would pick, which starts selected. A listing reached from a row offers **Back to results** (the rows and the query come back; a listing still in flight is dropped), and if it fails, the results stay on screen with the error under them. One request runs at a time (the button reads `Searching…` or `Listing…` and is disabled meanwhile); a generation counter, also bumped by Back and by closing the dialog, drops the answer of a request nobody is waiting for.
- **Placement estimate and recommendation** (`hf_fit.rs`, its module header has the arithmetic). Each listed row gets a second line saying how that quant would run on THIS machine: `all on GPU` (with the GiB needed and usable), an MoE split (expert weights of how many layers fit on the GPU beside all attention and shared weights, the GiB left in RAM, the `--n-cpu-moe` value), a dense split by layers, or too big, plus whether the RAM part pages from disk through mmap. The numbers come from the candidate's GGUF header (block count, per-layer expert vs other tensor bytes, KV cache size), fetched with HTTP range requests (the first 8 MiB, more only for a huge tokenizer; up to 4 at a time, cached per repository commit), so the listing is usable at once and the rows fill in as answers arrive. The budget is each of the device probe's GPUs ON ITS OWN (integrated GPUs are left out when a discrete one exists; the same card under two backends counts once, under the id of its non-Vulkan backend: `CUDA0`, `ROCm1`) less 2 GiB each for compute buffers and the fit margin, with the KV cache at f16 for the model's context capped at 32k, and the system RAM less 4 GiB; the line above the rows names the cards in split order with what each can hold. With several cards the estimate is made card by card, the way llama.cpp's layer split cuts a model (every card a consecutive run of blocks, the output layer on the last one, a block never straddling two cards): a model the largest card holds alone goes there alone, else the cut that fills every card to the same share of its memory, and the row names the cards with their GiB and the `tensor-split` it would write (`all on GPU with a 32k context: AI PRO R9700 (ROCm1) 20.2 GiB + RTX 4070 SUPER (CUDA0) 9.1 GiB, tensor-split 26,23`). The split order is the one the guides measured on an R9700 + RTX 4070 SUPER: the ROCm card first on Windows, the CUDA card first on Linux; a machine without that pair keeps the probe's order. Every row counts the image encoder and drafter currently chosen, on the card each would land on (see "The placement is an estimate" below). Once every row has its answer, one is marked **recommended** with its reason: the best quality that fits in GPU memory with those extras, else the best that fits with its image encoder on the CPU, else for an MoE the best quality whose experts fit in RAM without paging, else none. The pick moves to it unless a row was already clicked; while estimates load, or with no GPU in the probe (every row then says the estimate is unavailable), llama.cpp's default stays the pick. `preset download --list` prints the same line per row, the basis and the recommendation.
- **Choose.** The mmproj tick appears only for a candidate that has one (ticked, as `-hf` would take it); the drafter pills (`none` and each drafter the candidate offers) only for one that has a drafter, `none` selected, since a drafter costs VRAM and llama.cpp's default is no speculation. A summary line counts the files and bytes the choice fetches.
- **Access token.** A masked field for a gated or private repository. Left empty, the environment's token is used (`HF_TOKEN`, else the `hf auth login` file: `hf::token_from_env`), and the placeholder says when one exists. The token is deliberately not *prefilled* into the field: it would then live in a UI property and a screen reader's tree for nothing. What the user types stays in memory, and neither reaches `settings.ini`, a log, a status line or a preset (`hf::Token` has no `Display`; `HfError` never carries it).
- **Download.** The modal closes, the footer says the download started in the background, and the **Downloads** window (its own top-level window, like View logs and HW Monitor; `ui\downloads_window.slint`) comes up with one card per download, newest first: `org/repo  ·  QUANT`, what it fetches, its state (Downloading, Cancelling…, Creating the preset…, Done, Failed, Cancelled), one readout for the whole job and one for the current file (bytes, percent, a bar each), the error or outcome, and its buttons (**Cancel download**, **Resume**, **Show preset**, **Dismiss**; **Clear finished** at the bottom). Closing the window only hides it; it is reopened from the footer indicator (`1 download running`, `Downloads: 1 done, 1 failed`, clickable, shown while there is any row), the Hugging Face dialog's **Downloads** button, or the tray's **Open downloads**. Downloads of different repositories run side by side; a second one of a repository already downloading is refused in the dialog (both would write its staging folder), and so is a Resume while another download of it runs. Progress is coalesced on the worker thread (one update per 250 ms, plus every file boundary), so llama-server's ten-lines-a-second-per-file reports never flood the event loop. The button reads **Resume download** when a stopped download left a partial (`.downloadInProgress`) of one of the PICKED candidate's own files under `ModelsDir\.hf-staging` (`hf::has_partial`, re-checked on every pick): llama-server resumes it with a range request. The staging folder alone does not count (the child creates it before its first byte), nor does a partial of another quant of the repo, which this download would not read.
- **Errors** before the download (a bad token, a refused repository) stay in the dialog, the listing kept; the not-found and gated errors also point at the token field. A failed transfer shows on its card in the Downloads window, plus the footer, and **Resume** retries it with the same choice.
- **Cancel, hide, Quit.** **Cancel download** closes the download child's stdin (a kill follows 10 s later if it lingers), and what was fetched is kept for a Resume. It deliberately does NOT send the router's exit line during a transfer: on that line llama.cpp's downloader cancels cleanly and DELETES its `.downloadInProgress` partial, while EOF makes the child exit on the spot with the partial intact (`hf.rs` module header). Closing the main window hides it to the tray with the downloads still running (they still create their presets). The tray's **Quit** while one runs does not quit: it opens the Downloads window with a red strip asking, **Keep running** or **Stop downloads and quit**, which cancels each the same way (partials kept for a later Resume) and quits once the last has stopped (15 s at most). The process exit closes any remaining child's stdin, so nothing is orphaned either way.
- **The end.** The files land in `models\` / `mmprojs\` / `mtps\` / `dflashs\` under `<org>\<repo>\` (the org included: `Qwen/` and `unsloth/` both publish a `Qwen3-8B-GGUF` with the same file names). The model and the drafter keep their Hugging Face file names; the mmproj, usually generic there (`mmproj-F16.gguf`), is named after the model so the mmproj picker says whose it is (`hf::mmproj_target_name`): the model's first shard's name without its shard suffix and quant tag (`UD-` included), `-mmproj`, then the projector's own quant tag when its name has one (`Qwen3-VL-8B-Instruct-Q4_K_M.gguf` + `mmproj-F16.gguf` → `Qwen3-VL-8B-Instruct-mmproj-F16.gguf`; `tinygemma3-Q8_0.gguf` + `mmproj-tinygemma3.gguf` → `tinygemma3-mmproj.gguf`). Two quants of one repo thus share one projector file: a file already at its target with the listed size is used as is, one of another size refuses the download. The preset is derived from their headers (`hf::preset_from_download`: paths, project URL, `general.sampling.*`, `jinja`, `fit`, and the placement below), saved through `hf::save_preset` (which pins an unset `ModelsDir` first); the header reads and the derivation run off the event loop (the card reads `Creating the preset…`), and the id is de-conflicted against the presets listed at save time. It does NOT disturb the user: the list reloads and the pickers rescan so the new files are in them, opencode.json follows, but the selection and the form stay as they were, unsaved edit included. The footer and the card say what was created; the card's **Show preset** opens it in the Models tab, through the discard guard when the form is dirty (refused, with a note on the card, while a dialog is open in the main window).
- **The placement is an estimate, written to be tuned.** The downloaded quantization's estimate (read again from the files on disk, against the same machine the row was estimated on) becomes the keys the Models tab edits (`hf_fit::placement`, the table in its module header): several cards with the model on one of them, `device` = that card (the fit then sizes the context to it); a cut over several cards, `device` + `tensor-split`; an MoE that spills, `n-cpu-moe` (the attention and shared weights of every block stay on the GPUs, with the experts of the last blocks); a dense model that spills, `n-gpu-layers` (the blocks from the output back, counted with the output layer). Whenever `tensor-split`, `n-cpu-moe` or `n-gpu-layers` is written, `ctx-size` is too, at the context the estimate reserved the KV cache for (32k, or the model's own when shorter), which turns `fit` off as the form would: llama.cpp's fit would otherwise shrink the context against the memory of all cards together and then keep the cut, which can over-fill one. A RAM shortfall changes nothing written (the rest pages from disk through mmap; the note says so). A separate drafter is pinned to the card it was counted on whenever the device list would not put it there: the last card of a split (`device-draft`; an empty one inherits the whole list, which crashes separate MTP heads), or another card that let the model stay alone on its own. With one card the model fits, no GPU in the probe, or a model too big to place, nothing is written and the preset keeps today's defaults (`fit` on). A placed preset carries a `; placement = ...` comment line (estimated at download, at which context, a starting point to tune with the `optimize-preset` procedure): a comment like the project URL, never a key, kept by a GUI save; the GPU distribution card shows it with a **Clear** button for once the values are tuned. The image encoder and a separate drafter ARE counted, as currently chosen (the dialog's mmproj tick and drafter pill, `--no-mmproj` and `--draft` for `preset download`), on the card they land on (`hf_fit` module header, "The extras"): the encoder as its file plus 512 MiB to encode an image (measured: 248 MiB at llama.cpp's warmup, 418 MiB for a 4K image, on Qwen3.8's 888 MiB encoder) on the first `device` entry, where llama.cpp puts it; the drafter as its tensors, its KV cache at the model's context (a sliding-window layer only its window) and 768 MiB of compute buffers (measured for a DFlash drafter of Qwen3.8-27B), beside a model alone on its card or on the last card of a split. The split shifts away from the card hosting them, and a quantization that fitted only without them spills or loses the recommendation. A full card moves the encoder rather than shrink the model: to another card (`mmproj-device`), else, for a dense model, to the CPU (`mmproj-offload = false`, recommended only below every quantization that keeps it on a GPU); an MoE instead moves one more block's experts to RAM, the CPU encoder only when no card takes it. An MTP head inside the model file is part of the model and counted once. Toggling the tick or the pill re-estimates every row and the recommendation without fetching again (a drafter kind not yet read fetches its headers once); the note names what was counted and where. `preset download` prints the same keys after `Created [...]`.

**Delete** opens a confirmation (`gui\models_tab.rs` `DeleteDialog`, the rules in `linked_files.rs`) that can also remove the model files the preset links, since a downloaded model is otherwise left behind as gigabytes nothing points at:

- **One row per linked file on disk**, with its size and folder: the model (a split model is ONE row covering every `-NNNNN-of-NNNNN` shard, shown as `(N shards)` with the total size, since a lone shard is useless), the mmproj, the drafter. A path that names no file on disk gets no row.
- **Keeping is the default.** Every tick starts cleared, Cancel (or Esc, or the backdrop) drops them, and the line under the list names exactly what a confirm removes, in the error colour once anything is ticked; the button then reads **Delete preset and files**.
- **A file another preset references cannot be ticked.** The check reads both `presets.ini` and `presets.ini.disabled` (a switched-off preset still points at its files) and compares paths the way the pickers do (case-insensitive on Windows, shards by base name); the row is greyed and says `in use by [id]: kept`. It is run again at confirm time against the presets as they stand then, so a file that became shared meanwhile is kept.
- **The section goes first, then the files.** A preset that cannot be removed keeps its files; a file that fails to delete does not block the rest and is named in the status line (shown as an error), beside what was removed and how much space that freed. The pickers are rescanned afterwards.
- **Empty download folders go with them, nothing else.** After the files, each one's folder is removed if it is now EMPTY, walking up to (never including) the `models\` / `mmprojs\` / `mtps\` / `dflashs\` subfolder of the saved `ModelsDir`: the `<org>\<repo>\` folders a Hugging Face download created. A folder with anything left in it, a link or junction, the subfolder itself, and every file outside those four subfolders stop the walk (the file itself is still deleted, only no folder is touched).

The CLI does the same with explicit flags: `preset delete <id>` keeps every file, `--delete-files all` (or a comma list of `model`, `mmproj`, `draft`) removes them too, and a picked file another preset references refuses the WHOLE command up front, nothing deleted, naming the presets, unless `--even-if-shared` (accepted only beside `--delete-files`) overrides it. A file that fails to delete is reported on stderr and makes the command exit with an error, the preset deleted all the same.

The editor is grouped into cards by concern:

- **Assets**, the file pickers and speculator selection: model file (`--model`), MMProj (`--mmproj`; its **Vision on GPU** offload toggle and the per-image token bounds moved to their own **Vision** card below), and ONE draft-model dropdown that merges MTP heads (scanned from `mtps\`) and DFlash drafters (scanned from `dflashs\`), both feeding `--model-draft`, plus the spec-type dropdown. The pick policy lives in Rust (`apply_draft_pick` in `gui/models_tab.rs`, unit-tested), not in the `.slint` handler:
  - The spec type comes from the picked FILE's own GGUF header (`gguf::draft_spec_type`, mirroring llama.cpp's `common_speculative_types_from_gguf`): arch `dflash` carrying a `markov_w1.weight` tensor → `draft-dspark`, without it → `draft-dflash`, a `blk.<block_count - 1>.nextn.eh_proj.weight` head → `draft-mtp`. The folder it was scanned from (`mtps\` → `draft-mtp`, `dflashs\` → `draft-dflash`) is only the fallback, for a header that names none of the three (a blockless MTP head file like gemma4-assistant) or a GGUF that will not open. The folder cannot be the primary source because `dflashs\` holds both DFlash and DSpark drafters, and running one as the other does not fail: `is_dspark` changes the drafting batch (`n_draft` masked positions against `n_draft + 1`, anchor-first, ceiling `block_size` rather than `block_size - 1`), so the drafts are read from the wrong positions and get rejected.
  - Either way, when a GPU is selected the draft is pinned to it, the FIRST one if several (`device-draft` takes a single device, and a multi-device draft split is exactly what crashes MTP heads; an EMPTY `device-draft` would inherit the preset's `device` list, but the picker writes it anyway, so the pin shows), with `n-gpu-layers-draft = 99` (the shared "all layers" sentinel, `Options.all_layers` / `form::ALL_LAYERS`, equality test-asserted); otherwise it falls back to CPU (`n-gpu-layers-draft = 0`).
- **Model info** (read-only, between Assets and Hardware Config): reads GGUF metadata through llama.cpp's own reader (runtime-loaded `ggml-base.dll`, `libggml-base.so.0` on Linux, no reimplemented parser; see `gguf.rs`): dense vs MoE (+ expert counts), layer count, trained context, GQA shape, the **Memory** kind (attention / recurrent / hybrid, `gguf::arch_memory`, a mirror of `llm_arch_is_recurrent` / `llm_arch_is_hybrid` to re-check on a llama.cpp bump: a recurrent state cannot be rewound, which is when context checkpoints matter), quant, and whether it embeds MTP layers, plus whether a matching MTP/DFlash drafter is present. A **Chat template** row reports the embedded `tokenizer.chat_template` as `Jinja (embedded)` / `embedded (non-Jinja)` / `none` (the `{%`/`{{` heuristic mirrors llama.cpp's `common_chat_verify_template`), with a **Preview** button (shown only when a template is present) that opens the raw template text in a modal. An **Embeddings** row reports `token_embd.weight`'s OWN quant and size, which neither the file name nor the `Arch / quant` row tells you (Unsloth's `Q6_K_XL` keeps the embedding table at `Q8_0`; its `Q4_K_XL`/`Q5_K_XL` drop it to a K-quant), and it is what decides whether the Tensor placement table may pin that table to a GPU: the backend needs a `get_rows` kernel for that exact type, and a type without one round-trips the table to host RAM on every token (25 → 2.8 tok/s measured with a Q4_K table, the GPU sitting at 0%). That whitelist (`gguf::gpu_has_get_rows`, mirroring `ggml-cuda.cu`'s `supports_op`) covers every K-quant and IQ-quant, so the Unsloth pair above both pin fine, and what trips the warning is Q8_1, Q8_K, the ternary TQ types, NVFP4, and IQ4_NL/MXFP4 on a model whose width is not a multiple of 256. The size is the VRAM the pin ADDS to that card. The verdict itself is not repeated in the row: it surfaces as a warning strip on the [Tensor placement table](#tensor-placement-table), at the moment a rule actually pins it. For MoE models a **MoE layers** row shows how many layers carry experts (with a "saves VRAM (slower)" note), sizing the `--n-cpu-moe` field; dense models have no such row because their FFN lever, `--n-cpu-ffn`, is sized by the plain layer count. Two rows read that same template for **reasoning**: **Thinking** says whether it does any (and whether `--reasoning on|off` can switch it: that flag only sets the template variable `enable_thinking`, so a template that never names it thinks whatever you pick), and **Past thinking** says whether `--reasoning-preserve` is a *lever* on this model at all; see [Keep past thinking](#keep-past-thinking-vs-a-raw-preserve_thinking-kwarg) for why that is the useful question and why llama-server's own log cannot answer it. Both are read from the template's **source text** (this app has no Jinja engine; llama.cpp answers the same question by rendering the template), so the subject of every verdict is the *template*, not the model: `no marker in the chat template` does not prove the model can't think; MiMo-VL's template names nothing at all, yet the model emits `<think>` and llama-server's parser picks it out of the output. What the silence *does* prove is that neither flag has anything there to act on. A **MMProj** row (projector type, vision/audio modality, encoder depth, image/patch size) and a **Draft file** row (the drafter's arch/layers and, for DFlash, the trained `block_size` → the implied `--spec-draft-n-max` ceiling) appear when those are selected. Reads are synchronous and uncached; if `ggml-base.dll` can't be loaded the box shows "unavailable" and the load is retried on the next read (only success is memoized), so a DLL that appears later (e.g. a finishing `xtask build`) is picked up without a restart.
- **GPU distribution** (directly under Model info): [the table](#gpu-distribution-table).
- **Tensor placement** (under GPU distribution), [the table](#tensor-placement-table) for `--override-tensor`: the exceptions to the card above, i.e. tensors that go on a device of their own whatever their layer does.
- **Hardware Config**, the remaining placement knobs: GPU layers, MoE CPU layers, MoE cache (`--moe-cache-mib`, llama.cpp v0.7.0+, experimental upstream: VRAM caching the experts kept in host RAM; it acts only on layers whose experts are ALL in RAM, and the model fails to load on a dense model, under split mode `tensor`, or below the experts of one token, so a dense model drops the key (`presets::prune_inactive_moe_cache`), Save refuses it beside `split-mode = tensor` (`validate_moe_cache_split`), and the Models tab's Save refuses a value under the preset's LOAD floor (`moe_cache.rs`: the budget is split across GPUs by `tensor-split` and within a GPU by host bytes, so the load floor is the cheapest group's `(n_expert_used + 1)` experts over its share, and the hint quotes a second, larger number at which EVERY group caches; with 2+ GPUs and a blank `tensor-split` llama.cpp weighs by free VRAM at load, and only the floor no split gets under is shown); llama-bench has no such option, so only the live engine measures it), Dense FFN CPU layers (`--n-cpu-ffn`: the dense twin of `--n-cpu-moe`, keeping the first N layers' `ffn_up/down/gate` on the CPU; on a MoE model it reaches only the dense layers such a model carries, never the experts), Op offload (`--op-offload` / `--no-op-offload`: a `default`/`on`/`off` tri-state, on upstream; `off` stops llama.cpp from running an operation on the GPU when its weights sit in host RAM, which otherwise copies those weights to the card on every prefill batch of 32+ tokens: 385 → 608 tok/s of prefill at 93.7k tokens on a MoE with 8 blocks of experts in RAM behind a Gen4 x4 link, decode unchanged, a no-op with every weight in VRAM), Repack (`--repack` / `--no-repack`, the same tri-state, on upstream: host weights of a type the CPU has an interleaved kernel for move into the `CPU_REPACK` buffer, but only without a GPU: with one, llama.cpp puts host weights in the GPU's pinned host buffer, which it picks before the repack types, so the key is a no-op there unless No host buffer is on; measured in the `moe_cache.rs` module header), No host buffer (`--no-host`, no negative form, so a plain on/off written only when on: host weights go to ordinary RAM instead of the GPU's pinned host buffer, which lets the CPU repack them and takes those layers out of the MoE cache, where the floor then falls back to the cheapest layer's need), draft device, draft GPU layers.
- The remaining cards group the runtime knobs by concern: **Resource / context** (ctx-size, parallel, batch/ubatch), **Embeddings** (`--embeddings`, no negative form, so a plain on/off written only when on: it turns on `/v1/embeddings`, which otherwise answers 501, and every input must fit one ubatch, so batch/ubatch must cover the longest text sent; plus `--pooling`, `default` = the model's own, where a wrong value degrades the vectors without an error: Qwen3-Embedding wants `last`), **KV cache** (K/V cache-type, flash-attn, cache-ram, cache-reuse: off by llama.cpp itself on a model with an mmproj or a cache that cannot shift), **Chat / reasoning** (jinja, [prefill assistant](#prefill-assistant), reasoning, reasoning-format, [reasoning-effort](#reasoning-effort), [keep-past-thinking](#keep-past-thinking-vs-a-raw-preserve_thinking-kwarg), plus the [output split](#thinking-budget-vs-the-answer): thinking budget, budget message, max output), **Sampling overrides** (temp, top-k, top-p, min-p, repeat/presence penalty, plus `backend-sampling`: a `default`/`on`/`off` tri-state like flash-attn, running the sampler chain on the GPU that holds the logits; `on` is the only value that changes the launch, since the flag has no negated form, and llama.cpp falls back to CPU sampling silently when the chain holds a sampler without a backend kernel, and turns it off outright under a grammar, a thinking budget or split mode `tensor`), **Advanced** (chat-template-kwargs), **Vision** (the `--mmproj-offload` offload toggle plus image-min/max-tokens, the per-image token bounds only dynamic-resolution vision models read; all gated on an mmproj being selected; Qwen-VL warns at load it wants `--image-min-tokens 1024`), and **Speculative decoding** (last, one sub-heading per speculator: the **draft model** group, Draft n-max, Draft p-min, plus the draft context's own K/V cache types, see the note below on why they are not the model's; then one group per n-gram speculator with its own `--spec-ngram-<type>-*` tuning: Match length, Min draft and Max draft for `ngram-mod`, Lookup n-gram and Draft m-gram for `ngram-simple`, `ngram-map-k` and `ngram-map-k4v`, plus Min hits for `ngram-map-k4v` alone (llama.cpp parses `--spec-ngram-simple-min-hits` and `--spec-ngram-map-k-min-hits` too, but v0.6.0 acts on neither, so they are not preset fields); every group is always shown, an n-gram group enabled while its type is ticked, and the save drops the other types' keys, `presets::prune_unused_ngram_keys`). Draft p-min (`--spec-draft-p-min`) is a confidence floor that stops a draft at its first unsure token; the verify batch is nearly free to lengthen on a bandwidth-bound card (halving it saved 5% per step on Qwen3.8-27B + DFlash2), so the floor only pays by cutting tokens that would have been rejected, and a high one loses (0.3 was a tie-to-small-gain there, 0.7 cost 10%). The field-by-field schema (each INI key, its `--flag`, and the "default checkbox omits the flag" numeric pattern: `DefaultSpinBox` for ints, `DefaultLineEdit` for floats) is owned by the `presets.rs` `Preset` field docs; the per-widget rationale (why top-k is an int SpinBox, the `SegmentedControl`s, the `DefaultLineEdit`'s reveal-on-uncheck) lives in `ui\models_page.slint`.

Field behaviors:

- **Fit to VRAM** (`fit = on|off`, the `-fit` flag) lets llama.cpp size the context and the GPU layers to fit device memory, leaving about 1 GiB free per GPU. The checkbox is live only with **Context** and **GPU layers** both at default, the two things it sizes (`form::fit_allowed`, applied on load and on save too); setting either one by hand switches it off. It is **always written**, `off` unless checked: llama.cpp's own default is on, and a "default" GPU layers here means "offload every layer", which the fit would cut. A preset without the key reads as off. With it on, `tensor-split`, Tensor placement, MoE CPU layers and Dense FFN CPU layers must stay empty too: any of them makes llama.cpp skip the layer placement (`common/fit.cpp`, a warning in the log) and fit only the context.
- **Load mode** (`load-mode`, `-lm`) is **one dropdown, not two checkboxes**: default (the key omitted: llama.cpp's `auto`, mmap unless a device can't), `auto`, `none`, `mmap`, `mlock`, `mmap+mlock`, `dio`. The states do not compose like two bools: `mlock` is mlock *without* mmap (`use_mmap` is true only for `mmap` / `mmap+mlock` / `auto`, `llama-model-loader.cpp`), and two independent toggles cannot express a six-state enum, which is why the UI is a combo.
- **Vision GPU** (`mmproj-device`, `-mmdev`): which GPU the mmproj/CLIP image encoder runs on. A separate dropdown because the encoder is **placed on its own**: it follows the FIRST entry of `--device` (the preset's `device` key included), and with no device pinned llama.cpp gives it the first GPU backend the registry offers, so on a mixed CUDA+ROCm box it lands on the NVIDIA card even when the model is on the AMD one, holds VRAM there for the model's whole lifetime, and computes only on image requests. The key overrides both defaults.
- The **draft device** and **Vision GPU** fields are dropdowns populated from `llama-server --list-devices` (e.g. `CUDA0`, `Vulkan0`). The probe runs async at startup and on Refresh/F5; its result is cached Rust-side (`devices::probed()`), not published as Slint state; the GPU table gets its rows built from it in Rust too (`gpu_split::build_rows`).
- The **GPU layers**, **MoE CPU layers**, **Dense FFN CPU layers**, and **Draft GPU layers** fields are sliders ranging `0..` the model's (or draft's) layer count read from the GGUF header, each with a **default** checkbox (on-screen label; the backing form field is `*_auto`), checked by default, that omits the flag and disables the slider. When the selected draft is an MTP/nextn head (no transformer layers, `block_count 0`) the Draft GPU layers control becomes a two-option on-GPU/on-CPU selector (a `SegmentedControl`, not a `Switch`, so its state is a pure read of the model and never goes stale) instead of a slider.
- Controls that don't apply are disabled: draft n-max, draft p-min, draft n-min, draft n-ubatch (`--spec-draft-n-ubatch`, v0.7.0+: the draft context's physical batch, which reaches embedded MTP heads too) and the two draft K/V cache types need a draft available (a draft model selected, or the main model embedding MTP heads); **draft device and Draft GPU layers need a draft FILE** (see the note below); MoE CPU layers and MoE cache need an MoE model (Dense FFN CPU layers is deliberately not gated the other way: a MoE model still has dense FFN in whichever layers carry no experts, and llama.cpp accepts the flag for both); split-mode needs other than exactly one GPU checked. `--spec-type` is a list, edited as two controls: **Drafter**, the one `draft-*` entry (only `none` without a draft), and **N-gram drafters**, a checkbox per `ngram-*` speculator (`ngram-mod`, `ngram-simple`, `ngram-map-k`, `ngram-map-k4v`), never disabled since they draft from the tokens already in the context, and combinable with each other and with the drafter (llama.cpp tries the n-grams first and falls back to the draft model: e.g. `ngram-map-k4v,draft-dflash`); llama.cpp's `ngram-cache` has no checkbox (its draft length is fixed at 8 and the server never saves its lookup caches), and a preset naming it keeps it in the list untouched (`presets::spec_type_is_draftless`); their tuning keys sit in the Speculative decoding card below.
- **Every field of the KV cache card can be left at `default`** (i.e. the flag is omitted and llama.cpp decides), but the affordance differs per field, because the shape of "unset" does: cache-ram takes the usual `DefaultSpinBox` checkbox; **K/V cache-type** carry it as the FIRST dropdown entry (`Options.cache_types[0]`, which is *not* the same as picking `f16`: that pins f16 whatever llama.cpp's default becomes); and **flash-attn is a three-pill `default`/`on`/`off` `SegmentedControl`, not a checkbox**, since `--flash-attn` takes `[on|off|auto]` and *defaults to auto* (on where the backend supports it); a bool could only ever reach two of its three states, and the one it couldn't reach was the default. `off` is a real instruction, distinct from unset: it forces the kernel away, which also costs a quantized K/V cache most of its benefit. Leaving these unset used to be unreachable from the GUI, and worse than unreachable: the form filled an absent `cache-type-k` in from the schema default, so a preset that had never named one displayed `q8_0` and *wrote* `q8_0` on the next save of any unrelated field, silently requantizing a cache llama.cpp would have left at f16 (guarded by `form.rs`'s `kv_cache_unset_state_survives_the_form_round_trip`).
- **The K/V cache-type dropdowns offer every type llama.cpp accepts** (`f32 f16 bf16 q8_0 q5_1 q5_0 q4_1 q4_0 iq4_nl`, highest precision first; there is no 6-bit K-quant cache type, q5_1 is the closest), and **a strip on the KV cache card says when the picked pair will not run where the preset runs** (`kv_cache::warning`, Rust-side because it parses the device pins; `AppWindow`'s `changed kv_cache_inputs` handler and every GPU-row rebuild recompute it). Accepted is not runnable, and each gap is silent in llama.cpp: CUDA and ROCm have no FlashAttention kernel for `iq4_nl` (a quantized V forces flash attention on, so the attention goes to the CPU; Vulkan does have one), Vulkan wants `bf16` on K and V together or on neither, a quantized V with flash attention `off` does not load at all, a type llama.cpp does not accept (a hand-edited `q6_K`) fails the load while the combo shows `default`, and on CUDA/ROCm a supported pair with no COMPILED vector kernel converts the whole used cache to f16 on every 1-2 token decode step. That last list is a build setting, `GGML_CUDA_FA_QUANTS` in the repo's `xtask/cmake/common.toml` (the framework adds `q5_0-q5_0` and `q5_1-q5_1` to upstream's `q4_0`/`q8_0`/`f16`/`bf16`), mirrored as `kv_cache::NATIVE_VEC_PAIRS` and pinned to that file by a test. Everything here is a copy of upstream logic, not a probe of the installed DLLs: re-check `ggml-cuda/fattn.cu`, the Vulkan `supports_op` arm and `kv_cache_types` on a llama.cpp bump.
- **A new preset leaves every tunable at `default`**, i.e. the key is omitted and the model runs on llama.cpp's own defaults until you override something on purpose (`Preset::default()`). Pinning one is not inert: `parallel` in particular turns off the unified KV cache llama-server's auto mode enables, quartering the context a single request may use (see the [Integrations tab](#integrations-tab)). The only keys a new preset writes are the four the form has no "unset" affordance for (`jinja`, `mmproj-offload`, `reasoning`, `reasoning-format`), each set to what llama.cpp would have done anyway, so writing them stays a no-op. **Clone** copies the source preset's values, which is its whole point.
- Changes are written to `presets.ini` (or to `presets.ini.disabled` for a preset that is switched off), preserving hand-edits to sections not currently touched. Path fields (model / mmproj / model-draft, and the server side's ModelsDir) containing `;` or `#` are rejected at save: the INI format can't escape them, so they would silently reload truncated (`ini::reject_comment_markers`).

> **Note: embedded MTP heads ignore the draft placement fields.** llama.cpp reads `--device-draft` and `--n-gpu-layers-draft` only when a separate `--model-draft` file is given (both live inside `if (has_dft())`). With MTP heads embedded in the main GGUF (`spec-type` set, no `model-draft`), it builds the draft context against the *target model*, so the draft runs on the model's own GPU and both keys are silently ignored. Setting them there is how a GPU ends up looking assigned to the draft while never drafting a token, so the UI disables them and says so. A **separate** MTP head file (e.g. gemma4-assistant) is the case where they do apply, and there, pin to ONE device: multi-device memory fitting crashes those heads. The full story lives in the `presets.rs` field docs, the single authority for this caveat.

> **Note: the draft context's KV cache does NOT follow the model's, and these two flags are the only way to reach it.** `common_base_params_to_speculative` (`common/speculative.cpp`) builds the draft params by copying the whole struct (the model's `--cache-type-k`/`-v` included) and then *unconditionally overwrites* both with `params.speculative.draft.cache_type_k/_v`, whose own default is `GGML_TYPE_F16` (`common/common.h`). So a preset running the model on a q8_0 KV cache still drafts against an **f16** one, and "leave the draft types unset and they inherit the model" is exactly backwards: unset means f16, always. **Draft K/V cache type** (`--spec-draft-type-k` / `--spec-draft-type-v`, aliases `-ctkd` / `-ctvd`) are the flags that reach it. Note this overwrite sits *outside* the `if (has_draft)` block that guards `devices` / `n_gpu_layers` / `tensor_buft_overrides`, so unlike the placement pair in the note above, these two **do** apply to MTP heads embedded in the main GGUF, which is why they stay enabled there and why `prune_inactive_draft_keys` groups them with the speculator rather than with the placement keys.

### GPU distribution table

`--tensor-split` is a positional vector indexed over the devices named by `--device`, **in `--device` order**. Typing `3,1` into a text box therefore means nothing until you know which devices those are, and with `--device` unset, "those devices" is every detected backend, which on a mixed box is a CUDA card, two ROCm devices (one of them an iGPU) and three duplicate Vulkan views of the same three GPUs. So the two settings share one widget (`GpuSplitTable`, used by both tabs): the **split-mode selector on top** (it decides what the rows below mean), then a row per detected GPU with a checkbox, its VRAM, an editable weight, and the derived share. There is deliberately no flags-preview line under the table: the values are persisted to the INIs, and a preview that showed `--device`/`--tensor-split` while ignoring the mode used to read as the whole truth while being stale.

Rows are built in Rust (`gpu_split::build_rows`): the **checked devices first, in split order**, then the rest in probe order. So the table read top to bottom *is* the `--device` list and its `--tensor-split` vector. Checking a box **appends** the device to the split; the **≡ drag handle** on each checked row is how you reorder it; the weight rides along with its device, so the proportions survive a move.

Position 0 is not cosmetic: it is `devices[0]`, which is also llama.cpp's **`main_gpu`** (it defaults `--main-gpu` to 0 and the framework never overrides it). With `--split-mode none` that is the *only* GPU llama.cpp keeps; under `layer` it takes the first slice of layers. Without the handle there was no way to put a chosen GPU at the head.

> The `--list-devices` ids are **not stable** across driver states: the same machine has enumerated its discrete AMD card as `ROCm0` on one boot and `ROCm1` on another, with the iGPU taking the other slot. Presets pin by id, so the table always shows the device **name** next to it: check the name, not the number.

The four states it can express map 1:1 onto llama.cpp:

| checked | `device` | `tensor-split` | meaning |
|---|---|---|---|
| 0 | *(blank)* | *(blank)* | llama.cpp uses all detected devices |
| 1 | `ROCm1` | *(blank)* | one GPU, nothing to split |
| ≥2, **Auto** | `ROCm1,CUDA0` | *(blank)* | llama.cpp splits by **free** VRAM at load |
| ≥2, explicit | `ROCm1,CUDA0` | `3,1` | 75% / 25% |

Note that blank-with-2-GPUs is *auto-by-free-VRAM*, **not** an even split; hence **Auto** and **Even** are two separate buttons, and the weight fields stay disabled until the split is explicit (Even is the way in). That is also what keeps the one-way `for`-row bindings honest: a weight edit never rewrites another row's weight, so it needs no model rebuild, while toggle / Auto / Even do rebuild, giving every delegate a fresh binding. All of it is guarded: `gpu_split`'s unit tests for the rules, and a `save_flow` phase that clicks the real checkboxes and asserts what reaches the INI.

#### The split mode decides what the columns mean

`--split-mode` is part of the same selection, which is why its combo sits **above** the table, and the columns follow it (`gpu_split::SplitMode`). It is a per-preset key (`split-mode`), so only the Models tab's table has the combo:

- **layer** (llama.cpp's default): the vector cuts consecutive runs of blocks; the block projection below applies.
- **none**: llama.cpp drops every device but `devices[main_gpu]` *before loading* (`llama_prepare_model_devices`), so the vector is dead. The editors retire, the head row reads **100%** and every other checked row says **unused**; the ≡ drag handle (which GPU leads) is the one control left.
- **tensor** (llama.cpp's tensor parallelism, **experimental** upstream, superseding `row`): the checked devices become *one* meta device, in split order, and every weight **and** the KV cache are cut along a tensor axis by the normalized vector (`llama_meta_device_get_split_state`, `llama-model.cpp`), so the table edits the **raw ratio** here too, with one difference the Share column states: a **blank vector is an even cut**, not the free-VRAM weighting of the other modes. `main_gpu` means nothing (there is one device). Three launch-time refusals the rows cannot show get a second strip under the combo (`preset_split_mode_warning`): the architecture must be one upstream implements (`gguf::arch_supports_sm_tensor` mirrors `llm_arch_supports_sm_tensor`'s deny-list; a listed arch throws at load), flash attention must not be `off` (`auto` is promoted to on), and with no device pinned llama.cpp pools **every** detected device into the split, duplicate Vulkan views and the iGPU included, since only the other modes dedup by device id. `--fit` is skipped with a log warning, so `ctx-size` is yours to size. Upstream tunes it for CUDA (NCCL) and promises nothing for other backends.
- **row** (**deprecated** upstream, superseded by `tensor`; still accepted by the flag, so still listed, last, and labelled, because an INI that carries it has to show it rather than read as layer): the weight *matrices* are split **row-wise** by the normalized vector, via the backend's split buffer type (CUDA/ROCm; a backend without one, Vulkan, quietly falls back to the layer cut). The layer assignment still runs over the same vector, so the KV cache and non-matrix tensors follow it, but the bulk of the bytes follow the row fractions, so the table edits the **raw ratio** and never shows blocks there. A hand-written value outside the four is preserved and treated like `row` for display: ratio, no block cut.

The combo has **one** "layer (default)" entry for both an absent key and `layer`: for a preset those are the same launch in every reachable configuration (an absent key falls back to layer). Picking it stores nothing in the INI. The mode pick is a `MappedComboBox` funnel (labels/values/index pushed from Rust, `preset_split_mode_picked` writes the form and re-projects the table).

#### Weights are ratios; the Models tab edits them as blocks

`--tensor-split` is normalized, so `85,15`, `17,3` and `29,5` are the same launch. What llama.cpp does with that ratio is cut **`n_layer_all + 1` positions** in two: every block of the GGUF (the nextn/MTP ones included) plus one more for the **output layer**, `dev_output = get_layer_buft_list(n_layer_all)`. On a 33-block model that is 34 places to cut and a percent field offers 100 of them: **83 / 84 / 85% all cut in the same place**, so two of every three edits move the number and change nothing.

So wherever a model is known (the Models tab, once its header has been read, and only under the **layer** mode; see above), the editable column switches to **`Blocks/34`** and each row gains the range it holds (`blocks 29-32 + output`). Until a header has been read the table keeps raw weights; one `positions` property switches it (pushed as 0 for every non-layer mode).

Writing a count back needs no inverse: a vector summing to the positions gives position `il` to the first device whose prefix sum passes it, so **the weights *are* the counts** and `set_blocks` stores what was typed (`29,5` → blocks 0-28 / 29-32+output, exactly). Three consequences worth knowing:

- **A count cannot be edited alone.** It is constrained to the positions, so one row going up means another coming down; the rows absorb from the back, which keeps a two-device edit local. That constraint also picks the widget: a **`Slider`** over `0..positions` with a live readout, committing once on **`released`**. Applying mid-drag would rewrite the other rows and rebuild the model, destroying the slider being dragged; `released` fires on pointer-up *and* on key-release for the arrows/Home/End, so the keyboard path commits too. (A `SpinBox` stays banned (a stray wheel over the page edits it silently), but `slider-base.slint` handles no scroll event at all, so a Slider is safe here. Its one gap: the *accessibility* set-value/increment actions route through `base.set-value`, which raises only `changed`, so an assistive client moves the thumb without committing.)
- **The INI still stores a ratio**, and that is the portable form. Re-point a preset at a model with a different `block_count` and `29,5` still means 85%, now cut somewhere else. The number in the cell is a *view* of the ratio under the current model, re-derived on every rebuild, never the source of truth.
- **Partial offload moves the target.** The split runs over `act_gpu_layers` starting at `i_gpu_start`, so lowering the GPU-layers slider shrinks the budget and the counts change on their own. That is the truth, not a glitch.

Auto has no counts to show (llama.cpp weighs the devices by their **free VRAM at load**), so the column falls back to ratios there too.

A selected device the probe doesn't know (a stale id, another machine's GPU, or simply the async probe not landed yet) is kept as a `(not detected)` checked row, so a save can never silently drop it.

> **Note:** `device`, `tensor-split` and `split-mode` are preset keys: each model launches with its own distribution.

### Tensor placement table

`--override-tensor` (`-ot`) is the exception list to the table above: `<regex>=<buffer type>` rules that send every tensor whose **name** matches the regex to a device of its own, whatever its layer does. llama.cpp matches with `std::regex_search` (`llama-model-loader.cpp`) and resolves the buffer type against every backend's `ggml_backend_dev_buffer_type`, so the legal targets are exactly the ids `--list-devices` prints, **plus `CPU`** (an unknown one is a hard `throw`: the model does not load). The CPU being a first-class target is why this table offers it and the GPU table filters it out.

The reason it exists, and the case the **+ Add override** button seeds in one click (`^token_embd\.weight` on the first GPU):

> llama.cpp keeps `token_embd.weight` in **host** memory even when it reports `offloaded 33/33 layers to GPU`. The embedding lookup is a `get_rows` over a handful of tokens: cheap on CPU, and worth a GB or two of VRAM. But with a GPU backend active that host buffer is **pinned** (it shows up in the log as `ROCm_Host` / `CUDA_Host`), and Windows counts pinned host memory as **Shared GPU memory**, so a model that fits in VRAM with room to spare still shows GBs of shared allocation, and the compute graph carries a CPU split it didn't need. On a big-vocab BF16 model the table is huge (`n_vocab 248320 × n_embd 4096 × 2 B` = 1940 MiB), which is when `token_embd\.weight=ROCm0` is worth the VRAM it costs.

The pattern is a **dropdown**, not a free-text field, because the value's grammar is unforgiving in two ways that llama.cpp applies *before* it parses anything, neither of them escapable:

- rules are split on `,`, so a `{1,2}` quantifier inside a regex tears its own rule in half, and the half without an `=` is a fatal `invalid value`;
- each rule is split at its **first** `=`, so an `=` inside the regex silently eats the pattern's tail.

So the **Tensor** dropdown names every tensor family llama.cpp's loaders use, and a regex is needed only for what none of them covers:

| Tensor | Pattern (every layer) |
| --- | --- |
| Embedding table | `^token_embd\.weight` |
| Per-layer embeddings (Gemma 3n) | `^per_layer_token_embd\.weight` |
| Output head | `^output\.weight` |
| Whole layer | `^blk\.\d+\.` |
| Attention | `\.attn_` |
| Linear attention / SSM | `\.ssm_` |
| Dense FFN, and its up / gate / down alone | `\.ffn_(up\|down\|gate)\.`, `\.ffn_up\.`, ... |
| MoE experts, and their up / gate / down alone | `\.ffn_(up\|down\|gate\|gate_up)_(ch\|)exps`, `\.ffn_up_(ch\|)exps`, ... |
| MoE shared expert | `\.ffn_(up\|down\|gate)_shexp` |
| MoE router | `\.ffn_gate_inp` |

The tensors outside the blocks are anchored with `^` because llama.cpp's `regex_search` matches anywhere in the name: an unanchored `output\.weight` also takes every `blk.<n>.attn_output.weight`, and `token_embd\.weight` also takes `per_layer_token_embd.weight` (that unanchored embedding rule reads as the Embedding table, and is saved anchored). Dense FFN and MoE experts are llama.cpp's own `LLM_FFN_DENSE_REGEX` and `LLM_FFN_EXPS_REGEX` verbatim, i.e. `MoE experts → CPU` *is* `--cpu-moe` and `Dense FFN → CPU` is `--n-cpu-ffn` over every layer; the dense regex's trailing `\.` is what keeps `ffn_up_exps` / `ffn_up_shexp` out of it.

A family inside the blocks also gets a **Layers** field: blank for every layer, or a list such as `10-12, 15`, which the rule writes as `blk\.(10|11|12|15)` in front of the family's pattern (`blk\.15` for one layer). It commits per keystroke without a row rebuild, like the regex field, and a text that is not a layer list yet (`10-`) leaves the value alone; the summary line under the table shows what is written. Switching the Tensor keeps the layers. A pattern reads back as a family with layers only in exactly that form (ascending, no repeats); any other is a hand-written regex.

**Choose…** on a row opens the **tensor picker**: every tensor of the selected model (read from its GGUF, every shard of a split model, with `gguf::read_tensors`), grouped as llama.cpp names them. The tensors outside the blocks are one group, and every block tensor joins the family of its name without the block number (`blk.N.ffn_up_exps.weight`), one line per layer under a header that ticks, clears, folds and unfolds the family and shows how many of its members are ticked and what they weigh. A tick goes to Rust, which rebuilds the list (the CheckBoxes sit under a TouchArea and are never self-assigned), and the list model is updated in place so a long list keeps its scroll. **Apply** writes the ticked set back into the rule as the shortest regex `tensor_picker::compile` knows: a family's own pattern, over every layer or some, when that matches exactly the ticked set (the row then reads as that family), else the families merged by ticked layers, `^(blk\.(10|11)\.(ffn_up\.weight|ffn_down\.weight)|output\.weight)$`, with `\d+` for every layer a family has. The result is checked against the tensor list before it is written: it never places a tensor more or less than the ticked ones. The picker opens with the rule's current matches ticked, and marks the tensors an earlier rule takes, since llama.cpp applies the first rule that matches.

Matching uses the `regex` crate, whose syntax agrees with llama.cpp's `std::regex` (ECMAScript) on everything this table writes and on the common hand-written forms. The same matching gives each row a **coverage** line, `12 tensors, 1.21 GiB` (counting first match wins, and saying how many more an earlier rule took), or `matches no tensor of this model`, which is where a rule that takes more than it says shows up: an unanchored `output\.weight` takes every `attn_output.weight` too. The line is its own model (`preset_tensor_coverage`), so a regex keystroke updates it without rebuilding the rows. Without a readable model the coverage lines are empty and **Choose…** is disabled.

**Custom regex…** reveals a text field that strips those two characters on the Rust side. A row's kind is *derived* from its pattern, with no hidden "is custom" bit to drift from a hand-edited INI, which is why picking Custom clears the regex rather than keeping the canned one it was switched from (a row still holding `\.ffn_…_exps` would simply read back as the MoE kind).

Rules apply **in order** (the first match wins), so no edit re-sorts them. A device the probe doesn't know is kept as a `(custom)` dropdown entry and flagged on its row, exactly as in the GPU table; a rule left with **no** device (only a hand-edited INI can produce one) is refused at save, because llama.cpp's failure mode for it is a throw during arg parsing, i.e. "the model didn't load" and nothing else. Same one-way `for`-row binding contract as the GPU table, with the same escape: add / remove / kind / device rebuild the row model, while a keystroke in the regex field must **not** (it would recreate the field mid-edit and drop the caret), and it can afford not to, since it changes no other row. Guarded by `tensor_override`'s unit tests for the rules and a `save_flow` phase that drives the real callbacks, types into the real regex field, and asserts what reaches the INI.

The rules are the preset's `override-tensor` key (`presets.ini`), one `--override-tensor` per model. The device dropdown is built from the rules: `device_options` appends a `(custom)` entry per unknown device id, so its length (and every row's `device_index`) depends on the preset's own rules.

### Prefill assistant

**Prefill assistant** (Chat / reasoning card, `prefill-assistant`) decides what happens when a request's *last* message is an assistant message: on (llama.cpp's own default, the key omitted) it is treated as the **start of the reply** and continued; off, it is treated as a finished turn and answered. Only the *off* state is written (`prefill-assistant = false`), and llama.cpp's preset reader turns it into `--no-prefill-assistant` (`common_preset::to_args` takes a bool option's negated form). Turn it off when a client legitimately ends on an assistant turn and the model resumes mid-sentence rather than replying.

### Keep past thinking, vs. a raw `preserve_thinking` kwarg

**Keep past thinking** (Chat / reasoning card) is `--reasoning-preserve` / `--no-reasoning-preserve`: replay the reasoning trace of *every* past assistant turn back to the model, not just the last one. It is a **tri-state**: `default` omits the flag and takes llama.cpp's own default, which is a third instruction, not the absence of one: it is **on** (the kwarg is written as `true` whenever the flag is absent, llama-server warns `it is enabled by default (may use more tokens, disable via --no-reasoning-preserve)` on every supporting template, and the `consider enabling it` line prints only when it is turned off explicitly). So `off` is the value that changes anything, and `on` merely pins the default. It is orthogonal to **Reasoning** (`--reasoning`, i.e. *whether the model thinks at all*): this one is about what happens to the thinking it already did.

It is also the **only** supported lever, and the reason it is a field of its own rather than something to hand-write into **Template kwargs** below it. llama.cpp turns this flag into the kwarg `preserve_reasoning`, and `caps_apply_preserve_reasoning` (`common/jinja/caps.cpp`) expands *that* into three template variables at once:

```
preserve_thinking = v      clear_thinking = !v      truncate_history_thinking = !v
```

because templates disagree on which name they read: Qwen3.6 and LFM2.5 read `preserve_thinking`, GLM-4.7 reads `clear_thinking`, Nemotron reads `truncate_history_thinking`. Setting one of those three by hand as a `chat-template-kwargs` entry therefore works only on the templates that happen to use that name, and is a **silent no-op** on the rest, and it skips the capability probe either way (a hand-written `preserve_reasoning` kwarg draws a DEPRECATED warning of its own). The flag sets all three and is checked, which is why the field writes it and not the kwarg.

Which template you are on is exactly what the **Past thinking** row of [Model info](#models-tab-presetsini) reports, by looking for those three names in the template source, and it is the one question llama-server's log cannot answer for you. Its probe renders the template and checks whether a past turn's trace came out, so it prints "supports preserving reasoning" both for a template you can *control* and for one that preserves **unconditionally**, which are opposite answers to "will this flag do anything". The row names the variable it found (`yes  ·  --reasoning-preserve (template reads clear_thinking)`) or says the flag is inert here (`no  ·  --reasoning-preserve is a no-op on this template`). In llama.cpp's bundled corpus only three templates gate on it at all: GLM-4.7 (`clear_thinking`), LFM2.5 (`preserve_thinking`) and Nemotron-3 (`truncate_history_thinking`).

Two things it does not promise. It only bites where the template actually gates on those variables: a template that emits history reasoning **unconditionally** (Ornith-1.0 does: no gate at all) already preserves it, and reads as "supported" to the probe purely because the trace shows up in the rendered output. And it is not free: the preserved trace is re-sent as prompt tokens every turn. What it buys, on a template that *does* gate (the Qwen3.6 form is `if preserve_thinking or loop.index0 > ns.last_query_index`), is a **stable prefix**: without it, an assistant turn is rendered *with* its thinking while it is the newest, then re-rendered *without* it as soon as the next user message arrives. That retroactive rewrite of an already-cached prefix is precisely what a KV cache cannot survive.

### Reasoning effort

`--reasoning-effort` hands the chat template a level: `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, with `default` omitting the flag. It is the same shape as [keep-past-thinking](#keep-past-thinking-vs-a-raw-preserve_thinking-kwarg) and carries the same warning with one variable fewer: `common/arg.cpp` stores it as `default_template_kwargs["reasoning_effort"]`, and `caps_apply_reasoning_effort` binds that one value to **two** template variables, `reasoning_effort` and `reasoning_strength`, because templates disagree on the name. Writing either one into **Template kwargs** by hand sets one of the two and is a silent no-op on a template keyed to the other.

What it is not: a switch, and not a budget. It tunes how the template asks for thinking, so on a template that names neither variable (most of them; gpt-oss and harmony are the ones that do) the value is simply never read. Two consequences worth knowing before you reach for it. llama-server prints **nothing** about this flag at startup, unlike the `supports preserving reasoning` line it prints for the neighbouring one, so the **Thinking** row of [Model info](#models-tab-presetsini) is the only place that tells you whether the level is a lever on this model.

Related: a client's OpenAI `reasoning_effort` request field reaches the template too. `none` disables reasoning for that request, and any other value is passed to the template as the level.

### Thinking budget, vs. the answer

Three fields at the bottom of the Chat / reasoning card split one output budget in two, and the asymmetry between them is the whole point: **llama.cpp can cap the thinking, and it can cap the total, but it has no cap for the answer alone.**

**Thinking budget** is `--reasoning-budget`, and it takes a real token count: `-1` unrestricted (llama.cpp's default, which the `default` checkbox omits the flag to get), `0` closes the block immediately, `N > 0` is a budget. It is **not** a truncation. At the limit `common_sampler_reasoning_budget_force` makes the sampler emit the template's own end-of-thinking sequence, so the model closes the block properly and writes a normal answer afterwards; the start and end tags come from the template, so the budget only arms where the template declares them.

**Budget message** is `--reasoning-budget-message`, injected immediately before that forced tag, which is the difference between a model that wraps up and one that stops mid-thought. It is free text reaching the model verbatim, so write it in the language the model is answering in: an injection in another language is an invitation to language mixing. It is also validated on save like every other free-text field, because a `;` or `#` would reload truncated.

**Max output** is `--n-predict`: thinking **and** answer together. So the answer's room is whatever the thinking leaves, `n_predict` minus the thinking actually spent, and if you want to guarantee the answer some space you set `n_predict = budget + the answer length you want`. It is a **default and never a clamp**: `server-context.cpp` reads `task.params.n_predict != -1 ? task.params.n_predict : params_base.n_predict`, so a client's own `max_tokens` wins in either direction and this only bites clients that send none.

One trap worth naming, because model cards invite it. A card that recommends "reasoning: maximum 262,144 tokens, final response: maximum 131,072" is describing ceilings **inside the extended context it assumes** (1M for Qwen3.8), not values to copy. Copied onto a smaller context they are worse than nothing: they sum to more output than the context holds, so the budget never fires, and the runaway generation you were trying to bound ends by filling the KV cache instead. What transfers is the *fraction* and the *ratio*: that pair is 37.5% of the context, split 2:1. Scale those to the context you actually run, and sanity-check the result in wall-clock rather than tokens, since at ~20 tok/s a 262,144-token thinking budget is over three hours.

### Benchmark tab

Measures one preset, or compares several. **The unit is the preset, not the model file**: two presets pointing at the same `.gguf` with different placement, KV types or drafters are a legitimate comparison, and usually the interesting one, so the tab lists presets and keys every result by preset id. The rules live in `src\bench.rs` (pure, unit-tested), the running in `src\bench\exec.rs`, the wiring in `src\gui\bench_tab.rs`.

#### Two engines, because one measurement cannot be both things

The **Engine** selector sits at the top for the same reason the GPU table's split-mode combo does: it decides what everything below it means, which half of the Workload card is live, and which llama-server state the run demands.

- **live** drives the RUNNING llama-server: one `/v1/chat/completions` per repetition with your prompt and a temperature override, reading `timings` off the response (`prompt_per_second`, `predicted_per_second`, `cache_n`, and `draft_n` / `draft_n_accepted` when the preset drafts). It is the only mode that measures what the framework actually ships: the preset's chat template, its MTP/DFlash drafter, its KV cache, its `--parallel`. Its numbers are production numbers.
- **synthetic** runs `llama-bench`, which **takes no prompt and no sampler settings at all**: `-p` is a token COUNT, not a text, and the tool never samples (`tools/llama-bench/README.md`: "the measurements with llama-bench do not include the times for tokenization and for sampling"). That is a *stronger* reproducibility guarantee than a fixed prompt at temperature 0, since the result cannot depend on what the model says. The price is that it cannot load the preset's drafter, so its `tg` reads roughly HALF of what the same preset does live with MTP on, and it ignores the mmproj, the chat template and every reasoning flag. The default sweep (prompt lengths 2048/8192/32768, depths 0/8192/32768, 128 generated) is inherited from the shell harness this tab replaced, so runs recorded before it stay comparable.

Whatever a mode cannot measure is printed under the selector and again in the saved report (`bench::caveats`), not left for the reader to remember.

#### The live prompt is a file, and the GUI only points at it

The Workload card's live half carries a **path**, not a text box: `config\bench-prompt-43k.txt` by default (settings.ini `BenchPromptFile` points it elsewhere), with **Browse…** to pick another and **Edit** to open the current one in the system's default text editor. Under the field sits what is on disk right now: `169289 chars, 169289 bytes, sha256 96d8fb…`, or the reason it cannot be read.

**Two prompts ship**, the two the `standard` spec pins, compiled into the binary and written to `config\` on first use: `bench-prompt-43k.txt` (169,289 characters, **43.7k tokens** on Qwen3.8, the default) and `bench-prompt-110k.txt` (404,098 characters, **110k tokens**, for settings whose cost grows with the context). A prompt no spec pins is not shipped: it measures nothing another machine can compare with, so it is a file of your own and a `custom` run. Neither is short because a benchmark ranks settings *in the regime it measured*, and a few hundred characters is a regime nobody works in: at 40k of context the same preset that benchmarks at 57 t/s serves at 24 to 40, and the ranking itself moves, since a verify pass costs more relative to a draft iteration at depth (`spec-draft-n-max` peaks at 5 near the start of a conversation and at 3 at 43k). They are seeded even though nothing points at them, so Browse… finds them next door instead of in the documentation. They are frozen snapshots of this repo's own docs and sources and must not be regenerated when those change: `assets\README.md` says why.

Four decisions, each of which was the alternative's defect.

- **One source for the GUI and the CLI.** `bench sweep` takes `--prompt-file`, because the prompt worth measuring is a long one (a decode rate at 40k of context is a different number from the same setting's at 2k) and that does not fit on a command line. A text box beside it would be a second prompt no flag can reach, so a scripted sweep and a run from the tab would measure different things without saying so. With no flag, the CLI now reads the same file the tab does.
- **The framework's prompt ships as a seed, not as an installed file.** A shipped prompt is written to its path the first time anything asks for it (`ensure_prompt_file`, which only ever creates, picks the text by file name, and never seeds a name of the user's). Installing it into `bin\` instead would put it under `$PROGRAMFILES64\llama.cpp`, where an editor could not save it without elevation and the next upgrade (which removes the old version's files and installs its own) would overwrite the edit.
- **Editing happens in your editor, not in a window here.** A Slint `TextEdit` is already sluggish at a few hundred KB (the View-logs window shows a list of rows rather than a `TextEdit` for exactly that reason), and the prompts worth keeping in a file are the long ones. **Edit** shells out to the default `.txt` handler, and the readout follows the file within one 5 s status tick, which is also what picks up an edit made in any other program.
- **The file is read at Run, never from a cache.** The tab caches one read for the readout and the preview, gated on `(path, mtime, len)` so a keystroke in another field does not re-read a megabyte; `on_bench_run` re-reads the file itself. A run that measured the previous version of the text would be wrong in the one way nothing downstream could detect, since the report's own digest would agree with itself.

`normalize_prompt` folds a leading UTF-8 BOM and CRLF away on read, because both are invisible differences that the tokenizer is not blind to: the same prompt saved by Notepad and by another editor must be the same prompt. The report's digest is of that normalized text and therefore does **not** match `Get-FileHash` on a CRLF file, which the report says out loud.

#### The preflights are opposite, and the synthetic one stops the server for you

live needs llama-server **up**: it measures that process, so a run with it down is refused rather than started. synthetic needs it **down**, because llama-server holds the whole model resident and benching alongside it does not fail cleanly: the second copy spills into shared memory over PCIe and the numbers read as a backend regression rather than as a mistake. The tab therefore **stops llama-server itself** before a synthetic run, through the canonical stop path (`gui::stop_server_async_with`), never through a bare `runstate::stop`: that path also writes the conversation snapshot when `SaveStateOnShutdown` is on, and it is what keeps the footer, the tray and the run-status generation counter in step, so the next periodic tick doesn't report the deliberate stop as "llama-server is no longer running", in red. It is **not** restarted afterwards; the closing status line says so.

#### Three separator traps between an INI value and a llama-bench flag

Every one of them is silent, and each turns one benchmark into several of a configuration the preset never runs in, because a comma in llama-bench means "benchmark these as SEPARATE configurations":

| key | INI | llama-bench |
|---|---|---|
| `device` | `ROCm0,CUDA0` | `-dev ROCm0/CUDA0` |
| `tensor-split` | `54,12` | `-ts 54/12` |
| `override-tensor` | `a=ROCm0,b=CUDA0` | `-ot a=ROCm0;b=CUDA0` |

The last one is two levels deep: llama-bench splits `-ot` on `,` into configuration groups **first**, and only then on `;` into rules (`llama-bench.cpp`). All three are pinned by a unit test.

The placement (`device`, `tensor-split`, `split-mode`, `override-tensor`) is the preset's own, as at launch. What is deliberately not mapped, because llama-bench has no equivalent: the drafter, the mmproj, `--ctx-size` (it sizes the context as prompt + generated + depth), `--parallel`, `--cache-ram`, and every chat / reasoning / sampling key.

#### The workload runs as two invocations, not one

`bench::synthetic_sweeps` splits it into a prefill sweep (`-p <lengths> -n 0`) and a decode sweep (`-p 0 -n <gen> -d <depths>`), because llama-bench runs the **cartesian product** of its test parameters and `-d` multiplies the pp tests as well as the tg ones: the default sweep in one call is 3 lengths x 3 depths + 3 depths = 12 tests, split it is 3 + 3 = 6, for the same information at half the wall clock. The **Preview** card shows both command lines per preset, built by the same code that runs them (`bench::synthetic_argv` + `runstate::render_command_line`), the same single-source rule as the Server tab's Command Line card.

#### The live mode warms up, and groups by preset

llama-server's router loads a model on demand, so the first request for a preset pays a model load of tens of seconds; a throwaway two-word request loads it without prefilling anything worth timing. Every measured request then asks for **`cache_prompt: false`**, which is load-bearing: without it the second repetition hits the prefix cache, reports a prompt rate of tens of thousands of tokens per second, and the mean it feeds is a fiction. `timings.cache_n` is read back anyway and surfaces as a note on the row, so a build that ignored the field would be caught rather than believed. The request is **streamed with `timings_per_token`**, and that is not about latency: llama-server then puts its cumulative timings (tokens, milliseconds, drafts) on every event, so the decode can be split at the reasoning/answer boundary using the server's own numbers, with no clock of ours involved. A reasoning model's output is two workloads, thinking that a drafter predicts poorly and an answer that restates it and drafts well (on Qwen3.8-27B + DFlash2 at 93.6k: ~22 t/s against ~40), so the single `decode` row is joined by **`decode (reasoning)`** and **`decode (answer)`**, each noting its mean length and acceptance; how much of the output each phase takes moves with the question, which is why a mean alone describes a regime nothing runs in. The jsonl sample line additionally carries the per-phase figures and a **trace**, the cumulative timings every 64 tokens, so the rate curve of any repetition is recoverable from the file rather than from a server log that rotates away. A model that does not reason gets neither phase row. The same split was requested server-side as ggml-org/llama.cpp#29372; once `timings` carries it, the stream is no longer needed. Repetitions of one preset run together rather than interleaved, because switching preset is another model load; the cost is that a card heating up over a long run charges the drift to the last preset, which the report says out loud.

#### Results: on screen and on disk, written as they land

The table fills as each test completes: `test | preset | t/s | sd | n | vs <baseline>`, plus a note column (the cache hit above; the drafter's acceptance on a decode row, reported *next to* the rate and never instead of it, since acceptance is not the metric). The baseline is the **first selected preset**, which is why the selection is an ordered list: checking appends, unchecking closes the gap, and the row's position number is shown.

#### What the report records besides the rates

Three blocks exist so that a comparison can be falsified rather than merely believed.

**The prompt's identity**, in the settings table: its path (or "given inline (`--prompt`)"), its size, and its **sha256**, with the text itself embedded up to 4096 characters. The prompt is a file anyone can edit between two runs, so only the digest makes "these two reports measured the same prompt" a checkable claim, and only the cap keeps a 100k-character prompt from turning a 4 KB report into a 400 KB one. The same three facts go into the jsonl header.

**Warnings, printed above the table** because a reader who stops at the numbers must already have seen them. Two are raised today. The first is a **flash-attention mismatch**: a preset that pins nothing runs at llama.cpp's `auto`, which resolves *per backend*, so a ROCm leg and a Vulkan leg of one comparison can land on different kernels with nothing in the rates to show it. The tab does not pin the value (pinning would benchmark a configuration the preset does not run, and the tab's premise is that it measures the one in use); it reads back what llama-bench resolved and says so when the legs disagree. The second is an **unknown device id**: `--list-devices` ids are not stable across driver states, so a preset can point at a card that is not there, and llama.cpp would then fail or quietly land elsewhere.

**An Environment table**, because two runs that disagree are only interpretable if you can tell whether the machine was the same machine. It records the boot time (with uptime), each display adapter's driver version and date, what each preset's device ids resolved to by NAME, and the resolved flash-attn per preset. The reason is specific: on 2026-08-24 a full day of measurements here was invalidated by Windows Update installing display drivers underneath them, and nothing in the numbers said so. The Windows Update event log is deliberately *not* scanned (see `bench\env.rs`): the pair (boot time, driver version) answers the same question when two reports are diffed, and recording facts beats recording an inference about them.

Every run goes into one SQLite file, `%LOCALAPPDATA%\llama.cpp\bench\bench.db`, **preset by preset**, not at the end: a benchmark is minutes of sustained GPU load, which is exactly when a driver reset or a bugcheck arrives, so each preset's run is committed as soon as the engine moves past it, and a run that dies at its third preset keeps the first two. llama-bench's own row is kept **verbatim** beside each repetition (the point keeps mean, spread and count, the row carries everything else it measured; the first version of this tab kept only the aggregate, which is how the resolved flash-attention of a finished comparison turned out to be unrecoverable), and so is the engine's output. **Saved runs** reloads any campaign, and **Open report** opens the markdown report stored with it. Cancel takes effect at the next repetition or test boundary; a request already in flight is not interrupted.

#### bench.db: every finished run, queryable

The file (`~/.local/share/llama.cpp/bench/bench.db` on Linux, or whatever settings.ini `BenchDb` names: a clone's `benchmarks/bench.db` records straight into the repo's database; the **Database** field at the top of Saved runs edits it, with Browse…, the list following the field as it is typed and settings.ini on Enter, Browse… or Run) has the same SQLite schema as the repo's `benchmarks\bench.db` (`benchmarks\schema.sql`, compiled in). A tab run is a **campaign** (`bench-<stamp>`) with one **run** per preset; a sweep is a campaign (`sweep-<stamp>`, or `--campaign`) with one run per value, labelled `key=value`. Each run stores the machine (CPU, RAM amount, type, speed and modules, the discrete GPUs with VRAM and driver, OS and kernel), the software (llama.cpp tag, build and commit, the framework version, the TheRock, CUDA and Vulkan SDK dist versions it was built against, the patches applied), the model file, the preset's whole section, `server.ini`'s `[Server]`, the environment llama-server gets, the plan, and one result row per request (live) or per llama-bench repetition (synthetic), with the phases, the rate trace and llama-bench's row verbatim in `detail`. A live run also gets one `run_device` row per backend its load names (plus the preset's pinned `device` ids): the model, cache (KV plus recurrent state) and compute buffers of the preset's latest load, read off `llama-server.log`, and the free memory a fresh `--list-devices` probe reports after the first measured prompt (`record::buffer_sizes` / `Recorder::read_memory`; host buffers such as `CPU_Mapped` or `ROCm_Host` carry no free figure). A synthetic run has none: llama-bench prints no load lines.

**Only finished runs are recorded.** A run is held in memory while its preset is measured and written in one transaction when the preset is done; a failed or cancelled run is dropped (its error message carries the engine's last lines instead), and a process that dies leaves nothing behind. A sweep's failed values are named in the campaign's notes instead. Credentials and service URLs are dropped and absolute paths cut to file names on the way in (in the engine's log, the notes and the report too: `db::public_text`, which also blanks the value after an `--api-key` or an `Authorization` header), because the file may be, or become, the public one:

```
llama-cpp-config bench query campaigns
llama-cpp-config bench query summary --model 27b --show ctx-size,cache-type-k
llama-cpp-config bench query runs --gpu r9700 --param no-host=true
llama-cpp-config bench query run 12          # everything about one run
llama-cpp-config bench query diff 11 12      # the parameters that differ
llama-cpp-config bench answer sweep-20261016-181500 "4 wins up to 40k, 3 beyond"
llama-cpp-config bench publish sweep-20261016-181500 --to benchmarks/bench.db
```

`--db <file>` points `query` at another database (the repo's); `publish` copies whole campaigns with everything their runs point at, the logs and the report included, and refuses one the target already has.

#### Sweeping one key, unattended: `bench sweep`

The tab measures a configuration. A sweep measures a *question* about one ("how far does raising `spec-draft-n-max` keep paying?"), by running the same engines once per value of one presets.ini key:

```powershell
llama-cpp-config bench sweep --preset Qwen3.8-27B-UD --key spec-draft-n-max --values 2..8
llama-cpp-config bench sweep --preset Qwen3.8-27B-UD --key device --values "Vulkan1,CUDA0;ROCm0,CUDA0" --apply best
llama-cpp-config bench sweep --preset Qwen3.8-27B-UD --key ubatch-size --values 256,384,512 --mode synthetic
```

It is a CLI command and not a button because of what a leg costs: a model load plus `reps` cold prefills, so seven values is half an hour during which nothing else may touch the machine. That is a thing to start from a terminal and walk away from. The sweep is one bench.db campaign and each leg a run of it labelled `key=value`, committed when the leg finishes, so a sweep killed at the fourth value leaves three finished runs that **Saved runs** shows side by side, not one truncated file; the cross-leg digest is printed and stored as the campaign's report. The one file it writes is `sweep-pending-<stamp>.json`, the value to restore, deleted once the key is back.

Five things it has to get right, each of which is a way the naive version would lie:

- **A live leg restarts llama-server**, because the key rides the *child's* launch args: the router hands a child the preset's keys when it spawns it and nothing re-reads presets.ini afterwards. The restart is deliberately the bare stop/start pair and not what `control restart` does, since that one saves and restores the conversation snapshot: gigabytes of IO per leg to reinstate a KV cache the benchmark then declines to use (`cache_prompt: false`). The synthetic engine wants the opposite state (server **down**) and needs no restart at all, llama-bench being a fresh process that reads presets.ini as it builds its argv.
- **`;` separates the values when a value contains a comma.** `device = Vulkan1,CUDA0` and `tensor-split = 60,6` are single values holding commas, so a comma-separated list could never sweep them; a `;` cannot appear in an INI value at all (llama-server's preset reader cuts a value at the first `;` or `#`), which makes it the one safe separator. `--values` splits on `;` when it sees one, on `,` otherwise, and expands `a..b` into the inclusive range. `unset` as a value removes the key for that leg.
- **The key is typed, not spliced.** `--key` resolves through `bench::sweep::SWEEPABLE` to the real preset field, so a typo is refused up front with the list of keys that work, and every value is parsed *before* the first leg runs. Writing an unknown key into the INI instead would have llama-server merely warn about it, and the leg would then measure the unchanged configuration and report it as a data point.
- **presets.ini is edited, and says so before it is.** The original value is written into the summary's first jsonl line before any leg starts, so a machine that reboots mid-sweep still has on disk the value to put back. At the end the preset is restored (`--apply original`, the default; `best` keeps the winner, `last` the final leg) and llama-server is left as the sweep found it: a running server is restarted onto the value presets.ini now names, rather than left running one the file no longer mentions.
- **A failed leg keeps its row.** "This value does not load" is a result; a table that dropped it would read as if the value had never been tried. The sweep continues through the remaining values and exits non-zero at the end, after the summary is written.

The summary ranks on `decode` (live) or the first `tg` row (synthetic), with the ratio measured against the *first* value, and carries the sweep's own caveats on top of the engine's: legs ran in order, so a card that heats up charges the drift to the last values, and two close values deserve a re-run with the order reversed.

#### Sweep at the depth you actually run at: `--prompt-file`

A sweep ranks settings **in the regime it measured**, and the default prompt is 230 characters, i.e. the shallow-context regime. Production is usually not that: on this machine a real agentic session sits at 40k tokens of context, where the same preset that benchmarks at 57 t/s serves at 24 to 40. Two things move between the two regimes and both are worth measuring rather than assuming. The obvious one is the absolute rate, since attention over 40k costs on every token. The one that decides whether a sweep's verdict transfers is the *ranking*: at depth a verify pass is far more expensive relative to a draft iteration, so the value of drafting more tokens per step goes up, and the optimum of a knob like `spec-draft-n-max` can sit somewhere else than it does at 2k.

`--prompt-file <path>` reads the prompt from a UTF-8 file (it conflicts with `--prompt`, since both set one field), which is the only practical way to hand a sweep tens of thousands of tokens. Such files ship and are written to `config\bench-prompt-43k.txt` and `config\bench-prompt-110k.txt` on first use, so the deep-regime sweep needs no preparation:

```powershell
llama-cpp-config bench sweep --preset Qwen3.8-27B-UD --key spec-draft-n-max --values 2..6 `
  --prompt-file "$env:LOCALAPPDATA\llama.cpp\config\bench-prompt-43k.txt" --max-tokens 512
```

With neither flag the sweep reads the **same file the Benchmark tab does** (settings.ini `BenchPromptFile`, default `config\bench-prompt-43k.txt`), so switching that file switches both front ends at once; `--prompt` is the one source that is not a file, and the report says so rather than printing an invented path. The file is read before anything restarts llama-server, so a missing or empty one fails immediately rather than after the first model load. Bear the cost in mind when sizing the run: every repetition asks for `cache_prompt: false`, so each one re-prefills the whole thing. With no `--max-tokens` the output is uncapped (below); pass a cap to fix the generation length, which removes one source of scatter, since a repetition's rate tracks the acceptance of *its own* content.

**Concurrent requests** (`bench sweep --concurrency`, or the Benchmark tab's Concurrency selector; live only): `single` (the default) sends one request per repetition; the other three send one request per slot of the preset at the same instant, one thread each, pinned with `id_slot`: N = the preset's `parallel` (absent = llama-server's auto 4), and N < 2 is refused before the first request. `prefill` sends N cold requests (`cache_prompt: false`): N prefills together, then N decodes. `decode` primes every slot with the prompt first (1 token out, cache on), so every repetition only decodes. `prefill+decode` primes all slots but the last: N-1 decode while the last prefills the whole prompt. Each reply is a `result` row of its own (`detail` names `slot`, `role` warm/cold, `sent_s`, `wall_s`). The points are the per-request means of what the scenario is about (`prefill` over the cold slots, `decode` over every slot but the cold one of `prefill+decode`) plus `prefill total` and `decode total` (`bench::concurrent_totals`: tokens over the shared window, from llama-server's own timings and each request's send offset). The leg's label ends in `concurrency=<scenario>`, so one campaign holds a value under several scenarios, and the scenario is the run's `bench` parameter `concurrency`. Without `--max-tokens` a sweep sets no output cap at all (the request carries no `max_tokens`; the model stops on its own, or at the preset's `n-predict`), so how long the model talks under a setting is part of the result; the tab sends its field's value, where 0 means the same no cap. A live request may take 900 s plus 0.1 s per allowed output token (100k tokens' worth with no cap), so a long reply is not cut by the clock. `--concurrency all` runs `single` and then, when the preset has two slots or more, the three concurrent scenarios, into one campaign; the tab's `all` does the same over its presets (the scenarios every selected preset supports), one step each (`exec::spawn_steps`), each result row prefixed with its scenario.

**Versioned specs** (`bench sweep --spec standard|<file>`, `bench\spec.rs`): the method of a measurement as an INI file (`standard` is the framework's, compiled in from `benchmarks\specs\standard.ini`), with `[Spec]` (`Name`, `Version`, `Prompts` as `<file>@<sha256 of its text>`, refused when a file no longer matches, `MaxTokens`) and one `[Pass.<name>]` per pass (`Temp`, `Reps`, `Concurrency` including `all`, `Override` as `;`-separated `key=value`). The sweep runs once per prompt, pass and scenario into one campaign; a pass's overrides are written to the preset before it and put back after it, each with a pending marker (`sweep::hold_key`) so an interrupted run is reported like an interrupted sweep. Only a published version of `standard` is a spec run. A flag beside it that it fixes (`--prompt`, `--prompt-file`, `--temp`, `--max-tokens`, `--concurrency`, `--reps`) replaces its value in every run, a swept key a pass overrides puts the leg's value over the pass's, and a file whose rules are no published version is a spec of your own: each of these records the runs as `spec = custom`, derived from the spec (`spec-derived-fields`: the fields, `override`, `spec-file`). The Benchmark tab runs one too: its **Campaign** card carries `--campaign`, `--question` and a **Spec** combo that offers only `custom` and the published versions of `standard` (`standard.versions`; a version other than the one compiled in is refused with the reason); with a version chosen the fields it replaces are greyed out. **Override** re-enables them: each field changed after the tick replaces the spec's value in every step, and the runs are recorded as `spec = custom` with `spec-derived-from` (`standard v1`), `spec-derived-sha256`, `spec-derived-fields` and `spec-pass` (`spec::Derive`). The preview lists the steps, and Run measures the selected presets once per prompt, pass and scenario (`spec::tab_steps`, run by `exec::spawn_steps`), writing a pass's overrides to every selected preset for its steps and restarting llama-server around them (the status tick does not report that restart as a crash while a benchmark runs). **Load…** opens a spec file and **Save as…** writes what the card describes as one (`spec::to_ini`: the chosen spec with Override's changes, or for `custom` one pass of the Workload fields, the ticked prompts pinned by digest, named after the file, `standard` and `custom` refused, Version 1); a file listed that way runs like a version but records `spec = custom`, derived from it (`spec-file`). The **Prompts** list holds the two shipped prompts plus any file added with **+ Browse…**: each ticked one is a step of its own, a spec ticks its own pins on selection, and a different set under Override is the `prompt` derivation; the first ticked one is saved as `BenchPromptFile`. **A/B key** and **Values** (the `SWEEPABLE` preset keys, `bench sweep --values` syntax, each value checked against every selected preset before Run) run every step once per value with the value written to the presets for it (`spec::ab_expand`); a key a pass overrides records the runs as derived (`override`). Every run records `spec`, `spec-version`, `spec-sha256` (of `spec::canonical`, the rules without comments or layout) and `spec-pass` as `bench` parameters; `benchmarks\specs\standard.versions` freezes each published version's digest, enforced by a test; a sweep without it records `spec = custom`. `benchmarks\README.md` describes version 1. **The GPU lock** (`bench\gpu_lock.rs`): every sweep and every Benchmark tab run holds an exclusive lock on `LLAMA_FW_GPU_LOCK` (default `bench\gpu.lock`) for its whole length, and on Linux waits until no process but llama-server has `/dev/kfd` or `/dev/nvidia*` open; the CLI waits, the tab refuses with the reason.

### Integrations tab

Two sections: **OpenCode** (status line + buttons) and **Claude Code** (env-variable snippet).

**OpenCode lists every enabled preset**, one model each: the on/off switch in the [Models tab](#models-tab-presetsini) is the whole selection. One switch decides both what llama-server serves and what OpenCode lists, so OpenCode can never be offered a model llama-server has no preset for. **Save** writes the provider section (Base URL and API Key read from server.ini) with that list, and is the only thing that ever *creates* it, so a machine that never set OpenCode up is never written to. From then on the list follows on its own (`integrations::follow_presets`): every preset switch, save, rename, delete, New…/Clone…, and every server.ini save rewrites it, from the GUI and the CLI alike, and a rebuild that comes out identical to the file is not written. **Open** launches Explorer on the folder containing `opencode.json` (`~/.config/opencode/`).

The status line says which of three states the file is in: no provider yet, in step with the enabled presets, or **out of step**, in which case it names the ids on each side (`enabled but not listed`, `listed but not enabled`). That last state is what a hand-edit or a failed write leaves behind; a refresh (F5) only reports it, and Save repairs it.

The **Claude Code** snippet includes the API key from server.ini when set (otherwise `not-needed`), and the compaction variables described below.

The one field that is not a straight copy is each model's **`limit.context`**, and it is not the preset's `ctx-size`. opencode fills a prompt up to whatever ceiling it is handed, so the number has to be the context **one request** can actually use, which llama.cpp derives from three things at once (`integrations::effective_ctx`):

1. **`ctx-size` absent means the model's TRAINED context**, not a fixed default: `n_ctx = 0` is llama.cpp's spelling of "load it from the model" (`common_params`; `llama-context.cpp` resolves `0` to `hparams.n_ctx_train`). A 256k model loads 256k.
2. **…but the context is split across slots**: `n_ctx_seq = n_ctx / n_parallel`. So `parallel = 2` halves what a single request may ask for; the same 256k model then serves 128k per request.
3. **…unless `parallel` is omitted.** llama-server defaults it to `-1` = auto, and auto picks 4 slots **and a unified KV cache** (`tools/server/server.cpp`), under which every slot sees the whole context.

A flat number would be right for one model at one `parallel` and wrong everywhere else. Note the trap in the "obvious" fix: publishing the trained context while a preset pins `parallel` would promise a context llama-server rejects. **Leaving `parallel` at `default` is what buys a model its full trained context per request**; pinning it is what quietly divides it.

**A model whose context llama.cpp's fit may cut gets no context window at all** (`integrations::fit_may_cut_ctx`). With `fit` on and the context automatic, the fit shrinks the context at load time until the model fits the free memory (`common/fit.cpp`, step 2), so any number published beforehand is only a ceiling. Exactly, a preset counts as autofit when all of these hold: the fit runs (`fit` not off in its section, nor in a `[*]` section; an ABSENT key is llama.cpp's default, on); `split-mode` is not `tensor` (the fit is skipped there); `ctx-size` is absent or `0`; `kv-unified-per-slot` does not size the pool first (with `ctx-size` absent it sets the context before the model loads); and the fit's floor is below the trained context: the floor is `fit-ctx`, else 4096, and an explicit `ctx-size = 0` without a `fit-ctx` asks for the full context and is never cut. Those models get:

- in `opencode.json`, an entry with **no `limit`** object (opencode requires `context` and `output` together when `limit` is present). opencode then caps a reply at its own 32000 tokens, never compacts ahead of time, and compacts when llama-server rejects a prompt as too long. A `limit` written earlier for the model goes with the next rewrite.
- in the **Claude Code** snippet, no context or compaction line: the example is the first enabled preset that has a context, and when none has, the snippet names the model only and says why. The loaded figure is the `n_ctx_slot` of the server log, to set by hand if wanted.

To give such a model a number, set its `ctx-size`, or turn its `fit` off.

**Both clients are told to compact 15% of that context plus 10,000 tokens short of it** (`COMPACT_RESERVE_PCT`, `COMPACT_RESERVE_TOKENS`: 49.3k free at 262k, 29.7k at 128k), so the summary and the turn that triggered it fit in what is left. On their own: opencode compacts at `limit.input` minus a fixed 20k buffer (`packages/opencode/src/session/overflow.ts`), only 7.6% of a 262k context, and Claude Code assumes a 200k window for a model id it does not know. So each opencode model's **`limit.input`** is `0.85 × context − 10000 + 20000`, never above `limit.context` (under ~67k the 20k buffer already exceeds the reserve), and the Claude Code snippet's example lines set `CLAUDE_CODE_MAX_CONTEXT_TOKENS` to that preset's context and `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` to the same point as a percentage, rounded down (81 at 262k).

## Control commands

The following subcommands control the llama-server process:

```powershell
llama-cpp-config control start      → start llama-server
llama-cpp-config control stop       → stop llama-server
llama-cpp-config control restart    → restart llama-server
llama-cpp-config control stop-and-close → stop llama-server and close the config GUI (Windows only)
```

The `stop-and-close` command is Windows-only and uses a named event to signal the running GUI instance to exit gracefully.

With **SaveStateOnShutdown** on, every stopping command snapshots the loaded models first and `start` restores the newest dump afterwards, so `restart` is the full round trip: it is what turns a restart on a long conversation from a multi-minute prefill into a disk read. Neither leg is ever fatal, in either direction: a snapshot that cannot be written must not block a stop the user asked for, and a server that started is started whether or not its cache came back. The restore first waits for the router to answer `/health` (it opens its port only after measuring the memory of its presets, which can take well over the few seconds a fixed look allowed) for up to `slot_state::LISTEN_TIMEOUT` (300 s, cut short if the server exits); the restore request itself then waits for the router to load the snapshot's model before it reaches the child. `stop` and `restart` wait for the old router and its children to exit (on Linux a child that held a large KV cache takes tens of seconds) for up to `runstate::STOP_GRACE` (120 s); one still running then fails the command, and `restart` does not start.

## Code conventions

- Zero Clippy warnings (checked manually).
- OS portability via `#[cfg(windows)]` / `#[cfg(not(windows))]` compile-time branching, no runtime OS detection.
- No external INI crate: `ini.rs` is a hand-rolled INI reader/writer with an explicit behavioral contract in its header (case/whitespace-tolerant section lookup, inline-comment stripping matching llama-server's own preset PEG, EOL detection, atomic writes).
- GUI callbacks are `Send + 'static` closures passed to `slint::ComponentHandle::global()`.
- Every property and callback the Rust side drives lives in the `AppState` global (`ui\state.slint`), declared once. Rust uses `app.global::<AppState>().set_x()/get_x()/on_x()`; the pages reference `AppState.x` directly. Adding a UI field that Rust reads/writes is a **one-file** change in `ui\state.slint`: no per-page re-declaration or forwarding. (The tray, `AppTray`, and the View-logs window, `LogWindow`, are separate roots and keep their own pushed-in state.)
- Editable widgets that back a scalar `AppState` field bind two-way (`<=>`), never one-way (`prop: AppState.x`): a one-way binding breaks the instant the user edits the field (Slint's "overwritten bindings" rule), leaving it stale on the next preset switch / Revert. The recognized one-way cases are:
  - **Read-only displays**: the `model_info_*` texts, the integration status field, the Server tab's Command Line `TextEdit`, the Claude-env snippet `LineEdit`.
  - **Per-row model widgets inside a `for`**: the preset list's on/off switch (`checked: p.enabled` + a `toggled` callback), the GPU table's row checkbox + weight field, the Server tab's "Bind to" checkboxes (`checked: row.checked`, rebuilt by `gui::populate_bind_options` on every toggle, since checking 0.0.0.0 clears and locks every other row), and the tensor-placement table's two row ComboBoxes + regex LineEdit. Safe ONLY because the sole in-place row write originates from the clicked/typed-into widget itself; any other change must rebuild the whole model so the delegates get fresh bindings (see `gui::refresh_preset_list`, which the switch's handler runs even when the move fails, `gui::refresh_gpu_rows`, `gui::refresh_tensor_rows`, which is also why neither a GPU weight edit nor a regex keystroke touches another row, and so needs no rebuild: rebuilding mid-keystroke would recreate the field and drop the caret).
  - **The `labels`/`values`/`index` ComboBox split**: see `MappedComboBox`.
  - **String-valued ComboBoxes**: a `current-value` two-way binding does NOT move the selection on a model change (Slint #11970), so `EnumComboBox` drives `current-index` instead, derived from the string `value` and pushed on change like the slider below (see `ui\components.slint`).
  - **Sliders**: the std `Slider` imperatively self-assigns `value` on every drag, so NO declarative binding on it survives. `AutoSlider` flows outward via `changed(v)` and pushes external updates back in via a `changed shown` hook (see `ui\components.slint`).
  - **`SegmentedControl`**, the reactive `RadioGroup`/`Switch` replacement for a picker over a non-bool model: reads `current` purely, reports clicks via `activated`. The draft on-GPU/on-CPU control uses it for exactly this reason.
- **Numeric fields are text, never a SpinBox.** Every number in both forms (integers included) rides as a **string** on `PresetForm`/`ServerForm` and is edited in a `DefaultLineEdit` (`input_type: InputType.number` for an integer, `decimal` where a `-` or a fraction must be typable), re-parsed on the Rust side with `ini::parse_int` / `parse_float`. This is not a style preference: Slint's `SpinBoxBase` puts a `TouchArea` over the whole widget whose `scroll-event` increments/decrements and **always returns `accept`**, with no `has-focus` guard, unlike its own `ComboBoxBase`, which rejects a scroll it is not focused for. So scrolling the page with the pointer merely *passing over* a SpinBox silently edits the preset, and eats the scroll, so the page does not even move. There is no property to disable it and no way to intercept the event from outside (the `TouchArea` lives *inside* the widget), so the only fix is not to use it; a `LineEdit` has no scroll handler at all. `binding_lint`'s `no_spinbox_widgets_anywhere` fails the build if one comes back. What a SpinBox would buy (refusing an out-of-range or non-integer value) lives in two places instead: `input-type: number` accepts ASCII digits only (i-slint-core's `accept_text_input`), so a `40.5` can't be typed into an int field, and the range checks are applied in the form conversions (`ini::parse_int_in`: e.g. a port outside 1–65535 reads as unset). Digits-only still lets through an empty field or a number past `i32` (a value typed next to the one already there: `196608245760`), and the conversions read both as unset, which is an instruction of its own (a preset with no `ctx-size` loads the model's TRAINED context). So every Save and Run asks first: `form::invalid_numbers` (Models), `server_form::invalid_numbers` (Server) and the Benchmark tab's own check (Repetitions, Max output tokens, Generate, and the Prompt lengths / Depths lists, which `bench sweep` checks too) refuse with a status line naming the field and the text, unless the field's "default" box is ticked. `form.rs`'s `every_integer_field_is_checked` holds the Models list to `PresetForm`. The GPU table's weight cell is the one integer left out on purpose: it applies as you type and the Share column shows the result at once, so there is no commit to refuse. Sliders keep their `int`s: `slider-base` has no scroll handler.
- **Wrapping text inside a component uses `WrapText`, not `Text`.** A word-wrapped `Text` sitting DIRECTLY in a page's `SectionCard` is fine: the layout asks for its height with no width constraint, and the item then measures itself at its own real `width`. Ask the same question **across a component boundary** and it is answered from that component's plain `layout_info_v`, which Slint 1.17 evaluates at the root's *preferred* width (`default_cross_axis_constraint`), i.e. the width the text would take on ONE unwrapped line. A value that wraps to three lines is then published as one, the card around it is sized two lines short, and the rows keep painting at their real height: in v1.11.2 the last "Model info" rows painted outside the card, over the heading of the card below. `WrapText` (in `ui\components.slint`) positions the text by hand at the width it really gets and republishes its own implicit height as the component's `height`, an explicit size the layout above reads as a fixed constraint. It is what `InfoRow`'s value, both tables' warning strips, the modal description and the ⓘ tooltip use. The same trick, spelled out inline, is what the Server tab's Command Line box uses (`mirror` in `ui\server_page.slint`).
- **Glyphs.** Text drawn with the default font may only use codepoints Segoe UI actually has: the allowlist is `RENDERABLE` in `src\tests\binding_lint.rs` (every entry checked against the font's cmap, not assumed), and a `.slint` string literal using anything else fails the build. Nothing falls back: a codepoint Segoe UI lacks draws as a correctly-laid-out **empty box**, which is how the tensor table's remove button first shipped reading `✕` (U+2715, Dingbats). Valid Slint, valid UTF-8, no warning; only a human looking at the window could catch it, which is what the lint replaces. An **icon** on a `Text` need not be an allowlist entry: it comes from the embedded icon font, Fluent UI System Icons (`ui\fonts\`, compiled into the binary by the `import` in `components.slint`, so Windows and Linux draw the same glyph; the "Segoe Fluent Icons" it replaced exists only on Windows 11 and drew empty boxes on Linux). Declare the codepoint in the `Icons` global and name the font at the call site, `text: Icons.info; font-family: Icons.font;`, as `LabeledField`'s hint glyph does (the scan skips `\u{…}` escapes to keep that path open). That escape is **not** available on a std `Button`: it has no `font-family` property, so its label is stuck with the default font and its glyph must be one Segoe UI covers (hence the tensor table's remove button reads `×`, U+00D7, and not an icon-font close glyph).

## Tests

Run it as a bare `cargo test` from anywhere in the repo: `xtask configure` generates a gitignored `.cargo\config.toml` at the repo root that caps **both** of cargo's thread pools, `[build] jobs` (rustc/codegen) and `[env] RUST_TEST_THREADS` (the libtest harness), at the same 3/4-of-logical-cores policy as `config-build.psd1`'s `BuildJobs`. Both default to *all* cores otherwise, and a `--jobs` flag would only cover the invocations `xtask build` makes. An explicit `RUST_TEST_THREADS` in the environment still wins (cargo does not force `[env]` over one already set), which is how you get a serial run to read an interleaved failure.

`cargo test` runs the per-module round-trip **unit** tests (INI / form / version: inline `#[cfg(test)] mod tests` in each file) plus the cross-cutting **end-to-end** tests under `src\tests\`. Unit tests stay next to the code they cover; e2e tests that span modules or need a built `AppWindow` live in `src\tests\` (an internal `#[cfg(test)]` module tree, so they reach `crate::…` directly, no lib/bin split needed; a top-level `tests\` dir would compile as a separate crate that can't see a binary crate's internals).

`src\tests\ui_bindings.rs` drives the real `AppWindow` on Slint's testing backend and asserts each editable-widget kind (LineEdit / CheckBox / the AutoSlider's Slider) still tracks a fresh model value after a simulated edit: the guard against the one-way-binding staleness class of bug. The `DefaultLineEdit` composite is exercised here via its inner widget (the `preset-ctx-size` and `server-port` integer fields, the `preset-temp` float) for the `value` leg; its `default`-checkbox leg is guarded statically by `binding_lint` (both call-site bindings, on every instance). It also pins the three Rust↔Slint mirrors that no compiler checks: `form::ALL_LAYERS` vs `Options.all_layers`, `server_form::LOG_LEVELS` vs `Options.log_levels`, and `server_cfg::LOAD_MODES` vs `Options.load_modes` (the last one twice as sharp: its entries reach `-lm` verbatim, so a drift either overwrites the user's choice with `auto` or hands llama-server a value it refuses to start on). It needs Slint element debug info, which `build.rs` emits only for non-release profiles, so run it with the default (debug) profile: `cargo test` works, `cargo test --release` cannot find the widgets. One phase there is not about bindings at all but about **geometry**: it gives the Model-info box a `Draft` value long enough to wrap and asserts the rows still end inside their card. Nothing else can see that bug (every string involved is correct; only the rows' position relative to the card gives it away), and it is what pins `WrapText`.

`src\tests\save_flow.rs` continues in the same window (the testing backend is a process-global, single-threaded platform, so all e2e phases share ui_bindings' single `#[test]`): it wires the real Models + Integrations tab callbacks via a test-only seam in `gui.rs` and exercises save → reload → reselect → re-baseline, Revert, delete's clear-selection, the rename and clone funnels, the discard-confirm guard on a dirty form (New…, and Rename…'s Rust-routed entry point), the New…-dialog's id de-conflict (a second New… on the same model must yield `<id>-2`, not overwrite), and the on/off switch: the section moves verbatim between the two files, an unsaved edit survives the switch and its Save stays in the parked file, the parked id is still taken for New… and Rename, the clicked switch follows a change made elsewhere (its broken one-way binding must be replaced by a list rebuild), and opencode.json follows the enabled set only once Save has created the provider, with a drifted file named by a refresh and never rewritten by one. It ends on the Hugging Face dialog, as far as it goes without a network (under `cfg(test)` the search and listing workers are not spawned; their answers land through test-only seams): the modal gate, the one field telling a search from a repository, a token that cannot be one refused in the dialog (for a search and a listing alike) and echoed nowhere, a search landing as rows, a row picked into a listing, Back to results, a failed listing falling back to the rows, a typed repository dropping them, then Download closing the modal and handing the job to the Downloads window (test-only seams in `gui\downloads.rs` land progress and transfer outcomes; no child is spawned): a second download of the same repository refused, progress, Quit asking while it runs, cancel, resume and failure on the card, and a finished download saving the derived preset and rescanning the pickers while a dirty editor keeps its preset, selection and edit, until the card's Show preset goes through the discard guard; a confirmed Quit waits for the cancelled transfer to land. Then deleting a preset with its files: the rows of a split model (one row, every shard), its mmproj and its drafter, none ticked, the mmproj a switched-off preset shares locked, Cancel dropping the ticks, a confirm removing the section, the ticked files and their emptied repository folders (never a folder with content, never the subfolders) and rescanning the pickers, a file that fails to delete reported as an error with the preset deleted all the same, and the CLI's `--delete-files` refusing a shared file (nothing deleted) until `--even-if-shared`. All config IO is redirected at a temp dir through the `LLAMA_CPP_CONFIG_DATA_ROOT` env var (see `paths::data_root`), so the flow never touches the user's real `%LOCALAPPDATA%\llama.cpp`, and because that env var is process-wide and never restored, unit tests elsewhere must never touch `paths::`.

Its last phase is about the **Benchmark** tab, whose selection is an ordered list of preset ids with the first entry as the baseline every ratio divides by: it pins that checking appends, that unchecking closes the gap (rather than leaving a hole or re-sorting), that the baseline follows position 1, that the preview names the preset it will request, that the caveat block follows the engine, and that an empty selection is refused by the shared validator instead of spawning a worker that would find out on its own. It then pins the prompt FILE, which only the redirect can reach because all three facts are about the tab meeting a real disk: that the file is seeded with the framework's own prompt, that the readout carries the digest of what is on disk, and that an edit made **out of process** (CRLF and a BOM included, exactly as Notepad would write it) reaches both the readout and the preview, hashing as its normalized self. That last one is the whole design: Edit hands the file to the system's text editor, so a tab that read the file once at startup would ignore every prompt change after it.

`src\tests\binding_lint.rs` is a plain text scan (its own `#[test]`, no Slint backend): it walks every `ui\*.slint` and fails on a one-way `prop: AppState.…` binding on a self-assigning widget property (LineEdit/TextEdit `text`, CheckBox/Switch `checked`, SpinBox/Slider `value`, ComboBox `current-*`, and the `DefaultLineEdit` composite's `value` + `default`), honoring the sanctioned escapes above (`<=>`, `read-only: true`, non-AppState expressions, custom components). ui_bindings proves each widget *kind* behaves; this catches the *new instance* someone wires one-way. The same file also carries two scans that are not about bindings at all, because only a text scan can enforce them: the glyph allowlist, and `no_spinbox_widgets_anywhere` (a SpinBox needs no binding to silently edit itself on a scroll; see the conventions above).
