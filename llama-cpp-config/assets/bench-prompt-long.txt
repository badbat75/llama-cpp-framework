# Project guide

## Project overview

Windows-only PowerShell scripts to install prerequisites, configure, build, and package [llama.cpp](https://github.com/ggerganov/llama.cpp) with CUDA, Vulkan, and ROCm (HIP) support, and NSIS installer packaging. Not compatible with Linux or macOS. llama.cpp's built-in chat interface (served by `llama-server`) is used as the frontend; no separate web UI is bundled.

A companion Rust binary (`llama-cpp-config`) provides a GUI + CLI configurator for `server.ini` and per-model `presets.ini`, replacing what were previously PowerShell config scripts.

## Structure

- `build\config-build.psd1`: build-time configuration (paths, GPU targets, compiler flags). Generated by `01-configure.ps1`; lives under `build\` (whole dir gitignored).
- `common.ps1` is the shared bootstrap: loads `$cfg` from `build\config-build.psd1`, adds ROCm to PATH (`HipPath\bin` plus, for the TheRock dist, `HipPath\lib\llvm\bin`; clang lives there, not in `bin` like the legacy HIP SDK), and is the **sole source** of the compile-time HIP vars (`HIP_DEVICE_LIB_PATH` → `lib\llvm\amdgcn\bitcode`, `HIP_PLATFORM`, `LLVM_PATH`), set per-process from `HipPath` (without `HIP_DEVICE_LIB_PATH` the HIP device compile dies with "cannot find ROCm device library"; TheRock's bitcode is not where clang's `--rocm-path` layout expects it). They must NEVER be set machine-wide: the Adrenalin driver's own HIP runtime (System32's `amdhip64_7.dll` + `amd_comgr_3.dll`) reads `LLVM_PATH` at runtime, and pointing it at TheRock's LLVM half-breaks it: `hipMemGetInfo` returns "invalid argument" (devices report 0 MiB) and every llama-server child dies with 0xC0000005 mid weight-upload (root-caused 2026-07-16; `00-install-prerequisites.ps1` self-heals poisoned machines). Exposes `Enable-VsDevShell` as a function. VS Dev Shell activation is **opt-in**: only build/package scripts call it. Dot-sourced by `02-build.ps1` and `03-package.ps1`.
- `00-install-prerequisites.ps1` is the idempotent toolchain bootstrapper: installs **and** updates the winget-tracked packages (PowerShell 7+ / OpenSSL / NSIS) in a single UAC-elevated session (`winget install` for missing, `winget upgrade` for present, plus the OpenSSL lib-symlink fixup), then `git fetch`es `$cfg.LlamaCppDir` when cloned and compares the checked-out tag against the newest **release** tag (`vX.Y.Z`) reachable from `origin/master`, by the same selection `02-build.ps1` makes (nightlies and pre-releases ignored; see that entry), or it would recommend a rebuild for a tag the build would never check out (no `git pull`: `02-build.ps1` keeps the clone on a detached tag, so a pull would always fail; the checkout onto the new tag is `02-build.ps1`'s job). **ROCm/HIP installs from AMD's TheRock dist tarball** (the classic HIP SDK installer is discontinued as of ROCm 7.14.0, 2026-07): the version is **pinned in `installer\dist-pins.psd1`**; bump it (and the `Dists` URL list) there deliberately and re-run to converge. The **multiarch** Windows tarball (rocBLAS/hipBLASLt kernels for every gfx family, so `HIP_PATH` serves whatever `GpuTargets` we build) is downloaded from the stable index (`stable.repo.amd.com/rocm/core/tarball/` from ROCm **10.0** on, `repo.amd.com/rocm/tarball-multi-arch/` for everything before it: see the pins) and extracted **into its own version directory** (`C:\TheRock\<version>`, the pins' `Root`) inside the same elevated session, which also sets the machine env: `HIP_PATH` **only**, naming the ACTIVE version; the compile-time vars (`HIP_DEVICE_LIB_PATH`, `HIP_PLATFORM`, `LLVM_PATH`) stay process-scoped in `common.ps1` because a machine-wide `LLVM_PATH` breaks the driver's HIP runtime (see `common.ps1` above), and the elevated leg deletes machine-wide copies left by earlier versions. Dists therefore sit **side by side**, which changes what "converge" costs: a version an earlier run already extracted is reached by moving `HIP_PATH` onto it, no download at all, and the pre-versioning single-directory layout (`C:\TheRock\build`, what every install through 1.11.3 wrote) is **renamed** into its version dir rather than re-fetched (same bytes, 4.6 GB cheaper). The price is disk, ~25 GB per dist: the report lists the inactive ones and never deletes them, since an inactive dist is a working rollback and 25 GB is the user's call. The same session appends `bin` + `lib\llvm\bin` to the machine PATH via the raw registry (`setx /M` truncates PATH at 1024 chars; `[Environment]::SetEnvironmentVariable` downgrades `REG_EXPAND_SZ` to `REG_SZ`) and **prunes every other `Root\*` entry out of it**, which is not tidiness: `amdhip64_*.dll` reachable from two PATH dirs is an ambiguous load order, the classic silent-crash cause the report warns about at the end. The installed version lives in a `.therock-version` marker written only after a successful extract (the env leg is gated on it, so a failed install never points `HIP_PATH` at a broken tree). A wipe + re-extract now only ever clears an **incomplete tree of the same version**, so llama-server has to be stopped for exactly two operations, both of which move ground under a loaded DLL: the rename of the legacy tree, and a re-extract over an existing version dir (the script checks and skips those, and installs a NEW version happily while it runs). The report also warns on a leftover legacy HIP SDK under `Program Files\AMD\ROCm`, a shadowing user-level `HIP_PATH`, any persistent-scope `LLVM_PATH`/`HIP_DEVICE_LIB_PATH`/`HIP_PLATFORM` (driver-runtime poison, see `common.ps1`), and `amdhip64_*.dll` in more than one PATH dir (ambiguous load order: the classic silent-crash cause). CUDA / Vulkan stay manual installs (probed, URLs printed). Reads `build\config-build.psd1` directly (does **not** dot-source `common.ps1`) so it works on a fresh machine before `01-configure.ps1` has run. End-of-run report shows before→after versions, plus rebuild recommendations: `02-build.ps1` / `03-package.ps1` when a newer llama.cpp release tag is available, preceded by `01-configure.ps1` when the ROCm dist changed (`HipPath` moves). It also **scans AMD's tarball indexes** (the pins' `Indexes`) for a stable newer than the `Pin`, and reports it with the `Dists` entry to paste: a report, never an install, for the same reason the llama.cpp check stops short of a `git checkout`. A dist bump can move the clang resource major (`patches\hip\<major>\` regenerated or `02-build.ps1` fails fast), re-derives `GpuTargets`, costs ~25 GB beside the dist in use, and can regress what the current one does right (10.0.0 did not fix the gfx1201 hipBLASLt bug 7.14.0 has), so which version the machines run stays one deliberate edit in one file. Best effort: an unreachable index leaves the row out rather than failing the run. Safe to re-run any time.
- `01-configure.ps1`: auto-detects paths, activates VS Dev Shell for tool discovery, verifies tools, creates `build\` if missing, writes `build\config-build.psd1` **and a generated `.cargo\config.toml`** (the same job count applied to cargo's two thread pools; see Key conventions). Accepts `-LlamaCppDir` param (defaults to `$PSScriptRoot\build\llama.cpp`). Writes GPU targets (**derived from the installed ROCm dist**, not hand-maintained; see Key conventions), build type (Release), compiler (the **full path** to the detected clang: TheRock's `lib\llvm\bin\clang.exe` when present; a bare `clang` in the config fails at cmake time in consoles whose PATH predates the machine-env change), **linker** (`lld-link.exe` from the same LLVM tree as that clang, blank when the compiler is not an LLVM one; see Key conventions), march flags (`-march=x86-64-v3`), and build jobs. `Find-ROCm` probes process then machine `HIP_PATH`, then legacy `Program Files\AMD\ROCm`; `Find-Tool` falls back to `HipPath\bin` and `HipPath\lib\llvm\bin`.
- `02-build.ps1`: dot-sources `common.ps1` + calls `Enable-VsDevShell`. Builds **both** llama.cpp (CMake configure + Ninja) **and** `llama-cpp-config` (cargo build --release). Auto-clones llama.cpp into `build\llama.cpp\` (or fetches if present) and **checks out its latest RELEASE tag** rather than tracking master HEAD, so the build is a clean tagged release and `git describe` yields e.g. `v0.2.0`, not `v0.2.0-11-g…`. Upstream tags two different things and the framework follows only one of them: every merge to master gets a lightweight `bNNNN` nightly, a release additionally gets an annotated `vX.Y.Z` on that same commit (semver adopted in b10398), and **the nightlies are ignored even when newer** (b10605 on master against v0.2.0 = b10566, 2026-08-24). That rules out `git describe --abbrev=0`, which answers with the NEAREST tag, i.e. the last nightly; the selection is instead the highest `^v\d+\.\d+\.\d+$` among `git tag --merged origin/master --sort=-v:refname` (`--merged` for reachability, `-v:refname` so v0.10.0 outranks v0.2.0, and the strict regex so a `v0.3.0-rc1` pre-release, which sorts above the release it precedes, is not mistaken for one). No release tag reachable = a hard failure, never a silent fall back to a nightly. Consequence: `LLAMA_BUILD_IS_DEV=OFF` is now unconditional (the checkout is always a release tag), so the server's own banner reads `0.2.0 · b10566` rather than `0.2.0-dev · …`. Builds CMake output into `build\llama.cpp-cmake\`; the Rust binary stays in cargo's `llama-cpp-config\target\release\` (no intermediate copy: `03-package.ps1` stages it from there). Uses sccache if available for the C++ build. For HIP it force-includes a checked-in patched `__clang_hip_runtime_wrapper.h` (a ROCm/MSVC `<cmath>` include-order workaround: MSVC 14.51's `_CLANG_BUILTIN2` constexpr overloads clash with the HIP device math declarations; first hit on ROCm 7.1, **re-verified still required 2026-07-16 with TheRock ROCm 7.14 / AMD clang 23**). The patched copy is a modified snapshot of the toolchain's own header, so it is **versioned per clang resource major** under `patches\hip\<major>\` and selected from the installed dist (`lib\llvm\lib\clang\<N>`, legacy `lib\clang\<N>`); a ROCm bump that changes the major **fails fast** with regeneration instructions: recipe and validation steps in `patches\hip\README.md`, never force-include a stale copy from a different clang. Also carries the **out-of-tree llama.cpp source patches** in `patches\llama.cpp\*.patch` (currently one: FastMTP `d2t` draft-vocab support for the qwen35 MTP loader): they are REVERTED before the fetch/checkout, because the clone is left patched and a tag bump touching a patched file would otherwise abort the checkout, then re-applied onto the fresh tag. Both legs probe with `git apply --check`, so a re-run is a no-op, and a patch that applies in NEITHER direction fails the build instead of being skipped: an out-of-tree change that silently stops applying ships a binary that behaves differently from the last one built, with nothing in the log saying so. Every patch there is **provisional by design**: when upstream lands the same support it stops applying and is meant to be DELETED, not rebased (per-patch provenance, sha256, blast radius and the log line that proves it is live: `patches\llama.cpp\README.md`). Wipes `build\llama.cpp-cmake\` automatically when `CMakeCache.txt` pins a different compiler path than the config (a ROCm dist move would otherwise poison the reconfigure). The **Vulkan SDK is resolved from the PARENT dir** (`Find-VulkanSdk`: the parent of process/machine `VULKAN_SDK`, then `C:\VulkanSDK` and the `Program Files` roots; highest `[version]` dir that actually has `Lib\vulkan-1.lib` + `Bin\glslc.exe`), because a LunarG upgrade installs a new versioned dir and deletes the old one, after which two things still point at the dead tree: `VULKAN_SDK` in any console opened before the upgrade (FindVulkan searches it first; ggml-vulkan also appends it to `CMAKE_PREFIX_PATH` for `find_package(SPIRV-Headers)`) and the `Vulkan_INCLUDE_DIR`/`Vulkan_LIBRARY`/`Vulkan_GLSLC_EXECUTABLE`/`Vulkan_GLSLANG_VALIDATOR_EXECUTABLE` cache entries, which CMake **reuses without checking the files still exist** (unlike a config-package `<pkg>_DIR`, re-searched when it vanishes). The resolved SDK is exported as `VULKAN_SDK` for the process and the four paths are passed as explicit `-D`s so they override the cache, deliberately not a build-dir wipe like the compiler check, which would cost a full CUDA + HIP rebuild to fix one backend. All under `.\build\` (gitignored).
- `03-package.ps1`: dot-sources `common.ps1` + calls `Enable-VsDevShell` (cmake --install needs the VS env). Stages from `build\llama.cpp-cmake\` + `llama-cpp-config\target\release\` into `build\staging\`, then builds NSIS installer to `.\dist\`. **Prunes llama.cpp's own `test*.exe`** right after `cmake --install` (24 harnesses, ~9.8 MB on v0.2.0: `test-backend-ops`, `test-tokenizer-0`, `test-chat-template` and friends), which cmake stages because it stages every executable carrying an `install()` rule (note that is a SUBSET of what gets built: the cmake bin dir holds 26, two of which are never installed, so count from the staging tree, not from the build). The size is the lesser reason; the real one is that the installer offers to put `bin\` on the **system PATH**, so shipping them would drop 26 generically-named `test-*` commands into every shell on the machine. Pruned in the staging tree rather than filtered in the `.nsi`, so what is staged is exactly what ships, which is also what the OpenSSL import scan below then reads. Also stages the **OpenSSL runtime DLLs** into `bin\` next to `llama-server.exe`: they are NORMAL imports of the server (`libcrypto-N-x64.dll`/`libssl-N-x64.dll`; without them the exe fails at load on a machine with no OpenSSL install), the ABI-versioned names are scanned from the staged binaries' import tables (plain ASCII in the PE, no tooling) rather than hard-coded, since the ABI number moves with the OpenSSL install the build linked against, and the DLLs are copied from `$cfg.OpenSSLDir\bin` (that same install; app dir wins the DLL search order so a system OpenSSL can't conflict). **Every** staged `.exe` and `.dll` is scanned, never a name pattern: llama.cpp **v0.2.0 split each tool into a thin launcher plus an impl DLL** (`llama-server.exe` is 9 KB and imports `llama-server-impl.dll`, 14.8 MB, which is where the OpenSSL imports moved, alongside a new `llama-common.dll` and per-tool `llama-cli-impl.dll`), and the old `llama-server*` scan survived that only by accident of the wildcard; one more rename, or the imports moving into another shared DLL, would have staged NOTHING and shipped a server that dies at load on any machine without OpenSSL. Only 6 DLLs sit in `OpenSSLDir\bin` and 4 of them are providers (`legacy`, `p_test`, `p_ossltest`, `p_minimal`), so copying `*.dll` wholesale is not the shortcut it looks like. Two implementation notes the scan cannot drop: it reads in 4 MB **chunks** with a 64-byte overlap (`ggml-hip.dll` alone is ~900 MB; `ReadAllBytes` + `ASCII.GetString` would cost ~2.8 GB of RAM for that one file), and it gates the regex behind an ordinal `IndexOf` (measured: 32.9 s against 0.9 s on `ggml-hip.dll`; whole tree 44 s against 2.6 s, same two names out of 99 binaries). Remaining runtime deps stay external on purpose: VC++ redist x64, and per-GPU: AMD Adrenalin driver + TheRock dist with `HIP_PATH` (rocBLAS/kpacks), NVIDIA driver + CUDA 13 cuBLAS (`cublas64_13`/`cublasLt64_13`, ~700 MB; documented, not bundled); cudart is linked statically, `vulkan-1.dll` ships with any GPU driver. What IS bundled for them is a helper: `installer\install-runtime-deps.ps1` + `dist-pins.psd1` are staged into `bin\`: self-elevating, PS 5.1-safe, idempotent; installs the missing pieces (VC++ redist ~19 MB; ROCm/TheRock ~4.3 GB for AMD, plus the dist's own `amdhip64_*.dll` copied next to `llama-server.exe`, which is what makes BF16/F16 run on RDNA4: see that script's entry; the official cuBLAS redist ~375 MB for NVIDIA, its two DLLs dropped next to `llama-server.exe`) and points at driver downloads it cannot perform. Component selection: the `-VcRedist`/`-Amd`/`-Nvidia` switches pick **exactly** those components (this is how the installer's three dependency checkboxes invoke it, each `-Unattended` + one switch); with no component switch, VC++ is always considered and the GPU legs are an interactive [A]MD/[N]VIDIA/[B]oth/[S]kip choice (detected GPUs only pre-fill the default), or follow detection under `-Unattended`/`-Report` (`-Report` = detection-only, no elevation). It stays in `bin\` for later re-runs. The package is named `llama-cpp-framework-v<frameworkVersion>-<llamaBuild>-<arch>-setup.exe`, e.g. `llama-cpp-framework-v1.11.2-v0.2.0-x64-setup.exe`: **frameworkVersion** = the `llama-cpp-config` crate version (parsed from `llama-cpp-config\Cargo.toml` `[package]`; the configurator and the framework are versioned together), **llamaBuild** = `git describe --tags` of `$cfg.LlamaCppDir`, which is the bundled **release tag** (e.g. `v0.2.0`), **arch** = `x64`/`arm64`. Two `vX.Y.Z` tokens in one name, and the order names them: framework first, llama.cpp second. No `--match` steers that describe: on a commit tagged both `b10566` and `v0.2.0` it prefers the ANNOTATED release tag over the lightweight nightly on its own. The `^v\d+\.\d+\.\d+$` check on the result therefore decides whether to trust it, not which tag to read: a describe that comes back `v0.2.0-11-g…` or empty means the checkout is not on a release (a hand-moved HEAD, an untagged tree), and the name falls back to a `b<rev-list --count>` build number, deliberately shaped unlike anything the happy path emits so a non-release package cannot pass for one.
- `installer\dist-pins.psd1` holds the pinned external distributions (ROCm/TheRock `Pin` + `Root` + tarball URLs + index URLs, NVIDIA cuBLAS redist URL + sha256, VC++ redist permalink): the **single source of truth** read by `00-install-prerequisites.ps1` on the build machine and by `installer\install-runtime-deps.ps1` on end-user machines (03-package stages the pair into the installer's `bin\`). Bump pins here only. `Dists` is an ordered candidate list, first REACHABLE wins, and it serves two readers with different needs: a machine already on a dist consults it only when the `Pin` is missing, and an unpublished pin then changes nothing (the report says "not published yet"), while a bare machine takes the first entry it can download. Hence the **previous stable stays listed below the pin**, as the fallback a fresh install lands on while the pinned version is still propagating, and prereleases are deliberately **not** listed: a pinned stable that is not out yet must install nothing, not an rc. The **host moved with ROCm 10.0** and a stale URL fails as a `403` that reads exactly like "not published yet": 10.0 stable and 10.1 nightlies live under `stable.repo.amd.com` / `rc.repo.amd.com` / `nightly.repo.amd.com` (all `/rocm/core/tarball/`), while everything up to 7.14 **and the 10.0.0 release candidates** stayed on the legacy `repo.amd.com/rocm/tarball-multi-arch/` (rcs on `rocm.prereleases.amd.com`). File names are unchanged, so a bump means choosing the index by version, not editing the number in the URL (source: ROCm/TheRock `RELEASES.md`). `Indexes` is the other half of that: the two listing pages `00-install-prerequisites.ps1` scans to **report** a stable newer than the `Pin` (never to install one, and never read by the end-user helper). Both are HTML carrying their listing as an inline JS `files` array, so the names are matched with a regex rather than parsed, and strictly (`\d+\.\d+\.\d+` immediately before the extension), or the `-tests-` builds sitting in the same listing and the nightlies, which are a version with a date glued on (`10.1.0a20260831`), come back as releases. Scanning both hosts and keeping the highest is also what retires the trap above: the URL arrives WITH the version, found rather than composed. Prerelease indexes stay out for the reason prereleases stay out of `Dists`.
- `installer\install-runtime-deps.ps1`: end-user runtime-deps helper (see `03-package.ps1` above for what it installs); PS 5.1-safe and ASCII-only on purpose (fresh Windows has no PS7; non-ASCII in 5.1 scripts needs a BOM). Its AMD leg does one thing the name does not suggest, and it is the one that makes BF16/F16 models run on RDNA4: after the dist is in place (freshly installed OR already there) it **copies the dist's own `amdhip64_*.dll` into `bin\`**, next to `llama-server.exe`. That is a load-order fix, not a bundled dependency. Windows resolves a static import from the exe's directory and then System32, **both before PATH**, and the Adrenalin driver keeps its own `amdhip64_7.dll` in System32, so without the copy every binary here runs the dist's `rocblas.dll` + `libhipblaslt.dll` against the DRIVER's HIP runtime and never the dist's, which is exactly the mix that aborts at the first prefill batch (see the hipBLASLt footgun below). Nothing else moves: `rocblas`, `hipblaslt`, `amd_comgr` and `rocm_kpack` keep resolving from `HIP_PATH\bin` over PATH, which the HIP backend already depends on, so the copy adds no new failure mode; deleting it reverts to the driver's runtime. Freshness is decided by **content** (size, then SHA256), never by the DLL's stamped version, and that is not paranoia: every dist here stamps the same `10.0.3581.0` into that file's VERSIONINFO (7.14.0, 7.15.0a20260728, 10.0.0 and 10.1.0a20260901 alike), and 10.0.0 and 7.15.0a20260728 are even the same 16,555,520 bytes while being different binaries, so a (size, version) check would call a stale copy current exactly when `HIP_PATH` moves between two such dists and leave the install running another version's runtime. One SHA256 of a ~17 MB file per run buys a `HIP_PATH` move that converges on a re-run. The copy is also reachable **on its own** as `-StageHipRuntime` (leg 2b): same staging, no download, no prompt, silent when there is no ROCm to copy from, and it is what the installer's hidden always-run section calls on every install and upgrade. That split is deliberate: leaving the copy inside the AMD leg alone hid a 17 MB fix behind a checkbox announcing a **4.3 GB download**, which is exactly the box a user who already has ROCm never ticks, i.e. the cure would have reached everyone except the people who need it. With both switches the stage-only leg stands down, since the AMD leg stages the runtime itself.
- `installer\llama-cpp-framework.nsi.template`: NSIS installer template with placeholders (`@VERSION@` = framework/configurator version, `@LLAMA_BUILD@` = the bundled llama.cpp **release tag**, e.g. `v0.2.0`, `@STAGING_DIR@`, `@OUTPUT_FILE@`) replaced by `03-package.ps1` into `build\llama-cpp.nsi` (transient, deleted after the build). The ARP DisplayName/installer title read "llama.cpp-framework v@VERSION@ (llama @LLAMA_BUILD@)", i.e. "llama.cpp-framework v1.11.2 (llama v0.2.0)"; DisplayVersion = framework version; the llama release is also written to `HKLM\Software\llama.cpp\LlamaBuild` (the placeholder and the registry value keep the `Build` name from when they carried a `bNNNN`: nothing reads either programmatically, and renaming the registry value would strand the installs that already wrote it). The welcome page doubles as the runtime-requirements notice (VC++ redist always; per-GPU: AMD Adrenalin + ROCm/TheRock for HIP, NVIDIA driver + CUDA 13 cuBLAS for CUDA; Vulkan needs nothing); backends with missing deps are skipped silently at runtime, so the installer is the one place the user is told. Six components: binaries (required), PATH addition (optional), Start Menu shortcut (optional), plus three dependency checkboxes: **base requirements** (VC++ runtime), **AMD ROCm runtime**, **NVIDIA cuBLAS runtime**, all unchecked by default, each running the bundled `install-runtime-deps.ps1` with `-Unattended` + its component switch in a visible console (`ExecWait`); the finish page points at the helper for later re-runs. A **seventh, hidden section** (`-StageHipRuntime`, the leading `-` in the name makes it invisible and always selected) runs the same helper one last time with `-Unattended -StageHipRuntime`, through `nsExec::ExecToLog` so it needs no console: on a machine that already has ROCm it copies the dist's ~17 MB HIP runtime next to `llama-server.exe`, which is what makes BF16/F16 models run on RDNA4. It is a section rather than a step inside **AMD ROCm runtime** precisely because that box announces a 4.3 GB download and so is never ticked by the machines that already have the dist; it downloads nothing, prompts nothing, and stays silent when there is no ROCm to copy from, and it runs LAST so an install that did tick the AMD box is staged from the dist it just installed. Installs `bin\` (llama.cpp binaries, plus `llama-cpp-config.exe`, `llama.ico` and the uninstaller side-by-side with `llama-server.exe`) and `lib\`, leaving **nothing at the install root**. The uninstaller is `bin\llama-cpp-uninstall.exe`, namespaced rather than a bare `uninstall.exe` because the optional PATH component puts `bin\` on the SYSTEM path. Two things that follow from the root staying empty, and one bug that came from it not being: the closing `RMDir "$INSTDIR"` is **non-recursive on purpose** (`$INSTDIR` is user-chosen, so `RMDir /r` would follow a careless choice down a shared folder or a drive root), which means anything left at the root is never removed AND keeps the directory alive, which is how a `llama-cpp-config.exe` from **2026-06-30** (the layout before the tree moved under `bin\`) survived every upgrade since, each uninstall having only ever cleaned `bin\` and `lib\`; the Uninstall section therefore carries an explicit list of legacy root files, and an entry may only be retired once no installed version can still have written it. And the uninstaller cannot delete itself on the UPGRADE path: `CheckPreviousInstall` runs it with `_?=$INSTDIR`, which suppresses the copy-to-`$TEMP` an NSIS uninstaller normally makes (that copy is what would let it vanish under itself, and suppressing it is what makes `ExecWait` able to wait), so the caller finishes the job after `ExecWait` returns and the image is unlocked, clearing both the new path and the legacy one. **No custom config page**: runtime configuration is handled entirely by `llama-cpp-config` post-install. Start Menu shortcut: "llama.cpp Config" → `llama-cpp-config.exe`.
- `llama-cpp-config\`: Rust GUI + CLI configurator for `server.ini` + per-model `presets.ini`; five tabs (**Server** → `server.ini`, **Models** → `presets.ini`, **Benchmark** → measure or compare presets, writing to `%LOCALAPPDATA%\llama.cpp\bench\` (its unattended half is the CLI's `bench sweep`, which runs the same engines once per value of ONE presets.ini key, leaves each leg's ordinary `bench-<stamp>` report behind plus a `sweep-<stamp>` digest, and puts the key back afterwards; a live leg RESTARTS llama-server, since the key rides the child's launch args, and `;` separates values because `device`/`tensor-split` values contain commas), **Integrations** → `opencode.json` model list + Claude Code snippet, **Settings** → the configurator's own preferences) plus llama-server run controls. This entry is only the **map**: the architecture, per-tab/per-card walkthrough, UI-binding conventions, source-layout table, and test topology all live in [llama-cpp-config\README.md](llama-cpp-config\README.md), and every module carries its own depth in a `//!` header comment; read those before diving in, not this file. Adding a preset field, a server field, or a UI property follows the checklists in **Common changes** below. Sixteen recurring footguns, each with a canonical write-up in the code:
  - **`--mlock` / `--no-mmap` are ONE enum now, and mixing them loses settings silently** (`server_cfg.rs` `load_mode`, `runstate.rs` `server_args`): llama.cpp folded `--mlock`/`--mmap`/`-dio` into `-lm`/`--load-mode` in **b10105** (PR #20834). The old flags still parse (with a `DEPRECATED` warning), but each now **overwrites the whole mode** instead of setting one bool of two, so they no longer compose: `--mlock --no-mmap` is last-one-wins (the mlock is dropped), and a lone `--mlock` selects `MLOCK`, which is mlock **without** mmap (`use_mmap` is true only for `mmap`/`mmap+mlock`/`auto`, see `llama-model-loader.cpp`; the mlock half is `mlock`/`mmap+mlock`, see `llama-model.cpp`). The framework shipped exactly that pair through v1.6.5, so its default silently ran with mmap off. Hence one dropdown, never two checkboxes, and an `-lm <mode>` always on the launch line. A pre-b10105 `server.ini` is migrated on read (`migrated_load_mode`): a deliberate `NoMmap = true` survives, the auto-written `Mlock = true` does not.
  - **GPU placement is a table, not two text fields** (`gpu_split.rs` + `GpuSplitTable`): `--tensor-split` is positional over the devices in `--device`, in that order, so neither means anything alone. A blank tensor-split over 2+ GPUs = split by *free VRAM*, not evenly. And the vector is **normalized**, so it is a ratio with far fewer distinct outcomes than a percentage suggests: llama.cpp cuts `n_layer_all + 1` positions, every block plus the **output layer** (`dev_output = get_layer_buft_list(n_layer_all)`), which on a 33-block model means 83/84/85% are one launch and two of every three edits do nothing. Hence `Layout`/`block_counts`: where a model is known (Models tab) the column is shown and edited in **blocks**, and because a vector summing to the positions assigns exactly itself, writing the counts back is the identity: no inverse invented, `29,5` *is* blocks 0-28 / 29-32+output. Two consequences: a count cannot be edited alone (the rows absorb from the back, which is also why the cell is a **`Slider`** committing once on `released`: applying mid-drag would rebuild the row being dragged; `SpinBox` stays banned for the stray-wheel reason but `slider-base.slint` handles no scroll event, and its only gap is that the *accessibility* set-value action raises `changed` without `released`), and the INI still stores the **ratio**: the count is a per-model view, re-derived every rebuild, so re-pointing a preset at another model rescales it instead of lying. The `--split-mode` combo sits ABOVE the table and the columns follow the EFFECTIVE mode (`gpu_split::effective_mode`, because a server-wide value rides the router's CLI and so shadows every preset's key, an explicit `layer` included): blocks exist only under `layer`; under `row` the table edits the raw ratio (the matrix bytes follow row fractions via the backend split buffer type; CUDA/ROCm only, Vulkan silently falls back to the layer cut, and the KV cache follows the layer cut regardless); under `none` the editors retire: llama.cpp drops every device but `devices[main_gpu]` before loading, so the head row reads 100%, the other checked rows read "unused", and the drag handle is the one control left. The combo's single "layer (default)" entry deliberately merges the old default/layer pair (same launch for a preset in every reachable configuration), and the flags-preview line under the table is GONE: it ignored the mode, so it read as stale truth. Corollary, and the reason a live preset combo could change NOTHING before v1.9.1: a server-wide `SplitMode = layer` is **dropped on read** (`server_cfg::server_split_mode`); llama.cpp already defaults to layer so it never changed the server's own launch, but the router merges its CLI args into every preset (`unset_reserved_args` does not prune `--split-mode`), so its only effect was to neuter each preset's mode. `none`/`row` survive: those change the launch, and overriding every preset with them is deliberate.
  - **"All layers offloaded" still leaves the embedding table in PINNED HOST RAM** (`tensor_override.rs` + `TensorOverrideTable`): llama.cpp parks `token_embd.weight` in a host buffer even at `offloaded N/N layers to GPU`, and with a GPU backend active that buffer is pinned (`ROCm_Host`/`CUDA_Host` in the log), which Windows reports as **Shared GPU memory**. So a model that fits in VRAM with room to spare still shows GBs of shared allocation. The cure is an `override-tensor` rule (`token_embd\.weight=ROCm0`); the value's grammar is split on `,` and at the first `=` *before* parsing and cannot be escaped, which is why it is a table and not a text field.
  - **…but that cure is CONDITIONAL, and violating either condition costs 10x** (`gguf.rs` `embd_line` / `embd_pin_warning`, surfaced as Model info → **Embeddings** + a warning strip on the table): the pin is **not model-agnostic**, which is the natural (and wrong) reading of the bullet above. (1) `token_embd`'s **own** quant must have a GPU `get_rows` kernel; ggml-cuda/ggml-hip whitelist `F32/F16/BF16/I32/Q1_0/Q4_0/Q4_1/Q5_0/Q5_1/Q8_0` and `default: return false` for **every K-quant and IQ-quant** (`ggml-cuda.cu`, `supports_op`). Pin a K-quant table and it sits in VRAM the GPU cannot read, so the lookup round-trips to the host *every token*: measured 25 → **2.8 tok/s** (Q4_K embd), → **1.9 tok/s** (Q5_K: bigger table, worse). Prefill is untouched (~400 tok/s: one round-trip per 2048-token batch amortizes it) and the GPU engines read **0%**, so it presents as an *idle* GPU, not a slow one. The file NAME does not tell you: Unsloth's `Q6_K_XL` keeps `token_embd` at **Q8_0** (safe) while its `Q4_K_XL`/`Q5_K_XL` drop it to Q4_K/Q5_K. Same model, same build, opposite outcome. (2) The card must have **room**: pinning MOVES the table from host RAM into VRAM (~1.26 GiB at Q8_0), a straight add that tips an already-full card into paging (Q6_K + f16 KV @ 256k ctx: 23 → **13.7 tok/s** *with* the pin). Because condition (1) is per-model, prefer the **per-preset** scope over the server-wide one. `gpu_has_get_rows` mirrors that upstream switch and must be re-checked when bumping llama.cpp: a type that gains a kernel and is missing here only costs a needless warning, but a type listed here *without* one green-lights the pin this exists to prevent.
  - **A server-wide `--override-tensor` REPLACES each preset's, it does not add to it** (`server_cfg.rs` `override_tensor`): the same table exists in both scopes, and `-ot` `push_back`s onto a vector inside llama.cpp, so "the two lists concatenate" is the natural guess and it is wrong. The router merges its own CLI args into every preset as a KEY→VALUE map (`common_preset::merge` → `options[opt] = val`, CLI as the writer), so exactly one `--override-tensor` reaches a child: the server's. Verified against b9976. Two consequences: the Models tab must say it is shadowed (`tensor_override_warning`), and the buffer type is validated by the ROUTER at startup; an unknown device in the server-wide value fails with `unknown buffer type` and **nothing starts**, where the same typo in a preset only kills that model.
  - **The image encoder ignores `--device`** (`server_cfg.rs` `mmproj_device`): `clip_ctx` takes the first GPU backend the registry offers unless `MTMD_BACKEND_DEVICE` names one, so on a mixed box it holds VRAM on the wrong card and computes only on image requests, which reads exactly like an idle GPU that has been "assigned something".
  - **Preserving past thinking is ONE flag, not a template kwarg** (`presets.rs` `reasoning_preserve` + the crate README): `--reasoning-preserve` sets the kwarg `preserve_reasoning`, which `caps_apply_preserve_reasoning` (`common/jinja/caps.cpp`) expands into THREE template variables at once (`preserve_thinking`, `clear_thinking`, `truncate_history_thinking`) because templates disagree on which they read (Qwen3.6/LFM2.5 the first, GLM-4.7 the second, Nemotron the third). Hand-writing one of them into `chat-template-kwargs` sets one of the three: it works on the templates using that name and is a **silent no-op** on the others, and it never registers with the capability probe, so llama-server still prints `consider enabling it via --reasoning-preserve`. Note "supported" only means the trace showed up in the probe's render: a template that preserves *unconditionally* (Ornith-1.0) reads as supported while gating on nothing.
  - **`--parallel` DIVIDES the context, and omitting it is not "1 slot"** (`integrations.rs` `effective_ctx`, surfaced as each opencode model's `limit.context`): the context one request may use is `n_ctx_seq = n_ctx / n_parallel` (`llama-context.cpp`), so `parallel = 2` halves it, **unless the key is absent**, because llama-server defaults `n_parallel` to `-1` = auto, and auto picks 4 slots *and a unified KV cache* (`tools/server/server.cpp`), under which every slot sees the whole `n_ctx`. Compounding it: `ctx-size` absent means the model's **trained** context (`n_ctx = 0` → `hparams.n_ctx_train`), not a fixed default. Both together are why opencode's advertised context is neither `ctx-size` nor the trained context, and why the naive fix is *worse* than the bug it replaces: publishing 256k for a 256k model that pins `parallel = 2` promises a context llama-server rejects at 128k+.
  - **Thinking support is read from the template's SOURCE, and the verdict is about the TEMPLATE** (`gguf.rs` `Thinking` / `thinking_line` / `past_thinking_line`, surfaced as Model info → **Thinking** + **Past thinking**): there is no Jinja engine here, while llama.cpp answers the same question by *rendering* the template (`caps_get`, `common_chat_templates_support_enable_thinking`). So the scan looks for the names the flags act on (`enable_thinking` for `--reasoning`, and `preserve_thinking`/`clear_thinking`/`truncate_history_thinking` for `--reasoning-preserve`), which makes a `yes` a fact and a `no` only "no marker this build knows about" (MiMo-VL's template names nothing yet the model thinks; llama-server parses `<think>` out of the *output* regardless). The **Past thinking** row is nonetheless the one thing llama-server's log CANNOT tell you: its probe prints `supports preserving reasoning` for a template that gates on the flag *and* for one that preserves unconditionally (Ornith-1.0), which are opposite answers to "will this flag do anything".
  - **The FOLDER a drafter sits in does not say which speculator it needs** (`gguf.rs` `draft_spec_type`, applied in `gui\models_tab.rs`'s `draft_picked` handler): the picker merges `mtps\` and `dflashs\` into one dropdown, and deriving `--spec-type` from that folder alone cannot separate the two DFlash flavours: `draft-dflash` and `draft-dspark` share the arch (`dflash`), the file-name shape and the folder, and are told apart only by a `markov_w1.weight` tensor INSIDE the file. Picking the wrong one of that pair does not fail; `is_dspark` changes the drafting batch itself (`n_draft` masked positions against `n_draft + 1`, an anchor-first layout, ceiling `block_size` rather than `block_size - 1`, `common/speculative.cpp`), so the drafts are read from the wrong positions and are simply rejected: speculation that costs and never pays. Hence the picked FILE's header decides, mirroring llama.cpp's own `common_speculative_types_from_gguf` (b10406, extended to MTP in b10428, which llama-server now runs itself when `--model-draft` arrives with no `--spec-type`). The framework still WRITES the key rather than leaving it to that auto-detect, both to show the verdict before launch and because the key works on older builds. The folder guess survives as the FALLBACK, and has to: a separate MTP head with no blocks of its own (gemma4-assistant, `block_count = 0`) matches no rule, upstream's included, and an unreadable GGUF is not evidence of anything either.
  - **Draft placement needs a draft FILE** (`presets.rs` field docs): llama.cpp reads `--device-draft` / `--n-gpu-layers-draft` only inside `if (has_dft())`. With MTP heads embedded in the main GGUF the draft context is built against the target model and runs on its device, ignoring both. With a SEPARATE MTP head file (gemma4-assistant, `n_layer=0`) they do apply, and there, pin model **and** draft to one device, or leave the draft on CPU: multi-device "auto" memory-fitting crashes those heads.
  - **BF16/F16 on gfx1201 dies inside hipBLASLt, and the fix is an env var no llama.cpp flag can reach** (`server_cfg.rs` `rocblas_use_hipblaslt` → `runstate.rs` `env_vars`, surfaced as Server → **SDK Tuning** → ROCm): on the R9700 under ROCm/TheRock 7.14, rocBLAS's default routing sends 16-bit GEMMs to **hipBLASLt**, and the **second** 16-bit GEMM in a process fails at kernel launch; f32 is immune, the same call sequence passes on Tensile, and a single visible GPU changes nothing (standalone repro: default and `ROCBLAS_USE_HIPBLASLT=1` fail; `=0` passes for batched/strided/plain × bf16/f16). llama-server aborts on the first prefill batch of any BF16/F16 model. The earlier reading, "hipBLASLt is not built for Windows, so this must be Tensile", was wrong: `libhipblaslt.dll` ships in the TheRock dist and is a static import of `rocblas.dll`. Forcing Tensile is a full-speed cure, not a degradation (pp512 **587** t/s / tg128 35 t/s on Ornith BF16, against ~19 t/s prefill for the older `GGML_CUDA_CUBLAS_COMPUTE_TYPE=f32` workaround). Two consequences for the code: it can only ride the **environment** (rocBLAS reads it below llama.cpp; hence the SDK Tuning card exists at all, and hence `env_vars` and not `server_args`), and it is a **tri-state** whose default is *unset*, because the bug is per-arch and hipBLASLt is the faster path where it works; `Some(false)` and `None` are opposite instructions, so a bool would hand every machine a workaround it never asked for. The value is parsed by rocBLAS as an int: export `"1"`/`"0"`, never `"true"`/`"false"`. Upstream: llama.cpp #25836, ROCm #6461, TheRock #7271. **The dist version was never the variable, the HIP RUNTIME is** (2026-09-01, and it retires "wait for a fixed tarball" as the plan): the driver's `amdhip64_7.dll` in System32 wins the load order over anything on PATH, so the dist's rocBLAS/hipBLASLt run against the DRIVER's runtime; put the dist's own runtime next to the exe and the same GEMMs pass on 7.14.0, 10.0.0 **and** nightly 10.1.0a20260901, with `=1` forced as well, i.e. hipBLASLt is healthy and it is the mix that fails (same-directory A/B with that one file as the variable; end-to-end `test-backend-ops test -o MUL_MAT -b ROCm0 -p "type_a=bf16"` goes from `ROCm error: invalid argument` to `5/5 backends passed` under default routing). `installer\install-runtime-deps.ps1` stages it on its AMD leg, so an install that has run that leg needs no knob here. Two things that follow: an upstream report of "fixed in nightly X" proves nothing unless it says which runtime the test loaded (7.14.0, the version originally reported, passes against its own), and the finding rests on ONE driver here (32.0.22042.14002), so the tri-state stays.
  - **The speculative widgets are DISABLED, not cleared, so a dead `spec-type` survives invisibly and kills the model** (`presets.rs` `prune_inactive_draft_keys`, applied to the form in `form.rs` `prune_inactive_draft_fields` and at the clone boundary in `gui\models_tab.rs`): all four speculative controls are `enabled: draft_active` (`state.slint`), i.e. greyed out (never blanked) when the model embeds no MTP heads and no draft file is picked. Any value that arrives from somewhere OTHER than those widgets therefore sits in the form unreadable and is written straight back out by `form_to_preset` on the next save. Two ordinary ways in, and the first writes to disk without ever passing through the form: **Clone** copies every field of its base onto a different model (`..base.clone()`), and re-pointing an existing preset at another model keeps the old one's keys. The result is not inert: `spec-type = draft-mtp` on a model without nextn layers makes llama-server build an MTP draft context against the target, `llama_init_from_model` returns nullptr (`context type MTP requested but model doesn't contain MTP layers`) and **the model fails to load at all**, with the GUI showing a greyed-out control as the only clue. Hence the prune runs at every boundary where the model becomes known (`update_model_info`, which also leaves the preset dirty so Save is reachable) or where a preset reaches disk without a form (clone, save). It is gated on having actually READ the GGUF: an unreadable header is not evidence a model has no MTP heads. Note the verdict is per-ARCH, not per-file: `muse-glimmer` carries no `nextn_predict_layers` key at all, while `src\models\<arch>.cpp` must also *read* that key for llama.cpp to honour it (only ~18 arches do), so a nextn-bearing GGUF on an arch that ignores it fails the same way.
  - **The one flag that can save a 17-minute prefill has NO env name, and that decides where it can be set** (`slot_state.rs` module header, emitted by `runstate.rs` `server_args`, surfaced as Server tab -> **Conversation snapshots**): reading a prompt is QUADRATIC in its length and the KV cache is process memory, so every restart re-reads the whole conversation. Measured on a 234k-token prompt (Qwen3.8-27B): `0.95 ms + 0.0287 ms per 1k of context` per token, i.e. 984 t/s at position 4k against 142 t/s at 218k, integrating to ~17 minutes, against ~8.3 GiB of sequential IO to reload the same state through `/slots/{id}?action=save|restore`. Those endpoints exist only under `--slot-save-path`, and the framework always launches the ROUTER, whose per-model children are separate processes: the natural conclusion is that a flag with no `.set_env(...)` (`common/arg.cpp` gives this one only `set_examples`) cannot reach them, and it is wrong. `get_map_key_opt` (`common/preset.cpp`) maps every option by its FLAG NAME with the dashes stripped as well as by its env name, so the router's own argv becomes `base_preset` (`load_from_args` -> `common_params_to_map`, which keys off `opt.args`), `preset.merge(base_preset)` copies it onto every model, and `unset_reserved_args` does not prune it. Same coin, other side: the key is therefore NOT writable as `LLAMA_ARG_*` anywhere. Two more traps in the same feature. The directory must EXIST before the launch, because llama.cpp validates it while PARSING the flag (`fs_is_directory` or it throws "not a directory"), so a missing folder does not degrade to "no snapshots", it stops the server from starting; hence `start()` creates it and the flag is emitted only when the toggle is on. And the restore is worth something only because `SERVER_TASK_TYPE_SLOT_RESTORE` also deserializes the saved token list into `slot->prompt.tokens`, which is what the next request's `get_common_prefix` compares against; without that half the dump would be a file nobody reads.
  - **`llama-bench` takes no prompt and no temperature, and a comma in its flags means "run these as SEPARATE benchmarks"** (`bench.rs` module header + `synthetic_argv` / `synthetic_sweeps`, surfaced as the Benchmark tab's **synthetic** engine): `-p` is a token COUNT, not a text, and the tool never samples (its own README: the measurements "do not include the times for tokenization and for sampling"), which is a *stronger* reproducibility guarantee than a fixed prompt at temp 0, not a weaker one, and is why the tab carries a second engine rather than one with the prompt field greyed out. The trap is the translation from an INI value: `device` and `tensor-split` are `,`-separated in `presets.ini` and `/`-separated for llama-bench, `override-tensor` is `,`-separated in the INI and `;`-separated there (llama-bench splits `-ot` on `,` into configuration GROUPS first, and only then on `;` into rules), so a preset's `54,12` silently becomes two benchmarks of one device each. Same shape one level up: llama-bench runs the CARTESIAN product of its test parameters and `-d` multiplies the pp tests as well as the tg ones, so the workload is split into a prefill and a decode invocation: 3 lengths x 3 depths + 3 depths = 12 tests in one call against 3 + 3 = 6 split, for the same information. What it cannot do at all is the preset's speculative drafter (so its `tg` reads roughly HALF the live rate with MTP on), the mmproj, the chat template, `--ctx-size` (it sizes the context as prompt + generated + depth) and `--parallel`; `bench::caveats` prints that list under the Run button and again in the saved report, because a benchmark that does not name what it left out is read as measuring everything.
  - **The two benchmark engines demand OPPOSITE llama-server states, and the live one must disable the prefix cache** (`bench\exec.rs` module header, `bench::live_body`): live measures the running server, so it needs it up; synthetic needs it DOWN, because llama-server holds the whole model resident and a second copy does not fail cleanly, it spills into shared memory over PCIe and reads as a backend regression rather than as a mistake, so the tab stops it first through `gui::stop_server_async_with` (never a bare `runstate::stop`: that path also writes the conversation snapshot when `SaveStateOnShutdown` is on, and keeps the footer, tray and run-status generation counter in step, or the next periodic tick reports the deliberate stop as "llama-server is no longer running", in red). On the live side the load-bearing field is `cache_prompt: false`: without it the SECOND repetition of the same prompt hits the prefix cache, reports a prompt rate of tens of thousands of tokens per second, and the mean it feeds is a fiction; `timings.cache_n` is read back anyway and surfaces as a row note, so a build that ignored the field is caught rather than believed. Results are appended to the run's jsonl as each one lands, not written at the end: a run is minutes of sustained GPU load, which is exactly when a TDR or a bugcheck arrives (one did during this feature's own testing), and results written only at the end are results lost on the first crash. Three things the report carries so a comparison can be FALSIFIED rather than believed, each one a measure the retired `tools\bench-backends.ps1` had: llama-bench's own row is kept **verbatim** in the jsonl beside the aggregated point (the point drops `flash_attn`, `n_batch`, `n_threads`, `backends`, `gpu_info`, and the first version of this feature kept only the aggregate, which is how the resolved flash-attention of a finished ROCm-versus-Vulkan comparison turned out to be unrecoverable); the resolved **flash-attn is read back** and a disagreement between the compared presets is a warning printed ABOVE the table, because a preset pinning nothing runs at `auto` and `auto` resolves per BACKEND, so two legs can silently land on different kernels (the tab does not PIN it: that would benchmark a configuration the preset does not run); and an **environment block** records the boot time and each display adapter's driver version plus what every device id resolved to by NAME, since the ids are not stable across driver states and since a Windows Update driver churn silently invalidated a full day of measurements on 2026-08-24. The one measure NOT carried over is INTERLEAVING the legs across passes, so a card that heats over a long run charges the drift to whichever preset ran last: re-run with the selection order reversed when a difference is small.
- `resources\llama.ico`: icon used by the NSIS installer and embedded in `llama-cpp-config.exe`. **Generated, not checked in** (gitignored): `resources\generate-llama-ico.mjs` rasterizes it from llama.cpp's webui logo (`tools\ui\src\lib\assets\logo.svg`, a `currentColor` SVG) as a `#111111` glyph on a white rounded tile, matching how upstream renders its own PWA/apple-touch icons (upstream commits no `.ico`; its `favicon.ico` comes from the webui npm build). `llama-cpp-config\build.rs` (and, belt-and-braces, `03-package.ps1`) runs the script automatically whenever the file is missing; it needs node+npm and the llama.cpp clone, so a fresh checkout needs `02-build.ps1` (which clones) before a bare `cargo build`/`cargo test` can succeed. Delete `llama.ico` to force a regeneration after an upstream logo change.
- `tools\report-memory.ps1`: diagnostic (not part of the build pipeline; reads only `%LOCALAPPDATA%\llama.cpp\`, so it runs on an installed machine with no repo or `config-build.psd1`). Slices the memory of the **currently running** llama-server across two sources and cross-checks them: llama-server's own load log (every buffer announces its size and device → the *requested* footprint, rebuilt exactly) and Windows' `GPU Process Memory` perf counters (what the driver *actually* handed out: dedicated VRAM vs shared system RAM). The divergence is the point: an oversubscribed device does not fail to allocate, WDDM silently pages the excess over PCIe and the only symptom is slow decoding. Each balance sheet folds tensor placement in as an **`of which tensor override`** sub-row under `model weights`, never a row of its own, and never summed: an `--override-tensor` rule *moves* a tensor into that device's model buffer, it allocates nothing extra, so it is already inside `model weights` and inside `requested`, and totalling it again would inflate the one figure the whole report exists to compare against `free at load`. The host section additionally names the pinned share of the model weights, which is the shared-GPU-memory number and the reason the tensor-placement table exists at all. `-Json` for machine output.

  Two sources for the placement leg, and neither is the obvious one. The **rules** come from the ROUTER's `spawning server instance with args:` block, not from `presets.ini`/`server.ini`: the router overlays its own CLI args onto every preset, so the files do not say what actually ran, and the spawn line is the already-merged winner. That block sits *outside* the load block (above the `device_info` banner), and it is matched to the child by the `[port]` prefix every child line carries, never by "the spawn header nearest above"; with several models up, that would pick the wrong one. The **hits** come from `tensor <name> (<n> MiB <type>) buffer type overridden to <buft>`, which is `LLAMA_LOG_DEBUG`, i.e. verbosity **5** (`common/log.h`: `LOG_LEVEL_DEBUG = 5`, printed when `verbosity <= thold`), so at the usual `-lv 4` it is absent and *no hits is not the same as nothing matched*; the report says which.

  Eight parsing traps, all handled, and the first one is **which block**: the report must describe the process running NOW, so the block is matched to a live listener by PORT (`Get-LivePorts`, against the `[58939]` prefix every child line carries; the log records no PIDs), never "the newest block in the file". Both the `device_info` banner and every `buffer size` line are TRACE (`COM_TRC` in `common/common.cpp`, i.e. `-lv >= 4`) while `server.ini` `LogVerbosity` may well be 3, at which point the running child writes NEITHER, the newest block belongs to some earlier chattier run, and the report prints that dead model's balance sheet against the live process' counters (hit 2026-08-18: a single-GPU Qwen3.8-27B reported as a two-GPU Ornith-35B, CUDA rows included, which is exactly the cross-check this tool exists to make). Two corollaries: an older block has to be cut at the next block's banner rather than run to EOF, or it absorbs the buffer lines of every child that started after it; and the failure path names the cause (live port plus its `-lv`) instead of asking whether llama-server is running. Then the parsing proper: llama.cpp **re-emits** `sched_reserve` for the draft context *after* the mmproj loads (so clip ownership must come from the `reserve_compute_meta` source line, never from a "seen the clip banner" latch) and **re-reserves** the compute graph once the slots come up (same buffer announced twice → collapse per `(owner, kind, device)`, do not sum). The log accounts for no driver context (a few hundred MiB per backend), so `requested` sitting just under `free at load` can still spill: the live counter decides, and in BOTH directions. Asking for more than the card reported free does not prove anything paged (WDDM can satisfy it in dedicated VRAM by trimming other processes, and `free at load` is a snapshot taken before the weights land), so the spill test is **shared memory beyond that backend's pinned `*_Host` buffers**, never the arithmetic alone and never raw shared. Two consequences the code spells out: an overflow the counter does not corroborate is reported as `AT THE LIMIT` (no headroom left) rather than as paging, because those are different instructions to the reader (seen 2026-08-18 at 85 MiB over: dedicated grew by exactly the requested amount, shared stayed flat at 124 MiB); and the same subtraction is what stops a 2 GiB host compute buffer, which Windows charts under the card, from reading as a 2 GiB spill on a device whose log fits. With `--fit on` the model is **loaded twice** (a `no_alloc` dry run to size the fit, then the real one) and every override line is emitted in both passes → collapse by tensor name or every rule double-counts. `CPU_Mapped` (the buffer holding mmap'd weights, i.e. the whole CPU-side model unless `--no-mmap`) is **host memory, not a device**: matching host on `^CPU$` (rather than `^CPU`) invents a phantom GPU called CPU_Mapped and charges the model to it. A **sliding-window model builds two KV caches** (`llama_kv_cache_iswa`: a full one for the global-attention layers, a small one for the SWA layers) and each announces itself with the *same* `llama_kv_cache: <dev> KV buffer size` line (same source, same device, same kind), so the de-duplication above silently eats one of them (Gemma-4-12B: 816 MiB kept, 255 MiB dropped, and a card that was 4 MiB from full read as comfortable); the cure is a latch on the `creating non-SWA / creating SWA KV cache` banner, which is safe here precisely where it was not for the clip graph, because llama.cpp prints it immediately before building each cache, in both passes. A **separate draft/MTP head prints its own `print_info` block after the model's**, so arch/params/file type/file size must take the FIRST occurrence; otherwise a gemma4 + gemma4-assistant pair reports the head's arch and its nonsense parameter count (`422.86 B params` for a 12B model). And the set of `buffer size` lines llama.cpp can print is exactly **model / KV / RS / compute / output / LoRA / DSV4 `<name>` state**: the regex must be exhaustive, because a kind it does not match does not come out small, it vanishes from the balance sheet altogether (LoRA adapters and DeepSeek-V4 state were doing exactly that).

  One asymmetry the report has to encode rather than infer: a rule ending in **`=CPU` does not mean ordinary RAM**. With a GPU backend up and mmap off, llama.cpp serves CPU-side weights out of that backend's *pinned* host buffer (`CUDA_Host`/`ROCm_Host`), which Windows charts under the card as **shared GPU memory**, so the VRAM is freed and the shared allocation is not. With mmap on, the same debug line is logged and the tensor is then served straight from the mapped file (`CPU_Mapped`, ordinary RAM), leaving the named pinned buffer at 0 MiB. Same log line, opposite outcome. Hence two rules in the code: the pinned verdict is gated on a pinned model buffer actually appearing in the `buffer size` lines, never on the override line alone; and an `of which` that comes out **larger than the row it hangs off** is not rounding, it is that contradiction; the sub-row is suppressed and the mismatch reported instead of printing `1,302 MiB of which` against a `0.00 MiB` row.


## Key conventions

- **No em-dashes anywhere in this repo.** Not in comments, doc comments, user-facing strings, the comment text written into `server.ini` / `presets.ini`, docs, or commit messages. Use `:` for an apposition or explanation, `;` between two independent clauses, `,` for an aside or trailing afterthought, or parentheses when a pair wrapped an aside. The one sanctioned exception is a `—` that is DATA rather than prose: the glyph the GPU table shows for a not-applicable cell (`gpu_split.rs`, `components.slint`), the assertions pinning it, and its entry in `binding_lint.rs`'s `RENDERABLE` whitelist.
- `common.ps1` is dot-sourced by `02-build.ps1` and `03-package.ps1`. Other scripts (`00-install-prerequisites.ps1`, `01-configure.ps1`) read `build\config-build.psd1` directly.
- `build\config-build.psd1` (build-time) uses single-quoted PowerShell-data-file syntax. Runtime config files (`server.ini`, `presets.ini`) are plain INI written as UTF-8 without BOM.
- All build artifacts (source clones, cmake binary dir, NSIS staging, sccache cache, `config-build.psd1`, generated `.nsi`) live under `.\build\` (gitignored). The two exceptions are cargo's `llama-cpp-config\target\` and the generated `.cargo\config.toml` (gitignored separately: cargo only discovers the latter by walking up from the cwd, so it cannot live under `build\`). The final installer goes to `.\dist\`. `rm -rf build\` wipes everything C++-side including the sccache (the next full build re-fills it from scratch) but leaves the Rust `target\` alone.
- The installer registers in `HKLM\Software\llama.cpp` (InstallDir) and supports upgrades (uninstalls previous version first). User runtime state lives under `%LOCALAPPDATA%\llama.cpp\`: `config\server.ini` (single `[Server]` section), `config\presets.ini` (per-model presets consumed by `llama-server --models-preset`), `logs\llama-server.log`, `bench\bench-<stamp>.{jsonl,md,log}` (one benchmark run each, written as it goes so a run killed by a driver reset keeps what it measured) and `bench\sweep-<stamp>.{jsonl,md}` (one `bench sweep` each, digesting the legs it ran; named `sweep-` so the tab's saved-runs list, which globs `bench-*.jsonl`, never tries to load one), and, only when `SaveStateOnShutdown` is on, `state\<model>.llamastate` (KV-cache snapshots, sized by the tokens the slot actually HOLDS rather than by `ctx-size`: 4.38 GiB measured at 127,579 tokens on Qwen3.8-27B, ~8.3 GiB for a full 262k context; the directory is overridable via `StateDir` precisely because the default sits on the system drive). The uninstaller asks (defaulting to No) whether to delete the whole tree, so it survives reinstall/upgrade by default.
- sccache is auto-detected; cache stored in `build\.sccache\`. Uses `SCCACHE_MAX_FRAME_LENGTH=104857600` for large GPU objects and `SCCACHE_CLIENT_SIDE=1` (sccache 0.17+ client-side mode: compile + cache lookup run in the client process, no per-compile daemon round-trip; older sccache ignores the var). nvcc is intentionally NOT wrapped with sccache: it mishandles multi-arch fatbin generation on CUDA 13.x (`fatbinary` fails with "Could not open input file '<tu>.compute_75.ptx'" on every `.cu.obj`). Retested with sccache 0.17.0 (2026-07-30): still broken, in server and client-side mode alike (minimal repro: any multi-gencode `nvcc -c`), so host C/CXX (clang) caching only.
- HIP GPU targets (`config-build.psd1` `GpuTargets` → `-DGPU_TARGETS`) are **derived programmatically by `01-configure.ps1`** (`Get-GpuTargets`), never hand-maintained: a ROCm dist bump only needs a re-run of `01-configure.ps1`. Derivation = enumeration + policy: the archs the installed dist ships Windows BLAS kernels for (`.kpack\blas_lib_gfx*.kpack` under `HIP_PATH`; legacy-SDK fallback `bin\rocblas\library\TensileLibrary_lazy_gfx*.dat`), **minus** CDNA/Vega `gfx9xx` (kpacks exist for MI cards but there is no Windows driver; TheRock also dropped gfx906/Radeon VII kernels: ROCm 7.1 was the last to serve it), **plus** the Ryzen iGPU safety set (`gfx1035/1036/1103/1152/1153`), unioned in even if a future dist drops their kernels: the driver-bundled HIP runtime (`amdhip64_7.dll`) fails kernel-module load on *every* visible device when one of them has no matching code object; a visible iGPU otherwise kills the dGPU with "device kernel image is invalid". A static 7.14.0 snapshot is used only when no dist is present at configure time. On TheRock 7.14.0 this yields 20 archs (RDNA1 `gfx1010-1012`, RDNA2 `gfx1030-1036`, RDNA3 `gfx1100-1103`, RDNA3.5 `gfx1150-1153`, RDNA4 `gfx1200/1201`), each costing ~56 MiB of `ggml-hip.dll` plus compile time; hand-prune the generated config only if size matters, and never prune the iGPU set. Related footgun: ROCm's `hip-config-amd.cmake` derives the `--offload-arch` flags from **`GPU_BUILD_TARGETS`**, which it seeds from `GPU_TARGETS` via `set(... CACHE ...)`, a no-op once cached, so editing `GpuTargets` silently does nothing on an existing `build\llama.cpp-cmake\`. `02-build.ps1` passes `-UGPU_BUILD_TARGETS` to clear it every configure.
- **A ROCm dist carries TWO kernel stores, and the framework's own recommended setting uses the one that looks legacy.** `.kpack\blas_lib_gfx*.kpack` (~41 MiB per arch) is **hipBLASLt**'s; `bin\rocblas\library\` (3,457 files, 693 MiB on TheRock 10.0.0) is **Tensile**'s, found by rocBLAS relative to `rocblas.dll`'s own directory. Which one is read is decided by `ROCBLAS_USE_HIPBLASLT`, and on gfx1201 the framework sets it to `off` (the hipBLASLt 16-bit GEMM bug, still unfixed in 10.0.0 and re-confirmed at runtime 2026-08-31), i.e. the configuration this project recommends runs **entirely out of `bin\rocblas\library`**. So the bullet above reads `.kpack` only to ENUMERATE the archs a dist ships, which is a different question from where the kernels come from at run time; do not infer from it that the kpacks are what gets loaded. Consequence for anyone trimming the ~13.6 GiB a dist costs: deleting `bin\rocblas` breaks the recommended configuration, and the failure is LATE and unlike a missing DLL, since the backend loads and the device enumerates normally, then the first matrix multiply dies with `Could not initialize Tensile host`. Within `bin\rocblas\library` the split is 351 MiB for the 20 RDNA archs the build targets against 343 MiB for `gfx908`/`gfx90a`, which it never builds (302 MiB of that is gfx90a alone), so the CDNA half is the safe thing to delete and the only one worth deleting.
- **lld links both halves of the build, by two different mechanisms.** *C++*: `01-configure.ps1` looks for `lld-link.exe` **next to the clang it resolved** and writes it as `config-build.psd1` `Linker`; `02-build.ps1` passes it as `-DCMAKE_LINKER` when non-empty. The condition is "we are building with an LLVM suite that ships lld", so a bare-name `clang` fallback or an MSVC `cl.exe` toolchain leaves it blank and CMake keeps `link.exe`; blank is a supported state, and the key is absent altogether from a config written before it existed (hence the truthiness check, not a `Test-Path`). CMake already picks `lld-link` unaided when clang comes from a full LLVM tree, so this mostly *pins* what happens anyway; what it buys is that the fallback to `link.exe` can no longer happen silently. *Rust*: unconditional, via the generated `.cargo\config.toml` (`[target.x86_64-pc-windows-msvc] linker = "rust-lld.exe"`). The bare name is deliberate: `rust-lld` ships **inside** the toolchain (`<sysroot>\lib\rustlib\<target>\bin`, not on PATH) and rustc resolves it from there, so it is always present and always version-matched to rustc, where naming an external `lld-link.exe` would borrow whatever LLVM happens to be installed (here AMD's LLD 23 from TheRock) and break on a machine without it. MSVC `link.exe` remains rustc's default on `x86_64-pc-windows-msvc`; only `x86_64-unknown-linux-gnu` switched to `rust-lld`. Neither toolchain announces its linker, so to tell which one produced a binary, look for the **Rich header** that MSVC's `link.exe` stamps into the PE's DOS stub and lld does not.
  - The Rust half carries `rustflags = ["-Clink-arg=/force:multiple"]`, and it is **load-bearing, not a leftover**: Skia links ICU *statically* (`skunicode_icu.lib`) while the `windows` crate imports the *system* one (`icuuc.dll`), so every `uloc_*` is defined twice. `link.exe` has always swallowed that (LNK4006, second definition ignored); the flag only makes lld behave the same for this one collision. It bites **only the test binary**: the second ICU arrives via `i-slint-backend-testing`, a dev-dependency (→ `i-slint-common` → `fontique` → `windows`), so `cargo build` links with no duplicates and the flag is inert there, while without it `cargo test` does not link at all. The knowingly-accepted cost: rustflags are not per-profile, so a real duplicate symbol in the shipped binary would be accepted rather than caught. Re-test and drop it if the two ICUs ever stop colliding.
- Build parallelism (`config-build.psd1` `BuildJobs`, written by `01-configure.ps1`) defaults to **3/4 of logical cores, clamped to at most `cores - 1`** (for both the CMake/Ninja `-j` and the `cargo build --jobs` legs), so at least one core stays free for interactive use during a long CUDA/HIP compile; at this ratio the clamp never binds, and it is kept anyway so the reservation is a property of the formula rather than a side effect of the ratio, surviving a later retune. A 1-core machine is the single case that cannot honour it (it gets 1 job, since 0 would build nothing). `BuildJobs = 0` means "use all cores". Note `-j` bounds concurrent COMPILE PROCESSES, not CPU: no affinity is set, and nvcc (forking `cicc`/`ptxas` per arch) plus the threaded lld links can still push past that share. The same number is also written as a generated, gitignored **`.cargo\config.toml`** at the repo root, because a `--jobs` flag only reaches the invocations `02-build.ps1` owns; a bare `cargo build`/`cargo test` typed by hand or fired by an IDE would otherwise take every core. It caps **both** of cargo's pools, which default to all cores independently: `[build] jobs` for rustc/codegen and `[env] RUST_TEST_THREADS` for the libtest harness (verified: cargo exports `[env]` to build scripts, rustc, `cargo run` and `cargo test` binaries, and does not force it over a value already in the environment, so `RUST_TEST_THREADS=1 cargo test` still wins for a serial debugging run).
- `llama-cpp-config` has zero Clippy warnings; uses `#[cfg]` compile-time branching for OS portability in `paths.rs`, `gui.rs`, `runstate.rs`, `main.rs`, `gguf\ffi.rs`, and `proc.rs` (the shared `CREATE_NO_WINDOW` process launcher used by `devices.rs` / `server_version.rs` / `runstate.rs`); `single_instance.rs` is Windows-only wholesale.

## Common changes in `llama-cpp-config`

The two recurring recipes live as authoritative checklists at the top of the module they start in; follow those, not a from-memory list:

- **Adding a per-model preset field** fans out to 7 places (kebab-case INI key ↔ snake_case Rust field; INI schema → form struct → widget → conversions). Checklist: top of `llama-cpp-config\src\presets.rs`. Trace an existing field like `ctx-size` as the template.
- **Adding a server (server.ini) field** is the same shape plus **three spots in `cli.rs`** (the server has a per-field `set`; the preset CLI is list/show/delete only) plus **`runstate::server_args`** (the launch/Command-Line leg). Checklist: top of `llama-cpp-config\src\server_cfg.rs`.

Cross-cutting rules the recipes rely on:

- **Before adding a new property, field, or function, search the codebase for existing ones that already cover the case.** `base_url_default` on `ServerForm` already tracked whether the Base URL was user-specified; I added a redundant `chat_url_specified` on `AppState` instead. Always grep first, then decide if something genuinely new is needed.
- **Model Info rows show facts, not explanations.** `moe_offload_line` used to append "saves VRAM (slower)"; `thinking_line` / `past_thinking_line` appended `--reasoning on|off switches it (enable_thinking)` after "yes". The doc comments (`///`) explain the why; the displayed value is just the fact. Keep them separate.
- **`open_chat_url` prefers Base URL custom over launch URL.** `state.slint` derives it from `chat_url` when `server_form.base_url_default` is false (user specified a custom Base URL), otherwise from `launched_url` (the URL the running server was started with), falling back to `chat_url` as the last default. The form's `base_url_default` field is the single source of truth: no duplicate property needed.
- **Model info names only files the preset LOADS.** `draft_line()` reports the model's own MTP heads plus the preset's `--model-draft` ("draft file: x.gguf", whose header is the "Draft file" row below), and "none" when there is neither, never a blank. Until v1.11.3 it also advertised the drafter whose filename best matched the model in `mtps\` / `dflashs\` (the deleted `ExternalDraft` / `external_drafters` / `family_tokens` / `token_overlap`), and a box that otherwise reports the running config was read as claiming that drafter was in use: the row was identical whether one was picked or not, and identical again after a restart (reported twice against v1.11.2). The match was a token overlap, so `Qwen3.8-27B-UD` was offered the head built for `Qwen3.8-27B-Uncensored-…` on `qwen3` + `27b` alone, a drafter for a different fine-tune that llama.cpp loads and then rejects nearly every token of. Choosing a drafter belongs to the Assets picker, which lists every one on disk; do not reintroduce a "best match" line here.
- Editable widgets bind **two-way** (`<=>`) to `AppState.…`; a one-way binding goes stale after the first edit. The sanctioned one-way exceptions (read-only displays, `for`-row widgets, `MappedComboBox`, the Slider/AutoSlider push, `SegmentedControl`) are catalogued in the crate README's conventions section.
- Nearly every step is guarded by a test that fails when skipped: INI and form round-trips (`presets.rs` / `form.rs`; `server_cfg.rs` / `server_form.rs`), the CLI leg's exhaustive-struct tests (`cli.rs`), the launch-arg leg (`runstate.rs`), widget-binding staleness (`src\tests\ui_bindings.rs`: one widget PER KIND, plus the one-way-binding text lint `src\tests\binding_lint.rs`) and the Models/Integrations callback funnel (`src\tests\save_flow.rs`). The unguarded remainder (nothing fails for either): forgetting the widget entirely (the field just never appears in the UI), and skipping the path-field `validate_for_save` step (a `;`/`#` path then saves fine and reloads truncated; see the checklists' final step).
- Run the e2e tests with `cargo test` (debug profile), **not** `--release`: they need Slint element debug info that `build.rs` emits for non-release builds only. Bare `cargo test` is the right command: the generated `.cargo\config.toml` already caps both thread pools at `BuildJobs` (see Key conventions), so no `--jobs`/`--test-threads` flags are needed. Full test-topology rationale (single shared `#[test]`, `LLAMA_CPP_CONFIG_DATA_ROOT` redirect, `src\tests\` vs `tests\`): crate README "Tests" section.

## Release process

1. **Bump version** in `llama-cpp-config\Cargo.toml` (`[package] version = "X.Y.Z"`). The next build also refreshes the crate's line in `Cargo.lock`: both files belong to the release commit.
2. **Run `02-build.ps1`**: builds llama.cpp (fetches and checks out the latest `vX.Y.Z` **release** tag; the `bNNNN` nightlies are not candidates) and llama-cpp-config.
3. **Run `03-package.ps1`**: stages binaries, builds NSIS installer to `.\dist\llama-cpp-framework-vX.Y.Z-vA.B.C-x64-setup.exe` (framework version first, bundled llama.cpp release second).
4. **Commit** all changes. Subject: **`Release vX.Y.Z: <summary>`**, the SAME first line as the tag (step 5); every release commit follows this (`git log --oneline`: a `feat:`/`docs:`-style subject is not the convention here). Body: a prose summary, closing with a **`Bundles llama.cpp <tag> (up from <previous tag>).`** line, both being release tags now: `Bundles llama.cpp v0.2.0 (up from v0.1.2).`. Releases through 1.11.1 bundled a `bNNNN` nightly, so the first one after the switch reads `up from b10524`.
5. **Tag**: `git tag -a X.Y.Z -m "Release vX.Y.Z: <short summary>..." && git push origin X.Y.Z`
   - Tag name: **no `v` prefix** (e.g. `1.5.1`, not `v1.5.1`).
   - Tag message: starts with `Release vX.Y.Z: <summary>` on first line, then blank line, then bullet points of changes. Match the style of previous tags (`git show 1.5.0`).
6. **Create release**: `gh release create X.Y.Z --title "vX.Y.Z (llama.cpp vA.B.C)" --notes "<markdown body>"`
   - Title format: **`vX.Y.Z (llama.cpp vA.B.C)`** (with `v` prefix, includes the bundled llama.cpp release).
   - Body: detailed markdown with sections (`##`, `###`), bullet points, code formatting. Match the style of previous releases (`gh release view 1.5.0`). End with test count and bundled llama.cpp release.
7. **Attach installer**: `gh release upload X.Y.Z dist\llama-cpp-framework-vX.Y.Z-vA.B.C-x64-setup.exe`

**Formatting conventions** (verified against 1.5.0; the llama.cpp token switched from `bNNNN` to `vA.B.C` after 1.11.1, so examples older than that show the previous shape):

| Artifact | Format | Example |
|---|---|---|
| Commit subject | `Release vX.Y.Z: <summary>` (matches the tag) | `Release v1.5.1: proxy/gateway support...` |
| Tag name | `X.Y.Z` (no `v`) | `1.5.1` |
| Tag message | `Release vX.Y.Z: <summary>\n\n- bullets...` | `Release v1.5.1: proxy/gateway support...` |
| Release title | `vX.Y.Z (llama.cpp vA.B.C)` | `v1.11.2 (llama.cpp v0.2.0)` |
| Installer name | `llama-cpp-framework-vX.Y.Z-vA.B.C-x64-setup.exe` | `llama-cpp-framework-v1.11.2-v0.2.0-x64-setup.exe` |

# llama-cpp-config

GUI + CLI configurator for [llama.cpp-framework](..).

```text
llama-cpp-config                  → launch the GUI
llama-cpp-config gui              → same, explicit
llama-cpp-config control start    → start llama-server
llama-cpp-config control stop     → stop llama-server
llama-cpp-config control restart  → restart llama-server
llama-cpp-config control stop-and-close → stop llama-server and close the GUI
llama-cpp-config server show      → print server.ini
llama-cpp-config server set ...   → update server.ini fields
llama-cpp-config preset list      → list models with their presets
llama-cpp-config preset show ...  → print one preset
llama-cpp-config preset delete .. → remove one preset
```

## GUI

Built with [Slint](https://slint.dev). The nav rail switches between five tabs (Server, Models, Benchmark, Integrations, Settings) and carries the server run controls (Start/Stop over Open chat UI over View logs over Refresh) at its bottom, reachable from any tab. A status footer shows the llama-server state (running / not running) and version.

The non-obvious run controls:

- **Open chat UI** launches the URL the RUNNING server was started with (`AppState.launched_url`, snapshotted at launch: a save while running changes the file, not the listening process; the footer says "restart llama-server to apply"). When the GUI didn't start the server it falls back to the SAVED Base URL (`AppState.chat_url`, from `ServerConfig::opencode_base_url_or_default()`: uses the custom Base URL if set, otherwise auto-derives from host+port; a `0.0.0.0` bind maps to `localhost`, since a listen address isn't a connectable one).
- **View logs** opens `logs\llama-server.log` in an independent, non-modal window (`LogWindow`) that follows the file live like `tail -f`, leaving the main window fully interactive while it is open. Auto-scroll (checkbox, on by default) parks the cursor at the end; untick it to read scrolled-back text while the server keeps writing. A header readout ("17.3 MB · updated 5 s ago") ages every tick, so a live-but-quiet tail (llama-server goes silent between requests) reads differently from a stuck one. Always enabled: the log outlives the process, so it's exactly what you want after a crash or failed start. The tail mechanics (500 ms timer armed/stopped with the window, bounded in-memory buffer, truncation/rotation handling) live in `gui\log_window.rs` and `ui\log_window.slint`.
- **Refresh** (the button, or F5) re-reads `server.ini` / `presets.ini`, re-scans the models directory, reloads integration state, and re-probes the run status, llama-server version, and GPU devices (the exe can change under us, e.g. a `02-build.ps1` rerun). Use it after adding a model file or hand-editing a config file outside the GUI, without restarting.

Each tab body is its own Slint component (`ui\server_page.slint`, `ui\models_page.slint`, `ui\bench_page.slint`, `ui\integrations_page.slint`, `ui\settings_page.slint`). All shared state (every property and callback the pages and Rust both touch) lives in a single `export global AppState` (`ui\state.slint`); the pages read/write `AppState.<name>` directly and Rust drives it via `app.global::<AppState>()`. `ui\app.slint` is just the window chrome (nav rail, run controls, modals, footer) plus the tray.

Modal dialogs (New/Clone picker, Rename, the Delete confirmation, the discard-confirm guard, and the chat-template preview) overlay the whole window: Esc or a backdrop click dismisses them, and the app-wide shortcuts (Ctrl+S, Ctrl+N (which jumps to the Models tab first), Ctrl+1–5, F5) are inert while any one is open (`AppState.modal_open`). The New/Clone picker is keyboard-completable: when the filter narrows the list to exactly one model, Enter picks and confirms it.

Any navigation that would replace a dirty form (switching presets, Refresh/F5, opening New…/Clone…/Rename…) first asks to discard the unsaved edits (`gui::confirm_discard_then` parks the action Rust-side until the verdict). What counts as "dirty", and how the Integrations list survives a rebuild:

- For Refresh/F5, "dirty" also counts pending Integrations toggles (`gui::integrations_dirty`: those rows have no form baseline, so it compares the enabled set against the on-disk `opencode.json`).
- The other write paths that rebuild the Integrations list (preset save/rename/clone/delete, server save) MERGE instead of asking: existing rows keep their pending in-UI toggle, only new ids take the disk value (`gui::refresh_integrations` vs `refresh_integrations_reset`, whose reset-to-disk semantics are reserved for F5 (behind the guard) and the Integrations tab's own Save/Revert).

### Server tab: `server.ini`

- Fields: port, hostname, load mode, threads, cache reuse, threads-batch, models-max, models-dir (with a Browse button). **threads** and **threads-batch** are sliders capped at the machine's logical-processor count, each with a "default" checkbox that omits the flag (let llama.cpp pick). The scalar fields (port, cache reuse, models-max) are `DefaultLineEdit`s: a "default" checkbox omits the flag, or an explicit integer (see [Numeric fields are text](#numeric-fields-are-text-never-a-spinbox) for why they are not SpinBoxes).
- **Load mode** (`-lm` / `--load-mode`) is **one dropdown, not two checkboxes**: `auto` (default; mmap unless a device can't, llama.cpp's own), `none`, `mmap`, `mlock`, `mmap+mlock`, `dio`. It used to be an mlock checkbox plus a no-mmap checkbox, until llama.cpp folded `--mlock` / `--mmap` / `-dio` into a single enum in **b10105** (PR #20834). The old flags still parse but no longer compose: each **overwrites the whole mode**, so the pair the configurator emitted (`--mlock --no-mmap`) was last-one-wins and silently dropped the mlock, while a lone `--mlock` selected `MLOCK`, which is mlock *without* mmap (`use_mmap` is true only for `mmap` / `mmap+mlock` / `auto`, `llama-model-loader.cpp`). Two independent toggles cannot express a six-state enum, which is why the UI is a combo. An older `server.ini` is migrated on read: an explicit `NoMmap = true` becomes `mlock` or `none` (it was a deliberate choice), while a bare `Mlock = true` does not carry over; it was the framework default and every save wrote it whether or not anyone picked it (`server_cfg::migrated_load_mode`).
- **GPU distribution** card: see [the table](#gpu-distribution-table) below (machine-wide default, overridable per-model), plus **Vision encoder**: which GPU the mmproj/CLIP image encoder runs on. That is a separate dropdown because the encoder **ignores `--device`**: llama.cpp gives it the first GPU backend the registry offers, so on a mixed CUDA+ROCm box it lands on the NVIDIA card even when the model is on the AMD one, holds VRAM there for the model's whole lifetime, and computes only on image requests. There is no flag for it: the field is written to `server.ini` as `MmprojDevice` and exported to the child as the `MTMD_BACKEND_DEVICE` env var (`runstate::env_vars`, which the Command Line card renders too).
- **Tensor placement** card: [the same table](#tensor-placement-table) as the Models tab, machine-wide (`server.ini` `OverrideTensor` → `--override-tensor`). Unlike the GPU card above, this one does not merely provide a *default*: anything set here **replaces** every preset's own rules rather than adding to them, and a device this machine doesn't have stops the **server** from starting (not just the model that would have used it). Leave it empty to let each preset keep its own placement.
- **Advanced** card: **Web UI MCP proxy** (`--webui-mcp-proxy`, on by default: the bundled chat UI needs it to call MCP tools), **Fit to VRAM** (`-fit on|off`, off by default so a preset's "offload all layers" isn't silently overridden), **Prefill assistant** (`--prefill-assistant` / `--no-prefill-assistant`), and **Log level** (`-lv`). These were previously fixed policy flags; they now round-trip through `server.ini` and default to the same framework values when untouched.
  - **Prefill assistant** decides what happens when a request's *last* message is an assistant message: on (llama.cpp's own default) it is treated as the **start of the reply** and continued; off, it is treated as a finished turn and answered. It is a server-scope flag upstream (`set_examples({LLAMA_EXAMPLE_SERVER})`, read from the child's `params_base`), not a model property, hence the Server tab and not `presets.ini`. Only the *off* state produces a flag (`--no-prefill-assistant`); the affirmative is redundant, so leaving it on passes nothing.
  - **Log level** is a **dropdown, not a number**: `-lv` has exactly six levels (`OUTPUT:0`, `ERROR:1`, `WARN:2`, `INFO:3`, `TRACE:4`, `DEBUG:5`; `common/arg.cpp`), a message prints when its own level is ≤ the threshold, and a free-number field could only ever offer levels that do not exist. The framework default is `TRACE:4`; `DEBUG:5` is what also logs the per-tensor `buffer type overridden` lines that `tools\report-memory.ps1` reads. The form carries the *label*, and `server_form::LOG_LEVELS` is asserted equal to `Options.log_levels` in the e2e so the two lists cannot drift.
- **SDK Tuning** card, the one card that holds no llama.cpp flags: environment variables of the GPU vendor's own libraries, exported onto llama-server at launch (`runstate::env_vars`, so the Command Line card renders them too) and inherited by the router's per-model children. It is split per SDK because a knob here is read *below* llama.cpp and is inert on every other backend; llama-server never sees it, so nothing validates it either. **CUDA** carries nothing today. **ROCm** carries **hipBLASLt** (`ROCBLAS_USE_HIPBLASLT`), a tri-state: `default` never exports the variable and leaves rocBLAS its own routing, `on` forces hipBLASLt (`=1`), `off` forces Tensile (`=0`).
  - `off` is the one that pays, and only on **gfx1201** (Radeon AI PRO R9700) under ROCm/TheRock 7.14: rocBLAS routes 16-bit GEMMs through hipBLASLt there, and the **second** 16-bit GEMM in a process fails at kernel launch; f32 is immune, and the identical call sequence passes on Tensile (standalone repro: default and `=1` fail, `=0` passes across batched/strided/plain × bf16/f16; a single visible GPU changes nothing). llama-server aborts on the first prefill batch of any BF16/F16 model. Forcing Tensile is a cure, not a trade: pp512 587 t/s / tg128 35 t/s measured on Ornith BF16, where the older `GGML_CUDA_CUBLAS_COMPUTE_TYPE=f32` workaround managed ~19 t/s prefill. Upstream: llama.cpp #25836, ROCm #6461, TheRock #7271.
  - What actually fails is a MIX, and the second cure follows from it: Windows resolves a static import from the exe's own directory and then System32, both before PATH, and the AMD driver keeps its own `amdhip64_7.dll` in System32, so llama-server runs the dist's `rocblas.dll` + `libhipblaslt.dll` against the DRIVER's HIP runtime rather than the dist's. Put the dist's runtime next to the exe and the same GEMMs pass on ROCm 7.14.0, 10.0.0 and the 10.1 nightlies alike, `on` included, so hipBLASLt itself is healthy and no ROCm bump was ever going to fix this. `installer\install-runtime-deps.ps1` does exactly that, from a hidden always-run installer section as well as from its AMD leg, which is why an install or upgrade carrying that helper can leave this knob at `default`.
  - The card also carries the **ROCm availability warning**, which is not a setting but the only place a missing HIP backend is ever mentioned. ggml loads backends dynamically and drops one whose imports don't resolve **without a word**, so a machine whose ROCm dist is absent, half-extracted, or simply not on the child's PATH does not fail: the same AMD card keeps working through Vulkan, slower, with nothing saying why. The verdict comes from the device probe, never from a file list (`devices::rocm_warning`): an AMD GPU present with no `ROCm*` device beside it *is* the diagnosis, and it holds whatever ROCm version is installed. Only the *hint* inspects the dist, and it checks two landmarks that survive a version bump, `bin\hipblas.dll` and `bin\rocblas\library` (a fuller file list would be wrong: `origami.dll` ships in TheRock 10.0.0 and not in 7.14.0, so requiring it would report a healthy 7.14 install as broken). The three hints name three different remedies: nothing installed, installed but incomplete, or complete and therefore a launch that isn't reaching it (most often a console whose PATH still names a dist directory that has since been renamed). The second one is worth its own row because it fails LATE: with `rocblas\library` missing the backend loads and the device enumerates, then the first matrix multiply dies with `Could not initialize Tensile host`.
  - It is a tri-state and not a checkbox for the usual reason (`--flash-attn`'s shape, and the same `form::tri_state` / `tri_bool` pair): "don't export the variable" is a third instruction, and it is the framework default; the bug is per-arch, and hipBLASLt is the faster path everywhere it works. The CLI reaches all three as words (`server set --rocblas-use-hipblaslt default|on|off`), which is also the only way to clear it back.
- **Conversation snapshots** card: `SaveStateOnShutdown` + `StateDir`. Dumps each loaded model's KV cache to disk when the server stops and pushes the newest one back on the next start, which buys back the one cost no amount of VRAM tuning touches: reading a prompt is **quadratic** in its length and the cache is *process memory*, so a restart re-reads the whole conversation from zero. Measured on a 234k-token prompt (Qwen3.8-27B, hybrid `qwen35`, 17 of 65 blocks carrying attention): the marginal cost per token fits `0.95 ms + 0.0287 ms per 1k of context`, i.e. 984 t/s at position 4k against 142 t/s at 218k, which integrates to roughly **17 minutes** of prefill, against ~8.3 GiB of sequential IO to reload the same state. Off by default: the disk cost is real, stopping waits for the write, and the next start loads the model eagerly to push the state back in, so a machine running short prompts pays all of that for nothing.
  - **How the flag reaches the child**, which is the part that nearly made this impossible. The `/slots` endpoints only exist on a server started with `--slot-save-path`, and the framework always launches the **router** (`--models-preset`), whose per-model children are separate processes with their own command lines. `--slot-save-path` has **no env name** upstream (`common/arg.cpp` gives it only `set_examples`), so it cannot ride a preset key like `LLAMA_ARG_*`. It propagates anyway because `get_map_key_opt` (`common/preset.cpp`) maps every option by its **flag name with the dashes stripped** as well as by its env name: the router parses its own argv into `base_preset` (`load_from_args` then `common_params_to_map`, which keys off `opt.args`), `preset.merge(base_preset)` copies it onto every model, and `unset_reserved_args` does not prune it. One flag on the router's line therefore reaches every child.
  - **Why the restore is worth anything.** `SERVER_TASK_TYPE_SLOT_RESTORE` does not merely refill the KV buffer: it deserializes the token list saved alongside it into `slot->prompt.tokens`, which is exactly what the next request's `get_common_prefix` compares against. A restored slot is therefore indistinguishable from one the server prefilled itself, and the prompt is skipped. Without that half the dump would be a file nobody reads.
  - **The directory must exist before the launch.** llama.cpp validates `--slot-save-path` while *parsing* it (`fs_is_directory`, or it throws "not a directory"), so a missing folder does not degrade to "no snapshots this run", it stops the server from starting. `runstate::start` creates it, and the flag is emitted only when the toggle is on for the same reason.
  - Saving covers every model the router reports as `loaded` (never `loading`, which has no slot yet, nor `sleeping`, which has released its KV cache); dumps of models that are no longer loaded are pruned after a successful save, which is what keeps "the newest file" meaning "the model you were working on". Restoring deliberately takes **only** that newest dump: a dump is one conversation, restoring is an 8 GiB read plus a full model load, and the LRU would evict whatever a second restore pushed out anyway.
  - The path is overridable because the default sits under `%LOCALAPPDATA%`, on the system drive, and these files are large. Size follows the tokens the slot actually **holds**, not `ctx-size`: the dump is the conversation's KV cache, not the allocated context. Measured 4,703,061,864 bytes (4.38 GiB) for a 127,579-token conversation on Qwen3.8-27B, which is exactly the arch's 36 KiB per token; a full 262k context would be ~8.3 GiB. Plan disk against that ceiling, but a short conversation costs proportionally little.
- A read-only, multi-line **Command Line** card shows the exact `llama-server` invocation **Start** would run, one `--flag value` per line joined with the shell's line-continuation character (`` ` `` on Windows, `\` on Linux) so you can paste it straight into a terminal. It auto-sizes to its content (no inner scrollbar).
- **Network** card: **Base URL** and **API Key** fields for integration endpoints (opencode.json + Claude Code). **Base URL** has a **Default** checkbox: checked = auto-derived from host+port, nothing written to server.ini; unchecked = editable override (useful behind a reverse proxy or LLM gateway). The stored value is the base without `/v1`; the suffix is appended automatically only for opencode.json's `baseURL`. **API Key** has a **No key** checkbox: checked = no key used, field disabled; unchecked = editable. These fields also affect the Open chat UI button URL.

### Models tab: `presets.ini`

Scans `.gguf` files under the SAVED `ModelsDir`'s fixed subfolders: `models\` (main models), `mmprojs\`, `mtps\`, `dflashs\` (`model_scan::Category::subdir`); a file sitting at the `ModelsDir` root is not scanned, and an unsaved Server-tab `ModelsDir` edit doesn't move the scans until saved (like every client-facing projection, they follow the file). Shows the presets table, and edits per-model settings. The editor is grouped into cards by concern:

- **Assets**, the file pickers and speculator selection: model file (`--model`), MMProj (`--mmproj`; its **Vision on GPU** offload toggle and the per-image token bounds moved to their own **Vision** card below), and ONE draft-model dropdown that merges MTP heads (scanned from `mtps\`) and DFlash drafters (scanned from `dflashs\`), both feeding `--model-draft`, plus the spec-type dropdown. The pick policy lives in Rust (`apply_draft_pick` in `gui/models_tab.rs`, unit-tested), not in the `.slint` handler:
  - The spec type comes from the picked FILE's own GGUF header (`gguf::draft_spec_type`, mirroring llama.cpp's `common_speculative_types_from_gguf`): arch `dflash` carrying a `markov_w1.weight` tensor → `draft-dspark`, without it → `draft-dflash`, a `blk.<block_count - 1>.nextn.eh_proj.weight` head → `draft-mtp`. The folder it was scanned from (`mtps\` → `draft-mtp`, `dflashs\` → `draft-dflash`) is only the fallback, for a header that names none of the three (a blockless MTP head file like gemma4-assistant) or a GGUF that will not open. The folder cannot be the primary source because `dflashs\` holds both DFlash and DSpark drafters, and running one as the other does not fail: `is_dspark` changes the drafting batch (`n_draft` masked positions against `n_draft + 1`, anchor-first, ceiling `block_size` rather than `block_size - 1`), so the drafts are read from the wrong positions and get rejected.
  - Either way, when a GPU is selected the draft is pinned to it, the FIRST one if several (`device-draft` takes a single device, and a multi-device draft split is exactly what crashes MTP heads), with `n-gpu-layers-draft = 99` (the shared "all layers" sentinel, `Options.all_layers` / `form::ALL_LAYERS`, equality test-asserted); otherwise it falls back to CPU (`n-gpu-layers-draft = 0`).
- **Model info** (read-only, between Assets and Hardware Config): reads GGUF metadata through llama.cpp's own reader (runtime-loaded `ggml-base.dll`, no reimplemented parser; see `gguf.rs`): dense vs MoE (+ expert counts), layer count, trained context, GQA shape, quant, and whether it embeds MTP layers, plus whether a matching MTP/DFlash drafter is present. A **Chat template** row reports the embedded `tokenizer.chat_template` as `Jinja (embedded)` / `embedded (non-Jinja)` / `none` (the `{%`/`{{` heuristic mirrors llama.cpp's `common_chat_verify_template`), with a **Preview** button (shown only when a template is present) that opens the raw template text in a modal. An **Embeddings** row reports `token_embd.weight`'s OWN quant and size, which neither the file name nor the `Arch / quant` row tells you (Unsloth's `Q6_K_XL` keeps the embedding table at `Q8_0`; its `Q4_K_XL`/`Q5_K_XL` drop it to a K-quant), and it is what decides whether the Tensor placement table may pin that table to a GPU: ggml-cuda/ggml-hip implement `get_rows` for no K-quant, so pinning one round-trips the table to host RAM on every token (25 → 2.8 tok/s measured, with the GPU sitting at 0%), while the size is the VRAM the pin ADDS to that card. The verdict itself is not repeated in the row: it surfaces as a warning strip on the [Tensor placement table](#tensor-placement-table), at the moment a rule actually pins it. For MoE models a **MoE layers** row shows how many layers carry experts (with a "saves VRAM (slower)" note), sizing the `--n-cpu-moe` field. Two rows read that same template for **reasoning**: **Thinking** says whether it does any (and whether `--reasoning on|off` can switch it: that flag only sets the template variable `enable_thinking`, so a template that never names it thinks whatever you pick), and **Past thinking** says whether `--reasoning-preserve` is a *lever* on this model at all; see [Keep past thinking](#keep-past-thinking-vs-a-raw-preserve_thinking-kwarg) for why that is the useful question and why llama-server's own log cannot answer it. Both are read from the template's **source text** (this app has no Jinja engine; llama.cpp answers the same question by rendering the template), so the subject of every verdict is the *template*, not the model: `no marker in the chat template` does not prove the model can't think; MiMo-VL's template names nothing at all, yet the model emits `<think>` and llama-server's parser picks it out of the output. What the silence *does* prove is that neither flag has anything there to act on. A **MMProj** row (projector type, vision/audio modality, encoder depth, image/patch size) and a **Draft file** row (the drafter's arch/layers and, for DFlash, the trained `block_size` → the implied `--spec-draft-n-max` ceiling) appear when those are selected. Reads are synchronous and uncached; if `ggml-base.dll` can't be loaded the box shows "unavailable" and the load is retried on the next read (only success is memoized), so a DLL that appears later (e.g. a finishing `02-build.ps1`) is picked up without a restart.
- **GPU distribution** (directly under Model info): [the table](#gpu-distribution-table), overriding the server-wide default.
- **Tensor placement** (under GPU distribution), [the table](#tensor-placement-table) for `--override-tensor`: the exceptions to the card above, i.e. tensors that go on a device of their own whatever their layer does.
- **Hardware Config**, the remaining placement knobs: GPU layers, MoE CPU layers, draft device, draft GPU layers.
- The remaining cards group the runtime knobs by concern: **Resource / context** (ctx-size, parallel, batch/ubatch), **KV cache** (K/V cache-type, flash-attn, cache-ram), **Chat / reasoning** (jinja, reasoning, reasoning-format, [reasoning-effort](#reasoning-effort), [keep-past-thinking](#keep-past-thinking-vs-a-raw-preserve_thinking-kwarg), plus the [output split](#thinking-budget-vs-the-answer): thinking budget, budget message, max output), **Sampling overrides** (temp, top-k, top-p, min-p, repeat/presence penalty), **Advanced** (chat-template-kwargs), **Vision** (the `--mmproj-offload` offload toggle plus image-min/max-tokens, the per-image token bounds only dynamic-resolution vision models read; all gated on an mmproj being selected; Qwen-VL warns at load it wants `--image-min-tokens 1024`), and **Speculative decoding (MTP / DFlash)** (last: Draft n-max, plus the draft context's own K/V cache types; see the note below on why they are not the model's). The field-by-field schema (each INI key, its `--flag`, and the "default checkbox omits the flag" numeric pattern: `DefaultSpinBox` for ints, `DefaultLineEdit` for floats) is owned by the `presets.rs` `Preset` field docs; the per-widget rationale (why top-k is an int SpinBox, the `SegmentedControl`s, the `DefaultLineEdit`'s reveal-on-uncheck) lives in `ui\models_page.slint`.

Field behaviors:

- The **draft device** and **Vision encoder** fields are dropdowns populated from `llama-server --list-devices` (e.g. `CUDA0`, `Vulkan0`). The probe runs async at startup and on Refresh/F5; its result is cached Rust-side (`devices::probed()`), not published as Slint state; the GPU table gets its rows built from it in Rust too (`gpu_split::build_rows`).
- The **GPU layers**, **MoE CPU layers**, and **Draft GPU layers** fields are sliders ranging `0..` the model's (or draft's) layer count read from the GGUF header, each with a **default** checkbox (on-screen label; the backing form field is `*_auto`), checked by default, that omits the flag and disables the slider. When the selected draft is an MTP/nextn head (no transformer layers, `block_count 0`) the Draft GPU layers control becomes a two-option on-GPU/on-CPU selector (a `SegmentedControl`, not a `Switch`, so its state is a pure read of the model and never goes stale) instead of a slider.
- Controls that don't apply are disabled: spec-type, draft n-max and the two draft K/V cache types need a draft available (a draft model selected, or the main model embedding MTP heads); **draft device and Draft GPU layers need a draft FILE** (see the note below); MoE CPU layers needs an MoE model; split-mode needs other than exactly one GPU checked.
- **Every field of the KV cache card can be left at `default`** (i.e. the flag is omitted and llama.cpp decides), but the affordance differs per field, because the shape of "unset" does: cache-ram takes the usual `DefaultSpinBox` checkbox; **K/V cache-type** carry it as the FIRST dropdown entry (`Options.cache_types[0]`, which is *not* the same as picking `f16`: that pins f16 whatever llama.cpp's default becomes); and **flash-attn is a three-pill `default`/`on`/`off` `SegmentedControl`, not a checkbox**, since `--flash-attn` takes `[on|off|auto]` and *defaults to auto* (on where the backend supports it); a bool could only ever reach two of its three states, and the one it couldn't reach was the default. `off` is a real instruction, distinct from unset: it forces the kernel away, which also costs a quantized K/V cache most of its benefit. Leaving these unset used to be unreachable from the GUI, and worse than unreachable: the form filled an absent `cache-type-k` in from the schema default, so a preset that had never named one displayed `q8_0` and *wrote* `q8_0` on the next save of any unrelated field, silently requantizing a cache llama.cpp would have left at f16 (guarded by `form.rs`'s `kv_cache_unset_state_survives_the_form_round_trip`).
- **A new preset leaves every tunable at `default`**, i.e. the key is omitted and the model runs on llama.cpp's own defaults until you override something on purpose (`Preset::default()`). It used to seed the framework's own opinions instead (32k context, 4 slots, 512-token batches, a q8_0 KV cache, forced flash-attn), which *looked* like llama.cpp's defaults and were not, and `parallel = 4` in particular is not inert: pinning it turns off the unified KV cache llama-server's auto mode enables, quartering the context a single request may use (see the [Integrations tab](#integrations-tab)). The only keys a new preset still writes are the four the form has no "unset" affordance for (`jinja`, `mmproj-offload`, `reasoning`, `reasoning-format`), each set to what llama.cpp would have done anyway, so writing them stays a no-op. **Clone** is unchanged: it copies the source preset's values, which is its whole point.
- Changes are written to `presets.ini`, preserving hand-edits to sections not currently touched. Path fields (model / mmproj / model-draft, and the server side's ModelsDir) containing `;` or `#` are rejected at save: the INI format can't escape them, so they would silently reload truncated (`ini::reject_comment_markers`).

> **Note: embedded MTP heads ignore the draft placement fields.** llama.cpp reads `--device-draft` and `--n-gpu-layers-draft` only when a separate `--model-draft` file is given (both live inside `if (has_dft())`). With MTP heads embedded in the main GGUF (`spec-type` set, no `model-draft`), it builds the draft context against the *target model*, so the draft runs on the model's own GPU and both keys are silently ignored. Setting them there is how a GPU ends up looking assigned to the draft while never drafting a token, so the UI disables them and says so. A **separate** MTP head file (e.g. gemma4-assistant) is the case where they do apply, and there, pin to ONE device: multi-device memory fitting crashes those heads. The full story lives in the `presets.rs` field docs, the single authority for this caveat.

> **Note: the draft context's KV cache does NOT follow the model's, and these two flags are the only way to reach it.** `common_base_params_to_speculative` (`common/speculative.cpp`) builds the draft params by copying the whole struct (the model's `--cache-type-k`/`-v` included) and then *unconditionally overwrites* both with `params.speculative.draft.cache_type_k/_v`, whose own default is `GGML_TYPE_F16` (`common/common.h`). So a preset running the model on a q8_0 KV cache still drafts against an **f16** one, and "leave the draft types unset and they inherit the model" is exactly backwards: unset means f16, always. **Draft K/V cache type** (`--spec-draft-type-k` / `--spec-draft-type-v`, aliases `-ctkd` / `-ctvd`) are the flags that reach it. Note this overwrite sits *outside* the `if (has_draft)` block that guards `devices` / `n_gpu_layers` / `tensor_buft_overrides`, so unlike the placement pair in the note above, these two **do** apply to MTP heads embedded in the main GGUF, which is why they stay enabled there and why `prune_inactive_draft_keys` groups them with the speculator rather than with the placement keys.

### GPU distribution table

`--tensor-split` is a positional vector indexed over the devices named by `--device`, **in `--device` order**. Typing `3,1` into a text box therefore means nothing until you know which devices those are, and with `--device` unset, "those devices" is every detected backend, which on a mixed box is a CUDA card, two ROCm devices (one of them an iGPU) and three duplicate Vulkan views of the same three GPUs. So the two settings share one widget (`GpuSplitTable`, used by both tabs): the **split-mode selector on top** (it decides what the rows below mean), then a row per detected GPU with a checkbox, its VRAM, an editable weight, and the derived share. There is deliberately no flags-preview line under the table: the values are persisted to the INIs, and a preview that showed `--device`/`--tensor-split` while ignoring the mode used to read as the whole truth while being stale.

Rows are built in Rust (`gpu_split::build_rows`): the **checked devices first, in split order**, then the rest in probe order. So the table read top to bottom *is* the `--device` list and its `--tensor-split` vector. Checking a box **appends** the device to the split; the **≡ drag handle** on each checked row is how you reorder it; the weight rides along with its device, so the proportions survive a move.

Position 0 is not cosmetic: it is `devices[0]`, which is also llama.cpp's **`main_gpu`** (it defaults `--main-gpu` to 0 and the framework never overrides it). With `--split-mode none` that is the *only* GPU llama.cpp keeps; under `layer` it takes the first slice of layers. Without the handle there was no way to put a chosen GPU at the head.

> The `--list-devices` ids are **not stable** across driver states: the same machine has enumerated its discrete AMD card as `ROCm0` on one boot and `ROCm1` on another, with the iGPU taking the other slot. Presets pin by id, so the table always shows the device **name** next to it: check the name, not the number.

The four states it can express map 1:1 onto llama.cpp:

| checked | `device` | `tensor-split` | meaning |
|---|---|---|---|
| 0 | *(blank)* | *(blank)* | llama.cpp uses all detected devices |
| 1 | `ROCm1` | *(blank)* | one GPU, nothing to split |
| ≥2, **Auto** | `ROCm1,CUDA0` | *(blank)* | llama.cpp splits by **free** VRAM at load |
| ≥2, explicit | `ROCm1,CUDA0` | `3,1` | 75% / 25% |

Note that blank-with-2-GPUs is *auto-by-free-VRAM*, **not** an even split; hence **Auto** and **Even** are two separate buttons, and the weight fields stay disabled until the split is explicit (Even is the way in). That is also what keeps the one-way `for`-row bindings honest: a weight edit never rewrites another row's weight, so it needs no model rebuild, while toggle / Auto / Even do rebuild, giving every delegate a fresh binding. All of it is guarded: `gpu_split`'s unit tests for the rules, and a `save_flow` phase that clicks the real checkboxes and asserts what reaches the INI.

#### The split mode decides what the columns mean

`--split-mode` is part of the same selection, which is why its combo sits **above** the table, and the columns follow the **effective** mode (`gpu_split::SplitMode` / `effective_mode`), not just the combo:

- **layer** (llama.cpp's default): the vector cuts consecutive runs of blocks; the block projection below applies.
- **none**: llama.cpp drops every device but `devices[main_gpu]` *before loading* (`llama_prepare_model_devices`), so the vector is dead. The editors retire, the head row reads **100%** and every other checked row says **unused**; the ≡ drag handle (which GPU leads) is the one control left.
- **row**: the weight *matrices* are split **row-wise** by the normalized vector, via the backend's split buffer type (CUDA/ROCm; a backend without one, Vulkan, quietly falls back to the layer cut). The layer assignment still runs over the same vector, so the KV cache and non-matrix tensors follow it, but the bulk of the bytes follow the row fractions, so the table edits the **raw ratio** and never shows blocks there. (llama.cpp's experimental `tensor` mode is not offered; a hand-written value is preserved and treated like `row` for display: ratio, no block cut.)

The combo has **one** "layer (default)" entry where there used to be a separate "default" and "layer": for a preset those are the same launch in every reachable configuration (an absent key falls back to layer, or to the server-wide mode, which when set overrides an explicit preset key too, because the router's CLI wins the merge). Picking it stores nothing in the INI. The mode pick is a `MappedComboBox` funnel (labels/values/index pushed from Rust, `*_split_mode_picked` writes the form and re-projects both tables); the server-wide combo shadows the preset one, and the Models tab warns when a differing preset pick is dead on arrival.

> **A server-wide `SplitMode = layer` is dropped on read** (`server_cfg::server_split_mode`), and that is a real behaviour change, not a cosmetic one. llama.cpp already defaults to layer, so the flag changed nothing about the server's own launch, but the router copies its CLI args over **every** preset (`preset.merge(base_preset)` in `server-models.cpp`; `unset_reserved_args` does *not* prune `--split-mode`), so emitting it silently neutered each preset's mode: the Models tab combo stayed live while being unable to change anything. Nobody picks `layer` to mean "forbid every preset from choosing row/none"; it is simply what the old two-entry combo wrote when either of its identical entries was picked. So it collapses to unset: the server's launch is unchanged, presets get their mode back, and the next save removes the key from the file. `none` / `row` are kept, because those *do* change the launch and overriding every preset with them is a deliberate, visible choice.

#### Weights are ratios; the Models tab edits them as blocks

`--tensor-split` is normalized, so `85,15`, `17,3` and `29,5` are the same launch. What llama.cpp does with that ratio is cut **`n_layer_all + 1` positions** in two: every block of the GGUF (the nextn/MTP ones included) plus one more for the **output layer**, `dev_output = get_layer_buft_list(n_layer_all)`. On a 33-block model that is 34 places to cut and a percent field offers 100 of them: **83 / 84 / 85% all cut in the same place**, so two of every three edits move the number and change nothing.

So wherever a model is known (the Models tab, once its header has been read, and only under the **layer** mode; see above), the editable column switches to **`Blocks/34`** and each row gains the range it holds (`blocks 29-32 + output`). The server-wide table keeps raw weights: it applies to every preset, so it has no single `block_count` to project onto. Both are the same widget, switched by one `positions` property (pushed as 0 for every non-layer mode).

Writing a count back needs no inverse: a vector summing to the positions gives position `il` to the first device whose prefix sum passes it, so **the weights *are* the counts** and `set_blocks` stores what was typed (`29,5` → blocks 0-28 / 29-32+output, exactly). Three consequences worth knowing:

- **A count cannot be edited alone.** It is constrained to the positions, so one row going up means another coming down; the rows absorb from the back, which keeps a two-device edit local. That constraint also picks the widget: a **`Slider`** over `0..positions` with a live readout, committing once on **`released`**. Applying mid-drag would rewrite the other rows and rebuild the model, destroying the slider being dragged; `released` fires on pointer-up *and* on key-release for the arrows/Home/End, so the keyboard path commits too. (A `SpinBox` stays banned (a stray wheel over the page edits it silently), but `slider-base.slint` handles no scroll event at all, so a Slider is safe here. Its one gap: the *accessibility* set-value/increment actions route through `base.set-value`, which raises only `changed`, so an assistive client moves the thumb without committing.)
- **The INI still stores a ratio**, and that is the portable form. Re-point a preset at a model with a different `block_count` and `29,5` still means 85%, now cut somewhere else. The number in the cell is a *view* of the ratio under the current model, re-derived on every rebuild, never the source of truth.
- **Partial offload moves the target.** The split runs over `act_gpu_layers` starting at `i_gpu_start`, so lowering the GPU-layers slider shrinks the budget and the counts change on their own. That is the truth, not a glitch.

Auto has no counts to show (llama.cpp weighs the devices by their **free VRAM at load**), so the column falls back to ratios there too.

A selected device the probe doesn't know (a stale id, another machine's GPU, or simply the async probe not landed yet) is kept as a `(not detected)` checked row, so a save can never silently drop it.

> **Note:** a server-wide selection **overrides** every preset's own (the split mode included) because llama-server's router passes its own CLI args on top of each preset (`preset.merge(base_preset)`). The Models tab shows a warning strip when that is in effect, and the preset table's columns follow the *effective* mode, so a server-wide `none` visibly retires the preset's editors too.

### Tensor placement table

`--override-tensor` (`-ot`) is the exception list to the table above: `<regex>=<buffer type>` rules that send every tensor whose **name** matches the regex to a device of its own, whatever its layer does. llama.cpp matches with `std::regex_search` (`llama-model-loader.cpp`) and resolves the buffer type against every backend's `ggml_backend_dev_buffer_type`, so the legal targets are exactly the ids `--list-devices` prints, **plus `CPU`** (an unknown one is a hard `throw`: the model does not load). The CPU being a first-class target is why this table offers it and the GPU table filters it out.

The reason it exists, and the case the **+ Add override** button seeds in one click:

> llama.cpp keeps `token_embd.weight` in **host** memory even when it reports `offloaded 33/33 layers to GPU`. The embedding lookup is a `get_rows` over a handful of tokens: cheap on CPU, and worth a GB or two of VRAM. But with a GPU backend active that host buffer is **pinned** (it shows up in the log as `ROCm_Host` / `CUDA_Host`), and Windows counts pinned host memory as **Shared GPU memory**, so a model that fits in VRAM with room to spare still shows GBs of shared allocation, and the compute graph carries a CPU split it didn't need. On a big-vocab BF16 model the table is huge (`n_vocab 248320 × n_embd 4096 × 2 B` = 1940 MiB), which is when `token_embd\.weight=ROCm0` is worth the VRAM it costs.

The pattern is a **dropdown**, not a free-text field, because the value's grammar is unforgiving in two ways that llama.cpp applies *before* it parses anything, neither of them escapable:

- rules are split on `,`, so a `{1,2}` quantifier inside a regex tears its own rule in half, and the half without an `=` is a fatal `invalid value`;
- each rule is split at its **first** `=`, so an `=` inside the regex silently eats the pattern's tail.

So the three canned patterns (Embedding table, Output head, and MoE experts: llama.cpp's own `LLM_FFN_EXPS_REGEX` verbatim, i.e. `MoE experts → CPU` *is* `--cpu-moe`) cover what people reach for, and **Custom regex…** reveals a text field that strips those two characters on the Rust side. A row's kind is *derived* from its pattern, with no hidden "is custom" bit to drift from a hand-edited INI, which is why picking Custom clears the regex rather than keeping the canned one it was switched from (a row still holding `\.ffn_…_exps` would simply read back as the MoE kind).

Rules apply **in order** (the first match wins), so no edit re-sorts them. A device the probe doesn't know is kept as a `(custom)` dropdown entry and flagged on its row, exactly as in the GPU table; a rule left with **no** device (only a hand-edited INI can produce one) is refused at save, because llama.cpp's failure mode for it is a throw during arg parsing, i.e. "the model didn't load" and nothing else. Same one-way `for`-row binding contract as the GPU table, with the same escape: add / remove / kind / device rebuild the row model, while a keystroke in the regex field must **not** (it would recreate the field mid-edit and drop the caret), and it can afford not to, since it changes no other row. Guarded by `tensor_override`'s unit tests for the rules and a `save_flow` phase that drives the real callbacks, types into the real regex field, and asserts what reaches the INI.

The same table appears **twice**, once per scope: per-preset (`presets.ini` `override-tensor`) and server-wide (`server.ini` `OverrideTensor`). Same widget, same rules module, but not the same reach:

> **Note:** a server-wide value does not merely out-rank a preset's rules, it **replaces** them. `-ot` is a `push_back` onto a vector inside llama.cpp, so "the two lists concatenate" is the natural guess and it is **wrong**: the router merges its own CLI args into each preset as a key→value map (`common_preset::merge` → `options[opt] = val`, with the CLI as the writer), so exactly one `--override-tensor` ever reaches a child: the server's. Verified against b9976: a preset asking for `token_embd\.weight=CPU` under a server-wide `token_embd\.weight=CUDA0` spawns its child with the CUDA0 rule and no trace of the CPU one. The Models tab shows a warning strip naming the value that shadows it (`AppState.tensor_override_warning`), the twin of the GPU table's.

One asymmetry between the two scopes: the buffer type in the server-wide value is parsed by the **router itself**, at startup, against its own device registry. A rule naming a device this machine doesn't have therefore fails with `unknown buffer type` and **the server does not start at all**, where the same mistake in a preset only kills the model that uses it. (The two dropdowns are also built per-scope, not shared: `device_options` appends a `(custom)` entry per unknown device id, so its length (and every row's `device_index`) depends on that table's own rules.)

### Keep past thinking, vs. a raw `preserve_thinking` kwarg

**Keep past thinking** (Chat / reasoning card) is `--reasoning-preserve` / `--no-reasoning-preserve`: replay the reasoning trace of *every* past assistant turn back to the model, not just the last one. It is a **tri-state**: `default` omits the flag and leaves the template to its own behaviour, which is a third instruction, not the absence of one. It is orthogonal to **Reasoning** (`--reasoning`, i.e. *whether the model thinks at all*): this one is about what happens to the thinking it already did.

It is also the **only** supported lever, and the reason it is a field of its own rather than something to hand-write into **Template kwargs** below it. llama.cpp turns this flag into the kwarg `preserve_reasoning`, and `caps_apply_preserve_reasoning` (`common/jinja/caps.cpp`) expands *that* into three template variables at once:

```
preserve_thinking = v      clear_thinking = !v      truncate_history_thinking = !v
```

because templates disagree on which name they read: Qwen3.6 and LFM2.5 read `preserve_thinking`, GLM-4.7 reads `clear_thinking`, Nemotron reads `truncate_history_thinking`. Setting one of those three by hand as a `chat-template-kwargs` entry therefore works only on the templates that happen to use that name, and is a **silent no-op** on the rest, and it skips the capability probe either way, so `llama-server` still logs `chat template supports preserving reasoning, consider enabling it via --reasoning-preserve` as though nothing were set (verified against b9976). The flag sets all three and is checked, which is why the field writes it and not the kwarg.

Which template you are on is exactly what the **Past thinking** row of [Model info](#models-tab-presetsini) reports, by looking for those three names in the template source, and it is the one question llama-server's log cannot answer for you. Its probe renders the template and checks whether a past turn's trace came out, so it prints "supports preserving reasoning" both for a template you can *control* and for one that preserves **unconditionally**, which are opposite answers to "will this flag do anything". The row names the variable it found (`yes  ·  --reasoning-preserve (template reads clear_thinking)`) or says the flag is inert here (`no  ·  --reasoning-preserve is a no-op on this template`). In llama.cpp's bundled corpus only three templates gate on it at all: GLM-4.7 (`clear_thinking`), LFM2.5 (`preserve_thinking`) and Nemotron-3 (`truncate_history_thinking`).

Two things it does not promise. It only bites where the template actually gates on those variables: a template that emits history reasoning **unconditionally** (Ornith-1.0 does: no gate at all) already preserves it, and reads as "supported" to the probe purely because the trace shows up in the rendered output. And it is not free: the preserved trace is re-sent as prompt tokens every turn. What it buys, on a template that *does* gate (the Qwen3.6 form is `if preserve_thinking or loop.index0 > ns.last_query_index`), is a **stable prefix**: without it, an assistant turn is rendered *with* its thinking while it is the newest, then re-rendered *without* it as soon as the next user message arrives. That retroactive rewrite of an already-cached prefix is precisely what a KV cache cannot survive.

### Reasoning effort

`--reasoning-effort` (llama.cpp **b10434**+) hands the chat template a level: `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, with `default` omitting the flag. It is the same shape as [keep-past-thinking](#keep-past-thinking-vs-a-raw-preserve_thinking-kwarg) and carries the same warning with one variable fewer: `common/arg.cpp` stores it as `default_template_kwargs["reasoning_effort"]`, and `caps_apply_reasoning_effort` binds that one value to **two** template variables, `reasoning_effort` and `reasoning_strength`, because templates disagree on the name. Writing either one into **Template kwargs** by hand sets one of the two and is a silent no-op on a template keyed to the other.

What it is not: a switch, and not a budget. It tunes how the template asks for thinking, so on a template that names neither variable (most of them; gpt-oss and harmony are the ones that do) the value is simply never read. Two consequences worth knowing before you reach for it. llama-server prints **nothing** about this flag at startup, unlike the `supports preserving reasoning` line it prints for the neighbouring one, so the **Thinking** row of [Model info](#models-tab-presetsini) is the only place that tells you whether the level is a lever on this model. And an older llama-server does not ignore the key: `--models-preset` parsing throws `option 'reasoning-effort' not recognized in preset '<id>'` and the server refuses to start, because `ignore_unknown_keys` is set only for llama.cpp's own shared `config.ini`.

Related, and new in the same commit: a client's OpenAI `reasoning_effort` request field is no longer inert either. `none` disables reasoning for that request, and any other value now reaches the template, where it used to be parsed and dropped.

### Thinking budget, vs. the answer

Three fields at the bottom of the Chat / reasoning card split one output budget in two, and the asymmetry between them is the whole point: **llama.cpp can cap the thinking, and it can cap the total, but it has no cap for the answer alone.**

**Thinking budget** is `--reasoning-budget`, and since b10428 it takes a real token count, not just the old on/off pair: `-1` unrestricted (llama.cpp's default, which the `default` checkbox omits the flag to get), `0` closes the block immediately, `N > 0` is a budget. It is **not** a truncation. At the limit `common_sampler_reasoning_budget_force` makes the sampler emit the template's own end-of-thinking sequence, so the model closes the block properly and writes a normal answer afterwards; the start and end tags come from the template, so the budget only arms where the template declares them.

**Budget message** is `--reasoning-budget-message`, injected immediately before that forced tag, which is the difference between a model that wraps up and one that stops mid-thought. It is free text reaching the model verbatim, so write it in the language the model is answering in: an injection in another language is an invitation to language mixing. It is also validated on save like every other free-text field, because a `;` or `#` would reload truncated.

**Max output** is `--n-predict`: thinking **and** answer together. So the answer's room is whatever the thinking leaves, `n_predict` minus the thinking actually spent, and if you want to guarantee the answer some space you set `n_predict = budget + the answer length you want`. It is a **default and never a clamp**: `server-context.cpp` reads `task.params.n_predict != -1 ? task.params.n_predict : params_base.n_predict`, so a client's own `max_tokens` wins in either direction and this only bites clients that send none.

One trap worth naming, because model cards invite it. A card that recommends "reasoning: maximum 262,144 tokens, final response: maximum 131,072" is describing ceilings **inside the extended context it assumes** (1M for Qwen3.8), not values to copy. Copied onto a smaller context they are worse than nothing: they sum to more output than the context holds, so the budget never fires, and the runaway generation you were trying to bound ends by filling the KV cache instead. What transfers is the *fraction* and the *ratio*: that pair is 37.5% of the context, split 2:1. Scale those to the context you actually run, and sanity-check the result in wall-clock rather than tokens, since at ~20 tok/s a 262,144-token thinking budget is over three hours.

### Benchmark tab

Measures one preset, or compares several. **The unit is the preset, not the model file**: two presets pointing at the same `.gguf` with different placement, KV types or drafters are a legitimate comparison, and usually the interesting one, so the tab lists presets and keys every result by preset id. The rules live in `src\bench.rs` (pure, unit-tested), the running in `src\bench\exec.rs`, the wiring in `src\gui\bench_tab.rs`.

#### Two engines, because one measurement cannot be both things

The **Engine** selector sits at the top for the same reason the GPU table's split-mode combo does: it decides what everything below it means, which half of the Workload card is live, and which llama-server state the run demands.

- **live** drives the RUNNING llama-server: one `/v1/chat/completions` per repetition with your prompt and a temperature override, reading `timings` off the response (`prompt_per_second`, `predicted_per_second`, `cache_n`, and `draft_n` / `draft_n_accepted` when the preset drafts). It is the only mode that measures what the framework actually ships: the preset's chat template, its MTP/DFlash drafter, its KV cache, its `--parallel`. Its numbers are production numbers.
- **synthetic** runs `llama-bench`, which **takes no prompt and no sampler settings at all**: `-p` is a token COUNT, not a text, and the tool never samples (`tools/llama-bench/README.md`: "the measurements with llama-bench do not include the times for tokenization and for sampling"). That is a *stronger* reproducibility guarantee than a fixed prompt at temperature 0, since the result cannot depend on what the model says. The price is that it cannot load the preset's drafter, so its `tg` reads roughly HALF of what the same preset does live with MTP on, and it ignores the mmproj, the chat template and every reasoning flag. The default sweep (prompt lengths 2048/8192/32768, depths 0/8192/32768, 128 generated) is inherited from the shell harness this tab replaced, so runs recorded before it stay comparable.

Whatever a mode cannot measure is printed under the selector and again in the saved report (`bench::caveats`), not left for the reader to remember.

#### The preflights are opposite, and the synthetic one stops the server for you

live needs llama-server **up**: it measures that process, so a run with it down is refused rather than started. synthetic needs it **down**, because llama-server holds the whole model resident and benching alongside it does not fail cleanly: the second copy spills into shared memory over PCIe and the numbers read as a backend regression rather than as a mistake. The tab therefore **stops llama-server itself** before a synthetic run, through the canonical stop path (`gui::stop_server_async_with`), never through a bare `runstate::stop`: that path also writes the conversation snapshot when `SaveStateOnShutdown` is on, and it is what keeps the footer, the tray and the run-status generation counter in step, so the next periodic tick doesn't report the deliberate stop as "llama-server is no longer running", in red. It is **not** restarted afterwards; the closing status line says so.

#### Three separator traps between an INI value and a llama-bench flag

Every one of them is silent, and each turns one benchmark into several of a configuration the preset never runs in, because a comma in llama-bench means "benchmark these as SEPARATE configurations":

| key | INI | llama-bench |
|---|---|---|
| `device` | `ROCm0,CUDA0` | `-dev ROCm0/CUDA0` |
| `tensor-split` | `54,12` | `-ts 54/12` |
| `override-tensor` | `a=ROCm0,b=CUDA0` | `-ot a=ROCm0;b=CUDA0` |

The last one is two levels deep: llama-bench splits `-ot` on `,` into configuration groups **first**, and only then on `;` into rules (`llama-bench.cpp`). All three are pinned by a unit test.

The server-wide keys shadow the preset's here exactly as they do at launch (`bench::effective`, mirroring the router's `preset.merge(base_preset)`), and `device` + `tensor_split` shadow *together*: taking the server's devices with the preset's weights would index a ratio into the wrong cards. What is deliberately not mapped, because llama-bench has no equivalent: the drafter, the mmproj, `--ctx-size` (it sizes the context as prompt + generated + depth), `--parallel`, `--cache-ram`, and every chat / reasoning / sampling key.

#### The workload runs as two invocations, not one

`bench::synthetic_sweeps` splits it into a prefill sweep (`-p <lengths> -n 0`) and a decode sweep (`-p 0 -n <gen> -d <depths>`), because llama-bench runs the **cartesian product** of its test parameters and `-d` multiplies the pp tests as well as the tg ones: the default sweep in one call is 3 lengths x 3 depths + 3 depths = 12 tests, split it is 3 + 3 = 6, for the same information at half the wall clock. The **Preview** card shows both command lines per preset, built by the same code that runs them (`bench::synthetic_argv` + `runstate::render_command_line`), the same single-source rule as the Server tab's Command Line card.

#### The live mode warms up, and groups by preset

llama-server's router loads a model on demand, so the first request for a preset pays a model load of tens of seconds; a throwaway two-word request loads it without prefilling anything worth timing. Every measured request then asks for **`cache_prompt: false`**, which is load-bearing: without it the second repetition hits the prefix cache, reports a prompt rate of tens of thousands of tokens per second, and the mean it feeds is a fiction. `timings.cache_n` is read back anyway and surfaces as a note on the row, so a build that ignored the field would be caught rather than believed. Repetitions of one preset run together rather than interleaved, because switching preset is another model load; the cost is that a card heating up over a long run charges the drift to the last preset, which the report says out loud.

#### Results: on screen and on disk, written as they land

The table fills as each test completes: `test | preset | t/s | sd | n | vs <baseline>`, plus a note column (the cache hit above; the drafter's acceptance on a decode row, reported *next to* the rate and never instead of it, since acceptance is not the metric). The baseline is the **first selected preset**, which is why the selection is an ordered list: checking appends, unchecking closes the gap, and the row's position number is shown.

#### What the report records besides the rates

Two blocks exist so that a comparison can be falsified rather than merely believed.

**Warnings, printed above the table** because a reader who stops at the numbers must already have seen them. Two are raised today. The first is a **flash-attention mismatch**: a preset that pins nothing runs at llama.cpp's `auto`, which resolves *per backend*, so a ROCm leg and a Vulkan leg of one comparison can land on different kernels with nothing in the rates to show it. The tab does not pin the value (pinning would benchmark a configuration the preset does not run, and the tab's premise is that it measures the one in use); it reads back what llama-bench resolved and says so when the legs disagree. The second is an **unknown device id**: `--list-devices` ids are not stable across driver states, so a preset can point at a card that is not there, and llama.cpp would then fail or quietly land elsewhere.

**An Environment table**, because two runs that disagree are only interpretable if you can tell whether the machine was the same machine. It records the boot time (with uptime), each display adapter's driver version and date, what each preset's device ids resolved to by NAME, and the resolved flash-attn per preset. The reason is specific: on 2026-08-24 a full day of measurements here was invalidated by Windows Update installing display drivers underneath them, and nothing in the numbers said so. The Windows Update event log is deliberately *not* scanned (see `bench\env.rs`): the pair (boot time, driver version) answers the same question when two reports are diffed, and recording facts beats recording an inference about them.

Every run writes three files to `%LOCALAPPDATA%\llama.cpp\bench\` **as it goes**, not at the end: `bench-<stamp>.jsonl` (one appended line per measurement, flushed immediately, plus llama-bench's own row kept **verbatim** beside each point: the point keeps mean, spread and count, the row carries everything else it measured, and the first version of this file kept only the aggregate, which is how the resolved flash-attention of a finished comparison turned out to be unrecoverable), `bench-<stamp>.md` (the report), and `bench-<stamp>.log` (the engine's own output, tee'd while it runs). That is not belt-and-braces: a benchmark is minutes of sustained GPU load, which is exactly when a driver reset or a bugcheck arrives, and results written only at the end are results lost on the first crash. A run that dies is a partial result, never an empty file, and **Saved runs** reloads any of them (a live point is revised as its repetitions accumulate, so the same key is appended several times and the last line wins). Stamps are UTC: this crate has no time-zone database and the stamp is also the file name, so a value that jumped an hour twice a year would break the ordering. Cancel takes effect at the next repetition or test boundary; a request already in flight is not interrupted.

#### Sweeping one key, unattended: `bench sweep`

The tab measures a configuration. A sweep measures a *question* about one ("how far does raising `spec-draft-n-max` keep paying?"), by running the same engines once per value of one presets.ini key:

```powershell
llama-cpp-config bench sweep --preset Qwen3.8-27B-UD --key spec-draft-n-max --values 2..8
llama-cpp-config bench sweep --preset Qwen3.8-27B-UD --key device --values "Vulkan1,CUDA0;ROCm0,CUDA0" --apply best
llama-cpp-config bench sweep --preset Qwen3.8-27B-UD --key ubatch-size --values 256,384,512 --mode synthetic
```

It is a CLI command and not a button because of what a leg costs: a model load plus `reps` cold prefills, so seven values is half an hour during which nothing else may touch the machine. That is a thing to start from a terminal and walk away from. Each leg writes the ordinary `bench-<stamp>.{jsonl,md,log}` trio described above, so a sweep killed at the fourth value leaves four finished, openable runs in **Saved runs**, not one truncated file; only the cross-leg digest is added, as `sweep-<stamp>.{jsonl,md}`, named so it stays *out* of that listing (which globs `bench-*.jsonl` and would fail to parse it).

Five things it has to get right, each of which is a way the naive version would lie:

- **A live leg restarts llama-server**, because the key rides the *child's* launch args: the router hands a child the preset's keys when it spawns it and nothing re-reads presets.ini afterwards. The restart is deliberately the bare stop/start pair and not what `control restart` does, since that one saves and restores the conversation snapshot: gigabytes of IO per leg to reinstate a KV cache the benchmark then declines to use (`cache_prompt: false`). The synthetic engine wants the opposite state (server **down**) and needs no restart at all, llama-bench being a fresh process that reads presets.ini as it builds its argv.
- **`;` separates the values when a value contains a comma.** `device = Vulkan1,CUDA0` and `tensor-split = 60,6` are single values holding commas, so a comma-separated list could never sweep them; a `;` cannot appear in an INI value at all (llama-server's preset reader cuts a value at the first `;` or `#`), which makes it the one safe separator. `--values` splits on `;` when it sees one, on `,` otherwise, and expands `a..b` into the inclusive range. `unset` as a value removes the key for that leg.
- **The key is typed, not spliced.** `--key` resolves through `bench::sweep::SWEEPABLE` to the real preset field, so a typo is refused up front with the list of keys that work, and every value is parsed *before* the first leg runs. Writing an unknown key into the INI instead would have llama-server merely warn about it, and the leg would then measure the unchanged configuration and report it as a data point.
- **presets.ini is edited, and says so before it is.** The original value is written into the summary's first jsonl line before any leg starts, so a machine that reboots mid-sweep still has on disk the value to put back. At the end the preset is restored (`--apply original`, the default; `best` keeps the winner, `last` the final leg) and llama-server is left as the sweep found it: a running server is restarted onto the value presets.ini now names, rather than left running one the file no longer mentions.
- **A failed leg keeps its row.** "This value does not load" is a result; a table that dropped it would read as if the value had never been tried. The sweep continues through the remaining values and exits non-zero at the end, after the summary is written.

The summary ranks on `decode` (live) or the first `tg` row (synthetic), with the ratio measured against the *first* value, and carries the sweep's own caveats on top of the engine's: legs ran in order, so a card that heats up charges the drift to the last values, and two close values deserve a re-run with the order reversed.

### Integrations tab

Three sections: **Models** (toggle presets to expose), **OpenCode** (provider status + action buttons), and **Claude Code** (env-variable snippet).

The **OpenCode** box carries three buttons: **Save** writes the toggled model list to `opencode.json` (reading Base URL and API Key from server.ini), **Revert** reloads from disk, and **Open** launches Explorer on the folder containing `opencode.json` (`~/.config/opencode/`).

The **Claude Code** snippet includes the API key from server.ini when set (otherwise `not-needed`).

The one field that is not a straight copy is each model's **`limit.context`**, and it is not the preset's `ctx-size`. opencode fills a prompt up to whatever ceiling it is handed, so the number has to be the context **one request** can actually use, which llama.cpp derives from three things at once (`integrations::effective_ctx`):

1. **`ctx-size` absent means the model's TRAINED context**, not a fixed default: `n_ctx = 0` is llama.cpp's spelling of "load it from the model" (`common_params`; `llama-context.cpp` resolves `0` to `hparams.n_ctx_train`). A 256k model loads 256k.
2. **…but the context is split across slots**: `n_ctx_seq = n_ctx / n_parallel`. So `parallel = 2` halves what a single request may ask for; the same 256k model then serves 128k per request.
3. **…unless `parallel` is omitted.** llama-server defaults it to `-1` = auto, and auto picks 4 slots **and a unified KV cache** (`tools/server/server.cpp`), under which every slot sees the whole context.

The entry used to advertise a flat `131072` whenever `ctx-size` was absent, which happened to be right for a 256k model at `parallel = 2` and wrong everywhere else. Note the trap in the "obvious" fix: publishing the trained context while a preset pins `parallel` would promise a context llama-server rejects. **Leaving `parallel` at `default` is what buys a model its full trained context per request**; pinning it is what quietly divides it.

## Control commands

The following subcommands control the llama-server process:

```powershell
llama-cpp-config control start      → start llama-server
llama-cpp-config control stop       → stop llama-server
llama-cpp-config control restart    → restart llama-server
llama-cpp-config control stop-and-close → stop llama-server and close the config GUI (Windows only)
```

The `stop-and-close` command is Windows-only and uses a named event to signal the running GUI instance to exit gracefully.

With **SaveStateOnShutdown** on, every stopping command snapshots the loaded models first and `start` restores the newest dump afterwards, so `restart` is the full round trip: it is what turns a restart on a long conversation from a multi-minute prefill into a disk read. Neither leg is ever fatal, in either direction: a snapshot that cannot be written must not block a stop the user asked for, and a server that started is started whether or not its cache came back.

## Code conventions

- Zero Clippy warnings (checked manually).
- OS portability via `#[cfg(windows)]` / `#[cfg(not(windows))]` compile-time branching, no runtime OS detection.
- No external INI crate: `ini.rs` is a hand-rolled INI reader/writer with an explicit behavioral contract in its header (case/whitespace-tolerant section lookup, inline-comment stripping matching llama-server's own preset PEG, EOL detection, atomic writes).
- GUI callbacks are `Send + 'static` closures passed to `slint::ComponentHandle::global()`.
- Every property and callback the Rust side drives lives in the `AppState` global (`ui\state.slint`), declared once. Rust uses `app.global::<AppState>().set_x()/get_x()/on_x()`; the pages reference `AppState.x` directly. Adding a UI field that Rust reads/writes is a **one-file** change in `ui\state.slint`: no per-page re-declaration or forwarding. (The tray, `AppTray`, and the View-logs window, `LogWindow`, are separate roots and keep their own pushed-in state.)
- Editable widgets that back a scalar `AppState` field bind two-way (`<=>`), never one-way (`prop: AppState.x`): a one-way binding breaks the instant the user edits the field (Slint's "overwritten bindings" rule), leaving it stale on the next preset switch / Revert. The recognized one-way cases are:
  - **Read-only displays**: the `model_info_*` texts, the integration status field, the Server tab's Command Line `TextEdit`, the Claude-env snippet `LineEdit`.
  - **Per-row model widgets inside a `for`**: the integration checkboxes (`checked: item.enabled` + a `toggled` callback), the GPU table's row checkbox + weight field, and the tensor-placement table's two row ComboBoxes + regex LineEdit. Safe ONLY because the sole in-place row write originates from the clicked/typed-into widget itself; any other change must rebuild the whole model so the delegates get fresh bindings (see `gui/integrations_tab.rs`, `gui::refresh_gpu_rows`, `gui::refresh_tensor_rows`, which is also why neither a GPU weight edit nor a regex keystroke touches another row, and so needs no rebuild: rebuilding mid-keystroke would recreate the field and drop the caret).
  - **The `labels`/`values`/`index` ComboBox split**: see `MappedComboBox`.
  - **String-valued ComboBoxes**: a `current-value` two-way binding does NOT move the selection on a model change (Slint #11970), so `EnumComboBox` drives `current-index` instead, derived from the string `value` and pushed on change like the slider below (see `ui\components.slint`).
  - **Sliders**: the std `Slider` imperatively self-assigns `value` on every drag, so NO declarative binding on it survives. `AutoSlider` flows outward via `changed(v)` and pushes external updates back in via a `changed shown` hook (see `ui\components.slint`).
  - **`SegmentedControl`**, the reactive `RadioGroup`/`Switch` replacement for a picker over a non-bool model: reads `current` purely, reports clicks via `activated`. The draft on-GPU/on-CPU control uses it for exactly this reason.
- **Numeric fields are text, never a SpinBox.** Every number in both forms (integers included) rides as a **string** on `PresetForm`/`ServerForm` and is edited in a `DefaultLineEdit` (`input_type: InputType.number` for an integer, `decimal` where a `-` or a fraction must be typable), re-parsed on the Rust side with `ini::parse_int` / `parse_float`. This is not a style preference: Slint's `SpinBoxBase` puts a `TouchArea` over the whole widget whose `scroll-event` increments/decrements and **always returns `accept`**, with no `has-focus` guard, unlike its own `ComboBoxBase`, which rejects a scroll it is not focused for. So scrolling the page with the pointer merely *passing over* a SpinBox silently edited the preset, and ate the scroll, so the page did not even move. There is no property to disable it and no way to intercept the event from outside (the `TouchArea` lives *inside* the widget), so the only fix is not to use it; a `LineEdit` has no scroll handler at all. `binding_lint`'s `no_spinbox_widgets_anywhere` fails the build if one comes back. What the SpinBox did buy (refusing an out-of-range or non-integer value) now lives in two places instead: `input-type: number` accepts ASCII digits only (i-slint-core's `accept_text_input`), so a `40.5` can't be typed into an int field, and the range checks that were `minimum`/`maximum` are re-applied in the form conversions (e.g. a port outside 1–65535 reads as unset). Sliders keep their `int`s: `slider-base` has no scroll handler.
- **Wrapping text inside a component uses `WrapText`, not `Text`.** A word-wrapped `Text` sitting DIRECTLY in a page's `SectionCard` is fine: the layout asks for its height with no width constraint, and the item then measures itself at its own real `width`. Ask the same question **across a component boundary** and it is answered from that component's plain `layout_info_v`, which Slint 1.17 evaluates at the root's *preferred* width (`default_cross_axis_constraint`), i.e. the width the text would take on ONE unwrapped line. A value that wraps to three lines is then published as one, the card around it is sized two lines short, and the rows keep painting at their real height: in v1.11.2 the last "Model info" rows painted outside the card, over the heading of the card below. `WrapText` (in `ui\components.slint`) positions the text by hand at the width it really gets and republishes its own implicit height as the component's `height`, an explicit size the layout above reads as a fixed constraint. It is what `InfoRow`'s value, both tables' warning strips, the modal description and the ⓘ tooltip use. The same trick, spelled out inline, is what the Server tab's Command Line box uses (`mirror` in `ui\server_page.slint`).
- **Glyphs.** Text drawn with the default font may only use codepoints Segoe UI actually has: the allowlist is `RENDERABLE` in `src\tests\binding_lint.rs` (every entry checked against the font's cmap, not assumed), and a `.slint` string literal using anything else fails the build. Nothing falls back: a codepoint Segoe UI lacks draws as a correctly-laid-out **empty box**, which is how the tensor table's remove button first shipped reading `✕` (U+2715, Dingbats). Valid Slint, valid UTF-8, no warning; only a human looking at the window could catch it, which is what the lint replaces. An **icon** on a `Text` need not be an allowlist entry: name the icon font at the call site, `text: "\u{E946}"; font-family: "Segoe Fluent Icons";`, as `LabeledField`'s hint glyph does (the scan skips `\u{…}` escapes to keep that path open). That escape is **not** available on a std `Button`: it has no `font-family` property, so its label is stuck with the default font and its glyph must be one Segoe UI covers (hence the tensor table's remove button reads `×`, U+00D7, and not an icon-font close glyph).

## Tests

Run it as a bare `cargo test` from anywhere in the repo: `01-configure.ps1` generates a gitignored `.cargo\config.toml` at the repo root that caps **both** of cargo's thread pools, `[build] jobs` (rustc/codegen) and `[env] RUST_TEST_THREADS` (the libtest harness), at the same 3/4-of-logical-cores policy as `config-build.psd1`'s `BuildJobs`. Both default to *all* cores otherwise, and a `--jobs` flag would only cover the invocations `02-build.ps1` makes. An explicit `RUST_TEST_THREADS` in the environment still wins (cargo does not force `[env]` over one already set), which is how you get a serial run to read an interleaved failure.

`cargo test` runs the per-module round-trip **unit** tests (INI / form / version: inline `#[cfg(test)] mod tests` in each file) plus the cross-cutting **end-to-end** tests under `src\tests\`. Unit tests stay next to the code they cover; e2e tests that span modules or need a built `AppWindow` live in `src\tests\` (an internal `#[cfg(test)]` module tree, so they reach `crate::…` directly, no lib/bin split needed; a top-level `tests\` dir would compile as a separate crate that can't see a binary crate's internals).

`src\tests\ui_bindings.rs` drives the real `AppWindow` on Slint's testing backend and asserts each editable-widget kind (LineEdit / CheckBox / the AutoSlider's Slider) still tracks a fresh model value after a simulated edit: the guard against the one-way-binding staleness class of bug. The `DefaultLineEdit` composite is exercised here via its inner widget (the `preset-ctx-size` and `server-port` integer fields, the `preset-temp` float) for the `value` leg; its `default`-checkbox leg is guarded statically by `binding_lint` (both call-site bindings, on every instance). It also pins the three Rust↔Slint mirrors that no compiler checks: `form::ALL_LAYERS` vs `Options.all_layers`, `server_form::LOG_LEVELS` vs `Options.log_levels`, and `server_cfg::LOAD_MODES` vs `Options.load_modes` (the last one twice as sharp: its entries reach `-lm` verbatim, so a drift either overwrites the user's choice with `auto` or hands llama-server a value it refuses to start on). It needs Slint element debug info, which `build.rs` emits only for non-release profiles, so run it with the default (debug) profile: `cargo test` works, `cargo test --release` cannot find the widgets. One phase there is not about bindings at all but about **geometry**: it gives the Model-info box a `Draft` value long enough to wrap and asserts the rows still end inside their card. Nothing else can see that bug (every string involved is correct; only the rows' position relative to the card gives it away), and it is what pins `WrapText`.

`src\tests\save_flow.rs` continues in the same window (the testing backend is a process-global, single-threaded platform, so all e2e phases share ui_bindings' single `#[test]`): it wires the real Models + Integrations tab callbacks via a test-only seam in `gui.rs` and exercises save → reload → reselect → re-baseline, Revert, delete's clear-selection, the rename and clone funnels, the discard-confirm guard on a dirty form (New…, and Rename…'s Rust-routed entry point), the New…-dialog's id de-conflict (a second New… on the same model must yield `<id>-2`, not overwrite), and the Integrations row-checkbox rebuild invariant (a clicked delegate's broken one-way binding must be replaced, not `set_row_data`-patched, by `refresh_integrations`). All config IO is redirected at a temp dir through the `LLAMA_CPP_CONFIG_DATA_ROOT` env var (see `paths::data_root`), so the flow never touches the user's real `%LOCALAPPDATA%\llama.cpp`, and because that env var is process-wide and never restored, unit tests elsewhere must never touch `paths::`.

Its last phase is about the **Benchmark** tab, whose selection is an ordered list of preset ids with the first entry as the baseline every ratio divides by: it pins that checking appends, that unchecking closes the gap (rather than leaving a hole or re-sorting), that the baseline follows position 1, that the preview names the preset it will request, that the caveat block follows the engine, and that an empty selection is refused by the shared validator instead of spawning a worker that would find out on its own.

`src\tests\binding_lint.rs` is a plain text scan (its own `#[test]`, no Slint backend): it walks every `ui\*.slint` and fails on a one-way `prop: AppState.…` binding on a self-assigning widget property (LineEdit/TextEdit `text`, CheckBox/Switch `checked`, SpinBox/Slider `value`, ComboBox `current-*`, and the `DefaultLineEdit` composite's `value` + `default`), honoring the sanctioned escapes above (`<=>`, `read-only: true`, non-AppState expressions, custom components). ui_bindings proves each widget *kind* behaves; this catches the *new instance* someone wires one-way. The same file also carries two scans that are not about bindings at all, because only a text scan can enforce them: the glyph allowlist, and `no_spinbox_widgets_anywhere` (a SpinBox needs no binding to silently edit itself on a scroll; see the conventions above).

===== QUESTION =====
In about 200 words of plain prose, explain what the Benchmark tab's two engines measure differently and why the framework keeps both instead of one.
