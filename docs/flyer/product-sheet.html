Private AI Framework

Large language models served on your own GPUs, in your own machine room, governed by your own administrators. Your models, your data and your prompts stay inside the building.

Private by design

  • Inference runs on hardware you own. No subscription, no external service, no account with anyone else: the software runs entirely on machines you administer.
  • The model files sit on your disks. You choose which model answers which request, and you keep every version.
  • Administration is a group on the machine. Only its members can change anything, and a visitor who has not signed in sees nothing but the sign-in page.
  • The serving endpoint takes an API key, and its request log records the caller, the model and the timing, never the prompt text or the reply.

Runs on your hardware

  • Built on llama.cpp, the open source inference engine, always a published release, never a nightly build.
  • NVIDIA CUDA, AMD ROCm/HIP and Vulkan on Linux and Windows; Apple Silicon Metal, and Vulkan through MoltenVK, on macOS.
  • Mixed and matched cards in one machine: work spread across several GPUs, weights split between them, experts of a large model kept in system memory and streamed to the card when needed.
  • Installed like any other software: .deb and .rpm on Linux, an MSI on Windows, a .pkg on macOS, with the GPU runtimes bundled, so a server needs only its driver.
  • Engine and framework are packaged apart: refresh the engine, upgrade the tools, each on its own schedule, without touching the other's configuration.

Operate it simply

  • A manager service runs several model server instances on one host, each with its own network address, its own server profile and its own set of model profiles.
  • The web admin console, behind sign-in, starts, stops and restarts an instance, adds a new instance and removes one, switches start at boot, and lists the model profiles with their state.
  • GPU distribution is a table of the detected cards, not a command line. A memory check reads the model and refuses a profile that would not fit the machine before it is accepted.
  • The same operations from a desktop configurator, and from a command line for the hosts you reach over SSH.
  • A live hardware view, one sample a second: each GPU, its memory and what spills out of it, the PCIe link, the CPU, RAM and disk, next to the server's log, followed as it grows.
  • Benchmarking built in, with the method written down and versioned, so a change you measured is a change you can show, kept in a database that lets two configurations compare.

Scale out

  • One OpenAI-compatible endpoint in front of every instance: authenticated, sending each request to the instance serving the model asked for, so the tools your teams already use keep working.
  • Every request logged for audit: who called, which model, which instance answered, the status, the latency and the token counts, never the text.
  • Hardware metrics kept as history, and log consultation across the instances, on the same console.
  • A super-manager above the nodes: one console governing many GPU servers, where an administrator of the group administers every node that joined.
  • The same packages, the same console and the same endpoint from one workstation to a rack of GPU servers.

How it fits

A GPU node runs the manager service, which starts and stops the engine instances and owns their configuration. Your administrators work in the web console; your applications call one OpenAI-compatible endpoint.
