# Build pipeline

Details for the root-level scripts and build configuration (`00-install-prerequisites.ps1` to `03-package.ps1`, `common.ps1`, `cmake-options.psd1`, `build\windows\config-build.psd1`). Read this before changing any of them. The installer side of packaging (`installer\`) is in [installer\AGENTS.md](../installer/AGENTS.md).

## Files

- `build\windows\config-build.psd1`: build-time configuration (paths, GPU targets, compiler flags). Generated by `01-configure.ps1`; lives under `build\windows\`, the per-OS directory everything Windows generates goes to (`$buildRoot` in `common.ps1`; the whole `build\` is gitignored).
- `cmake-options.psd1` (repo root, checked in): the machine-independent half of the llama.cpp configure line, one `NAME[:TYPE]=VALUE` string per cmake `-D` with its reason beside it (backends, `GGML_BACKEND_DL`, `LLAMA_BUILD_IS_DEV=OFF`, `LLAMA_BUILD_UI=ON`, `GGML_LTO=ON`, and `GGML_CUDA_FA_QUANTS`, which adds the q5_0/q5_1 KV-cache pairs to upstream's native FlashAttention kernel set so a q5 cache does not convert to f16 on every short decode step; editing that list recompiles ggml-cuda and ggml-hip in full). Read and validated by `02-build.ps1`, which appends the machine-derived half from `config-build.psd1`.
- `common.ps1` is the shared bootstrap: sets `$buildRoot` (`build\windows`), loads `$cfg` from `build\windows\config-build.psd1`, loads `$sources` (`installer\dist-sources.psd1`) + `dists.ps1` and sets `$distRoot` (the root `01-configure.ps1` recorded), adds ROCm to PATH (`HipPath\bin` plus, for the TheRock dist, `HipPath\lib\llvm\bin`, where clang lives), and is the **sole source** of the compile-time HIP vars (`HIP_DEVICE_LIB_PATH` → `lib\llvm\amdgcn\bitcode`, `HIP_PLATFORM`, `LLVM_PATH`), set per-process from `HipPath` (without `HIP_DEVICE_LIB_PATH` the HIP device compile dies with "cannot find ROCm device library"). They must NEVER be set machine-wide: the Adrenalin driver's own HIP runtime (System32's `amdhip64_7.dll` + `amd_comgr_3.dll`) reads `LLVM_PATH` at runtime, and pointing it at TheRock's LLVM breaks it (`hipMemGetInfo` returns "invalid argument", devices report 0 MiB, every llama-server child dies with 0xC0000005 mid weight-upload; `00-install-prerequisites.ps1` self-heals poisoned machines). Exposes `Enable-VsDevShell`; VS Dev Shell activation is **opt-in** (only build/package scripts call it). Dot-sourced by `02-build.ps1` and `03-package.ps1`.
- `dists.ps1` (repo root): the **SDK dist layout**, dot-sourced by `00-install-prerequisites.ps1`, `01-configure.ps1` and `common.ps1` (PS 5.1-safe and ASCII-only, because 00 runs under Windows PowerShell 5.1). Every GPU SDK the build links lives at **`<DistRoot>\<Dir>\<Version>\<DistOs>`**, e.g. `E:\TheRock\10.1.0\windows`, with `Dir` = `TheRock`, `CUDA`, `VulkanSDK` and `DistOs` = `windows` (the Linux dists of the same drive sit beside them as `<Version>\linux`). Each dist carries a marker file written only after a successful install.
  - `Resolve-DistRoot`: an explicit `-DistRoot` wins, then `LLAMA_FW_DIST_ROOT` (the same variable as on Linux), then the `DistRoot` recorded in `config-build.psd1`, then the default in `installer\dist-sources.psd1` (`E:\`). `00` and `01` take `-DistRoot`; `01` **records** the resolved root, and `02`/`03` use the recorded one.
  - `Find-Dist <Rocm|Cuda|Vulkan>`: the newest version dir (numeric `[version]` compare) that has the marker AND the files the build consumes. It is the **only** SDK lookup: no `HIP_PATH`, `CUDA_PATH` or `VULKAN_SDK`, no vendor default location. An SDK installed anywhere else is not seen.
  - **The layout is trusted, so its ACLs matter**: the build runs the compiler `Find-Dist` returns, the elevated session unpacks into it, and the active ROCm dist is on the machine PATH. So the elevated session of `00-install-prerequisites.ps1` **locks every Windows dist** (`Protect-DistDir` on each `<DistRoot>\<Dir>\<Version>\windows`, the ones it installs and the ones it finds writable by Everyone, Authenticated Users or Users): owner set to Administrators (an unelevated owner could rewrite the ACL), inheritance off, administrators and SYSTEM full control, Users read + execute, inherited by the whole tree; the report flags a dist still unlocked. **Only the `windows` directories are touched**: `<DistRoot>\<Dir>` itself, its `.downloads` and the `linux` dists beside keep the ACL their owner gave them. The elevated batch is generated code, so every path, version and URL enters it through `Lit` (a single-quoted literal escaped by PowerShell's own `CodeGeneration.EscapeSingleQuotedStringContent`, which also covers the typographic quotes the parser accepts as a closing quote), and only directories named like a version are ever locked: a directory name planted under a writable root stays data. The residue of that choice: whoever can write `<DistRoot>\<Dir>` can still create a new version directory with a marker in it, and `Find-Dist` would take it as the newest. The ROCm tarball has no published checksum: HTTPS and the expected size are all that vouch for it.
  - **OpenSSL and the tools are not on the layout**: OpenSSL is treated as a system library and stays in winget's `Program Files\OpenSSL-Win64` (`Find-OpenSSL` in `01-configure.ps1`; when `OpenSSLDir` changes, `02-build.ps1` drops the paths FindOpenSSL cached in `CMakeCache.txt`, which CMake would otherwise reuse without checking them, so the search runs again without a build-dir wipe); Visual Studio, cmake, ninja, git, node, Rust, the .NET SDK, the WiX Toolset, PowerShell 7 and sccache stay where their own installers put them.
- `00-install-prerequisites.ps1` is the idempotent toolchain bootstrapper. Safe to re-run any time. Accepts `-DistRoot`.
  - **winget packages** (PowerShell 7+ / OpenSSL / the .NET SDK 10): installed or upgraded in a single UAC-elevated session, plus the OpenSSL lib-symlink fixup.
  - **WiX Toolset** (the MSI): a .NET global tool **pinned** to `installer\wix-toolset.psd1` (7.0.1; installed, or moved to the pin with `dotnet tool update --allow-downgrade`), plus its extensions (`WixToolset.UI.wixext`, `WixToolset.Util.wixext`) at the same version, user scope, after the elevated batch. WiX v7 needs `wix eula accept wix7` once per user: the script never runs it, the report names it as the missing step (and the extensions are added on the next run). The report's `WiX Toolset` row shows the version.
  - **sccache from its GitHub release**, NOT winget (the manifest lags upstream by days), user scope, outside the elevated session: the newest `x86_64`/`aarch64` `pc-windows-msvc` zip from `/releases/latest`, checked against the API's sha256 `digest` (fallback: the `.sha256` sidecar), `sccache.exe` staged and MOVED over `%LOCALAPPDATA%\Programs\sccache\sccache.exe` (an exe in use stays intact and the run says so), that dir appended to the user PATH through the raw registry plus a `WM_SETTINGCHANGE` broadcast, and a leftover winget `Mozilla.sccache` uninstalled once the release copy works. Tracks LATEST (a misbehaving cache costs a cold build, not a broken runtime). The directory is **versionless on purpose**: `02-build.ps1` passes that path to CMake as the compiler launcher, and a moving launcher path changes every compile command, so ninja would re-run all of them after each upgrade.
  - **llama.cpp**: `git fetch`es `$cfg.LlamaCppDir` when cloned and compares the checked-out tag against the newest **release** tag reachable from `origin/master`, by the same selection `02-build.ps1` makes. No `git pull`: the clone sits on a detached tag; the checkout is `02-build.ps1`'s job.
  - **Nothing is pinned**: ROCm, the CUDA Toolkit and the Vulkan SDK all converge to the **newest stable release** their vendor publishes, on every run. `installer\dist-sources.psd1` says where each is looked up (no versions). A source that cannot be reached keeps what is installed and the report says so; nothing is ever downgraded or deleted.
  - **ROCm/HIP installs from AMD's TheRock dist tarball** (the classic HIP SDK installer is discontinued): the newest stable is found by **scanning AMD's tarball indexes** (the sources' `Indexes`; strict `X.Y.Z` match so `-tests-` builds and dated nightlies are never taken; the URL is found, not composed, because the host depends on the version and a wrong one is a 403 that reads like "not published"). An install that does not parse as a version (`unknown`, a hand-installed nightly) is replaced; a newer one is never downgraded. The **multiarch** Windows tarball (kernels for every gfx family) is downloaded to `<DistRoot>\TheRock\.downloads` and extracted **into its own version directory** (`<DistRoot>\TheRock\<version>\windows`) inside the elevated session, which also sets the machine env: `HIP_PATH` **only**, naming the ACTIVE version (the one machine-wide variable of the layout: a llama-server run from the build tree finds the runtime through it; the installed one carries its own), and deletes machine-wide copies of the compile-time vars (see `common.ps1`). Dists sit **side by side**: a version already in the layout is reached by moving `HIP_PATH`, no download. A dist **outside** the layout (a `HIP_PATH` on `C:\TheRock\<version>`, what earlier versions of this script installed) is not adopted and not touched: the run converges to the newest stable inside the layout and the report names the old directory. ~25 GB per dist: the report lists inactive ones and never deletes them (a working rollback; the user's call).
  - The same session appends `bin` + `lib\llvm\bin` to the machine PATH via the raw registry (`setx /M` truncates PATH at 1024 chars; `[Environment]::SetEnvironmentVariable` downgrades `REG_EXPAND_SZ` to `REG_SZ`) and **prunes every other ROCm entry** (anything else under `<DistRoot>\TheRock\`, plus the dist `HIP_PATH` named before the run, wherever it sits): `amdhip64_*.dll` reachable from two PATH dirs is an ambiguous load order, a classic silent-crash cause. The installed version lives in a `.therock-version` marker written only after a successful extract (the env leg is gated on it). A wipe + re-extract only ever clears an **incomplete tree of the same version**, so llama-server must be stopped for exactly one operation (a re-extract over an existing version dir); the script checks and skips it, and installs a NEW version while it runs.
  - **Report**: warns on a leftover legacy HIP SDK under `Program Files\AMD\ROCm`, a shadowing user-level `HIP_PATH`, any persistent-scope `LLVM_PATH`/`HIP_DEVICE_LIB_PATH`/`HIP_PLATFORM`, and `amdhip64_*.dll` in more than one PATH dir. That last check **sets the installed framework's `bin\` aside** (found through `HKLM\Software\llama.cpp` `InstallDir`): it carries the bundled runtime of the dist it was built against on purpose, a self-contained set an exe resolves from its own directory before PATH, and PATH never decides `amdhip64_7.dll` for another exe. Shows before→after versions and rebuild recommendations (`02-build.ps1` / `03-package.ps1` for a newer llama.cpp release or a new ROCm/CUDA/Vulkan, preceded by `01-configure.ps1` when the ROCm dist changed or the config names another dist root: `DistRoot` and `HipPath` are recorded in the config, CUDA and Vulkan are found by `02-build.ps1` itself; the command carries `-DistRoot` when 01 would not resolve the same root by itself). A new ROCm dist costs a full rebuild (new compiler path) and re-derives `GpuTargets`; a dist whose clang resource major is below 24 is refused (see "ROCm clang 24 is the floor" below).
  - **CUDA Toolkit**: the newest release is the highest `redistrib_<X.Y.Z>.json` on NVIDIA's redist index; the installed one is `Find-Dist 'Cuda'` (the version is the directory name: the assembled tree has no `version.json`). An older or missing toolkit is **assembled from NVIDIA's redist archives**, as on Linux, not installed by NVIDIA's installer (which cannot be given a prefix per version and pulls in the display driver unless told otherwise): the `windows-x86_64` entry of each of the sources' `Components` in that manifest, downloaded to `<DistRoot>\CUDA\.downloads\<X.Y.Z>`, **sha256-verified** (each archive is held open with share = Read only from before the hash until `tar` is done, as the signed installers are, because `.downloads` may be writable by other accounts and the session is elevated), and unpacked with `tar.exe --strip-components=1` so the `<name>-archive\{bin,include,lib,nvvm}` trees merge into one toolkit prefix, `<DistRoot>\CUDA\<X.Y.Z>\windows` (`bin\nvcc.exe`, import libs in `lib\x64`, runtime DLLs in `bin\x64`). **Nothing is registered machine-wide**: no `CUDA_PATH`, no PATH entry, no driver touched. The `.cuda-version` marker is written once every component is in; a tree without it is cleared and redone, and a re-run reuses the downloads that finished. A new release lands beside the old one (kept, reported, never deleted).
  - **Vulkan SDK**: the newest version from LunarG's `sdk/latest/windows.txt`, installed from `vulkansdk-windows-X64-<version>.exe` (size-verified, downloaded to `<DistRoot>\VulkanSDK\.downloads`) headless (`--root <DistRoot>\VulkanSDK\<version>\windows --accept-licenses --default-answer --confirm-command install`); the `.vulkan-version` marker is written when the installer left `Lib\vulkan-1.lib` and `Bin\glslc.exe`. LunarG's installer still sets a machine `VULKAN_SDK` and PATH entry of its own; the build reads neither.
  - The elevated batch goes through a **temporary file**, not `-EncodedCommand`: base64 of UTF-16 inflates it ~2.7x and with the ROCm, CUDA and Vulkan legs together it no longer fits Windows' 32,767-character command line. TEMP is user-writable, so the file is **never run by path**: the elevated loader reads its bytes once, compares their SHA256 with the hash on its own command line, and runs the verified bytes from memory (a swap after the write exits 3). Every downloaded installer must also pass **Authenticode, signed by its vendor** (the sources' `Signer`, matched against the certificate's `O=`) before it runs elevated; the file is held open with share = Read only from before the check until the installer exits, so what was verified is what runs. Reads `build\windows\config-build.psd1` directly (does **not** dot-source `common.ps1`) so it works on a fresh machine before `01-configure.ps1` has run.
- `01-configure.ps1`: auto-detects paths, activates VS Dev Shell for tool discovery, verifies tools, creates `build\windows\` if missing, writes `build\windows\config-build.psd1` **and a generated `.cargo\config.toml`** (see Conventions). Accepts `-LlamaCppDir` (defaults to `$PSScriptRoot\build\windows\llama.cpp`) and **`-DistRoot`** (see `dists.ps1` above; the resolved root is written as `DistRoot`, so it is given once). `HipPath` is `Find-Dist 'Rocm'` under that root, `OpenSSLDir` is `Find-OpenSSL` (winget's `Program Files\OpenSSL-Win64`, outside the layout); the CUDA Toolkit and the Vulkan SDK are shown but not recorded. `WixExe` is the WiX Toolset's `wix.exe` (PATH, else `%USERPROFILE%\.dotnet\tools`), its version checked against `installer\wix-toolset.psd1`; missing or off-pin is a warning, not a gap, since only `03` needs it. Writes GPU targets (**derived from the installed ROCm dist**; see Conventions), build type (Release), compiler (the **full path** to the detected clang: `Find-Clang` takes `HipPath\lib\llvm\bin\clang.exe` BEFORE searching PATH, which may still name another dist; a bare `clang` fails at cmake time in consoles whose PATH predates the machine-env change), **linker** (`lld-link.exe` from the same LLVM tree, blank when the compiler is not LLVM), and build jobs. No `-march`. `Find-Tool` falls back to `HipPath\bin` and `HipPath\lib\llvm\bin`.
- `02-build.ps1`: dot-sources `common.ps1` + calls `Enable-VsDevShell`. Builds **both** llama.cpp (CMake + Ninja into `build\windows\llama.cpp-cmake\`) **and** `llama-cpp-config` (cargo build --release with `CARGO_TARGET_DIR=build\windows\cargo-target`, set process-scope from `$cargoTargetDir` in `common.ps1`; the binary stays in `build\windows\cargo-target\release\`, staged from there by `03-package.ps1`). Uses sccache if available for the C++ and HIP compiles.
  - **Release tag selection**: auto-clones llama.cpp into `build\windows\llama.cpp\` (or fetches) and **checks out its latest RELEASE tag**, not master HEAD. Upstream tags every master merge with a lightweight `bNNNN` nightly and a release additionally with an annotated `vX.Y.Z`; **nightlies are ignored even when newer**. `git describe --abbrev=0` would return the nearest nightly, so the selection is the highest `^v\d+\.\d+\.\d+$` among `git tag --merged origin/master --sort=-v:refname` (`--merged` for reachability, `-v:refname` so v0.10.0 outranks v0.2.0, the strict regex so a `-rc` pre-release is not mistaken for a release). No release tag reachable = hard failure. Hence `LLAMA_BUILD_IS_DEV=OFF` is unconditional.
  - **Configure line split in two files**: `cmake-options.psd1` holds what is built (validated by regex before cmake sees it); `02-build.ps1` adds everything machine-derived (compiler/linker/targets, OpenSSL root, Vulkan SDK, the HIP header workaround, sccache) and owns the `-U` unsets. These are CACHE entries: deleting a line does not restore cmake's default on an existing build dir, so retire an option by setting it explicitly.
  - **`LLAMA_BUILD_UI=ON` is pinned**: upstream's default is OFF, under which the chat UI is DOWNLOADED from a HuggingFace bucket at configure time and, when that fails, the build proceeds with NO UI on only a cmake warning. `02-build.ps1` therefore **refuses to finish a build whose UI did not get embedded** (`tools\ui\dist\index.html` under the build dir, or a `dist` in the source tree) and reports which path produced it (the download path leaves a `.ui-stamp`).
  - **ROCm clang 24 is the floor**: up to AMD clang 23 the stock `__clang_hip_runtime_wrapper.h` included `<cmath>` before the HIP device math headers, so MSVC's `_CLANG_BUILTIN2` constexpr overloads clashed with the device declarations; the repo carried a patched wrapper for it (`patches\hip\`, now only in git history). Clang 24 (TheRock ROCm 10.1.0) **fixed it upstream** (llvm/llvm-project#201563), so the stock header is used and nothing is force-included. The clang resource major is read from the dist (`lib\llvm\lib\clang\<N>`, legacy `lib\clang\<N>`) and a major below 24 **fails fast** (`02-build.ps1`, `tools\pcie-bench\build.ps1`).
  - **Out-of-tree llama.cpp patches** (`patches\llama.cpp\*.patch`): REVERTED before the fetch/checkout (a tag bump touching a patched file would abort the checkout), re-applied onto the fresh tag; what the reverts leave behind (an older revision of a changed patch, a hand edit) is stashed in the clone, never discarded. Both legs probe with `git apply --check`, so a re-run is a no-op, and a patch that applies in NEITHER direction fails the build rather than being skipped. Every patch is **provisional**: when upstream lands the same support it stops applying and is DELETED, not rebased (provenance and the log line proving it live: `patches\llama.cpp\README.md`).
  - **Compiler change**: wipes `build\windows\llama.cpp-cmake\` when `CMakeCache.txt` pins a different compiler path than the config.
  - **Vulkan SDK resolved from the layout** (`Find-Dist 'Vulkan'` on `$distRoot`: highest `[version]` dir with the marker, `Lib\vulkan-1.lib` and `Bin\glslc.exe`): each version has its own dir, while a stale console `VULKAN_SDK` and the `Vulkan_INCLUDE_DIR`/`Vulkan_LIBRARY`/`Vulkan_GLSLC_EXECUTABLE`/`Vulkan_GLSLANG_VALIDATOR_EXECUTABLE` cache entries (reused without existence checks) still point at the previous one. The resolved SDK is exported as `VULKAN_SDK` and the four paths passed as explicit `-D`s, deliberately not a build-dir wipe (that would cost a full CUDA + HIP rebuild).
  - **CUDA toolkit follows the newest installed version** (`Find-Dist 'Cuda'` on `$distRoot`: highest `X.Y.Z` with the marker, `bin\nvcc.exe`, `lib\x64\cudart_static.lib` and `cublas.lib`; by version and never by `CUDA_PATH`, which names whatever NVIDIA's installer set up last on a machine that has one), passed as `-DCMAKE_CUDA_COMPILER` and exported as `CUDA_PATH`. A toolkit upgrade leaves the old one working, so nothing would fail otherwise. A changed `CMAKE_CUDA_COMPILER` alone makes CMake **delete the whole cache plus top-level `CMakeFiles`**, so on a change the script removes only the CUDA identification files (`CMakeCUDACompiler.cmake`, `CMakeDetermineCompilerABI_CUDA.bin`, `CompilerIdCUDA\`) and `-U`s the toolkit entries (`CUDA_*`, `CUDAToolkit_*`, `_cmake_CUDAToolkit_*`, `FIND_PACKAGE_MESSAGE_DETAILS_CUDAToolkit`; the `GGML_CUDA_*` knobs survive): only CUDA objects recompile. CUDA 13.4+ keeps CUPTI's import libs in `extras\CUPTI\lib\x64`, where CMake's FindCUDAToolkit does not look, so the four `CUDA_cupti`/`nvperf_*`/`pcsamplingutil` entries may resolve to an older toolkit; ggml links none of them.
- `03-package.ps1`: dot-sources `common.ps1` + calls `Enable-VsDevShell` (cmake --install needs the VS env). Stages from `build\windows\llama.cpp-cmake\` + `build\windows\cargo-target\release\` into `build\windows\staging\`, then builds the MSI (WiX, `installer\llama-cpp-framework.wxs`) into `.\dist\` and validates it (ICE). The WiX check (tool found, EULA accepted, extensions present, added when missing) runs FIRST, before staging. `-Wix <wix.exe>` builds with another WiX than the recorded `WixExe` (a non-pinned version with a warning; 6.0.2 builds the same `.wxs` without the v7 EULA). On the 2.8 GB staging: a 1.16 GiB MSI in 2 to 3.5 minutes of `wix build` plus ~40 s of validation (details in [installer\AGENTS.md](../installer/AGENTS.md)).
  - **Prunes llama.cpp's own `test*.exe`** right after `cmake --install` (cmake stages every executable with an `install()` rule; count from the staging tree, not the build dir), and the `include\` headers, which never shipped. The installer can put `bin\` on the **system PATH**, so shipping them would drop generically-named `test-*` commands into every shell. Pruned in staging rather than filtered in the `.wxs`, so what is staged is exactly what ships: the `.wxs` harvests `bin\`, `lib\` and `.kpack\` whole, and `llama-cpp-config.exe` + `llama.ico` are staged into `bin\` too, so an administrative image (`msiexec /a`) compares 1:1 with the staging tree.
  - **Stages the OpenSSL runtime DLLs** into `bin\`: they are NORMAL imports (`libcrypto-N-x64.dll`/`libssl-N-x64.dll`; without them the server fails at load on a machine with no OpenSSL). Names are scanned from the staged binaries' import tables (plain ASCII in the PE) since the ABI number moves, and copied from `$cfg.OpenSSLDir\bin` (app dir wins the DLL search order). **Every** staged `.exe` and `.dll` is scanned, never a name pattern: llama.cpp tools are thin launchers plus impl DLLs (`llama-server.exe` imports `llama-server-impl.dll`, which carries the OpenSSL imports, alongside `llama-common.dll`), so a name-based scan breaks on the next rename. Don't copy `*.dll` wholesale: most of `OpenSSLDir\bin` is providers (`legacy`, `p_test`, `p_ossltest`, `p_minimal`). The scan reads in 4 MB **chunks** with a 64-byte overlap (`ggml-hip.dll` is ~900 MB; `ReadAllBytes` + `ASCII.GetString` would cost ~2.8 GB RAM) and gates the regex behind an ordinal `IndexOf` (~15x faster).
  - **Bundles the GPU runtimes**, as `03-package.sh` does: the import closure of the staged binaries, restricted to what resolves inside the ROCm dist (`HipPath\bin`), the CUDA dist (`Find-Dist 'Cuda'`, `bin\x64`) or the Vulkan SDK (`Bin\`), copied flat into `bin\`; plus, by name, the dist's `amd_comgr*.dll` and the ROCm kernel stores (`bin\rocblas\library`, `bin\hipblaslt\library`, `.kpack\blas_lib_*.kpack` beside `bin\`) for the architectures in `GpuTargets` only. About 1.6 GB on top of the binaries. **System libraries stay external**: the VC++ redist x64 (`libomp140.x86_64.dll` included), the GPU drivers, and `vulkan-1.dll`, which ships with any GPU driver and is not in the SDK as a DLL; cudart is static. Details and the load-order reasons: [installer\AGENTS.md](../installer/AGENTS.md).
  - `-KeepStaging` leaves `build\windows\staging\` in place for inspection.
  - **Package name**: `llama-cpp-framework-v<frameworkVersion>-<llamaBuild>-<arch>.msi`, e.g. `llama-cpp-framework-v2.2.0-v0.7.0-x64.msi`: frameworkVersion = `llama-cpp-config\Cargo.toml` `[package]` version (configurator and framework are versioned together), llamaBuild = `git describe --tags` of `$cfg.LlamaCppDir` (prefers the annotated release tag over the lightweight nightly on the same commit), arch = `x64`/`arm64`. The `^v\d+\.\d+\.\d+$` check decides whether to trust the describe: anything else (`v0.2.0-11-g…`, empty) falls back to `b<rev-list --count>`, deliberately shaped so a non-release package cannot pass for one.

## Conventions

- sccache is auto-detected by `02-build.ps1`: `%LOCALAPPDATA%\Programs\sccache\sccache.exe` first (where `00-install-prerequisites.ps1` installs it; fixed path so the launcher in every compile command does not move, found even from a console with a stale PATH), then PATH; cache in `build\windows\.sccache\`. Uses `SCCACHE_MAX_FRAME_LENGTH=104857600` for large GPU objects and `SCCACHE_CLIENT_SIDE=1` (0.17+ client-side mode, no per-compile daemon round-trip; older versions ignore it). **The build has its own daemon** on `SCCACHE_SERVER_PORT=4227` (not the default 4226), stopped and started explicitly before configuring, then its stats printed and the daemon stopped once the build ends, failed builds included (a `finally` in `02-build.ps1`; in `02-build.sh` right after the build, or from the `EXIT` trap when the configure or the build fails): the daemon's cache dir and settings win over the client's environment, `SCCACHE_CLIENT_SIDE` included, so a daemon some other process left on the default port would otherwise serve the whole build from its own cache, silently. **nvcc is intentionally NOT wrapped**: for the PTX-only `compute_90` gencode (ggml's default `90-virtual`) nvcc runs `ptxas -arch=compute_90` with no `-o`, sccache treats it as cacheable and every `.cu` dies with `Missing "cubin" file output`. Fix pending sccache PR #2809; until a release carries it, host C/CXX (clang) caching only. Do not drop `90-virtual` to dodge it: that changes what the shipped `ggml-cuda.dll` covers. **HIP is cached on both OSes**: on Windows the ggml-hip sources compile as CXX (no `enable_language(HIP)`), so the CXX launcher wraps them and sccache caches the `-x hip` compile as its HIP language (checked on 0.18.0: a repeat compile of one ggml-cuda object is a `Cache hits (HIP)` hit, 0 s against 27 s cold); `02-build.sh` gets the same with `CMAKE_HIP_COMPILER_LAUNCHER`. Without sccache both scripts `-U` every launcher (C, CXX, HIP, CUDA), so a cache configured while sccache was installed does not keep calling a missing exe.
- **No global `-march`, and LTO only as far as `GGML_LTO` reaches.** A global `-march` leaks into every ggml-cpu variant, so the fallback tiers (`ggml-cpu-x64.dll`, `ggml-cpu-sse42.dll`) would carry AVX2 code while ggml's runtime score (`ggml-cpu/arch/x86/cpu-feats.cpp`, keyed on per-variant `GGML_AVX2`-style macros) still picks them on pre-AVX2 CPUs. The variants carry their own `-m` flags; everything else builds at the compiler's default baseline, as upstream's release binaries do (`GGML_NATIVE=OFF`). The `sse42` variant compiles the SSSE3 branch of `ggml-cpu/arch/x86/quants.c`, whose `_mm_prefetch` calls pass a block pointer where clang's MSVC-compatible `xmmintrin.h` wants `const char *`, a default ERROR under AMD clang 23: hence `-Wno-error=incompatible-pointer-types` in `CMAKE_C_FLAGS`. `GGML_LTO=ON` sets `CMAKE_INTERPROCEDURAL_OPTIMIZATION` in `ggml/src` scope only: `-flto=thin` on ggml-base, every ggml-cpu variant, ggml-vulkan and the host half of ggml-hip, linked by lld-link; ggml-cuda (nvcc) and llama/common/llama-server are untouched. A global `CMAKE_INTERPROCEDURAL_OPTIMIZATION=ON` would also reach the CUDA target, so it is not passed. lld-link's ThinLTO backend already defaults to one thread per physical core, so no thread flag. Linker-flag traps: the three `CMAKE_*_LINKER_FLAGS` are language-agnostic (a `-Wl,...` also reaches the CUDA DLL, linked by lld-link DIRECTLY through `cmake -E vs_link_dll`, which warns `ignoring unknown argument`) and are CACHE entries (an experiment outlives itself), so `02-build.ps1` `-U`s all three on every configure and sets none. A per-language link option (e.g. a ThinLTO cache, `/lldltocache:<dir>`) needs a `$<LINK_LANGUAGE:CXX>` guard through a `CMAKE_PROJECT_INCLUDE` file. Never reconfigure or run ninja in `build\windows\llama.cpp-cmake\` while a build is running there: ninja holds `.ninja_deps` open, so the generate step fails with `failed recompaction: Permission denied` AFTER rewriting `build.ninja` and the cache, and the two disagree until the next configure.
- HIP GPU targets (`config-build.psd1` `GpuTargets` → `-DGPU_TARGETS`) are **derived by `01-configure.ps1`** (`Get-GpuTargets`), never hand-maintained: a ROCm dist bump only needs a re-run of `01-configure.ps1`. Derivation: the archs the installed dist ships Windows BLAS kernels for (`.kpack\blas_lib_gfx*.kpack` under `HIP_PATH`; legacy-SDK fallback `bin\rocblas\library\TensileLibrary_lazy_gfx*.dat`), **minus** CDNA/Vega `gfx9xx` (no Windows driver; gfx906 kernels dropped), **plus** the Ryzen iGPU safety set (`gfx1035/1036/1103/1152/1153`), unioned in even if a future dist drops their kernels: the driver's HIP runtime fails kernel-module load on *every* visible device when one has no matching code object ("device kernel image is invalid"). A static snapshot is used only when no dist is present. Currently 20 archs (RDNA1 `gfx1010-1012`, RDNA2 `gfx1030-1036`, RDNA3 `gfx1100-1103`, RDNA3.5 `gfx1150-1153`, RDNA4 `gfx1200/1201`), ~56 MiB of `ggml-hip.dll` each; hand-prune only if size matters, never the iGPU set. ROCm's `hip-config-amd.cmake` derives `--offload-arch` from **`GPU_BUILD_TARGETS`**, seeded from `GPU_TARGETS` via `set(... CACHE ...)` (a no-op once cached), so `02-build.ps1` passes `-UGPU_BUILD_TARGETS` every configure.
- **A ROCm dist carries TWO kernel stores, and the recommended setting uses the one that looks legacy.** `.kpack\blas_lib_gfx*.kpack` (~41 MiB per arch) is **hipBLASLt**'s; `bin\rocblas\library\` (~700 MiB) is **Tensile**'s, found relative to `rocblas.dll`. `ROCBLAS_USE_HIPBLASLT` decides which is read; with it `off` on gfx1201, everything runs **out of `bin\rocblas\library`**. The `.kpack` scan above only ENUMERATES archs. Deleting `bin\rocblas` to trim a dist breaks that configuration LATE: the backend loads and enumerates, then the first matmul dies with `Could not initialize Tensile host`. Within `bin\rocblas\library` about half is `gfx908`/`gfx90a` (never built): the CDNA half is the safe and only worthwhile thing to delete.
- **lld links both halves of the build, by two different mechanisms.** *C++*: `01-configure.ps1` looks for `lld-link.exe` **next to the clang it resolved** and writes it as `config-build.psd1` `Linker`; `02-build.ps1` passes it as `-DCMAKE_LINKER` when non-empty. A bare-name `clang` fallback or an MSVC toolchain leaves it blank and CMake keeps `link.exe`; blank (or absent from an older config, hence a truthiness check, not `Test-Path`) is supported. It mostly *pins* what CMake does anyway, so the fallback to `link.exe` cannot happen silently. *Rust*: unconditional, via the generated `.cargo\config.toml` (`[target.x86_64-pc-windows-msvc] linker = "rust-lld.exe"`). The bare name is deliberate: `rust-lld` ships **inside** the toolchain (`<sysroot>\lib\rustlib\<target>\bin`, not on PATH), always present and version-matched to rustc, where an external `lld-link.exe` would borrow whatever LLVM is installed. To tell which linker produced a binary, look for the **Rich header** MSVC's `link.exe` stamps into the PE's DOS stub; lld does not.
  - The Rust half carries `rustflags = ["-Clink-arg=/force:multiple"]`, and it is **load-bearing**: Skia links ICU *statically* (`skunicode_icu.lib`) while the `windows` crate imports the *system* one (`icuuc.dll`), so every `uloc_*` is defined twice; `link.exe` swallows that (LNK4006), the flag makes lld do the same. It bites **only the test binary** (the second ICU arrives via the dev-dependency `i-slint-backend-testing` → `i-slint-common` → `fontique` → `windows`): without it `cargo test` does not link. Accepted cost: rustflags are not per-profile, so a real duplicate symbol in the shipped binary would go uncaught. Re-test and drop it if the two ICUs stop colliding.
- Build parallelism (`config-build.psd1` `BuildJobs`, written by `01-configure.ps1`) defaults to **3/4 of logical cores, clamped to at most `cores - 1`** (CMake/Ninja `-j` and `cargo build --jobs`), so a core stays free during long CUDA/HIP compiles; the clamp is kept so the reservation survives a later retune. A 1-core machine gets 1 job. `BuildJobs = 0` means "use all cores". `-j` bounds compile PROCESSES, not CPU (no affinity; nvcc and threaded lld links can exceed it). The same number goes into the generated, gitignored **`.cargo\config.toml`** at the repo root, so bare `cargo build`/`cargo test` from a shell or IDE are capped too: `[build] jobs` for rustc/codegen and `[env] RUST_TEST_THREADS` for the libtest harness (an existing environment value still wins, so `RUST_TEST_THREADS=1 cargo test` works for serial debugging).

## Linux

`00-install-prerequisites.sh`, `01-configure.sh`, `02-build.sh`, `03-package.sh`, `common.sh` and `installer/dist-sources.sh` are the bash counterpart of scripts 00 to 03 (Debian/Ubuntu). 00 to 02 end at a working build tree holding llama.cpp and `llama-cpp-config`; 03 packages it as a `.deb` and an `.rpm` (the MSI stays Windows-only). Everything above applies unless this section says otherwise.

- **Dist layout: `<Root>/<Version>/linux`.** `/mnt/data` is the default dist root, the counterpart of the Windows `DistRoot`, and it is configurable the same way: `--dist-root <path>` on `00-install-prerequisites.sh` and `01-configure.sh` wins, then `LLAMA_FW_DIST_ROOT`, then the `CFG_DIST_ROOT` that `01-configure.sh` **recorded** in `config-build.sh`, then the default in `installer/dist-sources.sh`; `02-build.sh` and `03-package.sh` use the recorded one (`load_build_config` calls `use_dist_root`, which re-sources `dist-sources.sh` on the new base). Under it sit the roots `TheRock`, `CUDA` and `VulkanSDK`, e.g. `/mnt/data/TheRock/10.1.0/linux`. The OS level exists because the drive is shared with the Windows side of the same machine: a Windows dist of the same version sits beside it as `<Version>/windows`. `installer/dist-sources.sh` holds the roots and the sources, no versions. Each dist carries a marker file written only after a successful extract, and `common.sh`'s `find_rocm` / `find_cuda` / `find_vulkan` take the highest version that has the marker AND the files the build consumes.
- **Nothing is set machine-wide** (no profile script, no `/etc/environment`): the scripts resolve the newest complete dist under each root on every run. `common.sh` `load_build_config` sets `HIP_PATH`, `ROCM_PATH` (what llama.cpp's ggml-hip CMakeLists reads; its fallbacks are `/opt/rocm` and `/usr`), `HIP_DEVICE_LIB_PATH` and `PATH` for the build process only.
- **`build/linux/` holds everything Linux generates** (`config-build.sh`, the `llama.cpp` clone, `llama.cpp-cmake/`, `.sccache/`, `cargo-target/`), never the Windows artifacts under `build/windows/`: a shared clone would mix line endings, patch state and the UI's platform-specific `node_modules`. `.cargo/config.toml` is not written (the one the Windows side generated is read by cargo and is harmless: its linker settings are scoped to the msvc target).
- `00-install-prerequisites.sh`: one leg needs root, the **apt packages** (`git g++ make cmake ninja-build pkg-config libssl-dev nodejs npm curl jq xz-utils ca-certificates libfontconfig-dev`, the last one for the configurator's Skia renderer), through `sudo` and only when one is missing. `g++` is required although the host compiler is the dist's clang: clang takes libstdc++, the start files and libgcc from the distro GCC, and nvcc drives g++ as its host compiler. The rest is user scope:
  - **sccache**: the `unknown-linux-musl` tarball of the latest GitHub release, sha256 from the API `digest`, moved over `~/.local/bin/sccache` (versionless path, same reason as on Windows).
  - **Rust**: `rustup` (`--profile minimal`, stable, `--no-modify-path`) when no `cargo` is found; an existing toolchain is never updated (a rustc upgrade recompiles the whole dependency tree).
  - **ROCm**: `therock-dist-linux-multiarch-<X.Y.Z>.tar.gz`, found in the same indexes with the same strict match (~9.5 GB download, ~22 GB extracted). The indexes publish no checksum; a truncated download fails in the extract.
  - **NCCL** (optional, `--skip nccl`): NVIDIA keeps it out of the toolkit redist and publishes no archive index for it, so it comes from the **PyPI wheel** `nvidia-nccl-cu<major>`, the major being that of the installed toolkit (the leg runs after CUDA): version and sha256 from PyPI's JSON API, no root, no distro match. Only the wheel's `nvidia/nccl/{lib,include}` is kept, as `<Root>/NCCL/<X.Y.Z>/linux`, with `libnccl.so` aliased to the soname `libnccl.so.2` (the wheel carries no link name). The marker records the CUDA major, and a dist built for another major does not count as installed. A failed install is reported, not a gap: the build goes on without it. ~290 MB download, ~345 MB of `libnccl.so.2`.
  - **CUDA**: assembled from NVIDIA's **redist archives** (the `linux-x86_64` entries of the newest `redistrib_<X.Y.Z>.json`, each sha256-verified), not the `.run` installer or the apt repo: no root, no driver touched, any prefix. The `CUDA_COMPONENTS` are merged into one prefix by stripping each archive's top directory, which yields a regular toolkit tree except that the libraries land in `lib/`: nvcc links its own runtime (`cudart_static`, `cudadevrt`) from `<toolkit>/lib64`, so the install adds a `lib64 -> lib` symlink, and the completeness test goes through it. The version directory is the full `X.Y.Z` of the manifest.
  - **Vulkan SDK**: `vulkansdk-linux-x86_64-<version>.tar.xz`, sha256 from LunarG's `files.json` (no checksum = no install). The SDK proper, what `VULKAN_SDK` names, is `<Version>/linux/x86_64`. Since 1.4.3xx the loader lives in `lib/VulkanLoader/lib`, not `lib/`: `vulkan_loader` in `common.sh` copes with both.
  - Downloads go to `<Root>/.downloads` and **resume**; a finished archive is deleted after its install. A version dir without its marker is an interrupted install of that same version and is cleared and redone. `--skip apt,sccache,rust,rocm,cuda,vulkan` skips legs.
- `01-configure.sh` writes `build/linux/config-build.sh` (`CFG_*` shell variables, single-quoted), `CFG_DIST_ROOT` included. Accepts `--llama-cpp-dir` and `--dist-root`. Compiler: the dist's `lib/llvm/bin/clang` + `clang++` by full path, then a system clang, then GCC. `CFG_LINKER_TYPE=LLD` when `ld.lld` sits next to the clang. `CFG_CUDA_HOST_COMPILER` is the distro `g++`. GPU targets by the same derivation as Windows (`.kpack/blas_lib_gfx*.kpack`, fallback `lib/rocblas/library`); the gfx9xx drop is a **parity choice** on Linux, where the MI cards do have a driver. The Linux dist additionally ships `gfx1250` (the `gfx125X-dcgpu` family), dropped too, and not optionally: llama.cpp v0.6.0's `mma.cuh` uses the gfx12 WMMA builtins, which that arch lacks, so one such target fails the whole ggml-hip compile. That leaves the same 20 archs as Windows.
- `02-build.sh`:
  - **`cmake-options.psd1` is shared** and read with `sed`: every `Defines` entry must sit alone on its line as `'NAME[:TYPE]=VALUE'`, and a quoted line of that block with another shape fails the build.
  - **HIP is its own CMake language on Linux** (`enable_language(HIP)`; on Windows the sources compile as CXX), so `CMAKE_HIP_COMPILER` (the dist's `clang++`) and `CMAKE_HIP_COMPILER_ROCM_ROOT` are passed explicitly. The MSVC `<cmath>` header workaround does not exist here. **sccache wraps HIP too** (`CMAKE_HIP_COMPILER_LAUNCHER`, beside C and CXX; nvcc stays unwrapped as on Windows): the HIP compile is clang with `-x hip`, which sccache 0.18 caches as its HIP language, the whole `--offload-arch` list in the hash (checked: a repeat compile of one ggml-cuda object through the launcher is a cache hit). Switching the launcher on or off changes every HIP compile command, so the first build after it recompiles all of ggml-hip once.
  - **RCCL is linked on Linux** (`-DGGML_HIP_RCCL=ON`, passed here and not in the shared `cmake-options.psd1`: the Windows dist ships no RCCL and `find_package(rccl REQUIRED)` would fail the configure). It is the collective library `--split-mode tensor` reduces through when every device of the split is a ROCm one, in place of ggml's internal AllReduce, which stages each reduction through pinned host memory and is all Windows has. Upstream's default is OFF ("not universally beneficial during testing"), so it is a default to measure, not a guarantee: `GGML_CUDA_ALLREDUCE=internal` selects the internal path again at run time, with no rebuild (`nccl` and `none` are the other values): the configurator's Server tab exports it from SDK Tuning, Tensor-split AllReduce (`server.ini` `CudaAllreduce`). The option is passed as ON or OFF on every configure, by whether the dist has `lib/cmake/rccl/rccl-config.cmake`, so a cached ON cannot outlive a dist without the library. `03-package.sh` picks `librccl.so.1` and its dependencies up through the ldd closure. **NCCL, the CUDA counterpart, is linked when its dist is installed**: `GGML_CUDA_NCCL` is ON by upstream default and only needs ggml's `FindNCCL` to find the library, so the script pins its two cache paths (`NCCL_INCLUDE_DIR`, `NCCL_LIBRARY`) to the newest dist under `<Root>/NCCL` on every configure and `-U`s them when there is none (the configure then prints "NCCL not found" and two CUDA cards in tensor mode take the internal AllReduce). Adding or removing it changes a compile definition on every ggml-cuda source: the CUDA backend recompiles in full.
  - **lld by flag** (`-fuse-ld=lld` in the three `CMAKE_*_LINKER_FLAGS`, always passed, blank when there is no lld), not `CMAKE_LINKER`: the GNU-style drivers choose their linker by flag. Not `CMAKE_LINKER_TYPE=LLD` either: CMake 4.2 defines no linker types for the HIP language and the configure dies in the HIP compiler check. So on Linux the script SETS the three variables where the Windows one `-U`s them; the flag also reaches the CUDA link (g++, which finds `ld.lld` on the build PATH). It is what keeps `GGML_LTO` alive: ThinLTO objects are bitcode, GNU ld cannot link them, and llama.cpp then drops LTO on a failed `check_ipo_supported` without failing.
  - **nvcc's host compiler is `g++`** (`CMAKE_CUDA_HOST_COMPILER`): nvcc supports a narrow range of host compilers and the ROCm clang is not one. `CUDAToolkit_ROOT` is passed with the compiler so FindCUDAToolkit stays inside the pinned toolkit. `CMAKE_BUILD_RPATH` names the toolkit's `lib` by hand: it is an implicit link directory of nvcc, which CMake leaves out of the computed RPATH, and without it `libggml-cuda.so` cannot load `libcudart.so.13` / `libcublas.so.13` and the CUDA backend is silently absent (`llama-server --list-devices` shows no `CUDA0`).
  - The binaries get a **build-tree RPATH** to the dists they linked against, so `build/linux/llama.cpp-cmake/bin/llama-server` runs with no `LD_LIBRARY_PATH`; moving or deleting a dist breaks the backend that used it. The script ends by running `llama-server --version`.
  - **`llama-cpp-config`** is built last (`cargo build --release`, `cargo` from PATH or `~/.cargo/bin`) with `CARGO_TARGET_DIR=build/linux/cargo-target` (the Windows build has its own, `build/windows/cargo-target`), and then **copied into `build/linux/llama.cpp-cmake/bin/`**: `paths::llama_bin` looks in the exe's own directory first, so the copy is the one to launch (the exe left in `cargo-target/release` finds the same tree through the `..\..\llama.cpp-cmake` fallback). A missing `resources/llama.ico` is generated by the script from the Linux clone before cargo runs (`build.rs`'s own bootstrap assumes the default clone, `build/linux/llama.cpp`, where the script passes the configured one). The Linux file-dialog backend is a target-scoped `rfd` feature set in `Cargo.toml` (`xdg-portal` + `wayland`: rfd refuses to build on Linux with none). `cargo test` on Linux: 6 unit tests fail because their fixtures are Windows paths (`C:\m\x.gguf`), which `std::path` does not split on Linux; the code under test is not at fault.
- `03-package.sh` (`--deb` / `--rpm` for one format, `--keep-staging`): stages into `build/linux/staging/` and builds `dist/llama-cpp-framework-v<version>-<llamaRelease>-amd64.deb` and `-x86_64.rpm` (the Windows installer's name, with each format's own architecture token), about 1.2 GB each and 3.3 GB installed. The package **version** is `<framework>+llama.cpp.<tag>` (e.g. `2.0.0+llama.cpp.v0.7.0`), so a rebuild on a newer llama.cpp alone is an upgrade to apt/dnf (dpkg and rpm both order `2.0.0` < `2.0.0+llama.cpp.v0.7.0` < `2.0.0+llama.cpp.v0.10.0` < `2.0.1+...`). It refuses to run when the built `llama-cpp-config --version` differs from `Cargo.toml` (a bump without a rebuild).
  - **Self-contained under `/opt/llama.cpp/`**, like the Windows installer: the target machine needs the GPU drivers and nothing else. **`bin/`** holds the executables, llama.cpp's shared libraries, the ggml backends and `llama-cpp-config`, staged straight from the build's `bin/` (not `cmake --install`, which splits `bin/` and `lib/`): ggml looks for its backends next to the executable (`/proc/self/exe`, so through a symlink too) and `paths::llama_bin` looks for `llama-server` next to the configurator. **`lib/`** holds the bundled runtimes. **`/usr/bin/` holds one relative symlink per executable** (rpm warns on absolute ones). llama.cpp's `test-*` harnesses are pruned, as on Windows.
  - **Which runtime libraries is not a list**: it is the `ldd` closure of the staged files, restricted to what resolves inside the ROCm dist, the CUDA dist, the NCCL dist or the Vulkan SDK's loader dir; each lands under its soname, symlinks dereferenced. `libcuda.so.1` is the NVIDIA driver's and stays out. As on Windows, the script refuses to package a `libggml-hip.so` without `libhipblas.so.*` or a `libggml-cuda.so` without `libcublas.so.*` in `lib/`. What the Windows package adds by name has no Linux counterpart: `libamd_comgr.so.3` is a plain `DT_NEEDED` of `libamdhip64.so.7`, so the closure carries it, and a RUNPATH precedes the system library dirs, so no system ROCm can get mixed in (short of `LD_LIBRARY_PATH`).
  - **The ROCm part mirrors the dist's `lib/` layout** (`lib/`, `lib/llvm/lib/`, `lib/rocm_sysdeps/lib/`, `lib/rocblas/library/`, `lib/hipblaslt/library/`, and `.kpack/` beside `lib/`, with hipBLASLt's `blas_lib_*` and RCCL's `rccl_lib_*` archives): AMD's libraries find each other and their kernel files through `$ORIGIN`-relative RUNPATHs and paths, so a mirrored tree needs no patching of anything AMD shipped. The kernel data (which `ldd` cannot show) is copied **only for the architectures in `CFG_GPU_TARGETS`**, files or per-arch directories alike, plus whatever names no architecture: 359 + 467 + 91 MiB instead of 810 + 2198 + 2258. `libomp.so` comes along the same way: the CPU backends are built with the dist's clang and link its OpenMP runtime. CUDA (`libcudart`, `libcublas`, `libcublasLt`, ~575 MiB) and the Vulkan loader go flat into `lib/`.
  - **RUNPATH is rewritten with `patchelf`** on llama.cpp's own ELF files only (after `strip --strip-unneeded`, never before): `$ORIGIN:$ORIGIN/../lib:$ORIGIN/../lib/llvm/lib`. `LD_LIBRARY_PATH` still wins over RUNPATH. Verified by extracting the `.deb` and tracing a generation per backend with `strace`: no file opened under the dists or the build tree.
  - **Dependencies**: the `.deb`'s `Depends` come from `dpkg-shlibdeps` over the staged ELF files, bundled runtimes included, minus `libggml-cuda.so` (it links the driver's `libcuda.so.1`, which no Debian package provides, and `dpkg-shlibdeps` fails on a library it cannot find), with a fixed list as fallback; what `llama-cpp-config` only `dlopen`s (xkbcommon, Wayland/X11, EGL) is `Recommends`. The `.rpm` keeps rpm's automatic scan, with `__requires_exclude` covering every library the package carries (they are excluded from `Provides` too) and `libcuda`. `rpmbuild` runs against a throwaway `_dbpath`: a Debian host has no rpm database.
  - **No config directory is shipped.** `llama-cpp-config` writes the config files per user, in `${XDG_CONFIG_HOME:-~/.config}/llama.cpp/` (`paths::config_dir`), so the packages have no maintainer scripts and create no group.
  - Also shipped: `/usr/share/applications/llama-cpp-config.desktop` ("llama.cpp Config" in the desktop's application menu, GNOME's included), its icon (the largest PNG frame of `resources/llama.ico`, cut out of the container with `od`/`tail`, no image tool needed) and llama.cpp's licence. Modes are normalized to 755/644 because the repo drive may hand out group-writable ones. The payload is zstd in both formats (xz takes many minutes on 3 GiB of GPU kernels).
- `04-install.sh` (`--deb` / `--rpm`, `--force`, `--dry-run`, or a package file as argument): installs the newest `dist/llama-cpp-framework-v*` of this architecture (by write time) with the distribution's package manager, so one command covers a first install, an upgrade, a **same-version reinstall** (a repackage; a rebuild on a newer llama.cpp is an upgrade, since the package version is `<framework>+llama.cpp.<tag>`, set by `03-package.sh`) and a downgrade: `apt-get install --reinstall --allow-downgrades` for the `.deb`; `dnf install`/`reinstall`/`downgrade`, `zypper install --force` or `rpm -Uvh --replacepkgs --oldpackage` for the `.rpm`. The format comes from `ID`/`ID_LIKE` in `/etc/os-release`, the package managers on PATH only second: a Debian build host has `rpm` too. It refuses while a program from `/opt/llama.cpp/bin` runs (`--force` overrides): rocBLAS and hipBLASLt load their kernel files lazily, so a server outliving the upgrade would read the new kernels with the old libraries. It warns when the package predates the last `02-build.sh` and checks `llama-cpp-config --version` afterwards.
