# Build pipeline

Details for the root-level scripts and build configuration (`00-install-prerequisites.ps1` to `03-package.ps1`, `common.ps1`, `cmake-options.psd1`, `build\config-build.psd1`). Read this before changing any of them. The installer side of packaging (`installer\`) is in [installer\AGENTS.md](../installer/AGENTS.md).

## Files

- `build\config-build.psd1`: build-time configuration (paths, GPU targets, compiler flags). Generated by `01-configure.ps1`; lives under `build\` (whole dir gitignored).
- `cmake-options.psd1` (repo root, checked in): the machine-independent half of the llama.cpp configure line, one `NAME[:TYPE]=VALUE` string per cmake `-D` with its reason beside it (backends, `GGML_BACKEND_DL`, `LLAMA_BUILD_IS_DEV=OFF`, `LLAMA_BUILD_UI=ON`, `GGML_LTO=ON`, and `GGML_CUDA_FA_QUANTS`, which adds the q5_0/q5_1 KV-cache pairs to upstream's native FlashAttention kernel set so a q5 cache does not convert to f16 on every short decode step; editing that list recompiles ggml-cuda and ggml-hip in full). Read and validated by `02-build.ps1`, which appends the machine-derived half from `config-build.psd1`.
- `common.ps1` is the shared bootstrap: loads `$cfg` from `build\config-build.psd1`, adds ROCm to PATH (`HipPath\bin` plus, for the TheRock dist, `HipPath\lib\llvm\bin`, where clang lives), and is the **sole source** of the compile-time HIP vars (`HIP_DEVICE_LIB_PATH` → `lib\llvm\amdgcn\bitcode`, `HIP_PLATFORM`, `LLVM_PATH`), set per-process from `HipPath` (without `HIP_DEVICE_LIB_PATH` the HIP device compile dies with "cannot find ROCm device library"). They must NEVER be set machine-wide: the Adrenalin driver's own HIP runtime (System32's `amdhip64_7.dll` + `amd_comgr_3.dll`) reads `LLVM_PATH` at runtime, and pointing it at TheRock's LLVM breaks it (`hipMemGetInfo` returns "invalid argument", devices report 0 MiB, every llama-server child dies with 0xC0000005 mid weight-upload; `00-install-prerequisites.ps1` self-heals poisoned machines). Exposes `Enable-VsDevShell`; VS Dev Shell activation is **opt-in** (only build/package scripts call it). Dot-sourced by `02-build.ps1` and `03-package.ps1`.
- `00-install-prerequisites.ps1` is the idempotent toolchain bootstrapper. Safe to re-run any time.
  - **winget packages** (PowerShell 7+ / OpenSSL / NSIS): installed or upgraded in a single UAC-elevated session, plus the OpenSSL lib-symlink fixup.
  - **sccache from its GitHub release**, NOT winget (the manifest lags upstream by days), user scope, outside the elevated session: the newest `x86_64`/`aarch64` `pc-windows-msvc` zip from `/releases/latest`, checked against the API's sha256 `digest` (fallback: the `.sha256` sidecar), `sccache.exe` staged and MOVED over `%LOCALAPPDATA%\Programs\sccache\sccache.exe` (an exe in use stays intact and the run says so), that dir appended to the user PATH through the raw registry plus a `WM_SETTINGCHANGE` broadcast, and a leftover winget `Mozilla.sccache` uninstalled once the release copy works. Tracks LATEST (a misbehaving cache costs a cold build, not a broken runtime). The directory is **versionless on purpose**: `02-build.ps1` passes that path to CMake as the compiler launcher, and a moving launcher path changes every compile command, so ninja would re-run all of them after each upgrade.
  - **llama.cpp**: `git fetch`es `$cfg.LlamaCppDir` when cloned and compares the checked-out tag against the newest **release** tag reachable from `origin/master`, by the same selection `02-build.ps1` makes. No `git pull`: the clone sits on a detached tag; the checkout is `02-build.ps1`'s job.
  - **ROCm/HIP installs from AMD's TheRock dist tarball** (the classic HIP SDK installer is discontinued), version **pinned in `installer\dist-pins.psd1`**: bump it there deliberately and re-run to converge. The **multiarch** Windows tarball (kernels for every gfx family) is extracted **into its own version directory** (`C:\TheRock\<version>`, the pins' `Root`) inside the elevated session, which also sets the machine env: `HIP_PATH` **only**, naming the ACTIVE version, and deletes machine-wide copies of the compile-time vars (see `common.ps1`). Dists sit **side by side**: a version already extracted is reached by moving `HIP_PATH`, no download; the legacy single-directory layout (`C:\TheRock\build`) is **renamed** into its version dir rather than re-fetched. ~25 GB per dist: the report lists inactive ones and never deletes them (a working rollback; the user's call).
  - The same session appends `bin` + `lib\llvm\bin` to the machine PATH via the raw registry (`setx /M` truncates PATH at 1024 chars; `[Environment]::SetEnvironmentVariable` downgrades `REG_EXPAND_SZ` to `REG_SZ`) and **prunes every other `Root\*` entry**: `amdhip64_*.dll` reachable from two PATH dirs is an ambiguous load order, a classic silent-crash cause. The installed version lives in a `.therock-version` marker written only after a successful extract (the env leg is gated on it). A wipe + re-extract only ever clears an **incomplete tree of the same version**, so llama-server must be stopped for exactly two operations (the legacy-tree rename and a re-extract over an existing version dir); the script checks and skips those, and installs a NEW version while it runs.
  - **Report**: warns on a leftover legacy HIP SDK under `Program Files\AMD\ROCm`, a shadowing user-level `HIP_PATH`, any persistent-scope `LLVM_PATH`/`HIP_DEVICE_LIB_PATH`/`HIP_PLATFORM`, and `amdhip64_*.dll` in more than one PATH dir. That last check **sets the installed framework's `bin\` aside** (found through `HKLM\Software\llama.cpp` `InstallDir`): it carries the staged runtime trio on purpose (no rocblas/hipblaslt there, and PATH never decides `amdhip64_7.dll` for another exe). For that `bin\` it checks **staleness** instead: the trio compared by content (size, then SHA256) against the ACTIVE dist's `bin\`, warning with the `install-runtime-deps.ps1 -StageHipRuntime` command when it differs or is missing. Shows before→after versions and rebuild recommendations (`02-build.ps1` / `03-package.ps1` for a newer llama.cpp release, preceded by `01-configure.ps1` when the ROCm dist changed). It also **scans AMD's tarball indexes** (the pins' `Indexes`) for a stable newer than the `Pin` and prints the `Dists` entry to paste: a report, never an install, because a dist bump can move the clang resource major (`patches\hip\<major>\` must be regenerated), re-derives `GpuTargets`, costs ~25 GB, and can regress what the current one does right. Best effort: an unreachable index leaves the row out.
  - CUDA / Vulkan stay manual installs (probed, URLs printed). Reads `build\config-build.psd1` directly (does **not** dot-source `common.ps1`) so it works on a fresh machine before `01-configure.ps1` has run.
- `01-configure.ps1`: auto-detects paths, activates VS Dev Shell for tool discovery, verifies tools, creates `build\` if missing, writes `build\config-build.psd1` **and a generated `.cargo\config.toml`** (see Conventions). Accepts `-LlamaCppDir` (defaults to `$PSScriptRoot\build\llama.cpp`). Writes GPU targets (**derived from the installed ROCm dist**; see Conventions), build type (Release), compiler (the **full path** to the detected clang, TheRock's `lib\llvm\bin\clang.exe` when present; a bare `clang` fails at cmake time in consoles whose PATH predates the machine-env change), **linker** (`lld-link.exe` from the same LLVM tree, blank when the compiler is not LLVM), and build jobs. No `-march`. `Find-ROCm` probes process then machine `HIP_PATH`, then legacy `Program Files\AMD\ROCm`; `Find-Tool` falls back to `HipPath\bin` and `HipPath\lib\llvm\bin`.
- `02-build.ps1`: dot-sources `common.ps1` + calls `Enable-VsDevShell`. Builds **both** llama.cpp (CMake + Ninja into `build\llama.cpp-cmake\`) **and** `llama-cpp-config` (cargo build --release; the binary stays in `llama-cpp-config\target\release\`, staged from there by `03-package.ps1`). Uses sccache if available for the C++ build.
  - **Release tag selection**: auto-clones llama.cpp into `build\llama.cpp\` (or fetches) and **checks out its latest RELEASE tag**, not master HEAD. Upstream tags every master merge with a lightweight `bNNNN` nightly and a release additionally with an annotated `vX.Y.Z`; **nightlies are ignored even when newer**. `git describe --abbrev=0` would return the nearest nightly, so the selection is the highest `^v\d+\.\d+\.\d+$` among `git tag --merged origin/master --sort=-v:refname` (`--merged` for reachability, `-v:refname` so v0.10.0 outranks v0.2.0, the strict regex so a `-rc` pre-release is not mistaken for a release). No release tag reachable = hard failure. Hence `LLAMA_BUILD_IS_DEV=OFF` is unconditional.
  - **Configure line split in two files**: `cmake-options.psd1` holds what is built (validated by regex before cmake sees it); `02-build.ps1` adds everything machine-derived (compiler/linker/targets, OpenSSL root, Vulkan SDK, the HIP header workaround, sccache) and owns the `-U` unsets. These are CACHE entries: deleting a line does not restore cmake's default on an existing build dir, so retire an option by setting it explicitly.
  - **`LLAMA_BUILD_UI=ON` is pinned**: upstream's default is OFF, under which the chat UI is DOWNLOADED from a HuggingFace bucket at configure time and, when that fails, the build proceeds with NO UI on only a cmake warning. `02-build.ps1` therefore **refuses to finish a build whose UI did not get embedded** (`tools\ui\dist\index.html` under the build dir, or a `dist` in the source tree) and reports which path produced it (the download path leaves a `.ui-stamp`).
  - **HIP header workaround**: force-includes a checked-in patched `__clang_hip_runtime_wrapper.h` (MSVC's `_CLANG_BUILTIN2` constexpr `<cmath>` overloads clash with the HIP device math declarations; still required with TheRock / AMD clang 23). It is a modified snapshot of the toolchain's header, **versioned per clang resource major** under `patches\hip\<major>\` and selected from the installed dist (`lib\llvm\lib\clang\<N>`, legacy `lib\clang\<N>`); a changed major **fails fast** with regeneration instructions (`patches\hip\README.md`). Never force-include a copy from a different clang.
  - **Out-of-tree llama.cpp patches** (`patches\llama.cpp\*.patch`): REVERTED before the fetch/checkout (a tag bump touching a patched file would abort the checkout), re-applied onto the fresh tag. Both legs probe with `git apply --check`, so a re-run is a no-op, and a patch that applies in NEITHER direction fails the build rather than being skipped. Every patch is **provisional**: when upstream lands the same support it stops applying and is DELETED, not rebased (provenance and the log line proving it live: `patches\llama.cpp\README.md`).
  - **Compiler change**: wipes `build\llama.cpp-cmake\` when `CMakeCache.txt` pins a different compiler path than the config.
  - **Vulkan SDK resolved from the PARENT dir** (`Find-VulkanSdk`: parent of process/machine `VULKAN_SDK`, then `C:\VulkanSDK` and the `Program Files` roots; highest `[version]` dir with `Lib\vulkan-1.lib` + `Bin\glslc.exe`): a LunarG upgrade deletes the old versioned dir, while a stale console `VULKAN_SDK` and the `Vulkan_INCLUDE_DIR`/`Vulkan_LIBRARY`/`Vulkan_GLSLC_EXECUTABLE`/`Vulkan_GLSLANG_VALIDATOR_EXECUTABLE` cache entries (reused without existence checks) still point at it. The resolved SDK is exported as `VULKAN_SDK` and the four paths passed as explicit `-D`s, deliberately not a build-dir wipe (that would cost a full CUDA + HIP rebuild).
  - **CUDA toolkit follows the newest installed version** (`Find-CudaToolkit`: parent of process/machine `CUDA_PATH` plus `Program Files\NVIDIA GPU Computing Toolkit\CUDA`, highest `v<major>.<minor>` with `bin\nvcc.exe`, `lib\x64\cudart_static.lib` and `cublas.lib`; by version, since `CUDA_PATH` names whichever was installed last), passed as `-DCMAKE_CUDA_COMPILER` and exported as `CUDA_PATH`. A toolkit upgrade leaves the old one working, so nothing would fail otherwise. A changed `CMAKE_CUDA_COMPILER` alone makes CMake **delete the whole cache plus top-level `CMakeFiles`**, so on a change the script removes only the CUDA identification files (`CMakeCUDACompiler.cmake`, `CMakeDetermineCompilerABI_CUDA.bin`, `CompilerIdCUDA\`) and `-U`s the toolkit entries (`CUDA_*`, `CUDAToolkit_*`, `_cmake_CUDAToolkit_*`, `FIND_PACKAGE_MESSAGE_DETAILS_CUDAToolkit`; the `GGML_CUDA_*` knobs survive): only CUDA objects recompile. CUDA 13.4+ keeps CUPTI's import libs in `extras\CUPTI\lib\x64`, where CMake's FindCUDAToolkit does not look, so the four `CUDA_cupti`/`nvperf_*`/`pcsamplingutil` entries may resolve to an older toolkit; ggml links none of them.
- `03-package.ps1`: dot-sources `common.ps1` + calls `Enable-VsDevShell` (cmake --install needs the VS env). Stages from `build\llama.cpp-cmake\` + `llama-cpp-config\target\release\` into `build\staging\`, then builds the NSIS installer into `.\dist\`.
  - **Prunes llama.cpp's own `test*.exe`** right after `cmake --install` (cmake stages every executable with an `install()` rule; count from the staging tree, not the build dir). The installer can put `bin\` on the **system PATH**, so shipping them would drop generically-named `test-*` commands into every shell. Pruned in staging rather than filtered in the `.nsi`, so what is staged is exactly what ships.
  - **Stages the OpenSSL runtime DLLs** into `bin\`: they are NORMAL imports (`libcrypto-N-x64.dll`/`libssl-N-x64.dll`; without them the server fails at load on a machine with no OpenSSL). Names are scanned from the staged binaries' import tables (plain ASCII in the PE) since the ABI number moves, and copied from `$cfg.OpenSSLDir\bin` (app dir wins the DLL search order). **Every** staged `.exe` and `.dll` is scanned, never a name pattern: llama.cpp tools are thin launchers plus impl DLLs (`llama-server.exe` imports `llama-server-impl.dll`, which carries the OpenSSL imports, alongside `llama-common.dll`), so a name-based scan breaks on the next rename. Don't copy `*.dll` wholesale: most of `OpenSSLDir\bin` is providers (`legacy`, `p_test`, `p_ossltest`, `p_minimal`). The scan reads in 4 MB **chunks** with a 64-byte overlap (`ggml-hip.dll` is ~900 MB; `ReadAllBytes` + `ASCII.GetString` would cost ~2.8 GB RAM) and gates the regex behind an ordinal `IndexOf` (~15x faster).
  - **External runtime deps stay external**: VC++ redist x64, and per-GPU: AMD Adrenalin driver + TheRock dist with `HIP_PATH` (rocBLAS/kpacks), NVIDIA driver + CUDA 13 cuBLAS (`cublas64_13`/`cublasLt64_13`, ~700 MB, documented not bundled); cudart is static, `vulkan-1.dll` ships with any GPU driver. Bundled instead is the helper `installer\install-runtime-deps.ps1` + `dist-pins.psd1`, staged into `bin\` (see [installer\AGENTS.md](../installer/AGENTS.md)).
  - **Package name**: `llama-cpp-framework-v<frameworkVersion>-<llamaBuild>-<arch>-setup.exe`, e.g. `llama-cpp-framework-v1.11.2-v0.2.0-x64-setup.exe`: frameworkVersion = `llama-cpp-config\Cargo.toml` `[package]` version (configurator and framework are versioned together), llamaBuild = `git describe --tags` of `$cfg.LlamaCppDir` (prefers the annotated release tag over the lightweight nightly on the same commit), arch = `x64`/`arm64`. The `^v\d+\.\d+\.\d+$` check decides whether to trust the describe: anything else (`v0.2.0-11-g…`, empty) falls back to `b<rev-list --count>`, deliberately shaped so a non-release package cannot pass for one.

## Conventions

- sccache is auto-detected by `02-build.ps1`: `%LOCALAPPDATA%\Programs\sccache\sccache.exe` first (where `00-install-prerequisites.ps1` installs it; fixed path so the launcher in every compile command does not move, found even from a console with a stale PATH), then PATH; cache in `build\.sccache\`. Uses `SCCACHE_MAX_FRAME_LENGTH=104857600` for large GPU objects and `SCCACHE_CLIENT_SIDE=1` (0.17+ client-side mode, no per-compile daemon round-trip; older versions ignore it). **nvcc is intentionally NOT wrapped**: for the PTX-only `compute_90` gencode (ggml's default `90-virtual`) nvcc runs `ptxas -arch=compute_90` with no `-o`, sccache treats it as cacheable and every `.cu` dies with `Missing "cubin" file output`. Fix pending sccache PR #2809; until a release carries it, host C/CXX (clang) caching only. Do not drop `90-virtual` to dodge it: that changes what the shipped `ggml-cuda.dll` covers.
- **No global `-march`, and LTO only as far as `GGML_LTO` reaches.** A global `-march` leaks into every ggml-cpu variant, so the fallback tiers (`ggml-cpu-x64.dll`, `ggml-cpu-sse42.dll`) would carry AVX2 code while ggml's runtime score (`ggml-cpu/arch/x86/cpu-feats.cpp`, keyed on per-variant `GGML_AVX2`-style macros) still picks them on pre-AVX2 CPUs. The variants carry their own `-m` flags; everything else builds at the compiler's default baseline, as upstream's release binaries do (`GGML_NATIVE=OFF`). The `sse42` variant compiles the SSSE3 branch of `ggml-cpu/arch/x86/quants.c`, whose `_mm_prefetch` calls pass a block pointer where clang's MSVC-compatible `xmmintrin.h` wants `const char *`, a default ERROR under AMD clang 23: hence `-Wno-error=incompatible-pointer-types` in `CMAKE_C_FLAGS`. `GGML_LTO=ON` sets `CMAKE_INTERPROCEDURAL_OPTIMIZATION` in `ggml/src` scope only: `-flto=thin` on ggml-base, every ggml-cpu variant, ggml-vulkan and the host half of ggml-hip, linked by lld-link; ggml-cuda (nvcc) and llama/common/llama-server are untouched. A global `CMAKE_INTERPROCEDURAL_OPTIMIZATION=ON` would also reach the CUDA target, so it is not passed. lld-link's ThinLTO backend already defaults to one thread per physical core, so no thread flag. Linker-flag traps: the three `CMAKE_*_LINKER_FLAGS` are language-agnostic (a `-Wl,...` also reaches the CUDA DLL, linked by lld-link DIRECTLY through `cmake -E vs_link_dll`, which warns `ignoring unknown argument`) and are CACHE entries (an experiment outlives itself), so `02-build.ps1` `-U`s all three on every configure and sets none. A per-language link option (e.g. a ThinLTO cache, `/lldltocache:<dir>`) needs a `$<LINK_LANGUAGE:CXX>` guard through a `CMAKE_PROJECT_INCLUDE` file. Never reconfigure or run ninja in `build\llama.cpp-cmake\` while a build is running there: ninja holds `.ninja_deps` open, so the generate step fails with `failed recompaction: Permission denied` AFTER rewriting `build.ninja` and the cache, and the two disagree until the next configure.
- HIP GPU targets (`config-build.psd1` `GpuTargets` → `-DGPU_TARGETS`) are **derived by `01-configure.ps1`** (`Get-GpuTargets`), never hand-maintained: a ROCm dist bump only needs a re-run of `01-configure.ps1`. Derivation: the archs the installed dist ships Windows BLAS kernels for (`.kpack\blas_lib_gfx*.kpack` under `HIP_PATH`; legacy-SDK fallback `bin\rocblas\library\TensileLibrary_lazy_gfx*.dat`), **minus** CDNA/Vega `gfx9xx` (no Windows driver; gfx906 kernels dropped), **plus** the Ryzen iGPU safety set (`gfx1035/1036/1103/1152/1153`), unioned in even if a future dist drops their kernels: the driver's HIP runtime fails kernel-module load on *every* visible device when one has no matching code object ("device kernel image is invalid"). A static snapshot is used only when no dist is present. Currently 20 archs (RDNA1 `gfx1010-1012`, RDNA2 `gfx1030-1036`, RDNA3 `gfx1100-1103`, RDNA3.5 `gfx1150-1153`, RDNA4 `gfx1200/1201`), ~56 MiB of `ggml-hip.dll` each; hand-prune only if size matters, never the iGPU set. ROCm's `hip-config-amd.cmake` derives `--offload-arch` from **`GPU_BUILD_TARGETS`**, seeded from `GPU_TARGETS` via `set(... CACHE ...)` (a no-op once cached), so `02-build.ps1` passes `-UGPU_BUILD_TARGETS` every configure.
- **A ROCm dist carries TWO kernel stores, and the recommended setting uses the one that looks legacy.** `.kpack\blas_lib_gfx*.kpack` (~41 MiB per arch) is **hipBLASLt**'s; `bin\rocblas\library\` (~700 MiB) is **Tensile**'s, found relative to `rocblas.dll`. `ROCBLAS_USE_HIPBLASLT` decides which is read; with it `off` on gfx1201, everything runs **out of `bin\rocblas\library`**. The `.kpack` scan above only ENUMERATES archs. Deleting `bin\rocblas` to trim a dist breaks that configuration LATE: the backend loads and enumerates, then the first matmul dies with `Could not initialize Tensile host`. Within `bin\rocblas\library` about half is `gfx908`/`gfx90a` (never built): the CDNA half is the safe and only worthwhile thing to delete.
- **lld links both halves of the build, by two different mechanisms.** *C++*: `01-configure.ps1` looks for `lld-link.exe` **next to the clang it resolved** and writes it as `config-build.psd1` `Linker`; `02-build.ps1` passes it as `-DCMAKE_LINKER` when non-empty. A bare-name `clang` fallback or an MSVC toolchain leaves it blank and CMake keeps `link.exe`; blank (or absent from an older config, hence a truthiness check, not `Test-Path`) is supported. It mostly *pins* what CMake does anyway, so the fallback to `link.exe` cannot happen silently. *Rust*: unconditional, via the generated `.cargo\config.toml` (`[target.x86_64-pc-windows-msvc] linker = "rust-lld.exe"`). The bare name is deliberate: `rust-lld` ships **inside** the toolchain (`<sysroot>\lib\rustlib\<target>\bin`, not on PATH), always present and version-matched to rustc, where an external `lld-link.exe` would borrow whatever LLVM is installed. To tell which linker produced a binary, look for the **Rich header** MSVC's `link.exe` stamps into the PE's DOS stub; lld does not.
  - The Rust half carries `rustflags = ["-Clink-arg=/force:multiple"]`, and it is **load-bearing**: Skia links ICU *statically* (`skunicode_icu.lib`) while the `windows` crate imports the *system* one (`icuuc.dll`), so every `uloc_*` is defined twice; `link.exe` swallows that (LNK4006), the flag makes lld do the same. It bites **only the test binary** (the second ICU arrives via the dev-dependency `i-slint-backend-testing` → `i-slint-common` → `fontique` → `windows`): without it `cargo test` does not link. Accepted cost: rustflags are not per-profile, so a real duplicate symbol in the shipped binary would go uncaught. Re-test and drop it if the two ICUs stop colliding.
- Build parallelism (`config-build.psd1` `BuildJobs`, written by `01-configure.ps1`) defaults to **3/4 of logical cores, clamped to at most `cores - 1`** (CMake/Ninja `-j` and `cargo build --jobs`), so a core stays free during long CUDA/HIP compiles; the clamp is kept so the reservation survives a later retune. A 1-core machine gets 1 job. `BuildJobs = 0` means "use all cores". `-j` bounds compile PROCESSES, not CPU (no affinity; nvcc and threaded lld links can exceed it). The same number goes into the generated, gitignored **`.cargo\config.toml`** at the repo root, so bare `cargo build`/`cargo test` from a shell or IDE are capped too: `[build] jobs` for rustc/codegen and `[env] RUST_TEST_THREADS` for the libtest harness (an existing environment value still wins, so `RUST_TEST_THREADS=1 cargo test` works for serial debugging).
