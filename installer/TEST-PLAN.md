# Installer test plan

## Test plan (on a TEST machine or VM, never on the build machine's real install)

Each step: `msiexec ... /l*v <log>` keeps a verbose log; `StopProcesses`, `UninstallInstanceServices`, `RemoveInstanceServices`, `StopInstances`, `StartInstances`, `DeleteUserData` and `DeleteEngineData` show in it with their exit codes. "The engine" is llama.cpp's MSI, "the framework" the framework's.

**What CI covers** (`installers-windows.yml`, green in runs 43651545466, 43654217880 and 43743455408, with the minimal CPU-only engine, every msiexec `/qn` and `xtask install` `/qb`, default folders): step 1 without the `msiexec /a` comparison; step 2's silent half (exit 1603, the launch condition's message in the log, no `HKLM\Software\private-ai`, no `private-ai-manager`, no `%ProgramFiles%\private-ai` or `%ProgramData%\private-ai`); from steps 3, 4 and 21, both `InstallDir` values, `pai --version` and `llama-server --version` from the installed `bin\`, both services Running with automatic start and the path and account the `.wxs` declares, the two defaults in `%ProgramData%\llama.cpp\config\`, `/api/version` equal to `Cargo.toml`'s version and `/api/instances` answering 200 with exactly the one instance `default`, engine `llama.cpp`, state `inactive` (since run 43654217880); from step 7, a repair of each (`/fecmus`) that restores a deleted `models.ini`, keeps a changed `server@default.ini` and leaves no `instances.running`; from step 15, `xtask install` of both on a clean machine; from steps 12 to 14, `msiexec /x <msi> /qn` of the framework (its services, key and `%ProgramFiles%\private-ai` gone, the engine and its defaults kept) and then of the engine (no `llama.cpp_*` service, both keys and both `%ProgramFiles%` folders gone, a `bff.ini` and the engine's defaults kept in `%ProgramData%`); and the local group `pai`: `Get-LocalGroup -Name pai` after `xtask install`, `Add-LocalGroupMember -Group pai -Member $env:USERNAME` before the repairs, and `Get-LocalGroupMember -Group pai -Member $env:USERNAME` after the repairs and again between the framework's and the engine's uninstall, so a repair and an uninstall must leave the group and its members (the workflow lines of 1e4094a, pinned by a test in `xtask\src\ci_windows.rs`; run 43743455408, built on that commit, executed them and passed). Everything else in the steps is still for a test machine: the dialogs and full UI, the file layout, Apps entries, PATH and Start Menu, `sc qfailure`, `icacls`, the manager's record file under `%ProgramData%\private-ai\logs\` (CI asks the web service only the session-free `/api/version` and `/api/instances`, signs in nowhere and writes no file, so no `As` call crosses the pipe and no record is ever written there), `%LOCALAPPDATA%\private-ai`, the delete properties, the GPU runtimes, a started instance, the GUI, upgrades and downgrades (steps 5, 6, 8 to 11, 16 to 20, 22, 23 untouched).

1. **Both build**: `xtask package` on the build machine builds `llama.cpp-v<release>-x64.msi` and `private-ai-framework-v<version>-x64.msi`, each validated; note each size and `wix build` time (the figures in "Size" are the single MSI's). `msiexec /a` each into a short directory and compare it with its staging tree (`--keep-staging`).
2. **The framework alone is refused**: on a machine with neither installed, run the framework with full UI: the message "llama.cpp v<min> or newer must be installed first..." and the installer ends; `msiexec /i <framework> /qn /l*v <log>`: exit code 1603, the message in the log. Nothing changed: no `%ProgramFiles%\private-ai`, no `private-ai-manager` service, no `%ProgramData%\private-ai`, no `HKLM\Software\private-ai`, no Apps entry.
3. **Engine, fresh install**: double-click the engine: the welcome page shows the requirements text; the licence page shows the list of texts and NVIDIA's terms down to their last line, Next disabled until the box is ticked; CustomizeDlg shows one feature; Browse to a non-default folder; install. Check: `bin\`, `lib\`, `.kpack\`, `share\licenses\` with its `README.txt`, `share\defaults\` with the two files, nothing at the root; `HKLM\Software\llama.cpp` `InstallDir` (the chosen folder) and `Version`; one Apps entry `llama.cpp v<release>` with the icon, version and publisher, and no second entry; no PATH change, no Start Menu entry, no service. `%ProgramData%\llama.cpp\config\` holds `server@default.ini` (`Port = 9931`, `Hostname = localhost`) and an empty `models.ini`; `icacls "%ProgramData%\llama.cpp"` and the same for `config`, `logs`, `models` and `state`: no inherited entry, and exactly the entries of the table under "The machine data trees" (Users absent from `config`).
4. **Framework, fresh install** (over step 3): the welcome page names llama.cpp; the licence page; CustomizeDlg lists the three features, all on; Browse to a non-default folder; install. Check: `bin\` (`pai-config.exe`, `pai.exe`, `pai-manager.exe`, `pai-bff.exe`, `llama.ico`) and `share\` (`benchmarks\`, `strings\`, `licenses\`), no llama.cpp file; `HKLM\Software\private-ai` `InstallDir` and no `LlamaBuild`; one Apps entry `Private AI Framework vX.Y.Z` beside the engine's; the machine PATH ends with `<dir>\bin\` and a NEW console finds `pai` (`pai --version` prints the framework version); Start Menu > Private AI Framework > Private AI Framework starts the configurator. The manager, from an elevated console: `sc qc private-ai-manager` shows auto start, the binary path `"<dir>\bin\pai-manager.exe" serve` and LocalSystem; `sc query private-ai-manager` RUNNING; `sc qfailure private-ai-manager` a restart after 5000 ms and a reset period of 86400 s. `%ProgramData%\private-ai` holds `config\` only, with the entries of the table, and no `logs\` beside it: the MSI does not create that folder, the manager does, at its first guarded call (step 7). `Get-LocalGroup -Name pai` answers, and `Get-LocalGroupMember -Group pai` prints nothing: the group exists and is empty (Microsoft's PowerShell cmdlets, learn.microsoft.com/en-us/powershell/module/microsoft.powershell.localaccounts/get-localgroup and .../get-localgroupmember).
5. **The minimum engine**: with an engine older than the framework's `LlamaCppMin` installed (a scratch build of a lower release), the framework is refused as in step 2; with the minimum or a newer one it installs. Upgrade the engine to a newer release under an installed framework: the framework's Apps entry and version do not change, and the instances run the new llama-server.
6. **Feature change** (framework): Settings > Apps > Private AI Framework > Modify > Change, untick PATH and Start Menu: the PATH entry and the shortcut go, the binaries stay. Change again to put them back.
7. **Defaults only when missing**: as a member of `pai` change the port in the configurator (the manager rewrites `server@default.ini`; an Administrators member outside `pai` is refused); repair the engine, then upgrade it (step 9): the file keeps the new port. Delete `models.ini` and repair the engine: an empty one is back. Uninstall the engine without ticking the box: both files are still in `config\`. That save is a guarded call, so `logs\` exists beside `config\` now, with the entries of the table, and `%ProgramData%\private-ai\logs\private-ai-manager.log` holds one line naming the action, the target, the caller, the principal (the configurator sends none, so `-`; a save from the web UI names the signed-in user) and the outcome. No Windows run has seen this file.
8. **Process stopping** (framework): start the configurator and a model from it (ideally with a conversation so a snapshot is written), then run the framework > Repair, or an upgrade (step 9). The configurator closes, the instance stops, the snapshot appears in `%LOCALAPPDATA%\private-ai\state\` when `SaveStateOnShutdown` is on (which a force-stop alone would not do), no files-in-use dialog shows, `private-ai-manager` is left to the SCM. Run a `llama-server.exe` from a build tree at the same time: it must survive. Run a `pai bench run` from the framework's `bin\` in a console: it is stopped too.
9. **Same-version repackage and upgrade**, each product: build again with the same version and install over: a major upgrade, one Apps entry afterwards. Then version N, then N+1 (the root `Cargo.toml`'s `[workspace.package] version` in a scratch build for the framework; a newer release for the engine): the folder and features are kept, one Apps entry, `%LOCALAPPDATA%\private-ai` and `%ProgramData%\llama.cpp` untouched, no question asked, and the other product untouched. With instances: step 20 for the framework, step 22 for the engine.
10. **Downgrade refused**, each product: with N+1 installed, run N: "A newer version of llama.cpp is already installed..." or "A newer version of Private AI Framework is already installed...", and nothing changes.
11. **Previous non-MSI installation refused** (framework): with nothing installed but the engine, create `HKLM\Software\Microsoft\Windows\CurrentVersion\Uninstall\private-ai` with `UninstallString` = `"C:\Program Files\private-ai\bin\uninstall.exe"`. Run the framework with full UI: the message "A previous installation of Private AI Framework must be uninstalled first..." shows and the installer ends; then `msiexec /i <framework> /qn /l*v <log>`: exit code 1603, the message in the log. Both times nothing changed (as in step 2), the fake entry untouched. Delete the fake entry: the install proceeds. The engine's own `Uninstall\llama.cpp` entry does not stop it. The engine likewise: with nothing installed, create `Uninstall\llama.cpp` with `UninstallString` = `"C:\Program Files\llama.cpp\uninstall.exe"` and run the engine with full UI and with `/qn`: "A previous installation of llama.cpp must be uninstalled first...", exit code 1603, nothing changed (no `%ProgramFiles%\llama.cpp`, no `%ProgramData%\llama.cpp`, no `HKLM\Software\llama.cpp`), the fake entry untouched; delete it and the install proceeds; a repair and an upgrade of an installed engine are not stopped.
12. **Framework uninstall from Settings with the dialog**: Settings > Apps > Private AI Framework > Uninstall opens the removal page; with `%LOCALAPPDATA%\private-ai` present the checkbox shows, CLEARED, and the text names settings, benchmark results, logs and an earlier install's server settings and model profiles. (a) Remove with it cleared: the program, PATH entry, shortcut, `HKLM\Software\private-ai` and the Apps entry go (the `PaiGroup` value with the key); `%LOCALAPPDATA%\private-ai` stays, and so does the local group `pai` with its members: `Get-LocalGroup -Name pai` answers and `Get-LocalGroupMember -Group pai` still lists whoever was added (`RemoveOnUninstall="no"`: the group is machine data, not the product's). (b) Reinstall, uninstall again ticking the box: the tree is gone. (c) Rename the whole `%LOCALAPPDATA%\private-ai` folder away (or remove it): neither the text nor the checkbox shows; a folder without `config\server.ini` still shows them. Same from Control Panel > Programs and Features. After each uninstall: `sc query private-ai-manager` and `sc query private-ai-bff` say the service does not exist, `sc query type= service state= all | findstr /i llama.cpp_` prints nothing, `%ProgramData%\private-ai` is still there with its files, and the engine is still installed with `%ProgramData%\llama.cpp` unchanged.
13. **Engine uninstall with the configuration question**: with the framework installed and `default` running, Settings > Apps > llama.cpp > Uninstall opens `LlamaCppRemoveDlg`, naming `%ProgramData%\llama.cpp\`, the checkbox CLEARED. (a) Remove with it cleared: the program, `HKLM\Software\llama.cpp` and the Apps entry go, `sc query type= service state= all | findstr /i llama.cpp_` prints nothing, `%ProgramData%\llama.cpp` stays with its files, and the framework stays installed: note what the configurator shows and what a Start says. Restart `private-ai-manager`: by the code the services come back and fail to start. (b) Reinstall the engine (the old configuration is used again), uninstall ticking the box: `%ProgramData%\llama.cpp` is gone. (c) `msiexec /x {ProductCode} LLAMA_CPP_DELETECONFIG=1 /qn` and `msiexec /x <engine>` (basic UI): removed, `%ProgramData%\llama.cpp` intact both times.
14. **Silent uninstall keeps data** (framework): `msiexec /x {ProductCode} /qn` (the `QuietUninstallString`), and `msiexec /x {ProductCode} LLAMA_DELETEUSERDATA=1 /qn`: removed, `%LOCALAPPDATA%\private-ai` intact both times. Same for `msiexec /x <framework>` with its basic UI.
15. **Silent install**: `msiexec /i <engine> /qn`, then `msiexec /i <framework> /qn` (all features, default folders) and `msiexec /i <framework> /qn ADDLOCAL=Main INSTALLFOLDER="D:\private-ai\"` (binaries only). `xtask install` does both in order with `/qb`, and so does `xtask install <framework msi> <engine msi>` (files in either order: the engine goes first).
16. **Cancel and rollback**, each product: cancel an install half way: the machine returns to its prior state.
17. **Upgrade from 2.4**: with `llama-cpp-framework-v2.4.0-*-x64.msi` installed (once in its default folder, once in a chosen one), and its configurator and a llama-server running. Run the framework first: refused for want of llama.cpp (step 2). Run the engine: one Apps entry `llama.cpp v<release>` and none named `llama.cpp-framework`; the 2.4 files gone; `HKLM\Software\llama.cpp` holds the engine's `InstallDir` and `Version`; note the engine's folder (by the code: the one 2.4 recorded) and whether the 2.4 configurator and llama-server were stopped (the engine runs no `StopProcesses`; 2.4's own uninstall sequence runs). Then the framework: installed into `Program Files\private-ai\`, not 2.4's folder. Start `pai-config`: the old `%LOCALAPPDATA%\llama.cpp` tree is now `%LOCALAPPDATA%\private-ai` and a start-at-login entry that was on is the `org.privateai.Config` Run value.
18. **A standard user**: log on as a user outside Administrators and outside `pai`. The configurator starts, stops and restarts `default` and the Log window shows its log; saving the server settings or a model profile is refused with the manager's message; `type "%ProgramData%\llama.cpp\config\server@default.ini"` is denied, `type "%ProgramData%\llama.cpp\logs\llama-server@default.log"` works, and creating a file in `logs` or `models` is denied. `type "%ProgramData%\private-ai\logs\private-ai-manager.log"` works too, and the refused save of this step is a line in it naming this user as the caller; creating a `logs` folder under `%ProgramData%\private-ai` is denied: only the manager creates it, so a user cannot pre-create it to redirect the manager's writes. With an API key saved by a member of `pai`, the standard user's Server tab shows the key field unset and "A key is set. Only an administrator can see it." (the strings file's text; the rule behind it is `configure`, and `configure` is `pai`), `pai server show` prints `OpencodeApiKey: (set, withheld)` and the Claude Code snippet `<api-key>`. A member of `pai` saves with no UAC prompt, from an unelevated configurator too, and sees the key. An Administrators member outside `pai`, elevated or not, is refused the save and shown the key withheld: the group, not Administrators, configures. Then add that standard user from an elevated console, `Add-LocalGroupMember -Group pai -Member <user>`, sign out and back in: the save succeeds and the key shows (the membership is in the token, so the next logon is what makes it count: unverified, no Windows run).
19. **Instances and their log**: as a member of `pai`, set the server and a model profile in the configurator and Start. `sc qc llama.cpp_default`: demand start, `"<framework dir>\bin\pai-manager.exe" run-instance default`, account `NT SERVICE\llama.cpp_default`; `sc query llama.cpp_default` RUNNING; the running `llama-server.exe` is the engine's (`<engine dir>\bin\`, the non-default folder of step 3); `%ProgramData%\llama.cpp\logs\llama-server@default.log` fills with llama-server's output. Before the first save, with the shipped `server@default.ini` (no `ModelsDir`, no `StateDir`), turn on `SaveStateOnShutdown` by hand in that file as an elevated administrator (a `pai` member has no write on `config\`: only SYSTEM and Administrators do) and Start: the llama-server command line (Process Explorer, or `Get-CimInstance Win32_Process`) has `--slot-save-path %ProgramData%\llama.cpp\state`, its environment `LLAMA_CACHE=%ProgramData%\llama.cpp\models`, and a Stop writes the snapshot into `state\`; the llama-server's working directory (Process Explorer) is `state\` too. Then `pai server set --port 8080` as a member of `pai`: `server@default.ini` still has `ModelsDir` and `StateDir` only as commented hints, and no `~\.llama.cpp` was created. In the configurator's Server tab the models folder and the snapshot folder are blank, their placeholders `unset: the instance uses %ProgramData%\llama.cpp\models` (and `...\state`); change the port there and Save: the same two hints stay commented. With the models folder still unset, the Models tab scans `%ProgramData%\llama.cpp\models`, and the models field's Browse opens there. As the standard user of step 18 (and as an administrator not elevated), a Hugging Face download (the Models tab's New... > From Hugging Face..., or `pai model-profile download`) is refused before it starts with `Cannot write to %ProgramData%\llama.cpp\models: run as administrator, ...`; from an elevated console `pai model-profile download` lands under `models\` and `server@default.ini` still has `ModelsDir` only as a commented hint. Type a folder into the models field and Save: it is written and shown again after a restart of the configurator. Stop: the service STOPPED and no `llama-server.exe` left. Start again: the previous run is `llama-server@default.previous.log`. Rename the engine's `bin\llama-server.exe` away and Start: the start fails and the log says why; rename it back. Turn on "start llama-server when the system starts" in the Settings tab (or `pai server boot on`): `sc qc llama.cpp_default` shows auto start, and after a reboot the instance runs before anyone logs on; turn it off: demand start again, and `pai server boot` agrees both times. As the standard user of step 18 the change is refused and the toggle goes back.
20. **Framework repair and upgrade with instances**: with `default` running (and set to start at boot, then again with it not set), run the framework > Repair, then an upgrade (step 9). No files-in-use dialog; the verbose log shows `UninstallInstanceServices` running `pai-manager.exe uninstall-services`; afterwards `sc qc llama.cpp_default` exists again (recreated by the new manager), running when it starts at boot and stopped otherwise; `%ProgramData%\llama.cpp\config` unchanged.
21. **The web service**: after step 4, from an elevated console: `sc qc private-ai-bff` shows auto start, the binary path `"<dir>\bin\pai-bff.exe" service` and `NT SERVICE\private-ai-bff`; `sc query private-ai-bff` RUNNING; `sc qfailure private-ai-bff` a restart after 5000 ms and a reset period of 86400 s. `http://127.0.0.1:8590` in a browser shows the page with the framework version and the instance `default` with its state (Running or Stopped, as the configurator shows it); with `sc stop private-ai-manager`, a reload shows "The manager is not running or does not answer." in place of the table (`sc start private-ai-manager` after). `sc stop private-ai-bff` stops it (STOPPED, exit code 0) and `sc start private-ai-bff` brings it back. Uninstall (step 12): no files-in-use dialog for `pai-bff.exe`, and `sc query private-ai-bff` says the service does not exist.
22. **Engine repair, upgrade and downgrade with instances**: with the framework installed, a second instance created by hand (`server@second.ini` on another port, as an administrator, then restart `private-ai-manager`), `default` running and `second` stopped. (a) Engine > Repair: no files-in-use dialog, no reboot request; the verbose log shows `StopInstances` and `StartInstances`; afterwards `default` runs again, `second` is still stopped, both services exist with their start types unchanged, and `%ProgramData%\llama.cpp\instances.running` is gone. (b) The same for an upgrade to N+1 (step 9): `StopInstances` runs in the old package's part of the log, `StartInstances` in the new one's. (c) With N+1 installed and `default` running, `xtask install <engine N msi>`: the removal runs with `KEEPINSTANCES=1` (`--dry-run` prints it; `build\windows\msi-uninstall-llama.cpp.log` shows it, `StopInstances` and no `RemoveInstanceServices`), both services survive it, and after N installs `default` runs again on N's llama-server. (d) A real uninstall of the engine still deletes both services (step 13). (e) An engine upgrade with a `llama-server.exe` started by hand from the engine's `bin\`: not killed; Windows Installer's files-in-use dialog names it.
23. **A stale start-at-login entry is repaired**: as a user, set the HKCU Run value `org.privateai.Config` to `"C:\nowhere\pai-config.exe" gui --minimized` and start the configurator: the value is now `"<framework dir>\bin\pai-config.exe" gui --minimized`, and the next logon starts it in the tray. Again with `gui` alone: rewritten without `--minimized`. Set the stale value, switch the entry off in Task Manager > Startup apps and start the configurator: the value is left as it was. Delete the value and start it: no value is created.

### Open checks

What no test here can settle, to note in the run of the plan above:

- **The launch condition's order**: `FindRelatedProducts` must set `LLAMACPPFOUND` before `LaunchConditions` in both sequences, for a full-UI and a silent install alike (steps 2 and 5 show it).
- **Restart Manager at `InstallValidate`** (engine): `StopInstances` is deferred and runs after `InstallValidate`, where Windows Installer checks files in use, so a running instance's `llama-server.exe` is still running at that check; step 22 shows whether a files-in-use dialog or a reboot request comes up anyway. In an upgrade the old package's `StopInstances` runs inside the new package's transaction (`RemoveExistingProducts` right after `InstallValidate`).
- **Restart Manager at `InstallValidate`** (framework): the instance services run `llama-server.exe` from llama.cpp's `bin\` until `UninstallInstanceServices`, after `InstallValidate`; check that a running instance raises no files-in-use dialog and no reboot request on the framework's repair, upgrade and uninstall.
- **A killed instance service** reads Failed in the configurator until its service is deleted: kill `pai-manager.exe run-instance default` from an elevated Task Manager and check what the configurator and `sc query` show, before and after a Start.
- **The folders' owner**: `PermissionEx` sets the DACL only; read the owner of `%ProgramData%\llama.cpp`, `%ProgramData%\private-ai` and their folders (`icacls`, `Get-Acl`).
- **The manager's record file has no size cap and no rotation**: `%ProgramData%\private-ai\logs\private-ai-manager.log` grows with every guarded call. After a machine's worth of guarded calls note its size, that the file survived an uninstall (the MSI does not know the folder), and that records keep being appended after a repair and after an upgrade.
- **GPU compute from a session-0 virtual account**: the instance's log lists the GPUs on every backend (ROCm, CUDA, Vulkan) and a model runs on them as `NT SERVICE\llama.cpp_default`. If not, LocalService is the fallback agreed in `PLAN.md`.
- **The web service's account reads `config\`**: `NT SERVICE\private-ai-bff` gets its read of `%ProgramData%\private-ai\config\bff.ini` only through `NT SERVICE\ALL SERVICES`. Write `bff.ini` with `[Bff]` `Listen = 127.0.0.1:8591` as an administrator and restart the service: `http://127.0.0.1:8591` answers. If it still listens on 8590, the file was not read.
- **A failed web service start says nothing more**: set `Listen = 8590` in `bff.ini` (not an `ip:port`: `listen::parse` refuses it, exit 1; `0.0.0.0:8590` is accepted since 1aac8e1, so it starts), restart: the start fails; then a valid address on a port another program holds: the start fails too (the bind fails, exit 1). Note what `sc query private-ai-bff` (the exit code) and the System event log show in each case, since the service's own error line is lost.
- **`_` in a virtual account name**: the SCM accepts `NT SERVICE\llama.cpp_default` and the service logs on (no `ERROR_SERVICE_LOGON_FAILED`, 1069).
- **The `pai` group's custom action** (`PaiGroup`): a first install creates the group, a repair and the old half of an upgrade run it again on a group that already exists (what CI's two repairs do), and an uninstall leaves the group and its members. Steps 4, 9, 12 and 18 with `Get-LocalGroup` and `Get-LocalGroupMember`: run 43743455408 (the workflow lines of 1e4094a) showed the silent install creating the group and a member survive its two repairs and the framework's silent uninstall, so what is left of that list is the empty group of a full-UI install (step 4), an upgrade (step 9), the full-UI uninstall (step 12) and a save made as a member of `pai` (step 18).
