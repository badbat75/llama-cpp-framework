# installer\

The two MSI sources (WiX Toolset), their custom-action scripts, the WiX pin and the sources of the external distributions. Windows ships **two installers**: **llama.cpp's own MSI** (`llama.cpp.wxs`: the engine, its GPU runtimes and its default configuration) and **the framework's MSI** (`private-ai-framework.wxs`: `pai-config`, `pai`, `pai-manager`, `pai-bff`, no llama.cpp file), each with its own UpgradeCode and version, upgraded on its own. `xtask package [llama|framework]` (see [docs\build-packaging.md](../docs/build-packaging.md)) stages each product into its own tree, `build\windows\staging\llama\` and `build\windows\staging\framework\`, and builds its MSI from that tree. llama.cpp's MSI is **self-contained for the GPU backends**: nothing is downloaded on the end user's machine, and there is no post-install helper.

**Status: none of this has been compiled by WiX or run on Windows** since the split into two installers (commit `836fdc7`, 2026-11-14), nor since llama.cpp's MSI learned to keep its instances (commit `9462eab`). The `.wxs` files are checked as XML by xtask's tests (`xtask\src\common\msi\tests\`; `engine_lifecycle.rs` evaluates each of llama.cpp's custom-action conditions over a first install, a repair, an upgrade, an uninstall and `xtask install`'s downgrade), the Rust is type-checked with the GNU target, and the rest is read from the code. Facts below without a measurement are by the code until the test plan at the end has run.

- `dist-sources.psd1` says **where** each external distribution is looked up, and holds **no versions**: nothing is pinned, every reader resolves the newest STABLE release at run time (ROCm/TheRock `Dir` + `Marker` + tarball `Indexes`; CUDA `Dir` + `Marker`, redist index, `Platform` and the redist `Components` the toolkit is assembled from; Vulkan SDK `Dir` + `Marker`, latest-version URL, installer template and `Signer`). It also holds the **build machine's dist layout**: `DistRoot` (default `E:\`, overridden by `-DistRoot` on `scripts\00-install-prerequisites.ps1` and `--dist-root` on `xtask configure`, `PRIVATE_AI_DIST_ROOT`, or the root recorded in `config-build.psd1`) and `DistOs` (`windows`), giving `<DistRoot>\<Dir>\<Version>\<DistOs>`; the helpers that read it are in the root `scripts\dists.ps1`. **End users never see that layout**: what the backends load is copied out of it into the package. It is the source for `scripts\00-install-prerequisites.ps1` and `scripts\common.ps1`; xtask reads the same sources from `installer\dist-sources.toml`, so a source changes in both files. **ROCm host by version**: 10.0+ stables live under `stable.repo.amd.com/rocm/core/tarball/` (`rc.`/`nightly.repo.amd.com` for the others); everything up to 7.14 and the 10.0.0 rcs stay on `repo.amd.com/rocm/tarball-multi-arch/`. A wrong host fails with a `403` that reads exactly like "not published yet", so the URL is FOUND in an index, never composed: HTML with an inline JS `files` array, matched strictly (`\d+\.\d+\.\d+` immediately before the extension) so `-tests-` builds and dated nightlies (`10.1.0a20260831`) are not taken as releases. Prerelease indexes stay out. A new host for a future major means adding its index here.
- **The GPU runtimes are in llama.cpp's MSI** (`xtask\src\windows\package.rs` behind `xtask package`, "Bundle the GPU runtimes"; the Linux counterpart is the same section of `xtask\src\linux\package.rs`, behind `xtask package`). The target machine needs the GPU drivers and the VC++ runtime; no ROCm dist, no `HIP_PATH`, no cuBLAS download, no Vulkan runtime of its own.
  - **Which libraries is not a list**: it is the import closure of the staged `.exe`/`.dll` (`pe_imports` in `xtask\src\windows\package.rs` reads the PE import and delay-import directories, headers only), restricted to what resolves inside a dist: the ROCm dist's `bin\`, the CUDA dist's `bin\x64`, the Vulkan SDK's `Bin\` and `Runtime\`. Whatever else an import names is a **system library and stays out**: Windows' own DLLs, the VC++ runtime (`MSVCP140`, `VCRUNTIME140*`, `libomp140.x86_64`). Today that yields `hipblas`, `rocblas`, `rocsolver`, `libhipblaslt`, `origami`, `amdhip64_7`, `rocm_kpack`, `cublas64_13` + `cublasLt64_13` and `vulkan-1`. `xtask package` refuses to package a `ggml-hip.dll` without `hipblas.dll`, a `ggml-cuda.dll` without `cublas64_*.dll`, or a `ggml-vulkan.dll` without `vulkan-1.dll`.
  - **Licences**: `share\licenses\` holds a text for everything bundled, `README.txt` saying which covers what. `xtask\src\common\licenses.rs` maps each library to its text and refuses to package a library it does not name, or whose text it cannot find, so a new library in a dist gets read before it ships. Texts come from the dist when it carries them, otherwise from `licenses\` here (its README says where each was taken from).
  - **The Vulkan loader is bundled because a GPU driver does not guarantee one**: a machine can have the driver and no `vulkan-1.dll` in System32, and then `ggml-vulkan.dll` loads whichever copy PATH reaches, or none. The SDK ships no loader of its own, only an import lib and `Helpers\VulkanRT.exe`, the runtime installer that writes System32, and LunarG no longer publishes the standalone runtime archive the SDK's version used to ship (the `VulkanRT-*-Components.zip` is gone for every version, 1.3.x included), so `scripts\00-install-prerequisites.ps1` copies the loader out of System32, where that installer leaves it, into `Runtime\` of the dist, also for an SDK installed earlier, and only when Authenticode says it is LunarG-signed: a driver's own loader, signed by the vendor, is not bundled. Its licence is the vulkan-loader Apache 2.0 in `licenses\vulkan-loader.txt`, the text of the loader's own code, the same one Linux's `libvulkan.so.1` carries. The loader beside the exe still finds the driver's Vulkan implementation through the registry, so only the driver stays a requirement.
  - **Everything lands flat in `bin\`**, next to `llama-server.exe`, which is also what the dist's own `bin\` looks like. That is a load-order fix as much as a convenience, and it is what makes BF16/F16 run on RDNA4: Windows resolves imports from the exe's dir and then System32, **both before PATH**, and the driver keeps its own `amdhip64_7.dll` in System32, so a runtime reached through PATH means the dist's `rocblas.dll` + `libhipblaslt.dll` running against the DRIVER's HIP runtime, the mix that aborts at the first prefill batch. `rocm_kpack.dll` is `amdhip64_7`'s direct import, so it must come from the same dist.
  - **What no import table shows** is added by name, ROCm only: `amd_comgr*.dll` (asked for by bare name at run time, and System32 holds the driver's build; with the Ryzen iGPU (gfx1036) enabled that mix makes `hipGetDeviceCount` fail with `no ROCm-capable device is detected` and the HIP backend disappears), and the **kernel stores**: `bin\rocblas\library` (Tensile, found relative to `rocblas.dll`; without it the first matmul under `ROCBLAS_USE_HIPBLASLT=0` dies with `Could not initialize Tensile host`), `bin\hipblaslt\library`, and `.kpack\blas_lib_*.kpack`, which sits beside `bin\` as it does in the dist. Only the architectures in `GpuTargets` are copied (files or per-arch directories alike, plus whatever names no architecture): the CDNA `gfx908`/`gfx90a` half could never be used by a `ggml-hip.dll` with no code for it. About 355 + 465 + 95 MiB instead of 700 + 519 + 1535.
  - The bundle is the runtime of the dist the package was **built** against. It does not follow a later `HIP_PATH` move on the build machine and does not have to: it changes with the next package.

## The two MSIs

- `wix-toolset.psd1`: **the WiX pin**. WiX Toolset **7.0.1** as a .NET global tool (`dotnet tool install --global wix`), the extensions **`WixToolset.UI.wixext`** (WixUI dialogs) and **`WixToolset.Util.wixext`** (`WixQuietExec`), at the tool's version, and the .NET SDK winget id (`Microsoft.DotNet.SDK.10`). Pinned, unlike the dists: the `.wxs` files are written against one schema and one WixUI dialog set, and a WiX major changes both. `scripts\00-install-prerequisites.ps1` installs it, `xtask configure` records the exe as `WixExe` in `config-build.psd1`, `xtask package` builds with it (`xtask package --wix <wix.exe>` overrides, a non-pinned version with a warning).
  - **WiX v7 is under the Open Source Maintenance Fee EULA**: every command but `--version`/`eula` fails with `WIX7015` until `wix eula accept wix7` was run once by the user building. The scripts NEVER accept it on the user's behalf: the prerequisites script reports it, `xtask package` stops before staging with the command to run. (OSMF: organizations above USD 10,000 yearly revenue owe the fee.) WiX 6.0.2 built and validated the single MSI before the split without the EULA (`xtask package --wix <path to a 6.0.2 wix.exe>`); the two `.wxs` of today have not been built by either.
- **The two products**, side by side (`xtask\src\common\msi.rs`: `file_name`, `staging_dir`, `wxs`, `uninstall_key`):

  | | llama.cpp's MSI | The framework's MSI |
  | --- | --- | --- |
  | Source | `llama.cpp.wxs` | `private-ai-framework.wxs` |
  | File in `dist\` | `llama.cpp-v<release>-x64.msi` (no `+pai<N>`) | `private-ai-framework-v<version>-x64.msi` |
  | ProductVersion | The llama.cpp release without its `v` (`msi::product_version`: refused when it is not a `vX.Y.Z` release or does not fit 255.255.65535) | The framework version, `[workspace.package] version` of the root `Cargo.toml` |
  | UpgradeCode | `386BFFA7-BF06-4004-BA17-3F5C752DA61A` | `F21D044C-04F5-478D-8F0A-A9B940DB23C3` (release 2.4's `llama.cpp-framework` too) |
  | Install folder | `%ProgramFiles%\llama.cpp\` (choosable): `bin\`, `lib\`, `share\`, `.kpack\` | `%ProgramFiles%\private-ai\` (choosable): `bin\`, `share\` |
  | Registry (64-bit view) | `HKLM\Software\llama.cpp`: `InstallDir`, `Version` | `HKLM\Software\private-ai`: `InstallDir` (and the optional features' values) |
  | Apps entry | `Uninstall\llama.cpp`, "llama.cpp v<release>" | `Uninstall\private-ai`, "Private AI Framework v<version>" |
  | Machine data | `%ProgramData%\llama.cpp\{config,logs,models,state}` | `%ProgramData%\private-ai\config\` |
  | Services | None installed; stops the running instance services `llama.cpp_<id>` before a repair or upgrade and starts them again after, deletes them on uninstall | `private-ai-manager`, `private-ai-bff`; deletes the instance services on uninstall, repair and upgrade |
  | Requires | The GPU drivers, the VC++ runtime | llama.cpp at the release it was built against or newer, the VC++ runtime |

  **Never change either UpgradeCode**: it is the product's identity across versions, `MajorUpgrade` finds the installed version by it, and a new value installs side by side with the old one. The framework's also finds llama.cpp's by its UpgradeCode (below). ProductCode is generated per build, so every package is a major upgrade of the previous one.
- **Built by `xtask package [llama|framework]`** (default: both, llama.cpp's first; `xtask\src\windows\package.rs`). Both need the llama.cpp clone on a release tag, the framework's too: its minimum engine is that release. Each product is staged, harvested, built, size-checked and validated on its own; its licence page is written beside its staging tree (`build\windows\staging\llama.license.rtf`, `framework.license.rtf`, not installed) and its WiX intermediates go to `build\windows\staging\<product>.wix-obj\`, removed after the build. Defines passed to llama.cpp's: `Version` (the release), `StagingDir`, `HasLib`/`HasKpack`, `EstimatedSizeKb`, `LicenseRtf`, `RemoveInstancesCmd` (`msi-remove-instances.ps1` as `-EncodedCommand` base64), `StopInstancesCmd` and `StartInstancesCmd` (`msi-stop-instances.ps1`, `msi-start-instances.ps1`, the same way). To the framework's: `Version`, `LlamaCppMin` (the release, without its `v`), `StagingDir`, `EstimatedSizeKb`, `LicenseRtf`, `StopProcessesCmd` (`msi-stop-processes.ps1`).
- **Upgrades** (both): `MajorUpgrade` with the default `afterInstallValidate` (the old product is removed in full before anything new is written: the robust order for thousands of files whose component set moves with every llama.cpp release). `AllowSameVersionUpgrades="yes"`, so a repackage of the same version replaces the installed one; that is what ICE61 warns about, so `xtask package` validates with `-sice ICE61`. **Downgrades are refused** with a message telling the user to uninstall first ("A newer version of llama.cpp is already installed..." and "A newer version of Private AI Framework is already installed..."): an MSI downgrade over a newer tree has no use that outweighs a half-old install. Each product upgrades without touching the other: a newer llama.cpp installs under an installed framework, and the reverse while the engine stays at or above the framework's minimum.
- **The framework requires llama.cpp.** Windows Installer compares no versions in a condition, so the framework's MSI finds the engine by its UpgradeCode: `<Upgrade>` with `UpgradeVersion Minimum="<LlamaCppMin>" IncludeMinimum="yes" OnlyDetect="yes" Property="LLAMACPPFOUND"` (`FindRelatedProducts` sets the property when an installed llama.cpp is at that release or newer, and never removes it), then the launch condition `Installed OR LLAMACPPFOUND`, in full and silent UI alike, with the message "llama.cpp v<min> or newer must be installed first: run its installer, llama.cpp-v<min>-x64.msi or a newer one, then this installer again." Maintenance of an installed framework is never refused. The welcome page names the requirement too.
- **Release 2.4** (`llama.cpp-framework`, the framework's UpgradeCode) installed into `Program Files\llama.cpp\` and registered `HKLM\Software\llama.cpp`, both llama.cpp's MSI's now. **llama.cpp's MSI removes it**: an `<Upgrade>` of the framework's UpgradeCode with `Maximum="2.99.0" IncludeMaximum="no"`, not `OnlyDetect`, so `RemoveExistingProducts` removes a 2.4 install and never a 2.99+ framework. Its `INSTALLFOLDER` search reads `Software\llama.cpp\InstallDir`, which 2.4 wrote, before that removal: by the code the engine takes a directory chosen in 2.4 as its own default. **The framework's MSI no longer carries over a 2.4 install folder**: it reads only `Software\private-ai\InstallDir`, and installs into `Program Files\private-ai\` unless an earlier 2.99+ install recorded another. Install llama.cpp's MSI first: with 2.4 still installed, the framework's MSI finds no engine and refuses. `pai-config` moves the 2.4 user tree at its first start ([crates\config\README.md](../crates/config/README.md#migration-from-24)).
- **Layout**, per-machine, the folder choosable (CustomizeDlg's Browse), the default taken from the product's own `InstallDir` when an earlier install recorded one. **No file at either root.** The payload is **harvested** at build time (`<Files Include="...\**">`, built into WiX 6+; no heat): one component per file, GUIDs derived from the target path, so a file keeps its component across builds. The staging tree IS the installed tree.
  - llama.cpp's: `bin\` (llama.cpp's executables and DLLs, the ggml backends, the GPU runtimes and OpenSSL flat beside `llama-server.exe`, `llama.ico`), `lib\` and `.kpack\` (ROCm, beside `bin\` as in the dist), `share\` (`licenses\`, and `defaults\`: the read-only `server@default.ini` and `presets.ini`, below). `xtask package` prunes llama.cpp's `test*.exe` and `include\` before the harvest.
  - The framework's: `bin\` (`pai-config.exe`, `pai.exe`, `pai-manager.exe`, `pai-bff.exe` from cargo's release output, `msi::CARGO_EXES`, and `llama.ico`), `share\` (`benchmarks\`; `strings\`, the GUI's `en_US.toml` and the CLI's `cli.toml`; `licenses\`). `pai-manager.exe` and `pai-bff.exe` are left out of the harvest: each is the key path of its own component, `ManagerService` and `BffService`, since Windows Installer wants a service's executable there.
  - **The framework finds llama-server through the engine's registration**: `paths::llama_bin` looks in the tree builds first, then in `<HKLM\Software\llama.cpp InstallDir>\bin\` (`paths::engine_install_dir`, `llama_bin_with_engine`), so a tree build keeps running the llama-server it built and the installed manager runs the installed engine's.
- **Registry**: each `InstallDir` carries a trailing backslash (an MSI directory property always does); every reader joins onto it. Each key is removed on uninstall. The framework no longer writes `LlamaBuild`.
- **The Apps list entries are ours, not Windows Installer's.** Each MSI sets `ARPSYSTEMCOMPONENT=1`, which hides its own entry, and writes its key under `HKLM\...\Uninstall\` with DisplayName, DisplayVersion, Publisher `Private AI Framework`, DisplayIcon `bin\llama.ico`, InstallLocation, EstimatedSize, NoRepair, `ModifyPath = MsiExec.exe /I{ProductCode}` (the maintenance wizard), `UninstallString = MsiExec.exe /I{ProductCode} LLAMA_CPP_UNINSTALL=1` (llama.cpp's) or `LLAMA_UNINSTALL=1` (the framework's): the FULL UI, opened on the removal page, and `QuietUninstallString = MsiExec.exe /X{ProductCode} /qn`. Why: Windows runs an MSI-registered entry's Uninstall as a **basic-UI** `msiexec /x`, where no dialog of the package can show, so neither removal question below would be asked from Settings. `xtask install` reads `DisplayVersion` and the ProductCode of a downgrade from these entries.
- **Features and UI.** No custom config page in either: runtime configuration is `pai-config`'s job. The licence page (`LicenseAgreementDlg`, Next enabled once its checkbox is ticked) shows each MSI's own `license.rtf`: which text covers which library, the MIT licence, and, in llama.cpp's, NVIDIA's terms in full, since those restrict what the MIT does not. A silent or basic-UI install does not show it.
  - llama.cpp's (`LlamaCppUI`): one feature, `Main` (`AllowAbsent="no"`, carries the folder). `LlamaCppWelcomeDlg` (ours: WixUI's WelcomeDlg has room for four lines) doubles as the **runtime-requirements notice** (VC++ always; the Adrenalin driver for AMD, the NVIDIA driver for NVIDIA; for Vulkan, the GPU's driver, whatever the vendor): a backend whose driver is missing is skipped silently at runtime, so the installer is the one place the user is told. Then `LicenseAgreementDlg`, CustomizeDlg (Browse), VerifyReadyDlg. Maintenance: MaintenanceWelcomeDlg, MaintenanceTypeDlg (Change, Repair, Remove); Remove leads to `LlamaCppRemoveDlg`. No PATH entry and no Start Menu shortcut: llama.cpp's `bin\` is not on PATH.
  - The framework's (`LlamaUI`, WixUI_FeatureTree): `Main` ("Private AI Framework (required)": the programs, the services, the machine data; `AllowAbsent="no"`, carries the folder), `SystemPathFeature` "Add to system PATH" (`Environment` PATH, `Part="last"`, `System="yes"`: `[BINFOLDER]` appended to the machine PATH and removed on uninstall, so `pai` runs from any new console; Windows Installer broadcasts `WM_SETTINGCHANGE` itself), `StartMenuFeature` "Start Menu shortcut" (`Private AI Framework\Private AI Framework`, to `pai-config.exe`, in the all-users Start Menu). All three on by default. The two optional components key on `Software\private-ai` values `SystemPath`/`StartMenuShortcut` (a per-machine component needs a per-machine key path). `LlamaWelcomeDlg` names what is needed and not included: llama.cpp from its own installer, the VC++ runtime, the GPU drivers llama.cpp's installer names. Then `LicenseAgreementDlg`, CustomizeDlg, VerifyReadyDlg; Remove leads to `LlamaRemoveDlg`.
- **The manager service** (framework, component `ManagerService`): `ServiceInstall` `private-ai-manager`, display name "Private AI Framework manager", `pai-manager.exe serve`, own process, **LocalSystem** (no `Account`), **automatic** start; `ServiceConfigFailureActions` restarts it 5 s after a failure (every failure; the count resets after a day without one), as the Linux unit's `Restart=on-failure`. `ServiceControl` starts it on install, stops it on install and uninstall (`StopServices`, before its files are replaced or removed) and deletes it on uninstall. `StopProcesses` leaves it alone. At its start the manager creates, re-applies (the start type left as it is: `SERVICE_NO_CHANGE`) or deletes the instances' services to match the instances in `%ProgramData%\llama.cpp\config\` (an instance whose service cannot be set up is written to standard error as `manager-service-sync-failed`, "cannot set up the service of instance ...", and the others are still set up; a failure of the SCM itself, before any instance, as `manager-scm-sync-failed`), then serves the pipe `\\.\pipe\private-ai-manager`; it starts no instance itself: the SCM starts at boot those whose start type is automatic. Everything it does on Windows is type-checked with the GNU target and unit-tested on Linux, never run on Windows yet:
  - **The pipe**: SDDL `D:P(D;;GA;;;NU)(A;;GA;;;SY)(A;;GA;;;BA)(A;;0x12008b;;;IU)(A;;0x12008b;;;S-1-5-80-4088784262-1422927641-1363593751-33154763-2531830098)` (network logons denied; SYSTEM and Administrators full; interactive users read and write data, never `FILE_CREATE_PIPE_INSTANCE`; the last ACE gives the same client rights to `NT SERVICE\private-ai-bff`, the web service, by its service SID, computed by the [MS-LSAT] 3.1.1.1.2 rule from the service name and pinned by a test in `windows.rs`; its token is neither interactive nor an administrator's, so it gets the read-only calls only, `ListInstances` and `Status`), remote clients rejected, a byte stream: each request and reply a u32 little-endian length and a UTF-8 JSON body of at most 1 MiB, with the D-Bus method names and error names (`pai_core::client::pipe`, `crates\manager\src\manager\pipe.rs`). The caller is the client token's user SID: `control` (start, stop, restart) for an interactive user or an Administrators member, `configure` (writing a file) for an Administrators member, elevated or not (a deny-only Administrators counts); no prompt can cross the pipe (`crates\manager\src\manager\windows.rs`).
  - **The instances**: one SCM service per instance, `llama.cpp_<id>` (display name `llama.cpp server <id> (Private AI Framework)`), own process, created with the manual start type and switched between manual and automatic by the configurator's "start llama-server when the system starts" (the manager's `BootEnabled`, any client, and `SetBootEnabled`, `configure`; `QueryServiceConfigW` and `ChangeServiceConfigW` in `scm.rs`), running `"<framework bin>\pai-manager.exe" run-instance <id>` as the virtual account `NT SERVICE\llama.cpp_<id>` (`scm.rs`), which starts llama-server from llama.cpp's `bin\`. Its output goes to `%ProgramData%\llama.cpp\logs\llama-server@<id>.log`, opened before the launch so a launch error is written there too; a non-empty log of the run before becomes `llama-server@<id>.previous.log`, replacing the older one. Stop kills llama-server outright. A llama-server that exits on its own with a non-zero code leaves the service stopped with that code as its service-specific exit code, which the configurator shows as Failed.
- **The web service** (framework, component `BffService`): `ServiceInstall` `private-ai-bff`, display name "Private AI Framework web service", `pai-bff.exe service` (the entry that hands the process to the service dispatcher; from a console it exits 1), own process, **automatic** start, as the virtual account **`NT SERVICE\private-ai-bff`** (no password: a virtual account takes none), the way the instances run; `ServiceConfigFailureActions` restarts it 5 s after a failure, the count reset after a day, as the Linux unit's `Restart=on-failure`. `ServiceControl` starts it on install, stops it on install and uninstall and deletes it on uninstall; `StopProcesses` leaves it alone. It serves the web UI on `[Bff] Listen` of `%ProgramData%\private-ai\config\bff.ini`, `127.0.0.1:8590` without one ([crates\bff\README.md](../crates/bff/README.md)), and reads that file through the read `NT SERVICE\ALL SERVICES` has on `config\` (the table below). Its `Error:` line goes nowhere under the SCM: by the code, a bad `bff.ini` ends the process (exit 1) before it reaches the dispatcher, and a bind failure comes after the service reported running, which then stops with the bind error as its Win32 exit code, so either shows only in the SCM's state and exit code. Both are open checks below.
- **The machine data trees** (`paths::windows_machine_dirs`): **`%ProgramData%\llama.cpp\`**, created by llama.cpp's MSI (components `EngineData*`), with `config\` (the instances' `server@<id>.ini`, `presets.ini`, `presets.ini.disabled`, written by the manager, `paths::engine_config_dir`; `OpencodeApiKey` lives there), `logs\` (`paths::system_log_dir`), `models\` and `state\` (the default `ModelsDir` and `StateDir` of an instance: a folder under a user's profile is not readable by an instance's virtual account, so when `server@<id>.ini` leaves either unset or blank, `pai-manager run-instance` fills in `paths::instance_models_dir` or `paths::instance_state_dir`, on Windows only: `launch::with_instance_defaults`; `pai` and the GUI's Server tab leave an unset one unset at a save, written as its commented hint, `server_cfg::render_for`, the GUI showing it blank with the instance default as placeholder (what still reaches the user's folder: Known gaps); an instance's working directory is `state\`, `launch::instance_current_dir`); and **`%ProgramData%\private-ai\`**, created by the framework's MSI (components `MachineData*`), with `config\` only (`bff.ini`, `paths::system_config_dir`). Fixed GUIDs, each folder its own key path. Each folder has a protected DACL (`PermissionEx Sddl`, `P`: nothing inherited from `%ProgramData%`, whose ACL lets any user create files; `OICI`: inherited below it); `S-1-5-80-0` is `NT SERVICE\ALL SERVICES`, `0x1200a9` read and execute, `0x1301bf` modify without `WRITE_DAC`, `WRITE_OWNER` or delete-child:

  | Folder | SYSTEM, Administrators | Services (`S-1-5-80-0`) | Users (`BU`) |
  | --- | --- | --- | --- |
  | `llama.cpp\`, `private-ai\` | full | none | read |
  | `llama.cpp\config\`, `private-ai\config\` | full | read | none: they go through the manager |
  | `llama.cpp\logs\`, `llama.cpp\models\`, `llama.cpp\state\` | full | modify | read (the Log window opens the instance's file) |

  Windows Installer removes such a folder only when empty. Nothing in the framework's MSI deletes these files; llama.cpp's deletes `%ProgramData%\llama.cpp\` only when asked (below).
- **llama.cpp's defaults, copied only when missing.** `share\defaults\server@default.ini` and `presets.ini` are installed read-only in llama.cpp's folder, and each is also the key file of a component in `%ProgramData%\llama.cpp\config\` (`DefaultServerIni`, `DefaultPresetsIni`) marked **`NeverOverwrite`** (not installed when the file already exists, so what the user or the manager wrote stays, on repair and upgrade too) and **`Permanent`** (an uninstall or the old half of an upgrade leaves it). Their content is `crates\core\defaults\windows\` (`msi::engine_defaults`): [build-packaging.md](../docs/build-packaging.md#the-msis-windows) says what it holds. So once llama.cpp's MSI has run, the manager already has `server@default.ini` and `presets.ini`, and the configurator's import of an earlier per-user file offers only a missing `presets.ini.disabled` ([crates\config\README.md](../crates/config/README.md#through-the-manager-linux-windows)).
- **The instances' services** are created at run time by the manager, so Windows Installer does not know them. Each MSI deletes them with a deferred, not impersonated (deleting a service takes LocalSystem), `Return="ignore"` `WixQuietExec` after `StopServices`:
  - The framework's `UninstallInstanceServices` runs `"[BINFOLDER]pai-manager.exe" uninstall-services` before `RemoveFiles` when `REMOVE~="ALL" OR REINSTALL`: on an uninstall, a repair and the old product's half of an upgrade. It stops and deletes every `llama.cpp_<id>` service; what it prints lands in the MSI log, and a service left behind is deleted by the next manager's own sync. The new manager recreates the services from the instances on disk when it starts, so after a repair or upgrade an instance that was running without boot start comes back stopped.
  - llama.cpp's `RemoveInstanceServices` runs `msi-remove-instances.ps1` when `REMOVE~="ALL" AND NOT UPGRADINGPRODUCTCODE AND NOT KEEPINSTANCES`: on an uninstall, **not** on an upgrade, a repair or the removal `xtask install` makes before an engine downgrade. A script, not the manager: the engine does not require the framework, so the manager may be absent. It stops and deletes every service named `llama.cpp_*`, nothing else. With the framework still installed and `config\` kept, the manager's next start recreates them from the instances on disk (its sync), and their start then fails for want of a llama-server.
  - **`KEEPINSTANCES=1`** (a secure public property) is set only by `xtask install`'s removal of the newer engine before a downgrade (`msi::removal_args`): the instance services stay, so the older release installed next finds them.
- **Running instances kept across a repair, an upgrade and that downgrade** (llama.cpp's MSI, deferred, as LocalSystem, `Return="ignore"`: an instance that does not stop or start never rolls the installation back):
  - `StopInstances` runs `msi-stop-instances.ps1` before `DeleteServices` when `Installed AND (REINSTALL OR UPGRADINGPRODUCTCODE OR KEEPINSTANCES)`: in the package being repaired, in the OLD package of an upgrade (`MajorUpgrade` removes it in full right after `InstallValidate`, before the new one writes anything) and in the removal before a downgrade. It writes the names of the running `llama.cpp_*` services, one per line, to **`%ProgramData%\llama.cpp\instances.running`** (only when one runs, so a record an earlier failed run left is not overwritten with nothing), then stops them. The services themselves stay.
  - `StartInstances` runs `msi-start-instances.ps1` after `StartServices` when `NOT (REMOVE~="ALL")`: a first install (the older release of a downgrade), a repair and the new package of an upgrade. It starts each `llama.cpp_*` name in `instances.running`, then deletes the file; no file, nothing started. An instance that was stopped stays stopped, whatever its start type. By the code, an installation that fails between the two leaves `instances.running` in place, and the next install or repair starts what it names.
- **The configuration on llama.cpp's uninstall** (`%ProgramData%\llama.cpp\`: the instances' configuration, logs, models and, in `state\`, slot snapshots). `LlamaCppRemoveDlg` says where they are and offers them for deletion with a checkbox that starts **cleared** ("Also delete the configuration, logs, models and state (this cannot be undone)"). The deferred action `DeleteEngineData` (`rd /s /q`, not impersonated: users have no access to `config\`; `Return="ignore"`) runs after `RemoveFiles` only with `REMOVE~="ALL"`, not as the old half of an upgrade, with the box ticked and **`UILevel` 5 (full UI)**: a silent or basic-UI removal keeps the folder whatever properties the command line passes (`LLAMA_CPP_DELETECONFIG=1` included). The dialog appears and is skipped in the same cases as the framework's user-data dialog below, with `LLAMA_CPP_UNINSTALL=1` in place of `LLAMA_UNINSTALL=1`, and it always shows the checkbox (no folder search).
- **User data on the framework's uninstall** (`%LOCALAPPDATA%\private-ai`: settings, benchmark results, logs, state snapshots, an earlier install's server and preset files). `LlamaRemoveDlg` offers it for deletion with a checkbox that starts **cleared** (keeping the data is the default), shown whenever that folder exists (`LLAMA_USERDATA_FOUND`: a `DirectorySearch` of the folder itself). Its text names the settings, benchmark results and logs, and an earlier install's server settings and presets: under the manager the server and preset files are in `%ProgramData%\llama.cpp\config\`, which the framework's uninstall never deletes. The tree offered is the **uninstalling user's**: `%LOCALAPPDATA%` is per user, the install per machine; other users' trees are never touched. The deferred action `DeleteUserData` (impersonated: the user's rights on the user's tree; `Return="ignore"`: a held file never rolls back the uninstall) runs only with `REMOVE="ALL"`, not as the old half of an upgrade, with the checkbox ticked and **`UILevel` 5 (full UI)**: a silent or basic-UI removal never deletes the data, whatever properties the command line passes.
  - **The dialog appears** when the full UI removes the product: Settings > Apps > Private AI Framework > Uninstall (our `UninstallString`), Control Panel > Programs and Features > Uninstall (same string), Modify (or the `.msi` run again) > Remove, `msiexec /i <msi or {ProductCode}> LLAMA_UNINSTALL=1`, and `msiexec /i ... REMOVE=ALL` with full UI.
  - **It does not appear, and the data is kept**, when: the uninstalling user has no `%LOCALAPPDATA%\private-ai` (nothing to offer); the removal is the old half of an upgrade (`MajorUpgrade`); the UI is basic, reduced or none: `msiexec /x` (any UI level: `/x` alone is basic UI), `/qb`, `/qr`, `/qn`, the `QuietUninstallString`, winget/Intune/SCCM silent uninstalls; or the removal was started by another program through the Windows Installer API at a reduced UI level.
- **Previous non-MSI installation: refused by the framework's MSI, nothing changed.** An `HKLM\...\Uninstall\llama.cpp` or `HKLM\...\Uninstall\private-ai` entry whose `UninstallString` does not contain `msiexec` (AppSearch `PREVIOUSUNINSTALLSTRING`, `NEWUNINSTALLSTRING`) fails the launch condition (`Installed`, or each entry absent or containing `msiexec`), in full and silent UI alike (LaunchConditions runs after AppSearch in both sequences, before costing and anything that writes), with the message "A previous installation of Private AI Framework must be uninstalled first: Settings > Apps > Private AI Framework > Uninstall. Answer No when it asks whether to delete your data, to keep your configuration. Then run this installer again." (the `LaunchCondition` column holds at most 255 characters: ICE03). `Uninstall\llama.cpp` is llama.cpp's MSI's own entry now, whose `UninstallString` is `MsiExec.exe /I{ProductCode} LLAMA_CPP_UNINSTALL=1`, so an installed engine passes (`~><` is a case-insensitive substring test), as an upgrade or repackage of the framework does; maintenance (`Installed`) never evaluates the rest. **llama.cpp's MSI has the same guard for its own entry**: `ENGINEUNINSTALLSTRING`, read from `Uninstall\llama.cpp`, fails the launch condition `Installed OR NOT ENGINEUNINSTALLSTRING OR (ENGINEUNINSTALLSTRING ~>< "msiexec")` with "A previous installation of llama.cpp must be uninstalled first: Settings > Apps > llama.cpp > Uninstall. Then run this installer again." Its own entry and that of the framework's MSI of 2.1 to 2.4 are `msiexec` command lines, so an upgrade, a repackage and the removal of 2.4 pass.
- **Process stopping** (framework only, `msi-stop-processes.ps1`, custom action `StopProcesses`): immediate, impersonated, before `InstallValidate` (where Windows Installer checks files in use), on a first install or upgrade (the install being replaced is the one `HKLM\Software\private-ai\InstallDir` names; the script reads no other key), a removal and a repair; not on a feature change. It runs `bin\pai.exe control stop-and-close`, falling back to `bin\pai-config.exe` when the install being replaced has no `pai.exe` (an older build that still had the command in its configurator) (the graceful leg: the conversation snapshot is written first, then llama-server stops, then the GUI closes; up to 5 minutes for a multi-GiB snapshot), then force-stops any `pai`/`pai-config` still running from the framework's `bin\` (or whose path it cannot read): a `pai` there may be a benchmark sweep, which puts its key back at its next start. Same-named processes from a build tree are left alone. It names no llama-server: that is llama.cpp's, in llama.cpp's `bin\`, run by the instance services. llama.cpp's MSI kills no process by name either (it stops only its instance services): a llama-server started by hand from its `bin\` is left to Windows Installer's files-in-use dialog, as `xtask install` on Linux refuses rather than kills. Under the manager the graceful leg's stop goes through the manager (the instance service), and only for `default`; the other instance services are stopped by `UninstallInstanceServices`. **No "Stop running processes?" question**: the Install/Remove click is the consent, and a process this could not stop still lands in Windows Installer's own files-in-use (Restart Manager) dialog, which offers to close it or to schedule a reboot. Never fails the install.
- **Size**: measured on the single MSI before the split, not repeated on the two: a staged payload of 2.82 GB in 4,241 files (llama.cpp v0.7.0, ROCm + CUDA) gave **1,245,924,552 bytes (1.16 GiB)**, `wix build` 2:19 to 3:23 on the build machine, plus ~40 s of ICE validation (2026-10-27). Nearly all of that payload is llama.cpp's now. Cabinets are embedded (`MediaTemplate EmbedCab="yes"`, so each package stays ONE file), LZX `high`, at most 128 MB of input per cabinet so WiX compresses them in parallel. A cabinet holds at most 2 GB, and a release asset on GitHub must stay under 2 GiB: `xtask package` refuses an MSI at or above that and names the options (fewer `GpuTargets`, a higher compression level, or a second package for the ROCm kernel stores). NEVER switch to external cabinets: each installer is one file. Which files a release attaches (two installers per release) is to settle (`PLAN.md` step 11).
- **Validation**: `xtask package` runs `wix msi validate` (the ICEs) after each build. Suppressed: **ICE61** (same-version upgrades, on purpose: see Upgrades).
- **Custom-action scripts** (`msi-stop-processes.ps1` for the framework; `msi-remove-instances.ps1`, `msi-stop-instances.ps1` and `msi-start-instances.ps1` for llama.cpp) run under the TARGET machine's Windows PowerShell 5.1, embedded as `-EncodedCommand` in the Property table (a script inlined in a `SetProperty` overflows its 255 characters: ICE03; comment-only lines dropped by `xtask package`): keep them 5.1-safe and ASCII-only, argument-free (they read the registry or the SCM), and exit 0 whatever happens. A new script follows the same rules and gets its own define in `xtask package`'s defines (`xtask\src\windows\package.rs`).
- **Administrative image** (no install, no admin rights needed): `msiexec /a <msi> /qn TARGETDIR=<short dir>` unpacks a package as `<dir>\PFiles64\<folder>\...` plus an uncompressed copy of the `.msi` (16 s for the 2.8 GB single MSI before the split); compared file for file with the product's staging tree (`xtask package --keep-staging`) it must match exactly. A long `TARGETDIR` hits MAX_PATH in llama.cpp's `bin\hipblaslt\library`.
- What an older install left OUTSIDE the install directory is not touched: a ROCm dist its helper extracted under `C:\TheRock\<version>` (~25 GB), with the machine `HIP_PATH` and PATH entry naming it. Harmless to the new install (its own `bin\` precedes PATH) and the user's to delete.

### Open checks

What no test here can settle, to note in the run of the plan above:

- **The launch condition's order**: `FindRelatedProducts` must set `LLAMACPPFOUND` before `LaunchConditions` in both sequences, for a full-UI and a silent install alike (steps 2 and 5 show it).
- **Restart Manager at `InstallValidate`** (engine): `StopInstances` is deferred and runs after `InstallValidate`, where Windows Installer checks files in use, so a running instance's `llama-server.exe` is still running at that check; step 22 shows whether a files-in-use dialog or a reboot request comes up anyway. In an upgrade the old package's `StopInstances` runs inside the new package's transaction (`RemoveExistingProducts` right after `InstallValidate`).
- **Restart Manager at `InstallValidate`** (framework): the instance services run `llama-server.exe` from llama.cpp's `bin\` until `UninstallInstanceServices`, after `InstallValidate`; check that a running instance raises no files-in-use dialog and no reboot request on the framework's repair, upgrade and uninstall.
- **A killed instance service** reads Failed in the configurator until its service is deleted: kill `pai-manager.exe run-instance default` from an elevated Task Manager and check what the configurator and `sc query` show, before and after a Start.
- **The folders' owner**: `PermissionEx` sets the DACL only; read the owner of `%ProgramData%\llama.cpp`, `%ProgramData%\private-ai` and their folders (`icacls`, `Get-Acl`).
- **GPU compute from a session-0 virtual account**: the instance's log lists the GPUs on every backend (ROCm, CUDA, Vulkan) and a model runs on them as `NT SERVICE\llama.cpp_default`. If not, LocalService is the fallback agreed in `PLAN.md`.
- **The web service's account reads `config\`**: `NT SERVICE\private-ai-bff` gets its read of `%ProgramData%\private-ai\config\bff.ini` only through `NT SERVICE\ALL SERVICES`. Write `bff.ini` with `[Bff]` `Listen = 127.0.0.1:8591` as an administrator and restart the service: `http://127.0.0.1:8591` answers. If it still listens on 8590, the file was not read.
- **A failed web service start says nothing more**: set `Listen = 0.0.0.0:8590` in `bff.ini` (refused), restart: the start fails; then a valid address on a port another program holds: the start fails too. Note what `sc query private-ai-bff` (the exit code) and the System event log show in each case, since the service's own error line is lost.
- **`_` in a virtual account name**: the SCM accepts `NT SERVICE\llama.cpp_default` and the service logs on (no `ERROR_SERVICE_LOGON_FAILED`, 1069).
