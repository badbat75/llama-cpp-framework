# installer\

The MSI source (WiX Toolset), its custom-action script, the WiX pin and the sources of the external distributions. `xtask package` (see [docs\build-packaging.md](../docs/build-packaging.md)) stages the binaries and the GPU runtimes into `build\windows\staging\` and builds the MSI from that tree. The package is **self-contained for the GPU backends**: nothing is downloaded on the end user's machine, and there is no post-install helper.

- `dist-sources.psd1` says **where** each external distribution is looked up, and holds **no versions**: nothing is pinned, every reader resolves the newest STABLE release at run time (ROCm/TheRock `Dir` + `Marker` + tarball `Indexes`; CUDA `Dir` + `Marker`, redist index, `Platform` and the redist `Components` the toolkit is assembled from; Vulkan SDK `Dir` + `Marker`, latest-version URL, installer template and `Signer`). It also holds the **build machine's dist layout**: `DistRoot` (default `E:\`, overridden by `-DistRoot` on `scripts\00-install-prerequisites.ps1` and `--dist-root` on `xtask configure`, `PRIVATE_AI_DIST_ROOT`, or the root recorded in `config-build.psd1`) and `DistOs` (`windows`), giving `<DistRoot>\<Dir>\<Version>\<DistOs>`; the helpers that read it are in the root `scripts\dists.ps1`. **End users never see that layout**: what the backends load is copied out of it into the package. It is the source for `scripts\00-install-prerequisites.ps1` and `scripts\common.ps1`; xtask reads the same sources from `installer\dist-sources.toml`, so a source changes in both files. **ROCm host by version**: 10.0+ stables live under `stable.repo.amd.com/rocm/core/tarball/` (`rc.`/`nightly.repo.amd.com` for the others); everything up to 7.14 and the 10.0.0 rcs stay on `repo.amd.com/rocm/tarball-multi-arch/`. A wrong host fails with a `403` that reads exactly like "not published yet", so the URL is FOUND in an index, never composed: HTML with an inline JS `files` array, matched strictly (`\d+\.\d+\.\d+` immediately before the extension) so `-tests-` builds and dated nightlies (`10.1.0a20260831`) are not taken as releases. Prerelease indexes stay out. A new host for a future major means adding its index here.
- **The GPU runtimes are in the package** (`xtask\src\windows\package.rs` behind `xtask package`, "Bundle the GPU runtimes"; the Linux counterpart is the same section of `xtask\src\linux\package.rs`, behind `xtask package`). The target machine needs the GPU drivers and the VC++ runtime; no ROCm dist, no `HIP_PATH`, no cuBLAS download, no Vulkan runtime of its own.
  - **Which libraries is not a list**: it is the import closure of the staged `.exe`/`.dll` (`pe_imports` in `xtask\src\windows\package.rs` reads the PE import and delay-import directories, headers only), restricted to what resolves inside a dist: the ROCm dist's `bin\`, the CUDA dist's `bin\x64`, the Vulkan SDK's `Bin\` and `Runtime\`. Whatever else an import names is a **system library and stays out**: Windows' own DLLs, the VC++ runtime (`MSVCP140`, `VCRUNTIME140*`, `libomp140.x86_64`). Today that yields `hipblas`, `rocblas`, `rocsolver`, `libhipblaslt`, `origami`, `amdhip64_7`, `rocm_kpack`, `cublas64_13` + `cublasLt64_13` and `vulkan-1`. `xtask package` refuses to package a `ggml-hip.dll` without `hipblas.dll`, a `ggml-cuda.dll` without `cublas64_*.dll`, or a `ggml-vulkan.dll` without `vulkan-1.dll`.
  - **Licences**: `share\licenses\` holds a text for everything bundled, `README.txt` saying which covers what. `xtask\src\common\licenses.rs` maps each library to its text and refuses to package a library it does not name, or whose text it cannot find, so a new library in a dist gets read before it ships. Texts come from the dist when it carries them, otherwise from `licenses\` here (its README says where each was taken from).
  - **The Vulkan loader is bundled because a GPU driver does not guarantee one**: a machine can have the driver and no `vulkan-1.dll` in System32, and then `ggml-vulkan.dll` loads whichever copy PATH reaches, or none. The SDK ships no loader of its own, only an import lib and `Helpers\VulkanRT.exe`, the runtime installer that writes System32, and LunarG no longer publishes the standalone runtime archive the SDK's version used to ship (the `VulkanRT-*-Components.zip` is gone for every version, 1.3.x included), so `scripts\00-install-prerequisites.ps1` copies the loader out of System32, where that installer leaves it, into `Runtime\` of the dist, also for an SDK installed earlier, and only when Authenticode says it is LunarG-signed: a driver's own loader, signed by the vendor, is not bundled. Its licence is the vulkan-loader Apache 2.0 in `licenses\vulkan-loader.txt`, the text of the loader's own code, the same one Linux's `libvulkan.so.1` carries. The loader beside the exe still finds the driver's Vulkan implementation through the registry, so only the driver stays a requirement.
  - **Everything lands flat in `bin\`**, next to `llama-server.exe`, which is also what the dist's own `bin\` looks like. That is a load-order fix as much as a convenience, and it is what makes BF16/F16 run on RDNA4: Windows resolves imports from the exe's dir and then System32, **both before PATH**, and the driver keeps its own `amdhip64_7.dll` in System32, so a runtime reached through PATH means the dist's `rocblas.dll` + `libhipblaslt.dll` running against the DRIVER's HIP runtime, the mix that aborts at the first prefill batch. `rocm_kpack.dll` is `amdhip64_7`'s direct import, so it must come from the same dist.
  - **What no import table shows** is added by name, ROCm only: `amd_comgr*.dll` (asked for by bare name at run time, and System32 holds the driver's build; with the Ryzen iGPU (gfx1036) enabled that mix makes `hipGetDeviceCount` fail with `no ROCm-capable device is detected` and the HIP backend disappears), and the **kernel stores**: `bin\rocblas\library` (Tensile, found relative to `rocblas.dll`; without it the first matmul under `ROCBLAS_USE_HIPBLASLT=0` dies with `Could not initialize Tensile host`), `bin\hipblaslt\library`, and `.kpack\blas_lib_*.kpack`, which sits beside `bin\` as it does in the dist. Only the architectures in `GpuTargets` are copied (files or per-arch directories alike, plus whatever names no architecture): the CDNA `gfx908`/`gfx90a` half could never be used by a `ggml-hip.dll` with no code for it. About 355 + 465 + 95 MiB instead of 700 + 519 + 1535.
  - The bundle is the runtime of the dist the package was **built** against. It does not follow a later `HIP_PATH` move on the build machine and does not have to: it changes with the next package.

## The MSI

- `wix-toolset.psd1`: **the WiX pin**. WiX Toolset **7.0.1** as a .NET global tool (`dotnet tool install --global wix`), the extensions **`WixToolset.UI.wixext`** (WixUI dialogs) and **`WixToolset.Util.wixext`** (`WixQuietExec`), at the tool's version, and the .NET SDK winget id (`Microsoft.DotNet.SDK.10`). Pinned, unlike the dists: the `.wxs` is written against one schema and one WixUI dialog set, and a WiX major changes both. `scripts\00-install-prerequisites.ps1` installs it, `xtask configure` records the exe as `WixExe` in `config-build.psd1`, `xtask package` builds with it (`xtask package --wix <wix.exe>` overrides, a non-pinned version with a warning).
  - **WiX v7 is under the Open Source Maintenance Fee EULA**: every command but `--version`/`eula` fails with `WIX7015` until `wix eula accept wix7` was run once by the user building. The scripts NEVER accept it on the user's behalf: the prerequisites script reports it, `xtask package` stops before staging with the command to run. (OSMF: organizations above USD 10,000 yearly revenue owe the fee.) WiX 6.0.2 builds and validates the same `.wxs` without the EULA (`xtask package --wix <path to a 6.0.2 wix.exe>`).
- `private-ai-framework.wxs`: the package. `xtask package` passes `Version` (framework version: `[workspace.package] version` of the root `Cargo.toml`), `LlamaBuild` (the bundled llama.cpp release tag), `StagingDir`, `HasLib`/`HasKpack`, `EstimatedSizeKb` and the process-stopping script below as `-EncodedCommand` base64. Output: `dist\private-ai-framework-vX.Y.Z-vA.B.C-x64.msi`.
  - **UpgradeCode `F21D044C-04F5-478D-8F0A-A9B940DB23C3`: never change it.** It is the product's identity across versions, the 2.4 and earlier releases (named `llama.cpp-framework`) included: `MajorUpgrade` finds the installed version by it, and a new value installs side by side with the old one. ProductCode is generated per build, so every package is a major upgrade of the previous one.
  - **Upgrades**: `MajorUpgrade` with the default `afterInstallValidate` (the old product is removed in full before anything new is written: the robust order for thousands of files whose component set moves with every llama.cpp release). `AllowSameVersionUpgrades="yes"`, because the MSI version is the FRAMEWORK version only and a repackage on a newer llama.cpp keeps it; that is what ICE61 warns about, so `xtask package` runs validation with `-sice ICE61`. **Downgrades are refused** with a message telling the user to uninstall first: an MSI downgrade over a newer tree has no use that outweighs a half-old install.
  - **Layout**: per-machine, `ProgramFiles64Folder\private-ai` by default, the directory choosable (CustomizeDlg's Browse), the default taken from `HKLM\Software\private-ai\InstallDir` when an earlier install recorded one. **Upgrade from 2.4**: only the old key `HKLM\Software\llama.cpp\InstallDir` holds the directory (searched, never written); a directory the user chose in 2.4 is kept, while the old default `Program Files\llama.cpp\` moves to `Program Files\private-ai\`. `bin\` (llama.cpp, the GPU runtimes, `pai-config.exe`, `pai.exe`, `pai-manager.exe`, `pai-bff.exe`, `llama.ico`), `lib\`, `.kpack\`, `share\` (`benchmarks\`; `strings\`, the GUI's `en_US.toml` and the CLI's `cli.toml`), **no file at the root**. The payload is **harvested** at build time (`<Files Include="...\**">`, built into WiX 6+; no heat): one component per file, GUIDs derived from the target path, so a file keeps its component across builds. The staging tree IS the installed tree: `xtask package` stages `pai-config.exe`, `pai.exe`, `pai-manager.exe`, `pai-bff.exe` and the icon into `staging\bin\` (`msi::CARGO_EXES`) and prunes what does not ship (llama.cpp's `test-*.exe`, `include\`) before the harvest. `pai-manager.exe` and `pai-bff.exe` are left out of the harvest: each is the key path of its own component, `ManagerService` and `BffService`, since Windows Installer wants a service's executable there.
  - **Registry**: `HKLM\Software\private-ai` (64-bit view) `InstallDir` (with a trailing backslash, which every reader tolerates: they join onto it) and `LlamaBuild` (the `Build` name is kept: renaming it would strand existing installs). Removed on uninstall.
  - **The Apps list entry is ours, not Windows Installer's.** `ARPSYSTEMCOMPONENT=1` hides the MSI's own entry, and the package writes `HKLM\...\Uninstall\private-ai` with DisplayName `Private AI Framework v<ver> (llama <tag>)`, DisplayVersion, Publisher `Private AI Framework`, DisplayIcon `bin\llama.ico`, InstallLocation, EstimatedSize, NoRepair, `ModifyPath = MsiExec.exe /I{ProductCode}` (the maintenance wizard), `UninstallString = MsiExec.exe /I{ProductCode} LLAMA_UNINSTALL=1` (the FULL UI, opened on the removal page) and `QuietUninstallString = MsiExec.exe /X{ProductCode} /qn`. Why: Windows runs an MSI-registered entry's Uninstall as a **basic-UI** `msiexec /x`, where no dialog of the package can show, so the user-data question below would never be asked from Settings.
  - **Features** (CustomizeDlg): `Main` (binaries and runtimes; `AllowAbsent="no"`, carries the directory), `SystemPathFeature` "Add to system PATH" (`Environment` PATH, `Part="last"`, `System="yes"`: `[BINFOLDER]` appended to the machine PATH and removed on uninstall, so `pai` and `llama-server` run from any new console; Windows Installer broadcasts `WM_SETTINGCHANGE` itself), `StartMenuFeature` "Start Menu shortcut" (`Private AI Framework\Private AI Framework`, to `pai-config.exe`, in the all-users Start Menu). All three on by default. The two optional components key on `Software\private-ai` values `SystemPath`/`StartMenuShortcut` (a per-machine component needs a per-machine key path).
  - **UI** (`LlamaUI`, WixUI_FeatureTree): `LlamaWelcomeDlg` (ours: WixUI's WelcomeDlg has room for four lines) doubles as the **runtime-requirements notice** (VC++ always; the Adrenalin driver for AMD, the NVIDIA driver for NVIDIA; for Vulkan, the GPU's driver, whatever the vendor): a backend whose driver is missing is skipped silently at runtime, so the installer is the one place the user is told. Then `LicenseAgreementDlg`, Next enabled once its checkbox is ticked: its text is `build\windows\license.rtf`, which `xtask package` writes (`WixUILicenseRtf`): which text covers which library, the MIT licence and NVIDIA's terms in full, since those restrict what the MIT does not. A silent or basic-UI install does not show it. Then CustomizeDlg (features, Browse), VerifyReadyDlg. Maintenance: MaintenanceWelcomeDlg, MaintenanceTypeDlg (Change, Repair, Remove); Remove leads to `LlamaRemoveDlg`. No custom config page: runtime configuration is `pai-config`'s job.
- **The manager service** (component `ManagerService`): `ServiceInstall` `private-ai-manager`, display name "Private AI Framework manager", `pai-manager.exe serve`, own process, **LocalSystem** (no `Account`), **automatic** start; `ServiceConfigFailureActions` restarts it 5 s after a failure (every failure; the count resets after a day without one), as the Linux unit's `Restart=on-failure`. `ServiceControl` starts it on install, stops it on install and uninstall (`StopServices`, before its files are replaced or removed) and deletes it on uninstall. `StopProcesses` leaves it alone. At its start the manager creates, re-applies (the start type left as it is: `SERVICE_NO_CHANGE`) or deletes the instances' services to match the instances on disk, then serves the pipe `\\.\pipe\private-ai-manager`; it starts no instance itself: the SCM starts at boot those whose start type is automatic. Everything it does on Windows is type-checked with the GNU target and unit-tested on Linux, never run on Windows yet:
  - **The pipe**: SDDL `D:P(D;;GA;;;NU)(A;;GA;;;SY)(A;;GA;;;BA)(A;;0x12008b;;;IU)(A;;0x12008b;;;S-1-5-80-4088784262-1422927641-1363593751-33154763-2531830098)` (network logons denied; SYSTEM and Administrators full; interactive users read and write data, never `FILE_CREATE_PIPE_INSTANCE`; the last ACE gives the same client rights to `NT SERVICE\private-ai-bff`, the web service, by its service SID, computed by the [MS-LSAT] 3.1.1.1.2 rule from the service name and pinned by a test in `windows.rs`; its token is neither interactive nor an administrator's, so it gets the read-only calls only, `ListInstances` and `Status`), remote clients rejected, a byte stream: each request and reply a u32 little-endian length and a UTF-8 JSON body of at most 1 MiB, with the D-Bus method names and error names (`pai_core::client::pipe`, `crates\manager\src\manager\pipe.rs`). The caller is the client token's user SID: `control` (start, stop, restart) for an interactive user or an Administrators member, `configure` (writing a file) for an Administrators member, elevated or not (a deny-only Administrators counts); no prompt can cross the pipe (`crates\manager\src\manager\windows.rs`).
  - **The instances**: one SCM service per instance, `llama.cpp_<id>` (display name `llama.cpp server <id> (Private AI Framework)`), own process, created with the manual start type and switched between manual and automatic by the configurator's "start llama-server when the system starts" (the manager's `BootEnabled`, any client, and `SetBootEnabled`, `configure`; `QueryServiceConfigW` and `ChangeServiceConfigW` in `scm.rs`), running `"<bin>\pai-manager.exe" run-instance <id>` as the virtual account `NT SERVICE\llama.cpp_<id>` (`scm.rs`). Its output goes to `%ProgramData%\private-ai\logs\llama-server@<id>.log`, opened before the launch so a launch error is written there too; a non-empty log of the run before becomes `llama-server@<id>.previous.log`, replacing the older one. Stop kills llama-server outright. A llama-server that exits on its own with a non-zero code leaves the service stopped with that code as its service-specific exit code, which the configurator shows as Failed.
- **The web service** (component `BffService`): `ServiceInstall` `private-ai-bff`, display name "Private AI Framework web service", `pai-bff.exe service` (the entry that hands the process to the service dispatcher; from a console it exits 1), own process, **automatic** start, as the virtual account **`NT SERVICE\private-ai-bff`** (no password: a virtual account takes none), the way the instances run; `ServiceConfigFailureActions` restarts it 5 s after a failure, the count reset after a day, as the Linux unit's `Restart=on-failure`. `ServiceControl` starts it on install, stops it on install and uninstall and deletes it on uninstall; `StopProcesses` leaves it alone. It serves the web UI on `[Bff] Listen` of `config\bff.ini`, `127.0.0.1:8590` without one ([crates\bff\README.md](../crates/bff/README.md)), and reads that file through the read `NT SERVICE\ALL SERVICES` has on `config\` (the table below). Its `Error:` line goes nowhere under the SCM: by the code, a bad `bff.ini` ends the process (exit 1) before it reaches the dispatcher, and a bind failure comes after the service reported running, which then stops with the bind error as its Win32 exit code, so either shows only in the SCM's state and exit code. Type-checked only, never run on Windows yet: both are open checks below.
- **The machine data tree** `%ProgramData%\private-ai\` (components `MachineData*`, fixed GUIDs, each folder its own key path) with `config\` (the instances' `server@<id>.ini`, `presets.ini`, `presets.ini.disabled`, written by the manager; `OpencodeApiKey` lives there), `logs\` and `models\` (a models folder the instances can read: a `ModelsDir` under a user's profile is not readable by an instance's virtual account; making this one pai-config's default on Windows is open, `PLAN.md`). Each folder has a protected DACL (`PermissionEx Sddl`, `P`: nothing inherited from `%ProgramData%`, whose ACL lets any user create files; `OICI`: inherited below it); `S-1-5-80-0` is `NT SERVICE\ALL SERVICES`, `0x1200a9` read and execute, `0x1301bf` modify without `WRITE_DAC`, `WRITE_OWNER` or delete-child:

  | Folder | SYSTEM, Administrators | Services (`S-1-5-80-0`) | Users (`BU`) |
  | --- | --- | --- | --- |
  | `private-ai\` | full | none | read |
  | `config\` | full | read | none: they go through the manager |
  | `logs\`, `models\` | full | modify | read (the Log window opens the instance's file) |

  Windows Installer removes such a folder only when empty, and nothing in the package deletes the files, so the machine data outlives an uninstall.
- **The instances' services on removal, repair and upgrade** (custom action `UninstallInstanceServices`): they are created at run time, so Windows Installer does not know them. A deferred, not impersonated (deleting a service takes LocalSystem), `Return="ignore"` `WixQuietExec` of `"[BINFOLDER]pai-manager.exe" uninstall-services` runs after `StopServices` and before `RemoveFiles` when `REMOVE~="ALL" OR REINSTALL`: on an uninstall, a repair and the old product's half of an upgrade. It stops and deletes every `llama.cpp_<id>` service; what it prints lands in the MSI log, and a service left behind is deleted by the next manager's own sync. The new manager recreates the services from the instances on disk when it starts, so after a repair or upgrade an instance that was running without boot start comes back stopped.
- **User data on uninstall** (`%LOCALAPPDATA%\private-ai`: configs, presets, logs, `bench.db`, state snapshots). `LlamaRemoveDlg` offers it for deletion with a checkbox that starts **cleared** (keeping the data is the default), shown whenever that folder exists (`LLAMA_USERDATA_FOUND`: a `DirectorySearch` of the folder itself). Its text names the settings, benchmark results and logs, and an earlier install's server settings and presets: under the manager the server and preset files are in `%ProgramData%\private-ai\config\`, which the uninstall never deletes. The tree offered is the **uninstalling user's**: `%LOCALAPPDATA%` is per user, the install per machine; other users' trees are never touched. The deferred action `DeleteUserData` (impersonated: the user's rights on the user's tree; `Return="ignore"`: a held file never rolls back the uninstall) runs only with `REMOVE="ALL"`, not as the old half of an upgrade, with the checkbox ticked and **`UILevel` 5 (full UI)**: a silent or basic-UI removal never deletes the data, whatever properties the command line passes.
  - **The dialog appears** when the full UI removes the product: Settings > Apps > Private AI Framework > Uninstall (our `UninstallString`), Control Panel > Programs and Features > Uninstall (same string), Modify (or the `.msi` run again) > Remove, `msiexec /i <msi or {ProductCode}> LLAMA_UNINSTALL=1`, and `msiexec /i ... REMOVE=ALL` with full UI.
  - **It does not appear, and the data is kept**, when: the uninstalling user has no `%LOCALAPPDATA%\private-ai` (nothing to offer); the removal is the old half of an upgrade (`MajorUpgrade`); the UI is basic, reduced or none: `msiexec /x` (any UI level: `/x` alone is basic UI), `/qb`, `/qr`, `/qn`, the `QuietUninstallString`, winget/Intune/SCCM silent uninstalls; or the removal was started by another program through the Windows Installer API at a reduced UI level.
- **Previous non-MSI installation: refused, nothing changed.** An `HKLM\...\Uninstall\llama.cpp` (the 2.4 name) or `HKLM\...\Uninstall\private-ai` entry whose `UninstallString` does not contain `msiexec` (AppSearch `PREVIOUSUNINSTALLSTRING`, `NEWUNINSTALLSTRING`) fails the launch condition (`Installed`, or each entry absent or containing `msiexec`), in full and silent UI alike (LaunchConditions runs after AppSearch in both sequences, before costing and anything that writes), with the message "A previous installation of Private AI Framework must be uninstalled first: Settings > Apps > Private AI Framework > Uninstall. Answer No when it asks whether to delete your data, to keep your configuration. Then run this installer again." (the `LaunchCondition` column holds at most 255 characters: ICE03). Our own entry's `UninstallString` is always `MsiExec.exe /I{ProductCode} LLAMA_UNINSTALL=1` (`~><` is a case-insensitive substring test), so an upgrade or repackage of this MSI passes, and maintenance (`Installed`) never evaluates the rest.
- **Process stopping** (`msi-stop-processes.ps1`, custom action `StopProcesses`): immediate, impersonated, before `InstallValidate` (where Windows Installer checks files in use), on a first install or upgrade (the install being replaced is the one `InstallDir` names), a removal and a repair; not on a feature change. It runs `bin\pai.exe control stop-and-close`, falling back to `bin\pai-config.exe` when the install being replaced has no `pai.exe` (an older build that still had the command in its configurator), then to `bin\llama-cpp-config.exe` (a 2.4 install, whose directory only `Software\llama.cpp` names) (the graceful leg: the conversation snapshot is written first, then llama-server stops, then the GUI closes; up to 5 minutes for a multi-GiB snapshot), then force-stops any `llama-server`/`pai`/`pai-config`/`llama-cpp-config` (2.4) still running from the installed `bin\` (or whose path it cannot read): a `pai` there may be a benchmark sweep, which puts its key back at its next start. Same-named processes from a build tree are left alone. Under the manager the graceful leg's stop goes through the manager (the instance service), and only for `default`; the instance services run `llama-server` from the installed `bin\` and are stopped by `UninstallInstanceServices`, after `InstallValidate`, so whether a file is still in use there (the force-stop runs as the installing user, the service as its virtual account) is one of the open checks of the test plan. **No "Stop running processes?" question**: the Install/Remove click is the consent, and a process this could not stop still lands in Windows Installer's own files-in-use (Restart Manager) dialog, which offers to close it or to schedule a reboot. Never fails the install.
- **Size**: the staged payload is 2.82 GB in 4,241 files (llama.cpp v0.7.0, ROCm + CUDA). Cabinets are embedded (`MediaTemplate EmbedCab="yes"`, so the package stays ONE file), LZX `high`, at most 128 MB of input per cabinet so WiX compresses them in parallel. Measured 2026-10-27: **1,245,924,552 bytes (1.16 GiB)**, `wix build` 2:19 to 3:23 on the build machine, plus ~40 s of ICE validation. A cabinet holds at most 2 GB, and a release asset on GitHub must stay under 2 GiB: `xtask package` refuses an MSI at or above that and names the options (fewer `GpuTargets`, a higher compression level, or a second package for the ROCm kernel stores). NEVER switch to external cabinets: the release is one file.
- **Validation**: `xtask package` runs `wix msi validate` (the ICEs) after every build. Suppressed: **ICE61** (same-version upgrades, on purpose: see Upgrades).
- **Custom-action script** (`msi-stop-processes.ps1`) runs under the TARGET machine's Windows PowerShell 5.1, embedded as `-EncodedCommand` (comment-only lines dropped by `xtask package`): keep it 5.1-safe and ASCII-only, argument-free (it reads the registry), and exit 0 whatever happens. A new script follows the same rules and gets its own define in `xtask package`'s defines (`xtask\src\windows\package.rs`).
- **Administrative image** (no install, no admin rights needed): `msiexec /a <msi> /qn TARGETDIR=<short dir>` unpacks the package as `<dir>\PFiles64\private-ai\{bin,lib,.kpack}` plus an uncompressed copy of the `.msi` (16 s for the 2.8 GB); compared file for file with `build\windows\staging\` (`xtask package --keep-staging`) it must match exactly. A long `TARGETDIR` hits MAX_PATH in `bin\hipblaslt\library`.
- What an older install left OUTSIDE the install directory is not touched: a ROCm dist its helper extracted under `C:\TheRock\<version>` (~25 GB), with the machine `HIP_PATH` and PATH entry naming it. Harmless to the new install (its own `bin\` precedes PATH) and the user's to delete.

## Test plan (on a TEST machine or VM, never on the build machine's real install)

Each step: `msiexec ... /l*v <log>` keeps a verbose log; `StopProcesses` and `DeleteUserData` show in it with their exit codes.

1. **Fresh install**: nothing of this product installed. Double-click the `.msi`: the welcome page shows the requirements text; the licence page shows the list of texts and NVIDIA's terms down to their last line, with Next disabled until the box is ticked; CustomizeDlg lists the three features, all on; Browse to a non-default directory; install. Check: `bin\`, `lib\`, `.kpack\`, `share\licenses\` with its `README.txt`, nothing at the root; `HKLM\Software\private-ai` `InstallDir` (the chosen dir) and `LlamaBuild`; one Apps entry `Private AI Framework vX.Y.Z (llama vA.B.C)` with the icon, version and publisher, and no second entry; the machine PATH ends with `<dir>\bin\` and a NEW console finds `llama-server` and `pai` (`pai --version` prints the framework version); Start Menu > Private AI Framework > Private AI Framework starts the configurator. The manager, from an elevated console: `sc qc private-ai-manager` shows auto start, the binary path `"<dir>\bin\pai-manager.exe" serve` and LocalSystem; `sc query private-ai-manager` RUNNING; `sc qfailure private-ai-manager` a restart after 5000 ms and a reset period of 86400 s. `icacls "%ProgramData%\private-ai"` and the same for `config`, `logs` and `models`: no inherited entry, and exactly the entries of the table under "The machine data tree" (Users absent from `config`).

### Open checks

What no test here can settle, to note in the run of the plan above:

- **Restart Manager at `InstallValidate`**: the instance services run `llama-server.exe` from `bin\` until `UninstallInstanceServices`, after `InstallValidate`; check that a running instance raises no files-in-use dialog and no reboot request on repair, upgrade and uninstall.
- **A killed instance service** reads Failed in the configurator until its service is deleted: kill `pai-manager.exe run-instance default` from an elevated Task Manager and check what the configurator and `sc query` show, before and after a Start.
- **The folders' owner**: `PermissionEx` sets the DACL only; read the owner of `%ProgramData%\private-ai` and its folders (`icacls`, `Get-Acl`).
- **GPU compute from a session-0 virtual account**: the instance's log lists the GPUs on every backend (ROCm, CUDA, Vulkan) and a model runs on them as `NT SERVICE\llama.cpp_default`. If not, LocalService is the fallback agreed in `PLAN.md`.
- **The web service's account reads `config\`**: `NT SERVICE\private-ai-bff` gets its read of `config\bff.ini` only through `NT SERVICE\ALL SERVICES`. Write `config\bff.ini` with `[Bff]` `Listen = 127.0.0.1:8591` as an administrator and restart the service: `http://127.0.0.1:8591` answers. If it still listens on 8590, the file was not read.
- **A failed web service start says nothing more**: set `Listen = 0.0.0.0:8590` in `config\bff.ini` (refused), restart: the start fails; then a valid address on a port another program holds: the start fails too. Note what `sc query private-ai-bff` (the exit code) and the System event log show in each case, since the service's own error line is lost.
- **`_` in a virtual account name**: the SCM accepts `NT SERVICE\llama.cpp_default` and the service logs on (no `ERROR_SERVICE_LOGON_FAILED`, 1069).
