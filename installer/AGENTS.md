# installer\

The NSIS template, the sources of the external distributions, and the end-user runtime-deps helper. `03-package.ps1` (see [docs\build-pipeline.md](../docs/build-pipeline.md)) stages the helper and the sources into the installer's `bin\` and renders the template.

- `dist-sources.psd1` says **where** each external distribution is looked up, and holds **no versions**: nothing is pinned, every reader resolves the newest STABLE release at run time (ROCm/TheRock `Root` + `Marker` + tarball `Indexes`; CUDA redist index, network-installer URL templates, toolkit `Root` and the silent-install `Subpackages`; Vulkan SDK latest-version URL + installer template + `Root`; VC++ redist permalink). It is the **single source** for `00-install-prerequisites.ps1` and `install-runtime-deps.ps1`. **ROCm host by version**: 10.0+ stables live under `stable.repo.amd.com/rocm/core/tarball/` (`rc.`/`nightly.repo.amd.com` for the others); everything up to 7.14 and the 10.0.0 rcs stay on `repo.amd.com/rocm/tarball-multi-arch/`. A wrong host fails with a `403` that reads exactly like "not published yet", so the URL is FOUND in an index, never composed: HTML with an inline JS `files` array, matched strictly (`\d+\.\d+\.\d+` immediately before the extension) so `-tests-` builds and dated nightlies (`10.1.0a20260831`) are not taken as releases. Prerelease indexes stay out. A new host for a future major means adding its index here.
- `install-runtime-deps.ps1`: end-user runtime-deps helper; PS 5.1-safe and ASCII-only on purpose (fresh Windows has no PS7; non-ASCII in 5.1 needs a BOM). Self-elevating, idempotent; installs VC++ redist (~19 MB), ROCm/TheRock (~4.3 GB, the newest stable from the indexes, plus the dist's HIP runtime staged next to `llama-server.exe`, below; a complete dist OLDER than the newest stable, or one whose version does not parse, is offered the upgrade side by side, and `-Report` shows "newer stable available"), and the official cuBLAS redist (~400 MB, its two DLLs dropped next to `llama-server.exe`). **cuBLAS follows the build, not the newest CUDA**: the major is read from the `cublas64_<N>.dll` import string inside `ggml-cuda.dll` (streamed in 8 MB blocks; the DLL is ~150 MB), and the archive comes from the newest `redistrib_*.json` whose libcublas has that major, sha256 from the same JSON. It is installed only when NO `cublas64_<N>.dll` is reachable: a copy already present is never replaced (the ABI holds within a major, and its VERSIONINFO does not carry the release version). It points at driver downloads it cannot perform. Component selection: `-VcRedist`/`-Amd`/`-Nvidia` pick **exactly** those (the installer's three checkboxes each run `-Unattended` + one switch); with no switch, VC++ is always considered and GPU legs are an interactive [A]MD/[N]VIDIA/[B]oth/[S]kip choice (detection only pre-fills the default), or follow detection under `-Unattended`/`-Report` (`-Report` = detection-only, no elevation). It stays in `bin\` for later re-runs.
  - **The AMD leg stages the dist's HIP runtime.** After the dist is in place (fresh or existing), it **copies the dist's own `amdhip64_*.dll`, `amd_comgr*.dll` and `rocm_kpack.dll` into `bin\`** next to `llama-server.exe`. That is a load-order fix, and it is what makes BF16/F16 run on RDNA4: Windows resolves static imports from the exe's dir and then System32, **both before PATH**, and the driver keeps its own `amdhip64_7.dll` in System32, so without the copy the dist's `rocblas.dll` + `libhipblaslt.dll` run against the DRIVER's runtime, the mix that aborts at the first prefill batch. `rocblas`/`hipblaslt` keep resolving from `HIP_PATH\bin` (System32 has none). `rocm_kpack.dll` is `amdhip64_7`'s direct import, so it must come from the same dist. `amd_comgr` is asked for by bare name and System32 holds the driver's build; with the Ryzen iGPU (gfx1036) enabled that mix makes `hipGetDeviceCount` fail with `no ROCm-capable device is detected` and the HIP backend disappears. Deleting the three copies reverts to the driver's runtime.
  - Freshness is decided by **content** (size, then SHA256), never by the stamped version: different dists stamp the same VERSIONINFO and can even share a byte size.
  - The copy is also reachable **on its own** as `-StageHipRuntime` (leg 2b): no download, no prompt, silent when there is no ROCm; the installer's hidden always-run section calls it on every install and upgrade, because the AMD checkbox announces a 4.3 GB download that users who already have ROCm never tick. With both switches the stage-only leg stands down.
- `llama-cpp-framework.nsi.template`: NSIS installer template with placeholders (`@VERSION@` = framework version, `@LLAMA_BUILD@` = the bundled llama.cpp release tag, `@STAGING_DIR@`, `@OUTPUT_FILE@`) replaced by `03-package.ps1` into `build\windows\llama-cpp.nsi` (transient). ARP DisplayName/title: "llama.cpp-framework v@VERSION@ (llama @LLAMA_BUILD@)"; DisplayVersion = framework version; the llama release also goes to `HKLM\Software\llama.cpp\LlamaBuild` (the `Build` name is kept: renaming the registry value would strand existing installs).
  - The welcome page doubles as the runtime-requirements notice (VC++ always; AMD Adrenalin + ROCm/TheRock for HIP; NVIDIA driver + CUDA 13 cuBLAS for CUDA; Vulkan needs nothing): backends with missing deps are skipped silently at runtime, so the installer is the one place the user is told.
  - Six visible components: binaries (required), PATH addition, Start Menu shortcut, plus three dependency checkboxes (**base requirements** / **AMD ROCm runtime** / **NVIDIA cuBLAS runtime**, unchecked by default), each running `install-runtime-deps.ps1 -Unattended` + its switch in a visible console (`ExecWait`). A **seventh, hidden section** (`-StageHipRuntime`, leading `-` = invisible and always selected) runs the helper with `-Unattended -StageHipRuntime` through `nsExec::ExecToLog`, LAST, so an install that ticked the AMD box is staged from the dist it just installed.
  - Installs `bin\` (llama.cpp binaries, `llama-cpp-config.exe`, `llama.ico`, the uninstaller) and `lib\`, leaving **nothing at the install root**. The uninstaller is `bin\llama-cpp-uninstall.exe`, namespaced because `bin\` may be on the SYSTEM path. The closing `RMDir "$INSTDIR"` is **non-recursive on purpose** (`$INSTDIR` is user-chosen); anything left at the root is never removed and keeps the directory alive, so the Uninstall section carries an explicit list of legacy root files, and an entry may only be retired once no installed version can still have written it.
  - **Upgrade path**: `CheckPreviousInstall` runs the old uninstaller with `_?=$INSTDIR` (suppresses its copy-to-`$TEMP`, so `ExecWait` can wait, but then it cannot delete itself), so the caller removes it after `ExecWait` returns, both the new path and the legacy one. **The cuBLAS runtime is parked**: `cublas64_13.dll` + `cublasLt64_13.dll` (~550 MB) sit in `bin\` without being part of the package and the old uninstaller's `RMDir /r "$INSTDIR\bin"` would take them (silently dropping NVIDIA GPUs to Vulkan), so `CheckPreviousInstall` moves them to `$INSTDIR\cublas-parked\` before the old uninstaller and `SecMain` moves them back (before the `SecDeps*` sections), with a copy fallback across volumes and a pickup of a pair left parked by a cancelled upgrade. Both halves live in the INSTALLER, and **no uninstaller may ever delete `cublas-parked\`**.
  - **No custom config page**: runtime configuration is `llama-cpp-config`'s job. Start Menu shortcut: "llama.cpp Config" → `llama-cpp-config.exe`.
