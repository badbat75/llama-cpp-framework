# installer\

The MSI source (WiX Toolset), its custom-action script, the WiX pin and the sources of the external distributions. `xtask package` (see [docs\build-pipeline.md](../docs/build-pipeline.md)) stages the binaries and the GPU runtimes into `build\windows\staging\` and builds the MSI from that tree. The package is **self-contained for the GPU backends**: nothing is downloaded on the end user's machine, and there is no post-install helper.

- `dist-sources.psd1` says **where** each external distribution is looked up, and holds **no versions**: nothing is pinned, every reader resolves the newest STABLE release at run time (ROCm/TheRock `Dir` + `Marker` + tarball `Indexes`; CUDA `Dir` + `Marker`, redist index, `Platform` and the redist `Components` the toolkit is assembled from; Vulkan SDK `Dir` + `Marker`, latest-version URL, installer template and `Signer`). It also holds the **build machine's dist layout**: `DistRoot` (default `E:\`, overridden by `-DistRoot` on `scripts\00-install-prerequisites.ps1` and `--dist-root` on `xtask configure`, `LLAMA_FW_DIST_ROOT`, or the root recorded in `config-build.psd1`) and `DistOs` (`windows`), giving `<DistRoot>\<Dir>\<Version>\<DistOs>`; the helpers that read it are in the root `scripts\dists.ps1`. **End users never see that layout**: what the backends load is copied out of it into the package. It is the source for `scripts\00-install-prerequisites.ps1` and `scripts\common.ps1`; xtask reads the same sources from `installer\dist-sources.toml`, so a source changes in both files. **ROCm host by version**: 10.0+ stables live under `stable.repo.amd.com/rocm/core/tarball/` (`rc.`/`nightly.repo.amd.com` for the others); everything up to 7.14 and the 10.0.0 rcs stay on `repo.amd.com/rocm/tarball-multi-arch/`. A wrong host fails with a `403` that reads exactly like "not published yet", so the URL is FOUND in an index, never composed: HTML with an inline JS `files` array, matched strictly (`\d+\.\d+\.\d+` immediately before the extension) so `-tests-` builds and dated nightlies (`10.1.0a20260831`) are not taken as releases. Prerelease indexes stay out. A new host for a future major means adding its index here.
- **The GPU runtimes are in the package** (`xtask\src\windows\package.rs` behind `xtask package`, "Bundle the GPU runtimes"; the Linux counterpart is the same section of `xtask\src\linux\package.rs`, behind `xtask package`). The target machine needs the GPU drivers, which also bring `vulkan-1.dll`, and the VC++ runtime; no ROCm dist, no `HIP_PATH`, no cuBLAS download.
  - **Which libraries is not a list**: it is the import closure of the staged `.exe`/`.dll` (`Get-PeImports` reads the PE import and delay-import directories, headers only), restricted to what resolves inside a dist: the ROCm dist's `bin\`, the CUDA dist's `bin\x64`, the Vulkan SDK's `Bin\`. Whatever else an import names is a **system library and stays out**: Windows' own DLLs, the VC++ runtime (`MSVCP140`, `VCRUNTIME140*`, `libomp140.x86_64`), the driver's `vulkan-1.dll` (the Vulkan SDK carries the loader only as `Helpers\VulkanRT.exe`, so nothing resolves there today). Today that yields `hipblas`, `rocblas`, `rocsolver`, `libhipblaslt`, `origami`, `amdhip64_7`, `rocm_kpack` and `cublas64_13` + `cublasLt64_13`. The script refuses to package a `ggml-hip.dll` without `hipblas.dll`, or a `ggml-cuda.dll` without `cublas64_*.dll`.
  - **Everything lands flat in `bin\`**, next to `llama-server.exe`, which is also what the dist's own `bin\` looks like. That is a load-order fix as much as a convenience, and it is what makes BF16/F16 run on RDNA4: Windows resolves imports from the exe's dir and then System32, **both before PATH**, and the driver keeps its own `amdhip64_7.dll` in System32, so a runtime reached through PATH means the dist's `rocblas.dll` + `libhipblaslt.dll` running against the DRIVER's HIP runtime, the mix that aborts at the first prefill batch. `rocm_kpack.dll` is `amdhip64_7`'s direct import, so it must come from the same dist.
  - **What no import table shows** is added by name, ROCm only: `amd_comgr*.dll` (asked for by bare name at run time, and System32 holds the driver's build; with the Ryzen iGPU (gfx1036) enabled that mix makes `hipGetDeviceCount` fail with `no ROCm-capable device is detected` and the HIP backend disappears), and the **kernel stores**: `bin\rocblas\library` (Tensile, found relative to `rocblas.dll`; without it the first matmul under `ROCBLAS_USE_HIPBLASLT=0` dies with `Could not initialize Tensile host`), `bin\hipblaslt\library`, and `.kpack\blas_lib_*.kpack`, which sits beside `bin\` as it does in the dist. Only the architectures in `GpuTargets` are copied (files or per-arch directories alike, plus whatever names no architecture): the CDNA `gfx908`/`gfx90a` half could never be used by a `ggml-hip.dll` with no code for it. About 355 + 465 + 95 MiB instead of 700 + 519 + 1535.
  - The bundle is the runtime of the dist the package was **built** against. It does not follow a later `HIP_PATH` move on the build machine and does not have to: it changes with the next package.

## The MSI

- `wix-toolset.psd1`: **the WiX pin**. WiX Toolset **7.0.1** as a .NET global tool (`dotnet tool install --global wix`), the extensions **`WixToolset.UI.wixext`** (WixUI dialogs) and **`WixToolset.Util.wixext`** (`WixQuietExec`), at the tool's version, and the .NET SDK winget id (`Microsoft.DotNet.SDK.10`). Pinned, unlike the dists: the `.wxs` is written against one schema and one WixUI dialog set, and a WiX major changes both. `scripts\00-install-prerequisites.ps1` installs it, `xtask configure` records the exe as `WixExe` in `config-build.psd1`, `xtask package` builds with it (`xtask package --wix <wix.exe>` overrides, a non-pinned version with a warning).
  - **WiX v7 is under the Open Source Maintenance Fee EULA**: every command but `--version`/`eula` fails with `WIX7015` until `wix eula accept wix7` was run once by the user building. The scripts NEVER accept it on the user's behalf: the prerequisites script reports it, `xtask package` stops before staging with the command to run. (OSMF: organizations above USD 10,000 yearly revenue owe the fee.) WiX 6.0.2 builds and validates the same `.wxs` without the EULA (`xtask package --wix <path to a 6.0.2 wix.exe>`).
- `llama-cpp-framework.wxs`: the package. `xtask package` passes `Version` (framework version from `llama-cpp-config\Cargo.toml`), `LlamaBuild` (the bundled llama.cpp release tag), `StagingDir`, `HasLib`/`HasKpack`, `EstimatedSizeKb` and the process-stopping script below as `-EncodedCommand` base64. Output: `dist\llama-cpp-framework-vX.Y.Z-vA.B.C-x64.msi`.
  - **UpgradeCode `F21D044C-04F5-478D-8F0A-A9B940DB23C3`: never change it.** It is the product's identity across versions: `MajorUpgrade` finds the installed version by it, and a new value installs side by side with the old one. ProductCode is generated per build, so every package is a major upgrade of the previous one.
  - **Upgrades**: `MajorUpgrade` with the default `afterInstallValidate` (the old product is removed in full before anything new is written: the robust order for thousands of files whose component set moves with every llama.cpp release). `AllowSameVersionUpgrades="yes"`, because the MSI version is the FRAMEWORK version only and a repackage on a newer llama.cpp keeps it; that is what ICE61 warns about, so `xtask package` runs validation with `-sice ICE61`. **Downgrades are refused** with a message telling the user to uninstall first: an MSI downgrade over a newer tree has no use that outweighs a half-old install.
  - **Layout**: per-machine, `ProgramFiles64Folder\llama.cpp` by default, the directory choosable (CustomizeDlg's Browse), the default taken from `HKLM\Software\llama.cpp\InstallDir` when an earlier install recorded one. `bin\` (llama.cpp, the GPU runtimes, `llama-cpp-config.exe`, `llama.ico`), `lib\`, `.kpack\`, **no file at the root**. The payload is **harvested** at build time (`<Files Include="...\**">`, built into WiX 6+; no heat): one component per file, GUIDs derived from the target path, so a file keeps its component across builds. The staging tree IS the installed tree: `xtask package` stages the configurator and the icon into `staging\bin\` and prunes what does not ship (llama.cpp's `test-*.exe`, `include\`) before the harvest.
  - **Registry**: `HKLM\Software\llama.cpp` (64-bit view) `InstallDir` (with a trailing backslash, which every reader tolerates: they join onto it) and `LlamaBuild` (the `Build` name is kept: renaming it would strand existing installs). Removed on uninstall.
  - **The Apps list entry is ours, not Windows Installer's.** `ARPSYSTEMCOMPONENT=1` hides the MSI's own entry, and the package writes `HKLM\...\Uninstall\llama.cpp` with DisplayName `llama.cpp-framework v<ver> (llama <tag>)`, DisplayVersion, Publisher `llama.cpp`, DisplayIcon `bin\llama.ico`, InstallLocation, EstimatedSize, NoRepair, `ModifyPath = MsiExec.exe /I{ProductCode}` (the maintenance wizard), `UninstallString = MsiExec.exe /I{ProductCode} LLAMA_UNINSTALL=1` (the FULL UI, opened on the removal page) and `QuietUninstallString = MsiExec.exe /X{ProductCode} /qn`. Why: Windows runs an MSI-registered entry's Uninstall as a **basic-UI** `msiexec /x`, where no dialog of the package can show, so the user-data question below would never be asked from Settings.
  - **Features** (CustomizeDlg): `Main` (binaries and runtimes; `AllowAbsent="no"`, carries the directory), `SystemPathFeature` "Add to system PATH" (`Environment` PATH, `Part="last"`, `System="yes"`: `[BINFOLDER]` appended to the machine PATH and removed on uninstall; Windows Installer broadcasts `WM_SETTINGCHANGE` itself), `StartMenuFeature` "Start Menu shortcut" (`llama.cpp\llama.cpp Config` in the all-users Start Menu). All three on by default. The two optional components key on `HKLM\Software\llama.cpp` values `SystemPath`/`StartMenuShortcut` (a per-machine component needs a per-machine key path).
  - **UI** (`LlamaUI`, WixUI_FeatureTree without its license page): `LlamaWelcomeDlg` (ours: WixUI's WelcomeDlg has room for four lines) doubles as the **runtime-requirements notice** (VC++ always; the Adrenalin driver for AMD, the NVIDIA driver for NVIDIA; Vulkan needs nothing): a backend whose driver is missing is skipped silently at runtime, so the installer is the one place the user is told. Then CustomizeDlg (features, Browse), VerifyReadyDlg. Maintenance: MaintenanceWelcomeDlg, MaintenanceTypeDlg (Change, Repair, Remove); Remove leads to `LlamaRemoveDlg`. No custom config page: runtime configuration is `llama-cpp-config`'s job.
- **User data on uninstall** (`%LOCALAPPDATA%\llama.cpp`: configs, presets, logs, `bench.db`, state snapshots). `LlamaRemoveDlg` offers it for deletion with a checkbox that starts **cleared** (keeping the data is the default), shown only when `config\server.ini` exists there. The tree offered is the **uninstalling user's**: `%LOCALAPPDATA%` is per user, the install per machine; other users' trees are never touched. The deferred action `DeleteUserData` (impersonated: the user's rights on the user's tree; `Return="ignore"`: a held file never rolls back the uninstall) runs only with `REMOVE="ALL"`, not as the old half of an upgrade, with the checkbox ticked and **`UILevel` 5 (full UI)**: a silent or basic-UI removal never deletes the data, whatever properties the command line passes.
  - **The dialog appears** when the full UI removes the product: Settings > Apps > llama.cpp-framework > Uninstall (our `UninstallString`), Control Panel > Programs and Features > Uninstall (same string), Modify (or the `.msi` run again) > Remove, `msiexec /i <msi or {ProductCode}> LLAMA_UNINSTALL=1`, and `msiexec /i ... REMOVE=ALL` with full UI.
  - **It does not appear, and the data is kept**, when: there is no `config\server.ini` in the uninstalling user's tree (nothing to offer); the removal is the old half of an upgrade (`MajorUpgrade`); the UI is basic, reduced or none: `msiexec /x` (any UI level: `/x` alone is basic UI), `/qb`, `/qr`, `/qn`, the `QuietUninstallString`, winget/Intune/SCCM silent uninstalls; or the removal was started by another program through the Windows Installer API at a reduced UI level.
- **Previous non-MSI installation: refused, nothing changed.** An `HKLM\...\Uninstall\llama.cpp` entry whose `UninstallString` does not contain `msiexec` (AppSearch `PREVIOUSUNINSTALLSTRING`) fails the launch condition `Installed OR NOT PREVIOUSUNINSTALLSTRING OR (PREVIOUSUNINSTALLSTRING ~>< "msiexec")`, in full and silent UI alike (LaunchConditions runs after AppSearch in both sequences, before costing and anything that writes), with the message "A previous installation of llama.cpp-framework must be uninstalled first: Settings > Apps > llama.cpp-framework > Uninstall. Answer No when it asks whether to delete your data, to keep your configuration. Then run this installer again." (the `LaunchCondition` column holds at most 255 characters: ICE03). Our own entry's `UninstallString` is always `MsiExec.exe /I{ProductCode} LLAMA_UNINSTALL=1` (`~><` is a case-insensitive substring test), so an upgrade or repackage of this MSI passes, and maintenance (`Installed`) never evaluates the rest.
- **Process stopping** (`msi-stop-processes.ps1`, custom action `StopProcesses`): immediate, impersonated, before `InstallValidate` (where Windows Installer checks files in use), on a first install or upgrade (the install being replaced is the one `InstallDir` names), a removal and a repair; not on a feature change. It runs `bin\llama-cpp-config.exe control stop-and-close` (the graceful leg: the conversation snapshot is written first, then llama-server stops, then the GUI closes; up to 5 minutes for a multi-GiB snapshot), then force-stops any `llama-server`/`llama-cpp-config` still running from the installed `bin\` (or whose path it cannot read). Same-named processes from a build tree are left alone. **No "Stop running processes?" question**: the Install/Remove click is the consent, and a process this could not stop still lands in Windows Installer's own files-in-use (Restart Manager) dialog, which offers to close it or to schedule a reboot. Never fails the install.
- **Size**: the staged payload is 2.82 GB in 4,241 files (llama.cpp v0.7.0, ROCm + CUDA). Cabinets are embedded (`MediaTemplate EmbedCab="yes"`, so the package stays ONE file), LZX `high`, at most 128 MB of input per cabinet so WiX compresses them in parallel. Measured 2026-10-27: **1,245,924,552 bytes (1.16 GiB)**, `wix build` 2:19 to 3:23 on the build machine, plus ~40 s of ICE validation. A cabinet holds at most 2 GB, and a release asset on GitHub must stay under 2 GiB: `xtask package` refuses an MSI at or above that and names the options (fewer `GpuTargets`, a higher compression level, or a second package for the ROCm kernel stores). NEVER switch to external cabinets: the release is one file.
- **Validation**: `xtask package` runs `wix msi validate` (the ICEs) after every build. Suppressed: **ICE61** (same-version upgrades, on purpose: see Upgrades).
- **Custom-action script** (`msi-stop-processes.ps1`) runs under the TARGET machine's Windows PowerShell 5.1, embedded as `-EncodedCommand` (comment-only lines dropped by `xtask package`): keep it 5.1-safe and ASCII-only, argument-free (it reads the registry), and exit 0 whatever happens. A new script follows the same rules and gets its own define in `xtask package`'s defines (`xtask\src\windows\package.rs`).
- **Administrative image** (no install, no admin rights needed): `msiexec /a <msi> /qn TARGETDIR=<short dir>` unpacks the package as `<dir>\PFiles64\llama.cpp\{bin,lib,.kpack}` plus an uncompressed copy of the `.msi` (16 s for the 2.8 GB); compared file for file with `build\windows\staging\` (`xtask package --keep-staging`) it must match exactly. A long `TARGETDIR` hits MAX_PATH in `bin\hipblaslt\library`.
- What an older install left OUTSIDE the install directory is not touched: a ROCm dist its helper extracted under `C:\TheRock\<version>` (~25 GB), with the machine `HIP_PATH` and PATH entry naming it. Harmless to the new install (its own `bin\` precedes PATH) and the user's to delete.

## Test plan (on a TEST machine or VM, never on the build machine's real install)

Each step: `msiexec ... /l*v <log>` keeps a verbose log; `StopProcesses` and `DeleteUserData` show in it with their exit codes.

1. **Fresh install**: no llama.cpp installed. Double-click the `.msi`: the welcome page shows the requirements text; CustomizeDlg lists the three features, all on; Browse to a non-default directory; install. Check: `bin\`, `lib\`, `.kpack\`, nothing at the root; `HKLM\Software\llama.cpp` `InstallDir` (the chosen dir) and `LlamaBuild`; one Apps entry `llama.cpp-framework vX.Y.Z (llama vA.B.C)` with the icon, version and publisher, and no second entry; the machine PATH ends with `<dir>\bin\` and a NEW console finds `llama-server`; Start Menu > llama.cpp > llama.cpp Config starts the configurator.
2. **Feature change**: Settings > Apps > Modify > Change, untick PATH and Start Menu: the PATH entry and the shortcut go, the binaries stay. Change again to put them back.
3. **Process stopping**: start the configurator and a model from it (llama-server running, ideally with a conversation so a snapshot is written), then run the same `.msi` > Repair, or an upgrade (step 5). The configurator closes, llama-server stops, the snapshot appears in `%LOCALAPPDATA%\llama.cpp\state\` when `SaveStateOnShutdown` is on, and no files-in-use dialog shows. Run a `llama-server.exe` from a build tree at the same time: it must survive.
4. **Same-version repackage**: build again (same framework version, new llama.cpp or none) and install over: a major upgrade, one Apps entry afterwards, `LlamaBuild` updated.
5. **Upgrade**: install version N, then N+1 (bump `Cargo.toml` in a scratch build): the directory and features are kept, one Apps entry, `%LOCALAPPDATA%\llama.cpp` untouched, no question asked.
6. **Downgrade refused**: with N+1 installed, run N: the message "A newer version of llama.cpp-framework is already installed..." and nothing changes.
7. **Previous non-MSI installation refused**: with no MSI installed, create `HKLM\Software\Microsoft\Windows\CurrentVersion\Uninstall\llama.cpp` with `UninstallString` = `"C:\Program Files\llama.cpp\bin\uninstall.exe"` (or install an old non-MSI release). Run the `.msi` with full UI: the message "A previous installation of llama.cpp-framework must be uninstalled first..." shows and the installer ends; then `msiexec /i <msi> /qn /l*v <log>`: exit code 1603, the message in the log. Both times nothing changed: no files, no `HKLM\Software\llama.cpp` change, the fake entry untouched, no PATH entry, no Start Menu shortcut. Delete the fake entry: the install proceeds.
8. **Uninstall from Settings with the dialog**: Settings > Apps > llama.cpp-framework > Uninstall opens the removal page; with `config\server.ini` present the checkbox shows, CLEARED. (a) Remove with it cleared: the program, PATH entry, shortcut, `HKLM\Software\llama.cpp` and the Apps entry go; `%LOCALAPPDATA%\llama.cpp` stays. (b) Reinstall, uninstall again ticking the box: the tree is gone. (c) Rename `config\server.ini` away: the checkbox does not show. Same from Control Panel > Programs and Features.
9. **Silent uninstall keeps data**: `msiexec /x {ProductCode} /qn` (the `QuietUninstallString`), and `msiexec /x {ProductCode} LLAMA_DELETEUSERDATA=1 /qn`: removed, `%LOCALAPPDATA%\llama.cpp` intact both times. Same for `msiexec /x <msi>` with its basic UI.
10. **Silent install**: `msiexec /i <msi> /qn` (all features, default directory) and `msiexec /i <msi> /qn ADDLOCAL=Main INSTALLFOLDER="D:\llama.cpp\"` (binaries only).
11. **Cancel and rollback**: cancel an install half way: the machine returns to its prior state.
