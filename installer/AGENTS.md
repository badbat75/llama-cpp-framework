# installer\

The NSIS template and the sources of the external distributions. `03-package.ps1` (see [docs\build-pipeline.md](../docs/build-pipeline.md)) stages the binaries and the GPU runtimes and renders the template. The installer is **self-contained for the GPU backends**: nothing is downloaded on the end user's machine, and there is no post-install helper.

- `dist-sources.psd1` says **where** each external distribution is looked up, and holds **no versions**: nothing is pinned, every reader resolves the newest STABLE release at run time (ROCm/TheRock `Dir` + `Marker` + tarball `Indexes`; CUDA `Dir` + `Marker`, redist index, `Platform` and the redist `Components` the toolkit is assembled from; Vulkan SDK `Dir` + `Marker`, latest-version URL, installer template and `Signer`). It also holds the **build machine's dist layout**: `DistRoot` (default `E:\`, overridden by `-DistRoot` on `00`/`01`, `LLAMA_FW_DIST_ROOT`, or the root recorded in `config-build.psd1`) and `DistOs` (`windows`), giving `<DistRoot>\<Dir>\<Version>\<DistOs>`; the helpers that read it are in the root `dists.ps1`. **End users never see that layout**: what the backends load is copied out of it into the installer. It is the **single source** for `00-install-prerequisites.ps1`, `01-configure.ps1` and `common.ps1`. **ROCm host by version**: 10.0+ stables live under `stable.repo.amd.com/rocm/core/tarball/` (`rc.`/`nightly.repo.amd.com` for the others); everything up to 7.14 and the 10.0.0 rcs stay on `repo.amd.com/rocm/tarball-multi-arch/`. A wrong host fails with a `403` that reads exactly like "not published yet", so the URL is FOUND in an index, never composed: HTML with an inline JS `files` array, matched strictly (`\d+\.\d+\.\d+` immediately before the extension) so `-tests-` builds and dated nightlies (`10.1.0a20260831`) are not taken as releases. Prerelease indexes stay out. A new host for a future major means adding its index here.
- **The GPU runtimes are in the package** (`03-package.ps1`, "Bundle the GPU runtimes"; the Windows counterpart of the same section in `03-package.sh`). The target machine needs the GPU drivers, which also bring `vulkan-1.dll`, and the VC++ runtime; no ROCm dist, no `HIP_PATH`, no cuBLAS download.
  - **Which libraries is not a list**: it is the import closure of the staged `.exe`/`.dll` (`Get-PeImports` reads the PE import and delay-import directories, headers only), restricted to what resolves inside a dist: the ROCm dist's `bin\`, the CUDA dist's `bin\x64`, the Vulkan SDK's `Bin\`. Whatever else an import names is a **system library and stays out**: Windows' own DLLs, the VC++ runtime (`MSVCP140`, `VCRUNTIME140*`, `libomp140.x86_64`), the driver's `vulkan-1.dll` (the Vulkan SDK carries the loader only as `Helpers\VulkanRT.exe`, so nothing resolves there today). Today that yields `hipblas`, `rocblas`, `rocsolver`, `libhipblaslt`, `origami`, `amdhip64_7`, `rocm_kpack` and `cublas64_13` + `cublasLt64_13`. The script refuses to package a `ggml-hip.dll` without `hipblas.dll`, or a `ggml-cuda.dll` without `cublas64_*.dll`.
  - **Everything lands flat in `bin\`**, next to `llama-server.exe`, which is also what the dist's own `bin\` looks like. That is a load-order fix as much as a convenience, and it is what makes BF16/F16 run on RDNA4: Windows resolves imports from the exe's dir and then System32, **both before PATH**, and the driver keeps its own `amdhip64_7.dll` in System32, so a runtime reached through PATH means the dist's `rocblas.dll` + `libhipblaslt.dll` running against the DRIVER's HIP runtime, the mix that aborts at the first prefill batch. `rocm_kpack.dll` is `amdhip64_7`'s direct import, so it must come from the same dist.
  - **What no import table shows** is added by name, ROCm only: `amd_comgr*.dll` (asked for by bare name at run time, and System32 holds the driver's build; with the Ryzen iGPU (gfx1036) enabled that mix makes `hipGetDeviceCount` fail with `no ROCm-capable device is detected` and the HIP backend disappears), and the **kernel stores**: `bin\rocblas\library` (Tensile, found relative to `rocblas.dll`; without it the first matmul under `ROCBLAS_USE_HIPBLASLT=0` dies with `Could not initialize Tensile host`), `bin\hipblaslt\library`, and `.kpack\blas_lib_*.kpack`, which sits beside `bin\` as it does in the dist. Only the architectures in `GpuTargets` are copied (files or per-arch directories alike, plus whatever names no architecture): the CDNA `gfx908`/`gfx90a` half could never be used by a `ggml-hip.dll` with no code for it. About 375 + 465 + 95 MiB instead of 700 + 519 + 1535.
  - The bundle is the runtime of the dist the installer was **built** against. It does not follow a later `HIP_PATH` move on the build machine and does not have to: it changes with the next installer.
- `llama-cpp-framework.nsi.template`: NSIS installer template with placeholders (`@VERSION@` = framework version, `@LLAMA_BUILD@` = the bundled llama.cpp release tag, `@STAGING_DIR@`, `@OUTPUT_FILE@`) replaced by `03-package.ps1` into `build\windows\llama-cpp.nsi` (transient). ARP DisplayName/title: "llama.cpp-framework v@VERSION@ (llama @LLAMA_BUILD@)"; DisplayVersion = framework version; the llama release also goes to `HKLM\Software\llama.cpp\LlamaBuild` (the `Build` name is kept: renaming the registry value would strand existing installs).
  - **`SetCompressor lzma`, not `/SOLID`**: a solid datablock is assembled uncompressed and the payload is ~2.9 GB, past the 2 GB an NSIS datablock can hold (`Internal compiler error #12345: error mmapping datablock`). Per-file compression puts the limit on the COMPRESSED total instead: ~1.2 GB, which also has to stay under the 2 GB of a GitHub release asset. makensis compresses on one core (NSIS 3.13 has no multithreaded mode): about 7 minutes.
  - The welcome page doubles as the runtime-requirements notice (VC++ always; the Adrenalin driver for AMD, the NVIDIA driver for NVIDIA; Vulkan needs nothing): a backend whose driver is missing is skipped silently at runtime, so the installer is the one place the user is told.
  - Three visible components: binaries with the bundled runtimes (required), PATH addition, Start Menu shortcut. No dependency checkboxes: there is nothing left to fetch.
  - Installs `bin\` (llama.cpp binaries, the GPU runtimes, `llama-cpp-config.exe`, `llama.ico`, the uninstaller), `lib\` and `.kpack\`, leaving **no file at the install root**. The uninstaller is `bin\llama-cpp-uninstall.exe`, namespaced because `bin\` may be on the SYSTEM path. The closing `RMDir "$INSTDIR"` is **non-recursive on purpose** (`$INSTDIR` is user-chosen); anything left at the root is never removed and keeps the directory alive, so the Uninstall section carries an explicit list of legacy root files, and an entry may only be retired once no installed version can still have written it.
  - **Upgrade path**: `CheckPreviousInstall` runs the old uninstaller with `_?=$INSTDIR` (suppresses its copy-to-`$TEMP`, so `ExecWait` can wait, but then it cannot delete itself), so the caller removes it after `ExecWait` returns, both the new path and the legacy one. Installers up to 1.16 did not carry cuBLAS and **parked** the downloaded pair in `$INSTDIR\cublas-parked\` across the old uninstaller's `RMDir /r "$INSTDIR\bin"`; `SecMain` now deletes a park dir left by a cancelled upgrade, since the package ships its own copy. The uninstaller still leaves `cublas-parked\` alone: a downgrade to such an installer parks there before running THIS uninstaller.
  - What an older install left OUTSIDE `$INSTDIR` is not touched: a ROCm dist its helper extracted under `C:\TheRock\<version>` (~25 GB), with the machine `HIP_PATH` and PATH entry naming it. Harmless to the new install (its own `bin\` precedes PATH) and the user's to delete.
  - **No custom config page**: runtime configuration is `llama-cpp-config`'s job. Start Menu shortcut: "llama.cpp Config" → `llama-cpp-config.exe`.
