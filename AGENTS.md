# Project guide

## Project overview

A build orchestrator for [llama.cpp](https://github.com/ggerganov/llama.cpp): it installs prerequisites, configures, builds and packages it on Windows (CUDA, Vulkan and ROCm/HIP, an MSI built with the WiX Toolset), on Linux (the same backends, split `.deb` and `.rpm` packages) and on macOS (Apple Silicon only: Metal + Vulkan through MoltenVK, split `.pkg`; written but untested on a Mac). Every phase is a cargo command (`install` installs the newest package in `.\dist\` on the build machine, on every OS), `cargo run -p xtask -- <phase>` (`prereq`, `configure`, `build`, `package`, `install`), written **`xtask <phase>`** in the docs; the logic is in `xtask\src\`, split into `common\` (shared) and `linux\`, `windows\`, `macos\` (per OS). The only step that is not cargo is the bootstrap that installs Rust and the system packages: `scripts\00-install-prerequisites.ps1` (Windows, which also installs the GPU dists) and `scripts/00-install-prerequisites.sh` (Linux, macOS). `scripts\` holds only helpers: those two, thin wrappers that run the cargo phases (`scripts\0N-*.ps1`, `scripts/0N-*.sh`), and the PowerShell libraries `common.ps1` and `dists.ps1`. llama.cpp's built-in chat interface (served by `llama-server`) is used as the frontend; no separate web UI is bundled.

A companion Rust binary (`llama-cpp-config`) provides a GUI + CLI configurator for `server.ini` and per-model `presets.ini`.

**Start here: read [PLAN.md](PLAN.md).** It holds the user's requirements, the Definition of Done, and what is left to do, in order.

## Map

This file is the map; the details of each area live in the guide named beside it. **Read that guide before changing the area.** Subdirectory `AGENTS.md` files are scoped to their folder.

- **Build pipeline** → [docs\build-pipeline.md](docs/build-pipeline.md) (the entry page: phases and options, what to re-run after a change, running them per OS, how the OSes differ, where things land, footguns) and its topic pages, read the one you change: [docs\build-prerequisites.md](docs/build-prerequisites.md) (dist layout and root, prerequisites on Windows and Linux), [docs\build-compiling.md](docs/build-compiling.md) (configure, release tag and patches, CMake options, sccache, LTO, lld, HIP targets, ROCm kernel stores, build parallelism, the Windows and Linux compile specifics, the source map), [docs\build-packaging.md](docs/build-packaging.md) (MSI, `.deb`, `.rpm`, install), [docs\build-macos.md](docs/build-macos.md) (all of macOS):
  - `scripts\00-install-prerequisites.ps1`: idempotent toolchain bootstrapper (winget packages, sccache from its GitHub release, the WiX Toolset pinned in `installer\wix-toolset.psd1` as a .NET tool, and the **newest stable** ROCm/TheRock dist, CUDA Toolkit and Vulkan SDK: nothing is pinned, `installer\dist-sources.psd1` says where each is looked up; llama.cpp release check, environment report). Safe to re-run.
  - `scripts\dists.ps1`: the SDK dist layout, dot-sourced by the prerequisites script and `scripts\common.ps1` (xtask has its own finders, `xtask\src\<os>\dists.rs`). Every GPU SDK the build links lives at **`<DistRoot>\<Name>\<Version>\windows`** (`TheRock`, `CUDA`, `VulkanSDK`; e.g. `E:\TheRock\10.1.0\windows`) and the layout wins over the environment (`Find-Dist`: no `HIP_PATH`/`CUDA_PATH`/`VULKAN_SDK`, no vendor default location; on Linux `xtask configure` takes a usable `HIP_PATH`/`ROCM_PATH` first, and with no CUDA or Vulkan in the layout the build warns and leaves detection to CMake). `DistRoot` defaults to `E:\` (`dist-sources.psd1`, and `dist-sources.toml` for xtask) and is configurable: `-DistRoot` on the prerequisites script, `--dist-root` on `xtask configure`, or `LLAMA_FW_DIST_ROOT`; `xtask configure` records it in the config. OpenSSL (a system library, winget's `Program Files\OpenSSL-Win64`) and the tools (VS, cmake, WiX, sccache...) are not on the layout.
  - `xtask configure`: detects paths and tools, writes `build\windows\config-build.psd1` (the dist root included) and the generated `.cargo\config.toml`.
  - `xtask build`: checks out the latest llama.cpp **release** tag (never a `bNNNN` nightly), applies `patches\llama.cpp\`, builds llama.cpp (CMake + Ninja) and `llama-cpp-config` (cargo).
  - `xtask package`: stages into `build\windows\staging\` (the ROCm and CUDA runtime libraries the backends load included, copied out of the dists: the installer is self-contained but for the GPU drivers and the VC++ runtime), builds the MSI into `.\dist\` with WiX and validates it.
  - `xtask install`: installs the newest MSI in `.\dist\` with `msiexec /i ... /qb` (basic UI: progress and the UAC prompt; all features, the recorded `InstallDir`), a downgrade by removing the installed version first; `--dry-run` prints the commands (`xtask\src\windows\install.rs`).
  - `scripts\common.ps1`: shared PowerShell bootstrap (`$cfg`, `$distRoot`, ROCm PATH, the compile-time HIP vars, `Enable-VsDevShell`), dot-sourced today by `tools\pcie-bench\build.ps1` only; xtask sets the same per process for `xtask build` and `xtask package` (`xtask\src\windows\mod.rs`). The HIP vars (`LLVM_PATH` above all) must NEVER be set machine-wide: they break the driver's HIP runtime.
  - `xtask\cmake\common.toml`: the machine-independent llama.cpp cmake `-D` options of every OS, each with its reason; `xtask\cmake\<os>.toml` (today `macos.toml` only) the ones of one OS, replacing the common entry of the same name. `build\<os>\config-build.*`: the machine-derived half, generated.
  - **Linux** (`scripts/00-install-prerequisites.sh`, `xtask configure`, `xtask build`, `xtask package`, `xtask install`, `installer\dist-sources.toml`): the Linux counterpart of the Windows phases, plus `xtask prereq` (the logic is in `xtask\`, a crate of the cargo workspace at the repo root beside `llama-cpp-config`; the bootstrap script installs the apt packages and Rust natively first). `xtask install` installs the newest package of each component in `.\dist\`, or the files named (format by distribution; install, upgrade, same-version reinstall or downgrade alike). `xtask build` ends at a working build tree with llama.cpp and `llama-cpp-config`; `xtask package` packages it in `.\dist\` as five `.deb` and five `.rpm` (`xtask\src\common\components.rs`): `llama-cpp-framework-config` (the configurator, which requires `llama` at its own version), `-llama` (llama.cpp, the ggml backends included) and `-rocm`, `-cuda`, `-vulkan` (only the external runtime libraries, versioned by their SDK; `llama` recommends them and refuses any other version). Together they are self-contained under `/opt/llama.cpp` (binaries in `bin/`, the runtimes in `lib/`; a symlink per executable in `/usr/bin`, a desktop entry for the configurator; the config files are not in the package, `llama-cpp-config` keeps them per user in `~/.config/llama.cpp`). Dists install as `<Root>/<Version>/linux` under `/mnt/data` (`TheRock`, `CUDA`, `VulkanSDK`, plus the optional `NCCL`; RCCL and NCCL are what `--split-mode tensor` reduces through and exist on Linux only; the root is configurable as on Windows: `--dist-root` on the prerequisites script and `xtask configure`, or `LLAMA_FW_DIST_ROOT`, recorded by `xtask configure` as `dist_root` in `build/linux/config-build.toml`), and everything generated goes to `build/linux/`, never into the Windows artifacts under `build/windows/`: see "Dist layout and root" and "Linux prerequisites" in [docs\build-prerequisites.md](docs/build-prerequisites.md), "Linux" in [docs\build-compiling.md](docs/build-compiling.md) and "Packaging" in [docs\build-packaging.md](docs/build-packaging.md).
  - **macOS** (the same cargo phases, `xtask\src\macos\`; Apple Silicon only, untested on a Mac): Metal + Vulkan through MoltenVK (`xtask\cmake\macos.toml`), the Vulkan SDK the only dist (`~/dists/VulkanSDK/<Version>/macos`), everything generated in `build/macos/`; `xtask package` builds three `.pkg` with `pkgbuild`, `dist/llama-cpp-framework-{config,llama}-v<version>-<llamaRelease>-arm64.pkg` and `-vulkan-v<sdkVersion>-arm64.pkg` (`/opt/llama.cpp`, links in `/usr/local/bin`, the MoltenVK manifest in `/usr/local/share/vulkan/icd.d`), `xtask install` installs them. See [docs\build-macos.md](docs/build-macos.md).
  - `patches\llama.cpp\` (provisional out-of-tree patches): its README says what each one changes and when to drop it.
- **Installer** → [installer\AGENTS.md](installer/AGENTS.md): the MSI (`llama-cpp-framework.wxs`, its custom-action script, the WiX pin `wix-toolset.psd1`, the UpgradeCode, the guard against a previous non-MSI installation, process stopping, the user-data dialog and when it shows), `dist-sources.psd1` (where every external distribution is looked up; no versions), what the installer bundles of the GPU runtimes and why (including the HIP runtime beside the exe that makes BF16/F16 run on RDNA4), and the licences every package carries in `share\licenses\` (`licenses\`, `xtask\src\common\licenses.rs`: a bundled library with no known licence stops the package).
- **Configurator** → [llama-cpp-config\AGENTS.md](llama-cpp-config/AGENTS.md) (tabs, common-change checklists, footguns) and [llama-cpp-config\README.md](llama-cpp-config/README.md) (architecture, conventions, tests).
- **Benchmarks** → [benchmarks\README.md](benchmarks/README.md): `bench.db` (SQLite, committed), every measurement behind the guides with its machine, software stack (llama.cpp, ROCm, CUDA, Vulkan SDK), model, full parameter set and prompts; `specs\` holds the versioned benchmark method (one file per published version, `standard-<X.Y>.ini`, and `prompts\` the prompts they pin, each named `<name>-<X.Y>`: installed read-only as `share\benchmarks\` beside the binaries, read in place, never copied into the user's config; only `standard.versions`, the digest of each version, is compiled in: `bench run --spec standard` runs the newest, `--spec standard-1.0` that one; prompts pinned by sha256; every run records the spec's name, version and sha256, a sweep without one `spec = custom`; every benchmark holds the GPU lock `bench::gpu_lock`); `schema.sql` is the data model, shared with the configurator, which records every finished benchmark run into its own working `bench.db` and copies chosen campaigns into this one (`llama-cpp-config bench publish`), or records straight into this one when `settings.ini` `BenchDb` names it; `llama-cpp-config bench query --db benchmarks/bench.db` queries it (campaigns, models, machines, per-run summary, filters by GPU, model, parameter); only finished runs are recorded. ## Key conventions

- **No em-dashes anywhere in this repo.** Not in comments, doc comments, user-facing strings, the comment text written into `server.ini` / `presets.ini`, docs, or commit messages. Use `:` for an apposition or explanation, `;` between two independent clauses, `,` for an aside or trailing afterthought, or parentheses when a pair wrapped an aside. The one sanctioned exception is a `—` that is DATA rather than prose: the glyph the GPU table shows for a not-applicable cell (`gpu_split.rs`, `components.slint`), the assertions pinning it, and its entry in `binding_lint.rs`'s `RENDERABLE` whitelist.
- **No user-visible text in the code.** Every text the configurator shows or prints goes in the strings file, linked from the code by a key: `llama-cpp-config\strings\en_US.toml` for the GUI, `strings\cli.toml` for the CLI (always English). Not language, so they stay in the code: numbers, units, acronyms, paths and format examples. Not user text, so they stay literal: what is written into bench.db or the comments of `server.ini` / `presets.ini`, text other code matches, and what scripts read: `--help` and the output of `server show` and `bench query`. How: "Adding a user-visible string" in [llama-cpp-config\AGENTS.md](llama-cpp-config/AGENTS.md).
- **Code comments state no facts that can change** (token counts, measured figures): they point to where the fact lives (a guide, bench.db).
- `scripts\common.ps1` is dot-sourced by `tools\pcie-bench\build.ps1` only. `scripts\00-install-prerequisites.ps1` and xtask read `build\windows\config-build.psd1` directly.
- `build\windows\config-build.psd1` (build-time) uses single-quoted PowerShell-data-file syntax. Runtime config files (`server.ini`, `presets.ini`) are plain INI written as UTF-8 without BOM.
- All build artifacts (source clones, cmake binary dir, MSI staging, WiX intermediates, sccache cache, `config-build.psd1`) live under `.\build\` (gitignored), in a per-OS directory: `build\windows\` (`$buildRoot` in `scripts\common.ps1`; `build/linux/` on Linux). Cargo's target dir is included: `build\windows\cargo-target\` (`build/linux/cargo-target/` on Linux), set by the build scripts through `CARGO_TARGET_DIR`. The one exception is the generated `.cargo\config.toml` (gitignored separately: cargo only discovers it by walking up from the cwd), which also pins `[build] target-dir = "build/windows/cargo-target"`, so a bare `cargo build`/`cargo test` outside the scripts lands in the same directory (before `xtask configure` has run, it still writes `target\` at the repo root, the cargo workspace root). rust-analyzer in VS Code checks into `build\rust-analyzer\` (`.vscode\settings.json`, checked in, relative paths only; not per-OS, since VS Code settings cannot be). The same file keeps CMake Tools from configuring anything on its own (`tools\pcie-bench\build.ps1` is its only configure path: the VS generator the extension's kits pick finds no CUDA toolset from the dist layout); C/C++ IntelliSense reads the `compile_commands.json` that `build.ps1` writes into `build\windows\pcie-bench\`. The final installer goes to `.\dist\`. `rm -rf build\` wipes everything, the sccache and the Rust release build included.
- The installer (an MSI) registers in `HKLM\Software\llama.cpp` (InstallDir) and supports upgrades (MajorUpgrade: removes the previous version first; downgrades refused). User runtime state lives under `%LOCALAPPDATA%\llama.cpp\`:
  - `config\server.ini` (single `[Server]` section), `config\presets.ini` (per-model presets for `llama-server --models-preset`), `config\presets.ini.disabled` (switched-off presets, never read by llama-server), `config\settings.ini` (the configurator's preferences), (the live benchmark's prompts are NOT here: the shipped ones are installed read-only under `share\benchmarks\prompts\`, the 43k one the default; `settings.ini` `BenchPromptFile` points at another, a file of the user's anywhere; `BenchDb` names the database benchmark runs go to, empty for `bench\bench.db`).
  - `logs\llama-server.log` (both output streams; on stop, a file LARGER than `settings.ini` `LogRotateKb`, 1024 by default, is filed as `logs\llama-server-<yyyymmdd-hhmmss>.log`, closing instant in UTC; a run that ended without a stop is filed at the next start under its last-write time; newest 10 kept; `LogRotate = false` keeps a single growing file: `runstate.rs` module header).
  - `bench\bench.db`, the only benchmark output: every FINISHED run of the Benchmark tab and of `bench run` (each preset committed with its points, repetitions, parameters and the engine's log when it is done; failed or cancelled presets are not recorded), one campaign per tab run or sweep, the markdown report stored with the campaign (`bench\db.rs` module header). Beside it only `bench\sweep-pending-<stamp>.json`, while a sweep has not yet put its key back (the value to restore).
  - Only when `SaveStateOnShutdown` is on: `state\<model>.llamastate` (KV-cache snapshots sized by the tokens the slot HOLDS, not `ctx-size`: ~4.4 GiB at 128k tokens on Qwen3.8-27B, ~8.3 GiB for a full 262k, plus, since llama.cpp v0.7.0, the slot's context checkpoints and the draft state; overridable via `StateDir` since the default sits on the system drive).
  - The uninstall offers the uninstalling user's tree for deletion (a checkbox, cleared by default) when it runs with the full UI (Settings > Apps > Uninstall included); a silent or basic-UI uninstall, and every upgrade, keeps it: [installer\AGENTS.md](installer/AGENTS.md) lists exactly when the question shows.
- On Linux the same tree is `~/.local/share/llama.cpp/`, except that everything `config\` holds lives in **`~/.config/llama.cpp/`** (`$XDG_CONFIG_HOME/llama.cpp` when that is set to an absolute path): `paths::config_dir`. The directory is per user and the same for a packaged install and a tree build; the packages ship no config directory and no post-install script. The Settings tab's "Start at login" is the HKCU Run registry entry on Windows and the XDG autostart file `~/.config/autostart/llama-cpp-config.desktop` on Linux (`startup.rs`); either way the entry itself is the state, with no INI mirror.

## Working from this plan

- Take the first open step unless the user says otherwise. Split it if it is too big for one sitting.
- The plan can change. The coordinator or the user can change any part of it when needed: steps, order, requirements or Definition of Done. Other agents propose changes to the coordinator. The commit says why, and the coordinator tells the user whenever a requirement changes.
- If a requirement is added, make sure a step covers it.
- A step is done only when it meets the Definition of Done in `PLAN.md` as well as its own "Done when".
- Steps in `PLAN.md` are only open work. When a step is done, remove it, and update the requirements' "State" and "Where things stand" if they changed.
- Do this in the same commit as the work. The commit message says what was closed and how it was checked, so `git log` is the record of closed work. Do not keep a done list in the plan.
- New work that comes up goes in the plan, in its place in the order. A step that turns out wrong gets rewritten, not worked around.

## Commands

Agents run only these, on the crate they are working on (`llama-cpp-config`, `xtask` or `docs-site`). They are fast and enough to see red and green:

    cargo test -p <crate> <test-name-filter>
    cargo clippy -p <crate> --all-targets -- -D warnings
    cargo fmt -p <crate> --check
    cargo run -p docs-site -- --check

- Tests run in the debug profile, never `--release`: the configurator's e2e tests need Slint debug info. On Windows `cargo test` links only with the `.cargo\config.toml` that `xtask configure` generates ([llama-cpp-config\AGENTS.md](llama-cpp-config/AGENTS.md)).
- The docs-site check is for changes to `docs\`, bench.db or the generator.

The user runs the full suite, once, on the main branch after the merge and before installing. Agents do not run it:

    cargo test --workspace

## Rules

**Test first, always.** Write a failing test, run it and see it fail, then write the code. A change without a test that failed first is not done. Tests never touch real systems or real data: the configurator's tests redirect the whole data tree with `LLAMA_CPP_CONFIG_DATA_ROOT`.

**Keep it simple.** Minimum that solves the problem, no speculative options or abstractions.

**Facts need a source.** Check commands, APIs and limits against official documentation or a real run. In the docs, keep what was measured, read in a source and assumed apart. Mark guesses as guesses. A measured value names its campaign in bench.db.

**Language.** Everything in the project is in English: code, comments, docs, plan, skills, commit messages and displayed text. Only the conversation with the user may be in their language.

**Displayed text.** Text a user sees goes in the strings files, never inline in the code: "No user-visible text in the code" under "Key conventions".

## Actions with real effects

- What counts here: installing or removing packages and SDKs (`xtask prereq`, `xtask install`, the bootstrap scripts), anything machine-wide (environment variables, registry, `/usr`, `/opt`), the user's own config and data (`%LOCALAPPDATA%\llama.cpp\`, `~/.config/llama.cpp/`, `~/.local/share/llama.cpp/`), starting llama-server or a benchmark on the GPUs, writing to the committed `benchmarks\bench.db` (`bench publish`), and git push, tags and GitHub releases.
- Reading is fine. Anything that changes the real thing needs the user's go-ahead each time.
- Agents may be blocked from running some commands. Give the user the exact command to run, and say what it does, how long it takes and what result to expect.
- A command must undo what it changed by itself, wherever it can (a sweep puts its key back: `bench\sweep-pending-<stamp>.json`).

## Skills

Each role has a skill in `.agents\skills\` in the standard `SKILL.md` format; `.claude\skills` is a symlink to that directory. Beside the role playbooks (`coordinator-playbook`, `tester-playbook`, `coder-playbook`, `docs-playbook`) are the task skills: `optimize-preset`, `bench-spec` and `write-docs`.

- A skill holds what its role has learned and is not obvious. Rules stay in this file.
- An agent can update its own skill. The coordinator can update any of them.
- Keep them short, and remove what stops being true. Say why in the commit, like any other change.

## Roles

Role definitions live in `.opencode\agents\`; `.claude\agents` is a symlink to that directory, so OpenCode and Claude Code read the same files. Keep the frontmatter to the fields both accept (`name`, `description`, `mode`), and write role limits in the body rather than in harness-specific tool lists.

- `coordinator`: plans and sequences the work, checks each result. The default agent for a session, set in `.claude\settings.json` and `.opencode\opencode.json`.
- `tester`: writes the failing tests.
- `coder`: makes them pass.
- `docs`: keeps the documentation true; for a guide in `docs\` it loads the `write-docs` skill.
- `spec-reviewer`: reviews a benchmark spec change before it is committed, read-only, with the `bench-spec` skill.

Cycle: coordinator takes the next step from `PLAN.md` and picks one small slice, tester writes tests and shows them red, coder turns them green, coordinator reruns everything, docs updates what changed.

## Release process

1. **Bump version** in `llama-cpp-config\Cargo.toml` (`[package] version = "X.Y.Z"`). The next build also refreshes the crate's line in the workspace's `Cargo.lock` (at the repo root): both files belong to the release commit.
2. **Run `xtask build`**: builds llama.cpp (fetches and checks out the latest `vX.Y.Z` **release** tag; `bNNNN` nightlies are not candidates) and llama-cpp-config.
3. **Run `xtask package`**: stages binaries, builds the MSI to `.\dist\llama-cpp-framework-vX.Y.Z-vA.B.C-x64.msi` (framework version first, bundled llama.cpp release second; the ProductVersion is the framework version) and validates it (ICE). It refuses a package of 2 GiB or more (GitHub's asset limit). Before tagging, run the installer test plan in [installer\AGENTS.md](installer/AGENTS.md) on a test machine whenever the `.wxs` or its scripts changed.
4. **Commit** all changes. Subject: **`Release vX.Y.Z: <summary>`**, the SAME first line as the tag (step 5); a `feat:`/`docs:`-style subject is not the convention for release commits. Body: a prose summary, closing with a **`Bundles llama.cpp <tag> (up from <previous tag>).`** line, e.g. `Bundles llama.cpp v0.2.0 (up from v0.1.2).`.
5. **Tag**: `git tag -a X.Y.Z -m "Release vX.Y.Z: <short summary>..." && git push origin X.Y.Z`
   - Tag name: **no `v` prefix** (e.g. `1.5.1`, not `v1.5.1`).
   - Tag message: starts with `Release vX.Y.Z: <summary>` on first line, then blank line, then bullet points of changes. Match the style of previous tags (`git show 1.5.0`).
6. **Create release**: `gh release create X.Y.Z --title "vX.Y.Z (llama.cpp vA.B.C)" --notes "<markdown body>"`
   - Title format: **`vX.Y.Z (llama.cpp vA.B.C)`** (with `v` prefix, includes the bundled llama.cpp release).
   - Body: detailed markdown with sections (`##`, `###`), bullet points, code formatting. Match the style of previous releases (`gh release view 1.5.0`). End with test count and bundled llama.cpp release.
7. **Attach installer**: `gh release upload X.Y.Z dist\llama-cpp-framework-vX.Y.Z-vA.B.C-x64.msi`
