# Project guide

## Project overview

Windows-only PowerShell scripts to install prerequisites, configure, build, and package [llama.cpp](https://github.com/ggerganov/llama.cpp) with CUDA, Vulkan, and ROCm (HIP) support, and NSIS installer packaging. Not compatible with Linux or macOS. llama.cpp's built-in chat interface (served by `llama-server`) is used as the frontend; no separate web UI is bundled.

A companion Rust binary (`llama-cpp-config`) provides a GUI + CLI configurator for `server.ini` and per-model `presets.ini`, replacing what were previously PowerShell config scripts.

## Structure

- `build\config-build.psd1`: build-time configuration (paths, GPU targets, compiler flags). Generated by `01-configure.ps1`; lives under `build\` (whole dir gitignored).
- `common.ps1` is the shared bootstrap: loads `$cfg` from `build\config-build.psd1`, adds ROCm to PATH (`HipPath\bin` plus, for the TheRock dist, `HipPath\lib\llvm\bin`; clang lives there, not in `bin` like the legacy HIP SDK), and is the **sole source** of the compile-time HIP vars (`HIP_DEVICE_LIB_PATH` → `lib\llvm\amdgcn\bitcode`, `HIP_PLATFORM`, `LLVM_PATH`), set per-process from `HipPath` (without `HIP_DEVICE_LIB_PATH` the HIP device compile dies with "cannot find ROCm device library"; TheRock's bitcode is not where clang's `--rocm-path` layout expects it). They must NEVER be set machine-wide: the Adrenalin driver's own HIP runtime (System32's `amdhip64_7.dll` + `amd_comgr_3.dll`) reads `LLVM_PATH` at runtime, and pointing it at TheRock's LLVM half-breaks it: `hipMemGetInfo` returns "invalid argument" (devices report 0 MiB) and every llama-server child dies with 0xC0000005 mid weight-upload (root-caused 2026-07-16; `00-install-prerequisites.ps1` self-heals poisoned machines). Exposes `Enable-VsDevShell` as a function. VS Dev Shell activation is **opt-in**: only build/package scripts call it. Dot-sourced by `02-build.ps1` and `03-package.ps1`.
- `00-install-prerequisites.ps1` is the idempotent toolchain bootstrapper: installs **and** updates the winget-tracked packages (PowerShell 7+ / OpenSSL / NSIS) in a single UAC-elevated session (`winget install` for missing, `winget upgrade` for present, plus the OpenSSL lib-symlink fixup), then `git fetch`es `$cfg.LlamaCppDir` when cloned and compares the checked-out tag against the newest **release** tag (`vX.Y.Z`) reachable from `origin/master`, by the same selection `02-build.ps1` makes (nightlies and pre-releases ignored; see that entry), or it would recommend a rebuild for a tag the build would never check out (no `git pull`: `02-build.ps1` keeps the clone on a detached tag, so a pull would always fail; the checkout onto the new tag is `02-build.ps1`'s job). **ROCm/HIP installs from AMD's TheRock dist tarball** (the classic HIP SDK installer is discontinued as of ROCm 7.14.0, 2026-07): the version is **pinned in `installer\dist-pins.psd1`**; bump it (and the `Dists` URL list) there deliberately and re-run to converge. The **multiarch** Windows tarball (rocBLAS/hipBLASLt kernels for every gfx family, so `HIP_PATH` serves whatever `GpuTargets` we build) is downloaded from the stable index (`stable.repo.amd.com/rocm/core/tarball/` from ROCm **10.0** on, `repo.amd.com/rocm/tarball-multi-arch/` for everything before it: see the pins) and extracted **into its own version directory** (`C:\TheRock\<version>`, the pins' `Root`) inside the same elevated session, which also sets the machine env: `HIP_PATH` **only**, naming the ACTIVE version; the compile-time vars (`HIP_DEVICE_LIB_PATH`, `HIP_PLATFORM`, `LLVM_PATH`) stay process-scoped in `common.ps1` because a machine-wide `LLVM_PATH` breaks the driver's HIP runtime (see `common.ps1` above), and the elevated leg deletes machine-wide copies left by earlier versions. Dists therefore sit **side by side**, which changes what "converge" costs: a version an earlier run already extracted is reached by moving `HIP_PATH` onto it, no download at all, and the pre-versioning single-directory layout (`C:\TheRock\build`, what every install through 1.11.3 wrote) is **renamed** into its version dir rather than re-fetched (same bytes, 4.6 GB cheaper). The price is disk, ~25 GB per dist: the report lists the inactive ones and never deletes them, since an inactive dist is a working rollback and 25 GB is the user's call. The same session appends `bin` + `lib\llvm\bin` to the machine PATH via the raw registry (`setx /M` truncates PATH at 1024 chars; `[Environment]::SetEnvironmentVariable` downgrades `REG_EXPAND_SZ` to `REG_SZ`) and **prunes every other `Root\*` entry out of it**, which is not tidiness: `amdhip64_*.dll` reachable from two PATH dirs is an ambiguous load order, the classic silent-crash cause the report warns about at the end. The installed version lives in a `.therock-version` marker written only after a successful extract (the env leg is gated on it, so a failed install never points `HIP_PATH` at a broken tree). A wipe + re-extract now only ever clears an **incomplete tree of the same version**, so llama-server has to be stopped for exactly two operations, both of which move ground under a loaded DLL: the rename of the legacy tree, and a re-extract over an existing version dir (the script checks and skips those, and installs a NEW version happily while it runs). The report also warns on a leftover legacy HIP SDK under `Program Files\AMD\ROCm`, a shadowing user-level `HIP_PATH`, any persistent-scope `LLVM_PATH`/`HIP_DEVICE_LIB_PATH`/`HIP_PLATFORM` (driver-runtime poison, see `common.ps1`), and `amdhip64_*.dll` in more than one PATH dir (ambiguous load order: the classic silent-crash cause). CUDA / Vulkan stay manual installs (probed, URLs printed). Reads `build\config-build.psd1` directly (does **not** dot-source `common.ps1`) so it works on a fresh machine before `01-configure.ps1` has run. End-of-run report shows before→after versions, plus rebuild recommendations: `02-build.ps1` / `03-package.ps1` when a newer llama.cpp release tag is available, preceded by `01-configure.ps1` when the ROCm dist changed (`HipPath` moves). It also **scans AMD's tarball indexes** (the pins' `Indexes`) for a stable newer than the `Pin`, and reports it with the `Dists` entry to paste: a report, never an install, for the same reason the llama.cpp check stops short of a `git checkout`. A dist bump can move the clang resource major (`patches\hip\<major>\` regenerated or `02-build.ps1` fails fast), re-derives `GpuTargets`, costs ~25 GB beside the dist in use, and can regress what the current one does right (10.0.0 did not fix the gfx1201 hipBLASLt bug 7.14.0 has), so which version the machines run stays one deliberate edit in one file. Best effort: an unreachable index leaves the row out rather than failing the run. Safe to re-run any time.
- `01-configure.ps1`: auto-detects paths, activates VS Dev Shell for tool discovery, verifies tools, creates `build\` if missing, writes `build\config-build.psd1` **and a generated `.cargo\config.toml`** (the same job count applied to cargo's two thread pools; see Key conventions). Accepts `-LlamaCppDir` param (defaults to `$PSScriptRoot\build\llama.cpp`). Writes GPU targets (**derived from the installed ROCm dist**, not hand-maintained; see Key conventions), build type (Release), compiler (the **full path** to the detected clang: TheRock's `lib\llvm\bin\clang.exe` when present; a bare `clang` in the config fails at cmake time in consoles whose PATH predates the machine-env change), **linker** (`lld-link.exe` from the same LLVM tree as that clang, blank when the compiler is not an LLVM one; see Key conventions), march flags (`-march=x86-64-v3`), and build jobs. `Find-ROCm` probes process then machine `HIP_PATH`, then legacy `Program Files\AMD\ROCm`; `Find-Tool` falls back to `HipPath\bin` and `HipPath\lib\llvm\bin`.
- `02-build.ps1`: dot-sources `common.ps1` + calls `Enable-VsDevShell`. Builds **both** llama.cpp (CMake configure + Ninja) **and** `llama-cpp-config` (cargo build --release). Auto-clones llama.cpp into `build\llama.cpp\` (or fetches if present) and **checks out its latest RELEASE tag** rather than tracking master HEAD, so the build is a clean tagged release and `git describe` yields e.g. `v0.2.0`, not `v0.2.0-11-g…`. Upstream tags two different things and the framework follows only one of them: every merge to master gets a lightweight `bNNNN` nightly, a release additionally gets an annotated `vX.Y.Z` on that same commit (semver adopted in b10398), and **the nightlies are ignored even when newer** (b10605 on master against v0.2.0 = b10566, 2026-08-24). That rules out `git describe --abbrev=0`, which answers with the NEAREST tag, i.e. the last nightly; the selection is instead the highest `^v\d+\.\d+\.\d+$` among `git tag --merged origin/master --sort=-v:refname` (`--merged` for reachability, `-v:refname` so v0.10.0 outranks v0.2.0, and the strict regex so a `v0.3.0-rc1` pre-release, which sorts above the release it precedes, is not mistaken for one). No release tag reachable = a hard failure, never a silent fall back to a nightly. Consequence: `LLAMA_BUILD_IS_DEV=OFF` is now unconditional (the checkout is always a release tag), so the server's own banner reads `0.2.0 · b10566` rather than `0.2.0-dev · …`. Builds CMake output into `build\llama.cpp-cmake\`; the Rust binary stays in cargo's `llama-cpp-config\target\release\` (no intermediate copy: `03-package.ps1` stages it from there). Uses sccache if available for the C++ build. For HIP it force-includes a checked-in patched `__clang_hip_runtime_wrapper.h` (a ROCm/MSVC `<cmath>` include-order workaround: MSVC 14.51's `_CLANG_BUILTIN2` constexpr overloads clash with the HIP device math declarations; first hit on ROCm 7.1, **re-verified still required 2026-07-16 with TheRock ROCm 7.14 / AMD clang 23**). The patched copy is a modified snapshot of the toolchain's own header, so it is **versioned per clang resource major** under `patches\hip\<major>\` and selected from the installed dist (`lib\llvm\lib\clang\<N>`, legacy `lib\clang\<N>`); a ROCm bump that changes the major **fails fast** with regeneration instructions: recipe and validation steps in `patches\hip\README.md`, never force-include a stale copy from a different clang. Also carries the **out-of-tree llama.cpp source patches** in `patches\llama.cpp\*.patch` (currently one: FastMTP `d2t` draft-vocab support for the qwen35 MTP loader): they are REVERTED before the fetch/checkout, because the clone is left patched and a tag bump touching a patched file would otherwise abort the checkout, then re-applied onto the fresh tag. Both legs probe with `git apply --check`, so a re-run is a no-op, and a patch that applies in NEITHER direction fails the build instead of being skipped: an out-of-tree change that silently stops applying ships a binary that behaves differently from the last one built, with nothing in the log saying so. Every patch there is **provisional by design**: when upstream lands the same support it stops applying and is meant to be DELETED, not rebased (per-patch provenance, sha256, blast radius and the log line that proves it is live: `patches\llama.cpp\README.md`). Wipes `build\llama.cpp-cmake\` automatically when `CMakeCache.txt` pins a different compiler path than the config (a ROCm dist move would otherwise poison the reconfigure). The **Vulkan SDK is resolved from the PARENT dir** (`Find-VulkanSdk`: the parent of process/machine `VULKAN_SDK`, then `C:\VulkanSDK` and the `Program Files` roots; highest `[version]` dir that actually has `Lib\vulkan-1.lib` + `Bin\glslc.exe`), because a LunarG upgrade installs a new versioned dir and deletes the old one, after which two things still point at the dead tree: `VULKAN_SDK` in any console opened before the upgrade (FindVulkan searches it first; ggml-vulkan also appends it to `CMAKE_PREFIX_PATH` for `find_package(SPIRV-Headers)`) and the `Vulkan_INCLUDE_DIR`/`Vulkan_LIBRARY`/`Vulkan_GLSLC_EXECUTABLE`/`Vulkan_GLSLANG_VALIDATOR_EXECUTABLE` cache entries, which CMake **reuses without checking the files still exist** (unlike a config-package `<pkg>_DIR`, re-searched when it vanishes). The resolved SDK is exported as `VULKAN_SDK` for the process and the four paths are passed as explicit `-D`s so they override the cache, deliberately not a build-dir wipe like the compiler check, which would cost a full CUDA + HIP rebuild to fix one backend. All under `.\build\` (gitignored).
- `03-package.ps1`: dot-sources `common.ps1` + calls `Enable-VsDevShell` (cmake --install needs the VS env). Stages from `build\llama.cpp-cmake\` + `llama-cpp-config\target\release\` into `build\staging\`, then builds NSIS installer to `.\dist\`. **Prunes llama.cpp's own `test*.exe`** right after `cmake --install` (24 harnesses, ~9.8 MB on v0.2.0: `test-backend-ops`, `test-tokenizer-0`, `test-chat-template` and friends), which cmake stages because it stages every executable carrying an `install()` rule (note that is a SUBSET of what gets built: the cmake bin dir holds 26, two of which are never installed, so count from the staging tree, not from the build). The size is the lesser reason; the real one is that the installer offers to put `bin\` on the **system PATH**, so shipping them would drop 26 generically-named `test-*` commands into every shell on the machine. Pruned in the staging tree rather than filtered in the `.nsi`, so what is staged is exactly what ships, which is also what the OpenSSL import scan below then reads. Also stages the **OpenSSL runtime DLLs** into `bin\` next to `llama-server.exe`: they are NORMAL imports of the server (`libcrypto-N-x64.dll`/`libssl-N-x64.dll`; without them the exe fails at load on a machine with no OpenSSL install), the ABI-versioned names are scanned from the staged binaries' import tables (plain ASCII in the PE, no tooling) rather than hard-coded, since the ABI number moves with the OpenSSL install the build linked against, and the DLLs are copied from `$cfg.OpenSSLDir\bin` (that same install; app dir wins the DLL search order so a system OpenSSL can't conflict). **Every** staged `.exe` and `.dll` is scanned, never a name pattern: llama.cpp **v0.2.0 split each tool into a thin launcher plus an impl DLL** (`llama-server.exe` is 9 KB and imports `llama-server-impl.dll`, 14.8 MB, which is where the OpenSSL imports moved, alongside a new `llama-common.dll` and per-tool `llama-cli-impl.dll`), and the old `llama-server*` scan survived that only by accident of the wildcard; one more rename, or the imports moving into another shared DLL, would have staged NOTHING and shipped a server that dies at load on any machine without OpenSSL. Only 6 DLLs sit in `OpenSSLDir\bin` and 4 of them are providers (`legacy`, `p_test`, `p_ossltest`, `p_minimal`), so copying `*.dll` wholesale is not the shortcut it looks like. Two implementation notes the scan cannot drop: it reads in 4 MB **chunks** with a 64-byte overlap (`ggml-hip.dll` alone is ~900 MB; `ReadAllBytes` + `ASCII.GetString` would cost ~2.8 GB of RAM for that one file), and it gates the regex behind an ordinal `IndexOf` (measured: 32.9 s against 0.9 s on `ggml-hip.dll`; whole tree 44 s against 2.6 s, same two names out of 99 binaries). Remaining runtime deps stay external on purpose: VC++ redist x64, and per-GPU: AMD Adrenalin driver + TheRock dist with `HIP_PATH` (rocBLAS/kpacks), NVIDIA driver + CUDA 13 cuBLAS (`cublas64_13`/`cublasLt64_13`, ~700 MB; documented, not bundled); cudart is linked statically, `vulkan-1.dll` ships with any GPU driver. What IS bundled for them is a helper: `installer\install-runtime-deps.ps1` + `dist-pins.psd1` are staged into `bin\`: self-elevating, PS 5.1-safe, idempotent; installs the missing pieces (VC++ redist ~19 MB; ROCm/TheRock ~4.3 GB for AMD, plus the dist's own `amdhip64_*.dll` copied next to `llama-server.exe`, which is what makes BF16/F16 run on RDNA4: see that script's entry; the official cuBLAS redist ~375 MB for NVIDIA, its two DLLs dropped next to `llama-server.exe`) and points at driver downloads it cannot perform. Component selection: the `-VcRedist`/`-Amd`/`-Nvidia` switches pick **exactly** those components (this is how the installer's three dependency checkboxes invoke it, each `-Unattended` + one switch); with no component switch, VC++ is always considered and the GPU legs are an interactive [A]MD/[N]VIDIA/[B]oth/[S]kip choice (detected GPUs only pre-fill the default), or follow detection under `-Unattended`/`-Report` (`-Report` = detection-only, no elevation). It stays in `bin\` for later re-runs. The package is named `llama-cpp-framework-v<frameworkVersion>-<llamaBuild>-<arch>-setup.exe`, e.g. `llama-cpp-framework-v1.11.2-v0.2.0-x64-setup.exe`: **frameworkVersion** = the `llama-cpp-config` crate version (parsed from `llama-cpp-config\Cargo.toml` `[package]`; the configurator and the framework are versioned together), **llamaBuild** = `git describe --tags` of `$cfg.LlamaCppDir`, which is the bundled **release tag** (e.g. `v0.2.0`), **arch** = `x64`/`arm64`. Two `vX.Y.Z` tokens in one name, and the order names them: framework first, llama.cpp second. No `--match` steers that describe: on a commit tagged both `b10566` and `v0.2.0` it prefers the ANNOTATED release tag over the lightweight nightly on its own. The `^v\d+\.\d+\.\d+$` check on the result therefore decides whether to trust it, not which tag to read: a describe that comes back `v0.2.0-11-g…` or empty means the checkout is not on a release (a hand-moved HEAD, an untagged tree), and the name falls back to a `b<rev-list --count>` build number, deliberately shaped unlike anything the happy path emits so a non-release package cannot pass for one.
- `installer\dist-pins.psd1` holds the pinned external distributions (ROCm/TheRock `Pin` + `Root` + tarball URLs + index URLs, NVIDIA cuBLAS redist URL + sha256, VC++ redist permalink): the **single source of truth** read by `00-install-prerequisites.ps1` on the build machine and by `installer\install-runtime-deps.ps1` on end-user machines (03-package stages the pair into the installer's `bin\`). Bump pins here only. `Dists` is an ordered candidate list, first REACHABLE wins, and it serves two readers with different needs: a machine already on a dist consults it only when the `Pin` is missing, and an unpublished pin then changes nothing (the report says "not published yet"), while a bare machine takes the first entry it can download. Hence the **previous stable stays listed below the pin**, as the fallback a fresh install lands on while the pinned version is still propagating, and prereleases are deliberately **not** listed: a pinned stable that is not out yet must install nothing, not an rc. The **host moved with ROCm 10.0** and a stale URL fails as a `403` that reads exactly like "not published yet": 10.0 stable and 10.1 nightlies live under `stable.repo.amd.com` / `rc.repo.amd.com` / `nightly.repo.amd.com` (all `/rocm/core/tarball/`), while everything up to 7.14 **and the 10.0.0 release candidates** stayed on the legacy `repo.amd.com/rocm/tarball-multi-arch/` (rcs on `rocm.prereleases.amd.com`). File names are unchanged, so a bump means choosing the index by version, not editing the number in the URL (source: ROCm/TheRock `RELEASES.md`). `Indexes` is the other half of that: the two listing pages `00-install-prerequisites.ps1` scans to **report** a stable newer than the `Pin` (never to install one, and never read by the end-user helper). Both are HTML carrying their listing as an inline JS `files` array, so the names are matched with a regex rather than parsed, and strictly (`\d+\.\d+\.\d+` immediately before the extension), or the `-tests-` builds sitting in the same listing and the nightlies, which are a version with a date glued on (`10.1.0a20260831`), come back as releases. Scanning both hosts and keeping the highest is also what retires the trap above: the URL arrives WITH the version, found rather than composed. Prerelease indexes stay out for the reason prereleases stay out of `Dists`.
- `installer\install-runtime-deps.ps1`: end-user runtime-deps helper (see `03-package.ps1` above for what it installs); PS 5.1-safe and ASCII-only on purpose (fresh Windows has no PS7; non-ASCII in 5.1 scripts needs a BOM). Its AMD leg does one thing the name does not suggest, and it is the one that makes BF16/F16 models run on RDNA4: after the dist is in place (freshly installed OR already there) it **copies the dist's own `amdhip64_*.dll` into `bin\`**, next to `llama-server.exe`. That is a load-order fix, not a bundled dependency. Windows resolves a static import from the exe's directory and then System32, **both before PATH**, and the Adrenalin driver keeps its own `amdhip64_7.dll` in System32, so without the copy every binary here runs the dist's `rocblas.dll` + `libhipblaslt.dll` against the DRIVER's HIP runtime and never the dist's, which is exactly the mix that aborts at the first prefill batch (see the hipBLASLt footgun below). Nothing else moves: `rocblas`, `hipblaslt`, `amd_comgr` and `rocm_kpack` keep resolving from `HIP_PATH\bin` over PATH, which the HIP backend already depends on, so the copy adds no new failure mode; deleting it reverts to the driver's runtime. Freshness is decided by **content** (size, then SHA256), never by the DLL's stamped version, and that is not paranoia: every dist here stamps the same `10.0.3581.0` into that file's VERSIONINFO (7.14.0, 7.15.0a20260728, 10.0.0 and 10.1.0a20260901 alike), and 10.0.0 and 7.15.0a20260728 are even the same 16,555,520 bytes while being different binaries, so a (size, version) check would call a stale copy current exactly when `HIP_PATH` moves between two such dists and leave the install running another version's runtime. One SHA256 of a ~17 MB file per run buys a `HIP_PATH` move that converges on a re-run. The copy is also reachable **on its own** as `-StageHipRuntime` (leg 2b): same staging, no download, no prompt, silent when there is no ROCm to copy from, and it is what the installer's hidden always-run section calls on every install and upgrade. That split is deliberate: leaving the copy inside the AMD leg alone hid a 17 MB fix behind a checkbox announcing a **4.3 GB download**, which is exactly the box a user who already has ROCm never ticks, i.e. the cure would have reached everyone except the people who need it. With both switches the stage-only leg stands down, since the AMD leg stages the runtime itself.
- `installer\llama-cpp-framework.nsi.template`: NSIS installer template with placeholders (`@VERSION@` = framework/configurator version, `@LLAMA_BUILD@` = the bundled llama.cpp **release tag**, e.g. `v0.2.0`, `@STAGING_DIR@`, `@OUTPUT_FILE@`) replaced by `03-package.ps1` into `build\llama-cpp.nsi` (transient, deleted after the build). The ARP DisplayName/installer title read "llama.cpp-framework v@VERSION@ (llama @LLAMA_BUILD@)", i.e. "llama.cpp-framework v1.11.2 (llama v0.2.0)"; DisplayVersion = framework version; the llama release is also written to `HKLM\Software\llama.cpp\LlamaBuild` (the placeholder and the registry value keep the `Build` name from when they carried a `bNNNN`: nothing reads either programmatically, and renaming the registry value would strand the installs that already wrote it). The welcome page doubles as the runtime-requirements notice (VC++ redist always; per-GPU: AMD Adrenalin + ROCm/TheRock for HIP, NVIDIA driver + CUDA 13 cuBLAS for CUDA; Vulkan needs nothing); backends with missing deps are skipped silently at runtime, so the installer is the one place the user is told. Six components: binaries (required), PATH addition (optional), Start Menu shortcut (optional), plus three dependency checkboxes: **base requirements** (VC++ runtime), **AMD ROCm runtime**, **NVIDIA cuBLAS runtime**, all unchecked by default, each running the bundled `install-runtime-deps.ps1` with `-Unattended` + its component switch in a visible console (`ExecWait`); the finish page points at the helper for later re-runs. A **seventh, hidden section** (`-StageHipRuntime`, the leading `-` in the name makes it invisible and always selected) runs the same helper one last time with `-Unattended -StageHipRuntime`, through `nsExec::ExecToLog` so it needs no console: on a machine that already has ROCm it copies the dist's ~17 MB HIP runtime next to `llama-server.exe`, which is what makes BF16/F16 models run on RDNA4. It is a section rather than a step inside **AMD ROCm runtime** precisely because that box announces a 4.3 GB download and so is never ticked by the machines that already have the dist; it downloads nothing, prompts nothing, and stays silent when there is no ROCm to copy from, and it runs LAST so an install that did tick the AMD box is staged from the dist it just installed. Installs `bin\` (llama.cpp binaries, plus `llama-cpp-config.exe`, `llama.ico` and the uninstaller side-by-side with `llama-server.exe`) and `lib\`, leaving **nothing at the install root**. The uninstaller is `bin\llama-cpp-uninstall.exe`, namespaced rather than a bare `uninstall.exe` because the optional PATH component puts `bin\` on the SYSTEM path. Two things that follow from the root staying empty, and one bug that came from it not being: the closing `RMDir "$INSTDIR"` is **non-recursive on purpose** (`$INSTDIR` is user-chosen, so `RMDir /r` would follow a careless choice down a shared folder or a drive root), which means anything left at the root is never removed AND keeps the directory alive, which is how a `llama-cpp-config.exe` from **2026-06-30** (the layout before the tree moved under `bin\`) survived every upgrade since, each uninstall having only ever cleaned `bin\` and `lib\`; the Uninstall section therefore carries an explicit list of legacy root files, and an entry may only be retired once no installed version can still have written it. And the uninstaller cannot delete itself on the UPGRADE path: `CheckPreviousInstall` runs it with `_?=$INSTDIR`, which suppresses the copy-to-`$TEMP` an NSIS uninstaller normally makes (that copy is what would let it vanish under itself, and suppressing it is what makes `ExecWait` able to wait), so the caller finishes the job after `ExecWait` returns and the image is unlocked, clearing both the new path and the legacy one. **No custom config page**: runtime configuration is handled entirely by `llama-cpp-config` post-install. Start Menu shortcut: "llama.cpp Config" → `llama-cpp-config.exe`.
- `llama-cpp-config\`: Rust GUI + CLI configurator for `server.ini` + per-model `presets.ini`; five tabs (**Server** → `server.ini`, **Models** → `presets.ini`, **Benchmark** → measure or compare presets, writing to `%LOCALAPPDATA%\llama.cpp\bench\` (the live engine's prompt is a FILE, `config\bench-prompt.txt` by default with a ~40k-token `bench-prompt-long.txt` seeded beside it, both from the binary, opened in the system's text editor by the tab's Edit button, and shared with the CLI; its unattended half is the CLI's `bench sweep`, which runs the same engines once per value of ONE presets.ini key, leaves each leg's ordinary `bench-<stamp>` report behind plus a `sweep-<stamp>` digest, and puts the key back afterwards; a live leg RESTARTS llama-server, since the key rides the child's launch args, and `;` separates values because `device`/`tensor-split` values contain commas), **Integrations** → `opencode.json` model list + Claude Code snippet, **Settings** → the configurator's own preferences) plus llama-server run controls. This entry is only the **map**: the architecture, per-tab/per-card walkthrough, UI-binding conventions, source-layout table, and test topology all live in [llama-cpp-config\README.md](llama-cpp-config\README.md), and every module carries its own depth in a `//!` header comment; read those before diving in, not this file. Adding a preset field, a server field, or a UI property follows the checklists in **Common changes** below. Seventeen recurring footguns, each with a canonical write-up in the code:
  - **`--mlock` / `--no-mmap` are ONE enum now, and mixing them loses settings silently** (`server_cfg.rs` `load_mode`, `runstate.rs` `server_args`): llama.cpp folded `--mlock`/`--mmap`/`-dio` into `-lm`/`--load-mode` in **b10105** (PR #20834). The old flags still parse (with a `DEPRECATED` warning), but each now **overwrites the whole mode** instead of setting one bool of two, so they no longer compose: `--mlock --no-mmap` is last-one-wins (the mlock is dropped), and a lone `--mlock` selects `MLOCK`, which is mlock **without** mmap (`use_mmap` is true only for `mmap`/`mmap+mlock`/`auto`, see `llama-model-loader.cpp`; the mlock half is `mlock`/`mmap+mlock`, see `llama-model.cpp`). The framework shipped exactly that pair through v1.6.5, so its default silently ran with mmap off. Hence one dropdown, never two checkboxes, and an `-lm <mode>` always on the launch line. A pre-b10105 `server.ini` is migrated on read (`migrated_load_mode`): a deliberate `NoMmap = true` survives, the auto-written `Mlock = true` does not.
  - **GPU placement is a table, not two text fields** (`gpu_split.rs` + `GpuSplitTable`): `--tensor-split` is positional over the devices in `--device`, in that order, so neither means anything alone. A blank tensor-split over 2+ GPUs = split by *free VRAM*, not evenly. And the vector is **normalized**, so it is a ratio with far fewer distinct outcomes than a percentage suggests: llama.cpp cuts `n_layer_all + 1` positions, every block plus the **output layer** (`dev_output = get_layer_buft_list(n_layer_all)`), which on a 33-block model means 83/84/85% are one launch and two of every three edits do nothing. Hence `Layout`/`block_counts`: where a model is known (Models tab) the column is shown and edited in **blocks**, and because a vector summing to the positions assigns exactly itself, writing the counts back is the identity: no inverse invented, `29,5` *is* blocks 0-28 / 29-32+output. Two consequences: a count cannot be edited alone (the rows absorb from the back, which is also why the cell is a **`Slider`** committing once on `released`: applying mid-drag would rebuild the row being dragged; `SpinBox` stays banned for the stray-wheel reason but `slider-base.slint` handles no scroll event, and its only gap is that the *accessibility* set-value action raises `changed` without `released`), and the INI still stores the **ratio**: the count is a per-model view, re-derived every rebuild, so re-pointing a preset at another model rescales it instead of lying. The `--split-mode` combo sits ABOVE the table and the columns follow the EFFECTIVE mode (`gpu_split::effective_mode`, because a server-wide value rides the router's CLI and so shadows every preset's key, an explicit `layer` included): blocks exist only under `layer`; under `row` the table edits the raw ratio (the matrix bytes follow row fractions via the backend split buffer type; CUDA/ROCm only, Vulkan silently falls back to the layer cut, and the KV cache follows the layer cut regardless); under `tensor` (upstream's tensor parallelism, b8738 / PR #19378, experimental, and what DEPRECATED `row`: `docs/multi-gpu.md` says "superseded by tensor"; both still parse, so both stay listed, row last and labelled, because an INI that carries it must show it) it edits the same raw ratio, since the checked devices become ONE meta device and every weight AND the KV cache are cut along a tensor axis by that vector (`llama_meta_device_get_split_state`), with one difference the share column states: a blank vector is an EVEN cut there, not the free-VRAM weighting; a second strip under the combo (`preset_split_mode_warning`, against the EFFECTIVE mode) names the three launch-time refusals no row can show: an arch on `llm_arch_supports_sm_tensor`'s deny-list (mirrored in `gguf::arch_supports_sm_tensor`, re-check on a llama.cpp bump), `flash-attn = off` (`auto` is promoted), and NO device pinned in either scope, under which llama.cpp pools every detected device, duplicate Vulkan views and iGPU included, since only the other modes dedup by device id; `--fit` is merely skipped with a log warning, so `ctx-size` is the user's to size; under `none` the editors retire: llama.cpp drops every device but `devices[main_gpu]` before loading, so the head row reads 100%, the other checked rows read "unused", and the drag handle is the one control left. The combo's single "layer (default)" entry deliberately merges the old default/layer pair (same launch for a preset in every reachable configuration), and the flags-preview line under the table is GONE: it ignored the mode, so it read as stale truth. Corollary, and the reason a live preset combo could change NOTHING before v1.9.1: a server-wide `SplitMode = layer` is **dropped on read** (`server_cfg::server_split_mode`); llama.cpp already defaults to layer so it never changed the server's own launch, but the router merges its CLI args into every preset (`unset_reserved_args` does not prune `--split-mode`), so its only effect was to neuter each preset's mode. `none`/`tensor`/`row` survive: those change the launch, and overriding every preset with them is deliberate.
  - **"All layers offloaded" still leaves the embedding table in PINNED HOST RAM** (`tensor_override.rs` + `TensorOverrideTable`): llama.cpp parks `token_embd.weight` in a host buffer even at `offloaded N/N layers to GPU`, and with a GPU backend active that buffer is pinned (`ROCm_Host`/`CUDA_Host` in the log), which Windows reports as **Shared GPU memory**. So a model that fits in VRAM with room to spare still shows GBs of shared allocation. The cure is an `override-tensor` rule (`token_embd\.weight=ROCm0`); the value's grammar is split on `,` and at the first `=` *before* parsing and cannot be escaped, which is why it is a table and not a text field.
  - **…but that cure is CONDITIONAL, and violating either condition costs 10x** (`gguf.rs` `embd_line` / `embd_pin_warning`, surfaced as Model info → **Embeddings** + a warning strip on the table): the pin is **not model-agnostic**, which is the natural (and wrong) reading of the bullet above. (1) `token_embd`'s **own** quant must have a GPU `get_rows` kernel; ggml-cuda/ggml-hip whitelist `F32/F16/BF16/I32/Q1_0/Q4_0/Q4_1/Q5_0/Q5_1/Q8_0` and `default: return false` for **every K-quant and IQ-quant** (`ggml-cuda.cu`, `supports_op`). Pin a K-quant table and it sits in VRAM the GPU cannot read, so the lookup round-trips to the host *every token*: measured 25 → **2.8 tok/s** (Q4_K embd), → **1.9 tok/s** (Q5_K: bigger table, worse). Prefill is untouched (~400 tok/s: one round-trip per 2048-token batch amortizes it) and the GPU engines read **0%**, so it presents as an *idle* GPU, not a slow one. The file NAME does not tell you: Unsloth's `Q6_K_XL` keeps `token_embd` at **Q8_0** (safe) while its `Q4_K_XL`/`Q5_K_XL` drop it to Q4_K/Q5_K. Same model, same build, opposite outcome. (2) The card must have **room**: pinning MOVES the table from host RAM into VRAM (~1.26 GiB at Q8_0), a straight add that tips an already-full card into paging (Q6_K + f16 KV @ 256k ctx: 23 → **13.7 tok/s** *with* the pin). Because condition (1) is per-model, prefer the **per-preset** scope over the server-wide one. `gpu_has_get_rows` mirrors that upstream switch and must be re-checked when bumping llama.cpp: a type that gains a kernel and is missing here only costs a needless warning, but a type listed here *without* one green-lights the pin this exists to prevent.
  - **A server-wide `--override-tensor` REPLACES each preset's, it does not add to it** (`server_cfg.rs` `override_tensor`): the same table exists in both scopes, and `-ot` `push_back`s onto a vector inside llama.cpp, so "the two lists concatenate" is the natural guess and it is wrong. The router merges its own CLI args into every preset as a KEY→VALUE map (`common_preset::merge` → `options[opt] = val`, CLI as the writer), so exactly one `--override-tensor` reaches a child: the server's. Verified against b9976. Two consequences: the Models tab must say it is shadowed (`tensor_override_warning`), and the buffer type is validated by the ROUTER at startup; an unknown device in the server-wide value fails with `unknown buffer type` and **nothing starts**, where the same typo in a preset only kills that model.
  - **The image encoder ignores `--device`** (`server_cfg.rs` `mmproj_device`): `clip_ctx` takes the first GPU backend the registry offers unless `MTMD_BACKEND_DEVICE` names one, so on a mixed box it holds VRAM on the wrong card and computes only on image requests, which reads exactly like an idle GPU that has been "assigned something".
  - **Preserving past thinking is ONE flag, not a template kwarg** (`presets.rs` `reasoning_preserve` + the crate README): `--reasoning-preserve` sets the kwarg `preserve_reasoning`, which `caps_apply_preserve_reasoning` (`common/jinja/caps.cpp`) expands into THREE template variables at once (`preserve_thinking`, `clear_thinking`, `truncate_history_thinking`) because templates disagree on which they read (Qwen3.6/LFM2.5 the first, GLM-4.7 the second, Nemotron the third). Hand-writing one of them into `chat-template-kwargs` sets one of the three: it works on the templates using that name and is a **silent no-op** on the others, and it never registers with the capability probe, so llama-server still prints `consider enabling it via --reasoning-preserve`. Note "supported" only means the trace showed up in the probe's render: a template that preserves *unconditionally* (Ornith-1.0) reads as supported while gating on nothing.
  - **`--parallel` DIVIDES the context, and omitting it is not "1 slot"** (`integrations.rs` `effective_ctx`, surfaced as each opencode model's `limit.context`): the context one request may use is `n_ctx_seq = n_ctx / n_parallel` (`llama-context.cpp`), so `parallel = 2` halves it, **unless the key is absent**, because llama-server defaults `n_parallel` to `-1` = auto, and auto picks 4 slots *and a unified KV cache* (`tools/server/server.cpp`), under which every slot sees the whole `n_ctx`. Compounding it: `ctx-size` absent means the model's **trained** context (`n_ctx = 0` → `hparams.n_ctx_train`), not a fixed default. Both together are why opencode's advertised context is neither `ctx-size` nor the trained context, and why the naive fix is *worse* than the bug it replaces: publishing 256k for a 256k model that pins `parallel = 2` promises a context llama-server rejects at 128k+.
  - **Thinking support is read from the template's SOURCE, and the verdict is about the TEMPLATE** (`gguf.rs` `Thinking` / `thinking_line` / `past_thinking_line`, surfaced as Model info → **Thinking** + **Past thinking**): there is no Jinja engine here, while llama.cpp answers the same question by *rendering* the template (`caps_get`, `common_chat_templates_support_enable_thinking`). So the scan looks for the names the flags act on (`enable_thinking` for `--reasoning`, and `preserve_thinking`/`clear_thinking`/`truncate_history_thinking` for `--reasoning-preserve`), which makes a `yes` a fact and a `no` only "no marker this build knows about" (MiMo-VL's template names nothing yet the model thinks; llama-server parses `<think>` out of the *output* regardless). The **Past thinking** row is nonetheless the one thing llama-server's log CANNOT tell you: its probe prints `supports preserving reasoning` for a template that gates on the flag *and* for one that preserves unconditionally (Ornith-1.0), which are opposite answers to "will this flag do anything".
  - **The FOLDER a drafter sits in does not say which speculator it needs** (`gguf.rs` `draft_spec_type`, applied in `gui\models_tab.rs`'s `draft_picked` handler): the picker merges `mtps\` and `dflashs\` into one dropdown, and deriving `--spec-type` from that folder alone cannot separate the two DFlash flavours: `draft-dflash` and `draft-dspark` share the arch (`dflash`), the file-name shape and the folder, and are told apart only by a `markov_w1.weight` tensor INSIDE the file. Picking the wrong one of that pair does not fail; `is_dspark` changes the drafting batch itself (`n_draft` masked positions against `n_draft + 1`, an anchor-first layout, ceiling `block_size` rather than `block_size - 1`, `common/speculative.cpp`), so the drafts are read from the wrong positions and are simply rejected: speculation that costs and never pays. Hence the picked FILE's header decides, mirroring llama.cpp's own `common_speculative_types_from_gguf` (b10406, extended to MTP in b10428, which llama-server now runs itself when `--model-draft` arrives with no `--spec-type`). The framework still WRITES the key rather than leaving it to that auto-detect, both to show the verdict before launch and because the key works on older builds. The folder guess survives as the FALLBACK, and has to: a separate MTP head with no blocks of its own (gemma4-assistant, `block_count = 0`) matches no rule, upstream's included, and an unreadable GGUF is not evidence of anything either.
  - **Draft placement needs a draft FILE** (`presets.rs` field docs): llama.cpp reads `--device-draft` / `--n-gpu-layers-draft` only inside `if (has_dft())`. With MTP heads embedded in the main GGUF the draft context is built against the target model and runs on its device, ignoring both. With a SEPARATE MTP head file (gemma4-assistant, `n_layer=0`) they do apply, and there, pin model **and** draft to one device, or leave the draft on CPU: multi-device "auto" memory-fitting crashes those heads.
  - **BF16/F16 on gfx1201 dies inside hipBLASLt, and the fix is an env var no llama.cpp flag can reach** (`server_cfg.rs` `rocblas_use_hipblaslt` → `runstate.rs` `env_vars`, surfaced as Server → **SDK Tuning** → ROCm): on the R9700 under ROCm/TheRock 7.14, rocBLAS's default routing sends 16-bit GEMMs to **hipBLASLt**, and the **second** 16-bit GEMM in a process fails at kernel launch; f32 is immune, the same call sequence passes on Tensile, and a single visible GPU changes nothing (standalone repro: default and `ROCBLAS_USE_HIPBLASLT=1` fail; `=0` passes for batched/strided/plain × bf16/f16). llama-server aborts on the first prefill batch of any BF16/F16 model. The earlier reading, "hipBLASLt is not built for Windows, so this must be Tensile", was wrong: `libhipblaslt.dll` ships in the TheRock dist and is a static import of `rocblas.dll`. Forcing Tensile is a full-speed cure, not a degradation (pp512 **587** t/s / tg128 35 t/s on Ornith BF16, against ~19 t/s prefill for the older `GGML_CUDA_CUBLAS_COMPUTE_TYPE=f32` workaround). Two consequences for the code: it can only ride the **environment** (rocBLAS reads it below llama.cpp; hence the SDK Tuning card exists at all, and hence `env_vars` and not `server_args`), and it is a **tri-state** whose default is *unset*, because the bug is per-arch and hipBLASLt is the faster path where it works; `Some(false)` and `None` are opposite instructions, so a bool would hand every machine a workaround it never asked for. The value is parsed by rocBLAS as an int: export `"1"`/`"0"`, never `"true"`/`"false"`. Upstream: llama.cpp #25836, ROCm #6461, TheRock #7271. **The dist version was never the variable, the HIP RUNTIME is** (2026-09-01, and it retires "wait for a fixed tarball" as the plan): the driver's `amdhip64_7.dll` in System32 wins the load order over anything on PATH, so the dist's rocBLAS/hipBLASLt run against the DRIVER's runtime; put the dist's own runtime next to the exe and the same GEMMs pass on 7.14.0, 10.0.0 **and** nightly 10.1.0a20260901, with `=1` forced as well, i.e. hipBLASLt is healthy and it is the mix that fails (same-directory A/B with that one file as the variable; end-to-end `test-backend-ops test -o MUL_MAT -b ROCm0 -p "type_a=bf16"` goes from `ROCm error: invalid argument` to `5/5 backends passed` under default routing). `installer\install-runtime-deps.ps1` stages it on its AMD leg, so an install that has run that leg needs no knob here. Two things that follow: an upstream report of "fixed in nightly X" proves nothing unless it says which runtime the test loaded (7.14.0, the version originally reported, passes against its own), and the finding rests on ONE driver here (32.0.22042.14002), so the tri-state stays.
  - **The speculative widgets are DISABLED, not cleared, so a dead `spec-type` survives invisibly and kills the model** (`presets.rs` `prune_inactive_draft_keys`, applied to the form in `form.rs` `prune_inactive_draft_fields` and at the clone boundary in `gui\models_tab.rs`): all four speculative controls are `enabled: draft_active` (`state.slint`), i.e. greyed out (never blanked) when the model embeds no MTP heads and no draft file is picked. Any value that arrives from somewhere OTHER than those widgets therefore sits in the form unreadable and is written straight back out by `form_to_preset` on the next save. Two ordinary ways in, and the first writes to disk without ever passing through the form: **Clone** copies every field of its base onto a different model (`..base.clone()`), and re-pointing an existing preset at another model keeps the old one's keys. The result is not inert: `spec-type = draft-mtp` on a model without nextn layers makes llama-server build an MTP draft context against the target, `llama_init_from_model` returns nullptr (`context type MTP requested but model doesn't contain MTP layers`) and **the model fails to load at all**, with the GUI showing a greyed-out control as the only clue. Hence the prune runs at every boundary where the model becomes known (`update_model_info`, which also leaves the preset dirty so Save is reachable) or where a preset reaches disk without a form (clone, save). It is gated on having actually READ the GGUF: an unreadable header is not evidence a model has no MTP heads. Note the verdict is per-ARCH, not per-file: `muse-glimmer` carries no `nextn_predict_layers` key at all, while `src\models\<arch>.cpp` must also *read* that key for llama.cpp to honour it (only ~18 arches do), so a nextn-bearing GGUF on an arch that ignores it fails the same way.
  - **The one flag that can save a 17-minute prefill has NO env name, and that decides where it can be set** (`slot_state.rs` module header, emitted by `runstate.rs` `server_args`, surfaced as Server tab -> **Conversation snapshots**): reading a prompt is QUADRATIC in its length and the KV cache is process memory, so every restart re-reads the whole conversation. Measured on a 234k-token prompt (Qwen3.8-27B): `0.95 ms + 0.0287 ms per 1k of context` per token, i.e. 984 t/s at position 4k against 142 t/s at 218k, integrating to ~17 minutes, against ~8.3 GiB of sequential IO to reload the same state through `/slots/{id}?action=save|restore`. Those endpoints exist only under `--slot-save-path`, and the framework always launches the ROUTER, whose per-model children are separate processes: the natural conclusion is that a flag with no `.set_env(...)` (`common/arg.cpp` gives this one only `set_examples`) cannot reach them, and it is wrong. `get_map_key_opt` (`common/preset.cpp`) maps every option by its FLAG NAME with the dashes stripped as well as by its env name, so the router's own argv becomes `base_preset` (`load_from_args` -> `common_params_to_map`, which keys off `opt.args`), `preset.merge(base_preset)` copies it onto every model, and `unset_reserved_args` does not prune it. Same coin, other side: the key is therefore NOT writable as `LLAMA_ARG_*` anywhere. Two more traps in the same feature. The directory must EXIST before the launch, because llama.cpp validates it while PARSING the flag (`fs_is_directory` or it throws "not a directory"), so a missing folder does not degrade to "no snapshots", it stops the server from starting; hence `start()` creates it and the flag is emitted only when the toggle is on. And the restore is worth something only because `SERVER_TASK_TYPE_SLOT_RESTORE` also deserializes the saved token list into `slot->prompt.tokens`, which is what the next request's `get_common_prefix` compares against; without that half the dump would be a file nobody reads.
  - **`llama-bench` takes no prompt and no temperature, and a comma in its flags means "run these as SEPARATE benchmarks"** (`bench.rs` module header + `synthetic_argv` / `synthetic_sweeps`, surfaced as the Benchmark tab's **synthetic** engine): `-p` is a token COUNT, not a text, and the tool never samples (its own README: the measurements "do not include the times for tokenization and for sampling"), which is a *stronger* reproducibility guarantee than a fixed prompt at temp 0, not a weaker one, and is why the tab carries a second engine rather than one with the prompt field greyed out. The trap is the translation from an INI value: `device` and `tensor-split` are `,`-separated in `presets.ini` and `/`-separated for llama-bench, `override-tensor` is `,`-separated in the INI and `;`-separated there (llama-bench splits `-ot` on `,` into configuration GROUPS first, and only then on `;` into rules), so a preset's `54,12` silently becomes two benchmarks of one device each. Same shape one level up: llama-bench runs the CARTESIAN product of its test parameters and `-d` multiplies the pp tests as well as the tg ones, so the workload is split into a prefill and a decode invocation: 3 lengths x 3 depths + 3 depths = 12 tests in one call against 3 + 3 = 6 split, for the same information. What it cannot do at all is the preset's speculative drafter (so its `tg` reads roughly HALF the live rate with MTP on), the mmproj, the chat template, `--ctx-size` (it sizes the context as prompt + generated + depth) and `--parallel`; `bench::caveats` prints that list under the Run button and again in the saved report, because a benchmark that does not name what it left out is read as measuring everything.
  - **The two benchmark engines demand OPPOSITE llama-server states, and the live one must disable the prefix cache** (`bench\exec.rs` module header, `bench::live_body`): live measures the running server, so it needs it up; synthetic needs it DOWN, because llama-server holds the whole model resident and a second copy does not fail cleanly, it spills into shared memory over PCIe and reads as a backend regression rather than as a mistake, so the tab stops it first through `gui::stop_server_async_with` (never a bare `runstate::stop`: that path also writes the conversation snapshot when `SaveStateOnShutdown` is on, and keeps the footer, tray and run-status generation counter in step, or the next periodic tick reports the deliberate stop as "llama-server is no longer running", in red). On the live side the load-bearing field is `cache_prompt: false`: without it the SECOND repetition of the same prompt hits the prefix cache, reports a prompt rate of tens of thousands of tokens per second, and the mean it feeds is a fiction; `timings.cache_n` is read back anyway and surfaces as a row note, so a build that ignored the field is caught rather than believed. Results are appended to the run's jsonl as each one lands, not written at the end: a run is minutes of sustained GPU load, which is exactly when a TDR or a bugcheck arrives (one did during this feature's own testing), and results written only at the end are results lost on the first crash. Three things the report carries so a comparison can be FALSIFIED rather than believed, each one a measure the retired `tools\bench-backends.ps1` had: llama-bench's own row is kept **verbatim** in the jsonl beside the aggregated point (the point drops `flash_attn`, `n_batch`, `n_threads`, `backends`, `gpu_info`, and the first version of this feature kept only the aggregate, which is how the resolved flash-attention of a finished ROCm-versus-Vulkan comparison turned out to be unrecoverable); the resolved **flash-attn is read back** and a disagreement between the compared presets is a warning printed ABOVE the table, because a preset pinning nothing runs at `auto` and `auto` resolves per BACKEND, so two legs can silently land on different kernels (the tab does not PIN it: that would benchmark a configuration the preset does not run); and an **environment block** records the boot time and each display adapter's driver version plus what every device id resolved to by NAME, since the ids are not stable across driver states and since a Windows Update driver churn silently invalidated a full day of measurements on 2026-08-24. The one measure NOT carried over is INTERLEAVING the legs across passes, so a card that heats over a long run charges the drift to whichever preset ran last: re-run with the selection order reversed when a difference is small.
  - **The live benchmark's prompt is a FILE, and every decision about it follows from where it cannot live** (`bench.rs` module header + `normalize_prompt` / `ensure_prompt_file` / `prompt_report_rows`, tab wiring in `gui\bench_tab.rs`, path in `settings.rs` `BenchPromptFile`): the tab carries a PATH, never a text, so the Run button and `bench sweep` (with `--prompt-file`, or with no flag at all) send the same bytes; a text box beside a `--prompt-file` flag is a second prompt no flag can reach, and two front ends measuring different prompts do not say so. **Two** prompts ship, both compiled into the binary and **seeded** on first use rather than installed as files: `config\bench-prompt.txt` (`DEFAULT_PROMPT`, 230 chars, the default) and `config\bench-prompt-long.txt` (`LONG_PROMPT`, from `llama-cpp-config\assets\`, 169,289 chars / ~40k tokens). Seeded and not installed because `bin\` sits under `$PROGRAMFILES64\llama.cpp`, where an editor could not save without elevation and the next upgrade's NSIS `File` directive would overwrite the edit, so they live beside the three other files the user owns (`ensure_prompt_file` only ever CREATES, and picks its seed by FILE NAME so a deleted long prompt comes back long rather than as 230 characters under a name promising 40k). The long one is seeded although nothing points at it, because a benchmark ranks settings IN THE REGIME IT MEASURED and the short prompt's regime is one nobody works in (at 40k of context the preset that benchmarks at 57 t/s serves at 24 to 40, and the ranking moves too: `spec-draft-n-max` peaks at 5 near the start of a conversation and at 3 at 43k), so the deep-regime run has to be one Browse… away rather than a documentation lookup. It is a FROZEN snapshot of this repo's `AGENTS.md` + the crate README, pinned to LF in `.gitattributes` (it is compiled in as bytes) and **not to be regenerated when those docs change**: every measurement recorded against it stops being comparable the moment it moves, which is the failure the report's sha256 exists to catch. `llama-cpp-config\assets\README.md` carries that plus the two other edits that would silently break it. **Edit** shells out to the system's default `.txt` handler instead of opening a window of ours, because a Slint `TextEdit` is already sluggish at a few hundred KB (`log_window.rs` caps its tail at 256 KB for exactly that) and the prompts worth putting in a file are the long ones; the readout under the field picks up an external save within one 5 s status tick, gated on `(path, mtime, len)` so a keystroke in another field does not re-read a megabyte. Two things that display cache must not touch. `on_bench_run` re-reads the file ITSELF: a run that measured the previous version of the text would be wrong in the one way nothing downstream could detect, since the report's own digest would agree with itself. And the report identifies the prompt by path + size + **sha256** (`src\sha256.rs`, hand-rolled: `sha2` is six crates for one call site) with the text embedded only up to 4096 chars, because embedding it whole is what made an old comparison checkable and stops being enough the moment anyone can edit the file between two runs; the same three facts go into the jsonl header, which carried nothing about the prompt before. `normalize_prompt` strips a leading BOM and folds CRLF on read, so the same prompt saved by two editors hashes the same, and the price is a digest that does NOT match `Get-FileHash` on a CRLF file, which the report says out loud.
- `resources\llama.ico`: icon used by the NSIS installer and embedded in `llama-cpp-config.exe`. **Generated, not checked in** (gitignored): `resources\generate-llama-ico.mjs` rasterizes it from llama.cpp's webui logo (`tools\ui\src\lib\assets\logo.svg`, a `currentColor` SVG) as a `#111111` glyph on a white rounded tile, matching how upstream renders its own PWA/apple-touch icons (upstream commits no `.ico`; its `favicon.ico` comes from the webui npm build). `llama-cpp-config\build.rs` (and, belt-and-braces, `03-package.ps1`) runs the script automatically whenever the file is missing; it needs node+npm and the llama.cpp clone, so a fresh checkout needs `02-build.ps1` (which clones) before a bare `cargo build`/`cargo test` can succeed. Delete `llama.ico` to force a regeneration after an upstream logo change.
- `tools\report-memory.ps1`: diagnostic (not part of the build pipeline; reads only `%LOCALAPPDATA%\llama.cpp\`, so it runs on an installed machine with no repo or `config-build.psd1`). Slices the memory of the **currently running** llama-server across two sources and cross-checks them: llama-server's own load log (every buffer announces its size and device → the *requested* footprint, rebuilt exactly) and Windows' `GPU Process Memory` perf counters (what the driver *actually* handed out: dedicated VRAM vs shared system RAM). The divergence is the point: an oversubscribed device does not fail to allocate, WDDM silently pages the excess over PCIe and the only symptom is slow decoding. Each balance sheet folds tensor placement in as an **`of which tensor override`** sub-row under `model weights`, never a row of its own, and never summed: an `--override-tensor` rule *moves* a tensor into that device's model buffer, it allocates nothing extra, so it is already inside `model weights` and inside `requested`, and totalling it again would inflate the one figure the whole report exists to compare against `free at load`. The host section additionally names the pinned share of the model weights, which is the shared-GPU-memory number and the reason the tensor-placement table exists at all. `-Json` for machine output.

  Two sources for the placement leg, and neither is the obvious one. The **rules** come from the ROUTER's `spawning server instance with args:` block, not from `presets.ini`/`server.ini`: the router overlays its own CLI args onto every preset, so the files do not say what actually ran, and the spawn line is the already-merged winner. That block sits *outside* the load block (above the `device_info` banner), and it is matched to the child by the `[port]` prefix every child line carries, never by "the spawn header nearest above"; with several models up, that would pick the wrong one. The **hits** come from `tensor <name> (<n> MiB <type>) buffer type overridden to <buft>`, which is `LLAMA_LOG_DEBUG`, i.e. verbosity **5** (`common/log.h`: `LOG_LEVEL_DEBUG = 5`, printed when `verbosity <= thold`), so at the usual `-lv 4` it is absent and *no hits is not the same as nothing matched*; the report says which.

  Eight parsing traps, all handled, and the first one is **which block**: the report must describe the process running NOW, so the block is matched to a live listener by PORT (`Get-LivePorts`, against the `[58939]` prefix every child line carries; the log records no PIDs), never "the newest block in the file". Both the `device_info` banner and every `buffer size` line are TRACE (`COM_TRC` in `common/common.cpp`, i.e. `-lv >= 4`) while `server.ini` `LogVerbosity` may well be 3, at which point the running child writes NEITHER, the newest block belongs to some earlier chattier run, and the report prints that dead model's balance sheet against the live process' counters (hit 2026-08-18: a single-GPU Qwen3.8-27B reported as a two-GPU Ornith-35B, CUDA rows included, which is exactly the cross-check this tool exists to make). Two corollaries: an older block has to be cut at the next block's banner rather than run to EOF, or it absorbs the buffer lines of every child that started after it; and the failure path names the cause (live port plus its `-lv`) instead of asking whether llama-server is running. Then the parsing proper: llama.cpp **re-emits** `sched_reserve` for the draft context *after* the mmproj loads (so clip ownership must come from the `reserve_compute_meta` source line, never from a "seen the clip banner" latch) and **re-reserves** the compute graph once the slots come up (same buffer announced twice → collapse per `(owner, kind, device)`, do not sum). The log accounts for no driver context (a few hundred MiB per backend), so `requested` sitting just under `free at load` can still spill: the live counter decides, and in BOTH directions. Asking for more than the card reported free does not prove anything paged (WDDM can satisfy it in dedicated VRAM by trimming other processes, and `free at load` is a snapshot taken before the weights land), so the spill test is **shared memory beyond that backend's pinned `*_Host` buffers**, never the arithmetic alone and never raw shared. Two consequences the code spells out: an overflow the counter does not corroborate is reported as `AT THE LIMIT` (no headroom left) rather than as paging, because those are different instructions to the reader (seen 2026-08-18 at 85 MiB over: dedicated grew by exactly the requested amount, shared stayed flat at 124 MiB); and the same subtraction is what stops a 2 GiB host compute buffer, which Windows charts under the card, from reading as a 2 GiB spill on a device whose log fits. With `--fit on` the model is **loaded twice** (a `no_alloc` dry run to size the fit, then the real one) and every override line is emitted in both passes → collapse by tensor name or every rule double-counts. `CPU_Mapped` (the buffer holding mmap'd weights, i.e. the whole CPU-side model unless `--no-mmap`) is **host memory, not a device**: matching host on `^CPU$` (rather than `^CPU`) invents a phantom GPU called CPU_Mapped and charges the model to it. A **sliding-window model builds two KV caches** (`llama_kv_cache_iswa`: a full one for the global-attention layers, a small one for the SWA layers) and each announces itself with the *same* `llama_kv_cache: <dev> KV buffer size` line (same source, same device, same kind), so the de-duplication above silently eats one of them (Gemma-4-12B: 816 MiB kept, 255 MiB dropped, and a card that was 4 MiB from full read as comfortable); the cure is a latch on the `creating non-SWA / creating SWA KV cache` banner, which is safe here precisely where it was not for the clip graph, because llama.cpp prints it immediately before building each cache, in both passes. A **separate draft/MTP head prints its own `print_info` block after the model's**, so arch/params/file type/file size must take the FIRST occurrence; otherwise a gemma4 + gemma4-assistant pair reports the head's arch and its nonsense parameter count (`422.86 B params` for a 12B model). And the set of `buffer size` lines llama.cpp can print is exactly **model / KV / RS / compute / output / LoRA / DSV4 `<name>` state**: the regex must be exhaustive, because a kind it does not match does not come out small, it vanishes from the balance sheet altogether (LoRA adapters and DeepSeek-V4 state were doing exactly that).

  One asymmetry the report has to encode rather than infer: a rule ending in **`=CPU` does not mean ordinary RAM**. With a GPU backend up and mmap off, llama.cpp serves CPU-side weights out of that backend's *pinned* host buffer (`CUDA_Host`/`ROCm_Host`), which Windows charts under the card as **shared GPU memory**, so the VRAM is freed and the shared allocation is not. With mmap on, the same debug line is logged and the tensor is then served straight from the mapped file (`CPU_Mapped`, ordinary RAM), leaving the named pinned buffer at 0 MiB. Same log line, opposite outcome. Hence two rules in the code: the pinned verdict is gated on a pinned model buffer actually appearing in the `buffer size` lines, never on the override line alone; and an `of which` that comes out **larger than the row it hangs off** is not rounding, it is that contradiction; the sub-row is suppressed and the mismatch reported instead of printing `1,302 MiB of which` against a `0.00 MiB` row.


## Key conventions

- **No em-dashes anywhere in this repo.** Not in comments, doc comments, user-facing strings, the comment text written into `server.ini` / `presets.ini`, docs, or commit messages. Use `:` for an apposition or explanation, `;` between two independent clauses, `,` for an aside or trailing afterthought, or parentheses when a pair wrapped an aside. The one sanctioned exception is a `—` that is DATA rather than prose: the glyph the GPU table shows for a not-applicable cell (`gpu_split.rs`, `components.slint`), the assertions pinning it, and its entry in `binding_lint.rs`'s `RENDERABLE` whitelist.
- `common.ps1` is dot-sourced by `02-build.ps1` and `03-package.ps1`. Other scripts (`00-install-prerequisites.ps1`, `01-configure.ps1`) read `build\config-build.psd1` directly.
- `build\config-build.psd1` (build-time) uses single-quoted PowerShell-data-file syntax. Runtime config files (`server.ini`, `presets.ini`) are plain INI written as UTF-8 without BOM.
- All build artifacts (source clones, cmake binary dir, NSIS staging, sccache cache, `config-build.psd1`, generated `.nsi`) live under `.\build\` (gitignored). The two exceptions are cargo's `llama-cpp-config\target\` and the generated `.cargo\config.toml` (gitignored separately: cargo only discovers the latter by walking up from the cwd, so it cannot live under `build\`). The final installer goes to `.\dist\`. `rm -rf build\` wipes everything C++-side including the sccache (the next full build re-fills it from scratch) but leaves the Rust `target\` alone.
- The installer registers in `HKLM\Software\llama.cpp` (InstallDir) and supports upgrades (uninstalls previous version first). User runtime state lives under `%LOCALAPPDATA%\llama.cpp\`: `config\server.ini` (single `[Server]` section), `config\presets.ini` (per-model presets consumed by `llama-server --models-preset`), `config\settings.ini` (the configurator's own preferences), `config\bench-prompt.txt` + `config\bench-prompt-long.txt` (the live benchmark's prompts, plain UTF-8, both seeded from the binary on first use and edited in place: the short one is the default, the long one is ~40k tokens for measuring the context depth you actually work at; `settings.ini` `BenchPromptFile` picks which, or points elsewhere entirely), `logs\llama-server.log`, `bench\bench-<stamp>.{jsonl,md,log}` (one benchmark run each, written as it goes so a run killed by a driver reset keeps what it measured) and `bench\sweep-<stamp>.{jsonl,md}` (one `bench sweep` each, digesting the legs it ran; named `sweep-` so the tab's saved-runs list, which globs `bench-*.jsonl`, never tries to load one), and, only when `SaveStateOnShutdown` is on, `state\<model>.llamastate` (KV-cache snapshots, sized by the tokens the slot actually HOLDS rather than by `ctx-size`: 4.38 GiB measured at 127,579 tokens on Qwen3.8-27B, ~8.3 GiB for a full 262k context; the directory is overridable via `StateDir` precisely because the default sits on the system drive). The uninstaller asks (defaulting to No) whether to delete the whole tree, so it survives reinstall/upgrade by default.
- sccache is auto-detected; cache stored in `build\.sccache\`. Uses `SCCACHE_MAX_FRAME_LENGTH=104857600` for large GPU objects and `SCCACHE_CLIENT_SIDE=1` (sccache 0.17+ client-side mode: compile + cache lookup run in the client process, no per-compile daemon round-trip; older sccache ignores the var). nvcc is intentionally NOT wrapped with sccache: it mishandles multi-arch fatbin generation on CUDA 13.x (`fatbinary` fails with "Could not open input file '<tu>.compute_75.ptx'" on every `.cu.obj`). Retested with sccache 0.17.0 (2026-07-30): still broken, in server and client-side mode alike (minimal repro: any multi-gencode `nvcc -c`), so host C/CXX (clang) caching only.
- HIP GPU targets (`config-build.psd1` `GpuTargets` → `-DGPU_TARGETS`) are **derived programmatically by `01-configure.ps1`** (`Get-GpuTargets`), never hand-maintained: a ROCm dist bump only needs a re-run of `01-configure.ps1`. Derivation = enumeration + policy: the archs the installed dist ships Windows BLAS kernels for (`.kpack\blas_lib_gfx*.kpack` under `HIP_PATH`; legacy-SDK fallback `bin\rocblas\library\TensileLibrary_lazy_gfx*.dat`), **minus** CDNA/Vega `gfx9xx` (kpacks exist for MI cards but there is no Windows driver; TheRock also dropped gfx906/Radeon VII kernels: ROCm 7.1 was the last to serve it), **plus** the Ryzen iGPU safety set (`gfx1035/1036/1103/1152/1153`), unioned in even if a future dist drops their kernels: the driver-bundled HIP runtime (`amdhip64_7.dll`) fails kernel-module load on *every* visible device when one of them has no matching code object; a visible iGPU otherwise kills the dGPU with "device kernel image is invalid". A static 7.14.0 snapshot is used only when no dist is present at configure time. On TheRock 7.14.0 this yields 20 archs (RDNA1 `gfx1010-1012`, RDNA2 `gfx1030-1036`, RDNA3 `gfx1100-1103`, RDNA3.5 `gfx1150-1153`, RDNA4 `gfx1200/1201`), each costing ~56 MiB of `ggml-hip.dll` plus compile time; hand-prune the generated config only if size matters, and never prune the iGPU set. Related footgun: ROCm's `hip-config-amd.cmake` derives the `--offload-arch` flags from **`GPU_BUILD_TARGETS`**, which it seeds from `GPU_TARGETS` via `set(... CACHE ...)`, a no-op once cached, so editing `GpuTargets` silently does nothing on an existing `build\llama.cpp-cmake\`. `02-build.ps1` passes `-UGPU_BUILD_TARGETS` to clear it every configure.
- **A ROCm dist carries TWO kernel stores, and the framework's own recommended setting uses the one that looks legacy.** `.kpack\blas_lib_gfx*.kpack` (~41 MiB per arch) is **hipBLASLt**'s; `bin\rocblas\library\` (3,457 files, 693 MiB on TheRock 10.0.0) is **Tensile**'s, found by rocBLAS relative to `rocblas.dll`'s own directory. Which one is read is decided by `ROCBLAS_USE_HIPBLASLT`, and on gfx1201 the framework sets it to `off` (the hipBLASLt 16-bit GEMM bug, still unfixed in 10.0.0 and re-confirmed at runtime 2026-08-31), i.e. the configuration this project recommends runs **entirely out of `bin\rocblas\library`**. So the bullet above reads `.kpack` only to ENUMERATE the archs a dist ships, which is a different question from where the kernels come from at run time; do not infer from it that the kpacks are what gets loaded. Consequence for anyone trimming the ~13.6 GiB a dist costs: deleting `bin\rocblas` breaks the recommended configuration, and the failure is LATE and unlike a missing DLL, since the backend loads and the device enumerates normally, then the first matrix multiply dies with `Could not initialize Tensile host`. Within `bin\rocblas\library` the split is 351 MiB for the 20 RDNA archs the build targets against 343 MiB for `gfx908`/`gfx90a`, which it never builds (302 MiB of that is gfx90a alone), so the CDNA half is the safe thing to delete and the only one worth deleting.
- **lld links both halves of the build, by two different mechanisms.** *C++*: `01-configure.ps1` looks for `lld-link.exe` **next to the clang it resolved** and writes it as `config-build.psd1` `Linker`; `02-build.ps1` passes it as `-DCMAKE_LINKER` when non-empty. The condition is "we are building with an LLVM suite that ships lld", so a bare-name `clang` fallback or an MSVC `cl.exe` toolchain leaves it blank and CMake keeps `link.exe`; blank is a supported state, and the key is absent altogether from a config written before it existed (hence the truthiness check, not a `Test-Path`). CMake already picks `lld-link` unaided when clang comes from a full LLVM tree, so this mostly *pins* what happens anyway; what it buys is that the fallback to `link.exe` can no longer happen silently. *Rust*: unconditional, via the generated `.cargo\config.toml` (`[target.x86_64-pc-windows-msvc] linker = "rust-lld.exe"`). The bare name is deliberate: `rust-lld` ships **inside** the toolchain (`<sysroot>\lib\rustlib\<target>\bin`, not on PATH) and rustc resolves it from there, so it is always present and always version-matched to rustc, where naming an external `lld-link.exe` would borrow whatever LLVM happens to be installed (here AMD's LLD 23 from TheRock) and break on a machine without it. MSVC `link.exe` remains rustc's default on `x86_64-pc-windows-msvc`; only `x86_64-unknown-linux-gnu` switched to `rust-lld`. Neither toolchain announces its linker, so to tell which one produced a binary, look for the **Rich header** that MSVC's `link.exe` stamps into the PE's DOS stub and lld does not.
  - The Rust half carries `rustflags = ["-Clink-arg=/force:multiple"]`, and it is **load-bearing, not a leftover**: Skia links ICU *statically* (`skunicode_icu.lib`) while the `windows` crate imports the *system* one (`icuuc.dll`), so every `uloc_*` is defined twice. `link.exe` has always swallowed that (LNK4006, second definition ignored); the flag only makes lld behave the same for this one collision. It bites **only the test binary**: the second ICU arrives via `i-slint-backend-testing`, a dev-dependency (→ `i-slint-common` → `fontique` → `windows`), so `cargo build` links with no duplicates and the flag is inert there, while without it `cargo test` does not link at all. The knowingly-accepted cost: rustflags are not per-profile, so a real duplicate symbol in the shipped binary would be accepted rather than caught. Re-test and drop it if the two ICUs ever stop colliding.
- Build parallelism (`config-build.psd1` `BuildJobs`, written by `01-configure.ps1`) defaults to **3/4 of logical cores, clamped to at most `cores - 1`** (for both the CMake/Ninja `-j` and the `cargo build --jobs` legs), so at least one core stays free for interactive use during a long CUDA/HIP compile; at this ratio the clamp never binds, and it is kept anyway so the reservation is a property of the formula rather than a side effect of the ratio, surviving a later retune. A 1-core machine is the single case that cannot honour it (it gets 1 job, since 0 would build nothing). `BuildJobs = 0` means "use all cores". Note `-j` bounds concurrent COMPILE PROCESSES, not CPU: no affinity is set, and nvcc (forking `cicc`/`ptxas` per arch) plus the threaded lld links can still push past that share. The same number is also written as a generated, gitignored **`.cargo\config.toml`** at the repo root, because a `--jobs` flag only reaches the invocations `02-build.ps1` owns; a bare `cargo build`/`cargo test` typed by hand or fired by an IDE would otherwise take every core. It caps **both** of cargo's pools, which default to all cores independently: `[build] jobs` for rustc/codegen and `[env] RUST_TEST_THREADS` for the libtest harness (verified: cargo exports `[env]` to build scripts, rustc, `cargo run` and `cargo test` binaries, and does not force it over a value already in the environment, so `RUST_TEST_THREADS=1 cargo test` still wins for a serial debugging run).
- `llama-cpp-config` has zero Clippy warnings; uses `#[cfg]` compile-time branching for OS portability in `paths.rs`, `gui.rs`, `runstate.rs`, `main.rs`, `gguf\ffi.rs`, and `proc.rs` (the shared `CREATE_NO_WINDOW` process launcher used by `devices.rs` / `server_version.rs` / `runstate.rs`); `single_instance.rs` is Windows-only wholesale.

## Common changes in `llama-cpp-config`

The two recurring recipes live as authoritative checklists at the top of the module they start in; follow those, not a from-memory list:

- **Adding a per-model preset field** fans out to 7 places (kebab-case INI key ↔ snake_case Rust field; INI schema → form struct → widget → conversions). Checklist: top of `llama-cpp-config\src\presets.rs`. Trace an existing field like `ctx-size` as the template.
- **Adding a server (server.ini) field** is the same shape plus **three spots in `cli.rs`** (the server has a per-field `set`; the preset CLI is list/show/delete only) plus **`runstate::server_args`** (the launch/Command-Line leg). Checklist: top of `llama-cpp-config\src\server_cfg.rs`.

Cross-cutting rules the recipes rely on:

- **Before adding a new property, field, or function, search the codebase for existing ones that already cover the case.** `base_url_default` on `ServerForm` already tracked whether the Base URL was user-specified; I added a redundant `chat_url_specified` on `AppState` instead. Always grep first, then decide if something genuinely new is needed.
- **Model Info rows show facts, not explanations.** `moe_offload_line` used to append "saves VRAM (slower)"; `thinking_line` / `past_thinking_line` appended `--reasoning on|off switches it (enable_thinking)` after "yes". The doc comments (`///`) explain the why; the displayed value is just the fact. Keep them separate.
- **`open_chat_url` prefers Base URL custom over launch URL.** `state.slint` derives it from `chat_url` when `server_form.base_url_default` is false (user specified a custom Base URL), otherwise from `launched_url` (the URL the running server was started with), falling back to `chat_url` as the last default. The form's `base_url_default` field is the single source of truth: no duplicate property needed.
- **Model info names only files the preset LOADS.** `draft_line()` reports the model's own MTP heads plus the preset's `--model-draft` ("draft file: x.gguf", whose header is the "Draft file" row below), and "none" when there is neither, never a blank. Until v1.11.3 it also advertised the drafter whose filename best matched the model in `mtps\` / `dflashs\` (the deleted `ExternalDraft` / `external_drafters` / `family_tokens` / `token_overlap`), and a box that otherwise reports the running config was read as claiming that drafter was in use: the row was identical whether one was picked or not, and identical again after a restart (reported twice against v1.11.2). The match was a token overlap, so `Qwen3.8-27B-UD` was offered the head built for `Qwen3.8-27B-Uncensored-…` on `qwen3` + `27b` alone, a drafter for a different fine-tune that llama.cpp loads and then rejects nearly every token of. Choosing a drafter belongs to the Assets picker, which lists every one on disk; do not reintroduce a "best match" line here.
- Editable widgets bind **two-way** (`<=>`) to `AppState.…`; a one-way binding goes stale after the first edit. The sanctioned one-way exceptions (read-only displays, `for`-row widgets, `MappedComboBox`, the Slider/AutoSlider push, `SegmentedControl`) are catalogued in the crate README's conventions section.
- Nearly every step is guarded by a test that fails when skipped: INI and form round-trips (`presets.rs` / `form.rs`; `server_cfg.rs` / `server_form.rs`), the CLI leg's exhaustive-struct tests (`cli.rs`), the launch-arg leg (`runstate.rs`), widget-binding staleness (`src\tests\ui_bindings.rs`: one widget PER KIND, plus the one-way-binding text lint `src\tests\binding_lint.rs`) and the Models/Integrations callback funnel (`src\tests\save_flow.rs`). The unguarded remainder (nothing fails for either): forgetting the widget entirely (the field just never appears in the UI), and skipping the path-field `validate_for_save` step (a `;`/`#` path then saves fine and reloads truncated; see the checklists' final step).
- Run the e2e tests with `cargo test` (debug profile), **not** `--release`: they need Slint element debug info that `build.rs` emits for non-release builds only. Bare `cargo test` is the right command: the generated `.cargo\config.toml` already caps both thread pools at `BuildJobs` (see Key conventions), so no `--jobs`/`--test-threads` flags are needed. Full test-topology rationale (single shared `#[test]`, `LLAMA_CPP_CONFIG_DATA_ROOT` redirect, `src\tests\` vs `tests\`): crate README "Tests" section.

## Release process

1. **Bump version** in `llama-cpp-config\Cargo.toml` (`[package] version = "X.Y.Z"`). The next build also refreshes the crate's line in `Cargo.lock`: both files belong to the release commit.
2. **Run `02-build.ps1`**: builds llama.cpp (fetches and checks out the latest `vX.Y.Z` **release** tag; the `bNNNN` nightlies are not candidates) and llama-cpp-config.
3. **Run `03-package.ps1`**: stages binaries, builds NSIS installer to `.\dist\llama-cpp-framework-vX.Y.Z-vA.B.C-x64-setup.exe` (framework version first, bundled llama.cpp release second).
4. **Commit** all changes. Subject: **`Release vX.Y.Z: <summary>`**, the SAME first line as the tag (step 5); every release commit follows this (`git log --oneline`: a `feat:`/`docs:`-style subject is not the convention here). Body: a prose summary, closing with a **`Bundles llama.cpp <tag> (up from <previous tag>).`** line, both being release tags now: `Bundles llama.cpp v0.2.0 (up from v0.1.2).`. Releases through 1.11.1 bundled a `bNNNN` nightly, so the first one after the switch reads `up from b10524`.
5. **Tag**: `git tag -a X.Y.Z -m "Release vX.Y.Z: <short summary>..." && git push origin X.Y.Z`
   - Tag name: **no `v` prefix** (e.g. `1.5.1`, not `v1.5.1`).
   - Tag message: starts with `Release vX.Y.Z: <summary>` on first line, then blank line, then bullet points of changes. Match the style of previous tags (`git show 1.5.0`).
6. **Create release**: `gh release create X.Y.Z --title "vX.Y.Z (llama.cpp vA.B.C)" --notes "<markdown body>"`
   - Title format: **`vX.Y.Z (llama.cpp vA.B.C)`** (with `v` prefix, includes the bundled llama.cpp release).
   - Body: detailed markdown with sections (`##`, `###`), bullet points, code formatting. Match the style of previous releases (`gh release view 1.5.0`). End with test count and bundled llama.cpp release.
7. **Attach installer**: `gh release upload X.Y.Z dist\llama-cpp-framework-vX.Y.Z-vA.B.C-x64-setup.exe`

**Formatting conventions** (verified against 1.5.0; the llama.cpp token switched from `bNNNN` to `vA.B.C` after 1.11.1, so examples older than that show the previous shape):

| Artifact | Format | Example |
|---|---|---|
| Commit subject | `Release vX.Y.Z: <summary>` (matches the tag) | `Release v1.5.1: proxy/gateway support...` |
| Tag name | `X.Y.Z` (no `v`) | `1.5.1` |
| Tag message | `Release vX.Y.Z: <summary>\n\n- bullets...` | `Release v1.5.1: proxy/gateway support...` |
| Release title | `vX.Y.Z (llama.cpp vA.B.C)` | `v1.11.2 (llama.cpp v0.2.0)` |
| Installer name | `llama-cpp-framework-vX.Y.Z-vA.B.C-x64-setup.exe` | `llama-cpp-framework-v1.11.2-v0.2.0-x64-setup.exe` |
