# Project guide

## Project overview

Private AI Framework (`private-ai-framework`) is a build orchestrator for [llama.cpp](https://github.com/ggerganov/llama.cpp): it installs prerequisites, configures, builds and packages it on Windows (CUDA, Vulkan and ROCm/HIP, two MSIs built with the WiX Toolset: llama.cpp's own and the framework's, which requires it; written, not yet compiled by WiX or run), on Linux (the same backends, split `.deb` and `.rpm` packages, the engine `llama.cpp` packaged apart from the framework at its own version) and on macOS (Apple Silicon only: Metal + Vulkan through MoltenVK, split `.pkg`; written but untested on a Mac). Every phase is a cargo command (`install` installs the newest package in `.\dist\` on the build machine, on every OS), `cargo run -p xtask -- <phase>` (`prereq`, `configure`, `build`, `package`, `install`), written **`xtask <phase>`** in the docs; the logic is in `xtask\src\`, split into `common\` (shared) and `linux\`, `windows\`, `macos\` (per OS). The only step that is not cargo is the bootstrap that installs Rust and the system packages: `scripts\00-install-prerequisites.ps1` (Windows, which also installs the GPU dists) and `scripts/00-install-prerequisites.sh` (Linux, macOS). `scripts\` holds only helpers: those two, thin wrappers that run the cargo phases (`scripts\0N-*.ps1`, `scripts/0N-*.sh`), and the PowerShell libraries `common.ps1` and `dists.ps1`. llama.cpp's built-in chat interface (served by `llama-server`) is used as the frontend; `pai-bff`, the backend-for-frontend service with its own web UI (`fe\`), ships as a service on Linux and Windows, not on macOS; today its web UI shows, read-only, the framework version and the manager's instances with their state (`PLAN.md` step 10).

Two companion Rust binaries configure `server.ini` and per-model `presets.ini`: `pai-config`, the GUI configurator, and `pai`, its command line (the same operations headless); a third one, `pai-manager`, runs llama-server as a system service on Linux and Windows, where the configurator is its client (the Windows side is type-checked only and has not yet run on Windows: `PLAN.md` step 1).

**Start here: read [PLAN.md](PLAN.md).** It holds the user's requirements, the Definition of Done, and what is left to do, in order.

## Key conventions

- **No em-dashes anywhere in this repo.** Not in comments, doc comments, user-facing strings, the comment text written into `server.ini` / `presets.ini`, docs, or commit messages. Use `:` for an apposition or explanation, `;` between two independent clauses, `,` for an aside or trailing afterthought, or parentheses when a pair wrapped an aside. The one sanctioned exception is a `—` that is DATA rather than prose: the glyph the GPU table shows for a not-applicable cell (`gpu_split.rs`, `components.slint`), the assertions pinning it, and its entry in `binding_lint.rs`'s `RENDERABLE` whitelist.
- **No user-visible text in the code.** Every text the configurator shows or prints goes in the strings file, linked from the code by a key: `crates\core\strings\en_US.toml` for the GUI, `crates\core\strings\cli.toml` for the CLI (always English). Not language, so they stay in the code: numbers, units, acronyms, paths and format examples. Not user text, so they stay literal: what is written into bench.db or the comments of `server.ini` / `presets.ini`, text other code matches, what scripts read: `--help` and the output of `server show` and `bench query`, and the system files the Linux packages ship (`xtask\src\linux\system_files.rs`: the polkit action descriptions and messages, the unit descriptions), read in place by polkit and systemd. How: "Adding a user-visible string" in [crates\config\AGENTS.md](crates/config/AGENTS.md).
- **Code comments state no facts that can change** (token counts, measured figures): they point to where the fact lives (a guide, bench.db).
- `scripts\common.ps1` is dot-sourced by `tools\pcie-bench\build.ps1` only. `scripts\00-install-prerequisites.ps1` and xtask read `build\windows\config-build.psd1` directly.
- `build\windows\config-build.psd1` (build-time) uses single-quoted PowerShell-data-file syntax. Runtime config files (`server.ini`, `presets.ini`) are plain INI written as UTF-8 without BOM.
- All build artifacts (source clones, cmake binary dir, MSI staging, WiX intermediates, sccache cache, `config-build.psd1`) live under `.\build\` (gitignored), in a per-OS directory: `build\windows\` (`$buildRoot` in `scripts\common.ps1`; `build/linux/` on Linux). Cargo's target dir is included: `build\windows\cargo-target\` (`build/linux/cargo-target/` on Linux), set by the build scripts through `CARGO_TARGET_DIR`. The exceptions are the web UI's `fe\node_modules\` and `fe\dist\` (gitignored, not per OS: every `xtask build` remakes both with `npm ci` and `npm run build`) and the generated `.cargo\config.toml` (gitignored separately: cargo only discovers it by walking up from the cwd), which also pins `[build] target-dir = "build/windows/cargo-target"`, so a bare `cargo build`/`cargo test` outside the scripts lands in the same directory (before `xtask configure` has run, it still writes `target\` at the repo root, the cargo workspace root). rust-analyzer in VS Code checks into `build\rust-analyzer\` (`.vscode\settings.json`, checked in, relative paths only; not per-OS, since VS Code settings cannot be). The same file keeps CMake Tools from configuring anything on its own (`tools\pcie-bench\build.ps1` is its only configure path: the VS generator the extension's kits pick finds no CUDA toolset from the dist layout); C/C++ IntelliSense reads the `compile_commands.json` that `build.ps1` writes into `build\windows\pcie-bench\`. The final installer goes to `.\dist\`. `rm -rf build\` wipes everything, the sccache and the Rust release build included.
- The framework's MSI registers in `HKLM\Software\private-ai` (InstallDir), installs the `private-ai-manager` service and the `private-ai-bff` web service with the machine tree `%ProgramData%\private-ai\` (only `config\`, the framework's own `bff.ini`), and supports upgrades (MajorUpgrade: removes the previous version first; downgrades refused). llama.cpp's MSI registers in `HKLM\Software\llama.cpp`, creates the engine's machine tree `%ProgramData%\llama.cpp\` (below), upgrades on its own and removes release 2.4's `llama.cpp-framework` first. User runtime state lives under `%LOCALAPPDATA%\private-ai\`:
  - `config\settings.ini` (the configurator's preferences); `config\server.ini` (single `[Server]` section), `config\presets.ini` (per-model presets for `llama-server --models-preset`) and `config\presets.ini.disabled` (switched-off presets, never read by llama-server) only where the configurator runs llama-server itself (macOS): under the manager they are an earlier install's files, offered for import (below). The live benchmark's prompts are NOT here: the shipped ones are installed read-only under `share\benchmarks\prompts\`, the 43k one the default; `settings.ini` `BenchPromptFile` points at another, a file of the user's anywhere; `BenchDb` names the database benchmark runs go to, empty for `bench\bench.db`.
  - `logs\llama-server.log`, only where the configurator runs llama-server itself (both output streams; on stop, a file LARGER than `settings.ini` `LogRotateKb`, 1024 by default, is filed as `logs\llama-server-<yyyymmdd-hhmmss>.log`, closing instant in UTC; a run that ended without a stop is filed at the next start under its last-write time; newest 10 kept; `LogRotate = false` keeps a single growing file: `runstate.rs` module header).
  - `bench\bench.db`, the only benchmark output: every FINISHED run of the Benchmark tab and of `bench run` (each preset committed with its points, repetitions, parameters and the engine's log when it is done; failed or cancelled presets are not recorded), one campaign per tab run or sweep, the markdown report stored with the campaign (`bench\db.rs` module header). Beside it only `bench\sweep-pending-<stamp>.json`, while a sweep has not yet put its key back (the value to restore).
  - Only when `SaveStateOnShutdown` is on: `state\<model>.llamastate` (KV-cache snapshots sized by the tokens the slot HOLDS, not `ctx-size`: ~4.4 GiB at 128k tokens on Qwen3.8-27B, ~8.3 GiB for a full 262k, plus, since llama.cpp v0.7.0, the slot's context checkpoints and the draft state; overridable via `StateDir` since the default sits on the system drive).
  - The uninstall offers the uninstalling user's tree for deletion (a checkbox, cleared by default) when it runs with the full UI (Settings > Apps > Uninstall included); a silent or basic-UI uninstall, and every upgrade, keeps it: [installer\AGENTS.md](installer/AGENTS.md) lists exactly when the question shows.
- **On Windows the server and preset files are the manager's**, in the engine's **`%ProgramData%\llama.cpp\config\`** (`server@default.ini`, `presets.ini`, `presets.ini.disabled`; `paths::engine_config_dir`; llama.cpp's MSI copies `server@default.ini` and `presets.ini` there only when missing; the framework's own, `bff.ini`, stay in `%ProgramData%\private-ai\config\`, `paths::system_config_dir`): the configurator starts, stops and reads the state of the instance `default` and reads and writes those files only through the `private-ai-manager` service (LocalSystem, automatic start) over the named pipe `\\.\pipe\private-ai-manager`; `control` (start, stop, restart) is any interactive user or an Administrators member, `configure` (writing a file) an Administrators member, elevated or not, with no prompt. Each instance is the SCM service `llama.cpp_<id>`, running `pai-manager run-instance <id>` as the virtual account `NT SERVICE\llama.cpp_<id>`, which runs the llama-server of llama.cpp's install (`HKLM\Software\llama.cpp` `InstallDir`); its log is `%ProgramData%\llama.cpp\logs\llama-server@<id>.log`, the previous run kept as `llama-server@<id>.previous.log`, so `LogRotate`/`LogRotateKb` do not apply. Users read `%ProgramData%\llama.cpp\logs\` and `models\` and have no access to either `config\`. Uninstalling llama.cpp's MSI deletes the instance services and, only when its removal page's checkbox is ticked, `%ProgramData%\llama.cpp\`; its repair and upgrade stop the running instances and start them again. A `ModelsDir` under the user's profile is not readable by the instance's account: an instance whose `server@<id>.ini` leaves `ModelsDir` or `StateDir` unset uses `%ProgramData%\llama.cpp\models` or `state\` (`launch::with_instance_defaults`, Windows only), and `pai` leaves both unset at a save when the user has not set them (`server_control::dirs_left_unset`), but the GUI configurator's Save still writes the user's `~\.llama.cpp` as `ModelsDir` and the per-user state folder as `StateDir` (open, `PLAN.md` step 11). The instance runs in `%ProgramData%\llama.cpp\state` (`launch::instance_current_dir`). `settings.ini`, `bench\` and the earlier per-user files stay in `%LOCALAPPDATA%\private-ai\`, imported as on Linux. Type-checked only, not yet run on Windows; details in [installer\AGENTS.md](installer/AGENTS.md) and "Through the manager" in [crates\config\README.md](crates/config/README.md).
- On Linux the same tree is `~/.local/share/private-ai/`, with three differences. `settings.ini` lives in **`~/.config/private-ai/`** (`$XDG_CONFIG_HOME/private-ai` when that is set to an absolute path): `paths::config_dir`, per user, the same for a packaged install and a tree build. The server and preset files are the manager's, in the engine's **`/etc/llama.cpp/`** (`server@default.ini`, `presets.ini`, `presets.ini.disabled`; `paths::engine_config_dir`; the framework's own, `bff.ini`, stay in `/etc/private-ai/`, `paths::system_config_dir`): the configurator starts, stops and reads the state of the instance `default` and reads and writes those files only through `private-ai-manager` (D-Bus `org.privateai.Manager1`; polkit `org.privateai.manager.control` needs no password in the active session, `org.privateai.manager.configure` is `auth_admin_keep`), which runs every content check (`pai-core` `checks.rs`) and refuses in the configurator's strings (`crates\app\src\server_control.rs`); `bench\bench.db` stays per user. The log is the journal of `llama.cpp@default.service` (`journalctl -u llama.cpp@default`, readable by root and the groups `systemd-journal`, `adm`, `wheel`), not `logs\llama-server.log`, so `LogRotate`/`LogRotateKb` apply only where the configurator spawns llama-server itself (macOS). The per-user `server.ini` and preset files of an earlier install are offered to the manager at each start until the manager has every one (the GUI's Import / Not now dialog, or `pai config import`), and left in place; since `llama.cpp` copies its defaults at install, the manager already has `server@default.ini` and `presets.ini` there, so by the code only a missing `presets.ini.disabled` is offered. macOS keeps every file per user. The Settings tab's "Start at login" is the HKCU Run value `org.privateai.Config` on Windows and the XDG autostart file `~/.config/autostart/org.privateai.Config.desktop` on Linux (`startup.rs`); either way the entry itself is the state, with no INI mirror. Its "start llama-server when the system starts" (Linux, Windows) is likewise the service manager's own state: whether `llama.cpp@default.service` is enabled (the template's `[Install] WantedBy=multi-user.target`), on Windows whether the SCM start type of `llama.cpp_default` is automatic or manual (type-checked only); read and changed through the manager's `BootEnabled` and `SetBootEnabled` (`configure`), and by `pai server boot [on|off]`. A new instance starts disabled. The manager starts no instance at its own start (systemd and the SCM start the enabled ones) and `pai-config`'s launch starts nothing; macOS keeps "start llama-server when pai-config launches" (`settings.ini` `StartServerOnLaunch`).
- **Release 2.4 and earlier used `llama.cpp` names** for the user tree (`%LOCALAPPDATA%\llama.cpp`, `~/.config/llama.cpp`, `~/.local/share/llama.cpp`) and the start-at-login entry (`llama-cpp-config`). `pai-config` and `pai` move them once at start, before anything reads the tree (`crates\core\src\migrate.rs`, `crates\app\src\migration.rs`): only a tree holding files it writes, never into an existing new tree, the old one removed only once the new one is complete; llama.cpp's own `config.ini` stays in `~/.config/llama.cpp` on Linux, where llama.cpp reads it; the login entry carries over only when it was on (an entry switched off in Task Manager, or a disabled autostart file, is only removed). Details: "Migration from 2.4" in [crates\config\README.md](crates/config/README.md).

## Working from this plan

- Take the first open step unless the user says otherwise. Split it if it is too big for one sitting.
- The plan can change. The coordinator or the user can change any part of it when needed: steps, order, requirements or Definition of Done. Other agents propose changes to the coordinator. The commit says why, and the coordinator tells the user whenever a requirement changes.
- If a requirement is added, make sure a step covers it.
- A step is done only when it meets the Definition of Done in `PLAN.md` as well as its own "Done when".
- Steps in `PLAN.md` are only open work. When a step is done, remove it, and update the requirements' "State" and "Where things stand" if they changed.
- Do this in the same commit as the work. The commit message says what was closed and how it was checked, so `git log` is the record of closed work. Do not keep a done list in the plan.
- New work that comes up goes in the plan, in its place in the order. A step that turns out wrong gets rewritten, not worked around.

## Commands

Agents run only these, on the crate they are working on (`pai-core`, `pai-app`, `pai-manager`, `pai-config`, `pai-cli`, `pai-bff`, `xtask` or `docs-site`), or on the web UI in `fe\`: the tester the tests, the coder the tests, the linter and the format check; the coordinator runs none of them ("Roles"). They are fast and enough to see red and green:

    cargo test -p <crate> <test-name-filter>
    cargo clippy -p <crate> --all-targets -- -D warnings
    cargo fmt -p <crate> --check
    cargo run -p docs-site -- --check
    npm --prefix fe test
    npm --prefix fe run typecheck
    npm --prefix fe run lint
    npm --prefix fe run format:check

The last four are the web UI's, from the repo root: its tests (Vitest), its type check (`tsc`, the test files included, which Vitest does not type-check), its linter (ESLint) and its format check (Prettier); the coder runs the type check with the linter, and none of the four writes a file. Run `npm --prefix fe ci` first when `fe\node_modules\` is missing.

On Linux the coder also type-checks the Windows-only code (`cfg(windows)`) of `pai-core`, `pai-app`, `pai-cli`, `pai-manager`, `pai-bff` and `xtask`; nothing runs. For `pai-app` and `pai-cli`, prefix both commands with `PRIVATE_AI_LLAMA_CPP_DIR=$PWD/build/linux/llama.cpp` (from the repo root): `pai-app`'s build script otherwise looks for the Windows clone ("Generated architecture tables" in [docs\build-compiling.md](docs/build-compiling.md#generated-architecture-tables)):

    cargo check -p <crate> --all-targets --target x86_64-pc-windows-gnu
    cargo clippy -p <crate> --all-targets --target x86_64-pc-windows-gnu -- -D warnings

- Tests run in the debug profile, never `--release`: the configurator's e2e tests need Slint debug info. On Windows `cargo test` links only with the `.cargo\config.toml` that `xtask configure` generates ([crates\config\AGENTS.md](crates/config/AGENTS.md)).
- The docs-site check is for changes to `docs\`, bench.db or the generator.
- The Windows check needs, installed once by the user, `sudo apt install gcc-mingw-w64-x86-64` (the C cross-compiler for the bundled SQLite and the other C build scripts) and `rustup target add x86_64-pc-windows-gnu`. The GNU target stands in for the MSVC one the Windows build uses: no crate code uses `cfg(target_env)`. `pai-config` is not checked this way (slint's Skia renderer builds only with MSVC); its Windows code is checked by the user's build on Windows.

The user runs the full suite, once, on the main branch after the merge and before installing. Agents do not run it:

    cargo test --workspace
    npm --prefix fe ci && npm --prefix fe test

## Rules

**Test first, always.** Write a failing test, run it and see it fail, then write the code. A change without a test that failed first is not done. Tests never touch real systems or real data: the configurator's tests redirect the whole data tree with `PRIVATE_AI_DATA_ROOT`.

**Keep it simple.** Minimum that solves the problem, no speculative options or abstractions.

**Facts need a source.** Check commands, APIs and limits against official documentation or a real run. In the docs, keep what was measured, read in a source and assumed apart. Mark guesses as guesses. A measured value names its campaign in bench.db.

**Language.** Everything in the project is in English: code, comments, docs, plan, skills, commit messages and displayed text. Only the conversation with the user may be in their language.

**Displayed text.** Text a user sees goes in the strings files, never inline in the code: "No user-visible text in the code" under "Key conventions".

## Actions with real effects

- What counts here: installing or removing packages and SDKs (`xtask prereq`, `xtask install`, the bootstrap scripts), anything machine-wide (environment variables, registry, `/usr`, `/opt`), the user's own config and data (`%LOCALAPPDATA%\private-ai\`, `~/.config/private-ai/`, `~/.local/share/private-ai/`), starting llama-server or a benchmark on the GPUs, writing to the committed `benchmarks\bench.db` (`bench publish`), and git push, tags and GitHub releases.
- Reading is fine. Anything that changes the real thing needs the user's go-ahead each time.
- Agents may be blocked from running some commands. Give the user the exact command to run, and say what it does, how long it takes and what result to expect.
- A command must undo what it changed by itself, wherever it can (a sweep puts its key back: `bench\sweep-pending-<stamp>.json`).

## Skills

## Roles

Role definitions live in `.opencode\agents\`; `.claude\agents` is a symlink to that directory, so OpenCode and Claude Code read the same files. Keep the frontmatter to the fields both accept (`name`, `description`, `mode`), and write role limits in the body rather than in harness-specific tool lists.

- `coordinator`: plans, briefs, reads the reports, commits and keeps `PLAN.md`; it runs no tests, linter, formatter or other code tool (the one exception: at the end of each task it frees the workspace's own crate artifacts with `cargo clean`, `.opencode\agents\coordinator.md`), and reports a slice done only on the tester's green rerun plus the coder's lint and format report (and, for a web UI slice the designer briefed, the designer's review), never on a single agent's word. The default agent for a session, set in `.claude\settings.json` and `.opencode\opencode.json`.
- `designer`: designs the web UI (`fe\`) and its user experience; before a slice that changes what users see it writes the design brief the tester turns into tests, after the coder it reviews the result against it; keeps `fe\DESIGN.md` and edits no code, tests, styles or strings files.
- `tester`: writes the failing tests (for a web UI slice, from the designer's brief) and shows them red; after the coder, reruns the slice's tests and reports them green (the independent check of the coder's work).
- `coder`: makes them pass, then runs the linter and the format check and reports them.
- `docs`: keeps the documentation true; for a guide in `docs\` it loads the `write-docs` skill.
- `spec-reviewer`: reviews a benchmark spec change before it is committed, read-only, with the `bench-spec` skill.

Cycle: coordinator takes the next step from `PLAN.md` and picks one small slice, designer writes the brief (only for a slice that changes what users see in the web UI), tester writes tests and shows them red, coder turns them green and reports the linter and the format check, tester reruns the tests and reports them green, designer reviews the result against its brief (web UI slices only), coordinator reads the reports and commits, docs updates what changed.

## Release process

Cutting a release (version bump, packages of every OS, release commit, tag, GitHub release, uploads) follows the `release` skill, [.agents\skills\release\SKILL.md](.agents/skills/release/SKILL.md). Tags, pushes and releases need the user's go-ahead ("Actions with real effects").
